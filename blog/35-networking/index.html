第 35 章：网络与连接

Android 的网络协议栈是 AOSP 中最复杂的子系统之一。它自上层的 Java 框架 API，经由本地守护进程，一直延伸到 Linux 内核的网络原语。本章追踪一个网络数据包所经历的完整路径，考察负责管理连接性的关键服务与模块，并解释 Android 如何处理从 Wi-Fi 关联、DNS 解析到 VPN 隧道的各类事务。

35.1 网络架构概览

35.1.1 全貌

Android 的网络功能按层次组织，既沿用经典的操作系统模型，又加入了 Android 特有的模块化、安全性与可更新性设计。在最高层，应用使用 ConnectivityManager、WifiManager 这类 API；这些 API 通过 Binder IPC 与运行在 system_server 内的系统服务通信；这些服务又借助 Netlink socket、iptables/nftables 命令与 BPF 程序，与本地守护进程（netd、DNS 解析器）以及 Linux 内核交互。

35.1.3 Mainline 模块化

自 Android 10（API 29）起，Google 开始把网络组件抽取为可独立更新的 Mainline 模块。这是一个关键的架构决策：它把关键的网络代码从较慢的平台 OTA 节奏中解耦出来，使 Google 能够通过 Play Store 推送安全补丁与功能更新。

主要的网络 Mainline 模块包括：

  1. Connectivity 模块（packages/modules/Connectivity/）：包含 ConnectivityService、网络共享子系统及相关框架代码。
  2. NetworkStack 模块（packages/modules/NetworkStack/）：负责 DHCP 客户端、网络验证（捕获门户检测）与 IP 配置发放。
  3. Wi-Fi 模块（packages/modules/Wifi/）：整个 Wi-Fi 子系统， 包括 WifiService、ClientModeImpl 与扫描逻辑。
  4. DnsResolver 模块（packages/modules/DnsResolver/）：支持 DoT 与 DoH 的本地 DNS 解析器。

每个模块都以 APEX 包的形式交付，构成自包含的更新单元，具备各自的版本管理、签名与回滚能力。

Android 17 进一步推进了这一趋势：它把本地网络二进制文件也放进模块内部，而不再只放在只读的 system 与 vendor 分区。本章后文记录了两个例子。第一个是 mainline supplicant（/apex/com.android.wifi/bin/wpa_supplicant_mainline，随 Wi-Fi APEX 一同交付的 wpa_supplicant 构建，见 35.27 节）；第二个是 Connectivity APEX 以“驻留 APEX 的应用”方式绑定的多代理 PAC 处理服务（见 35.26 节）。两者都让 Google 无需 OEM 参与构建，即可通过 Play 系统更新修补安全敏感的网络代码。

35.1.4 网络 ID 与路由

Android 中每一个处于活动状态的网络都被分配一个唯一的网络 ID（netId），取值为 100–65535 的整数。这个 ID 是基础性的：它把路由、DNS 配置、iptables 规则与 socket 绑定串联在一起。应用打开 socket 时，内核会使用该 netId（通过 socket 上的 fwmark 施加）来选择正确的路由表。

35.1.5 数据路径：从应用到网线

应用发送数据时，会发生如下过程：

sequenceDiagram
    participant App as 应用
    participant Socket as Socket 层
    participant Kernel as Linux 内核
    participant BPF as eBPF 程序
    participant NF as Netfilter
    participant Driver as 网络驱动

    App->>Socket: write(fd, data)
    Socket->>Kernel: Socket 打上 fwmark（netId + 权限）
    Kernel->>BPF: 执行 cgroup/eBPF 程序
    Note over BPF: 基于 UID 的流量统计<br/>带宽计量<br/>防火墙规则
    BPF->>Kernel: 通过 fwmark ip rules<br/>与 netId 路由表做路由查找
    Kernel->>NF: 遍历 iptables OUTPUT 链
    Note over NF: bw_OUTPUT（带宽）<br/>fw_OUTPUT（防火墙）<br/>NAT（网络共享）
    NF->>Driver: POSTROUTING，随后发送数据包
    Driver-->>App: （异步）完成

fwmark 机制是 Android 按网络路由的核心。每个 socket 都带有一个 32 位标记，其位布局由 system/netd/include/Fwmark.h 中的 Fwmark 联合体定义：

  • 网络 ID（第 0–15 位）
  • 该网络是否被显式选择（第 16 位）
  • 该 socket 是否受 VPN 保护（第 17 位）
  • 权限位（第 18–19 位）

netd 中的 FwmarkServer 负责施加这些标记。它是 UNIX domain socket 上的一个 SocketListener。客户端把 socket 文件描述符交给它，它便用 setsockopt(SOL_SOCKET, SO_MARK, ...) 把算好的标记写到该 socket 上。它不是 BPF 程序，也不是 cgroup 钩子：

                   sizeof(fwmark.intValue)) == -1) {
        return -errno;

35.2.2 Handler 线程模型

ConnectivityService 几乎把所有工作都放在单个 handler 线程上处理。这是有意为之：单线程模型免去了在跟踪网络、请求与回调的众多数据结构之间做复杂加锁的需要。消息通过内部的 InternalHandler 分发，处理以下事件：

  • 网络代理的注册与注销
  • 网络能力变化
  • 链路属性更新
  • 网络评分变化
  • 来自 NetworkMonitor 的验证结果
  • 应用的网络请求与回调

NetworkAgent 的生命周期如下：

stateDiagram-v2
    [*] --> Created: new NetworkAgent
    Created --> Registered: register
    Registered --> Connecting: 代理上报能力
    Connecting --> Connected: markConnected
    Connected --> Connected: 更新能力 / 链路属性 / 评分
    Connected --> Lingering: 不再有请求

    Lingering --> Disconnected: 停留超时
    Connected --> Disconnected: unregister
    Disconnected --> [*]

即：网络代理从创建开始，经注册进入 Connecting，收到能力上报后转为 Connected；当没有请求再需要它时进入 Lingering 停留态，若停留期间出现匹配的新请求则回到 Connected，否则超时断开；显式注销同样会进入 Disconnected。

35.2.6 网络评分与选择

当多个网络都能满足某个请求时，ConnectivityService 必须选出最优者。这一选择算法在 Android 的历史中经历了显著演进：

  1. 传统评分（Android 12 之前）：简单的整数打分，高分者胜出。 Wi-Fi 默认为 60，蜂窝默认为 50。

  2. 现代评分（Android 12 及之后）：基于策略的 NetworkScore， 可编码多个维度：

// From NetworkAgent.java
public static final int WIFI_BASE_SCORE = 60;

rematchAllNetworksAndRequests() 方法是网络选择的核心。它在每一次重要的网络变化时运行，遍历所有活动请求，为每个请求找出最佳网络：

    REMATCH["rematchAllNetworksAndRequests()"]
    ITERATE["遍历每个 NetworkRequest"]
    FIND["寻找最佳匹配网络"]
    CHECK_CAPS["网络能力<br/>满足请求？"]

    REMATCH --> ITERATE

评分会考虑多种策略：

  • 传输优先：优先选择该传输类型的主网络
  • 已验证优于未验证：优先选择通过验证的网络
  • 计费与非计费：在有非计费网络时优先选择它
  • 用户偏好：尊重用户的网络选择
  • VPN：VPN 按自身的评分规则特殊处理

35.3.5 wpa_supplicant 集成

Android 使用业界标准的 wpa_supplicant 完成 802.11 认证。SupplicantStaIfaceHal 类通过 AIDL 接口与 wpa_supplicant 通信，处理：

  • WPA/WPA2/WPA3 认证
  • 802.1X 企业级认证（EAP-TLS、EAP-TTLS、EAP-PEAP、EAP-SIM 等）
  • FILS（快速初始链路建立），用于缩短连接耗时
  • OWE（机会性无线加密），用于开放网络
  • SAE（对等同时认证），用于 WPA3
  • DPP（设备配置协议），用于便捷入网

SupplicantStaIfaceHal 并不绑定到某一个固定实现。其工厂方法 createStaIfaceHalMockable()（位于 packages/modules/Wifi/service/java/com/android/server/wifi/SupplicantStaIfaceHal.java） 按严格的优先级顺序挑选第一个可用的后端。

第一个是 AIDL 的 mainline 实现（随 Wi-Fi APEX 一同交付的 supplicant 二进制，见 35.27 节）；第二个是 AIDL 的 vendor 实现（vendor 分区上的 supplicant）；第三个是遗留的 HIDL 实现。 每个候选都提供 isServiceAvailable() ／ serviceDeclared() 探测方法，第一个返回“可用”者胜出。Wi-Fi Direct 在 SupplicantP2pIfaceHal 中采用同样的三级选择逻辑。

35.3.6 网络选择

WifiNetworkSelector 评估可用的扫描结果并选出最佳网络进行连接。它考虑：

  1. 已保存网络优先级：用户配置的偏好
  2. 信号强度（RSSI）：按频段加权（2.4 GHz、5 GHz、6 GHz）
  3. 安全类型：偏好更强的安全性
  4. 历史表现：过往连接质量指标
  5. 网络建议：由应用建议的网络
  6. 企业策略：设备管理器的限制
  7. 被拉黑的网络：因连续失败而暂时禁用

35.4 netd（网络守护进程）

防火墙支持两种模式：

bool DnsResolver::start() {
    if (!verifyCallbacks()) {
        LOG(ERROR) << __func__ << ": Callback verification failed";
        return false;
    }
    if (mDnsProxyListener.startListener()) {
        PLOG(ERROR) << __func__ << ": Unable to start DnsProxyListener";
        return false;

        return false;
    }
    return true;
}

FeatureFlags makeDohFeatureFlags() {
    const Experiments* const instance = Experiments::getInstance();
    const auto getTimeout = [&](const std::string_view key,

        static constexpr int kMinTimeoutMs = 1000;

35.5.6 私人 DNS 配置

PrivateDnsConfiguration 类管理私人 DNS（DoT/DoH）服务器的生命周期，包括验证与故障转移。

源文件： packages/modules/DnsResolver/PrivateDnsConfiguration.cpp

// Source: packages/modules/DnsResolver/PrivateDnsConfiguration.cpp
// Returns the sorted (sort IPv6 before IPv4) servers.
std::vector<std::string> sortServers(
        const std::vector<std::string>& servers) {
    std::vector<std::string> out = servers;
    std::sort(out.begin(), out.end(),
        [](std::string a, std::string b) {
            return IPAddress::forString(a) > IPAddress::forString(b);
        });
    return out;
}

私人 DNS 模式：

  1. 关闭：所有 DNS 查询均为明文

  2. 机会性（默认）：尝试 DoT/DoH，失败则回退到明文

  3. 严格：强制使用 DoT/DoH，不可用即失败

验证状态机如下：

stateDiagram-v2
    [*] --> Unknown: 配置服务器
    Unknown --> InProgress: 开始验证
    InProgress --> Success: 探测成功
    InProgress --> Fail: 探测失败
    Success --> InProgress: 需要重新验证
    Fail --> InProgress: 退避后重试
    Success --> [*]: 服务器被移除
    Fail --> [*]: 服务器被移除

即：服务器配置后进入“未知”状态，开始验证时转为“验证中”，探测成功则进入“成功”、失败则进入“失败”；“成功”若需重新验证会回到“验证中”，“失败”则在退避之后重试；服务器被移除时无论成功还是失败都会终止。

Dns64Configuration 类负责纯 IPv6 网络下的 DNS64 前缀发现。当网络不具备 IPv4 连通性时，DNS64 由 A 记录合成 AAAA 记录，数据包则由 NAT64 转换（由 Connectivity 模块中的 clatd 负责）。

源文件： packages/modules/DnsResolver/Dns64Configuration.cpp

35.5.8 按网络的 DNS 缓存

解析器为每个网络 ID 维护独立的 DNS 缓存。这可以防止跨网络的 DNS 缓存投毒，也确保响应与网络上下文相匹配（例如捕获门户的响应不会被当作全局 DNS 结果缓存）。

关键的缓存行为：

  • 按 TTL 过期：尊重 DNS 记录的 TTL 值
  • 网络隔离：每个 netId 独立缓存
  • 负缓存：缓存 NXDOMAIN 响应
  • 缓存清空：在网络变化时触发

1. 第三方 VPN（VpnService API）

35.8.10 清单属性 usesCleartextTraffic 在 Android 17 中被废弃

清单属性 android:usesCleartextTraffic 是更早、粒度更粗的控制手段：<application> 上的一个布尔值。当应用没有自带 XML 配置时，运行时会把该属性折算进默认的 NetworkSecurityConfig。Android 17（CINNAMON_BUN，API 37）开始废弃它，转而推荐使用网络安全配置 XML。

这项变更由一项兼容性变更加一个 aconfig 标志共同实现。network_security 标志 deprecate_uses_cleartext_traffic2 （frameworks/base/core/java/android/security/flags.aconfig）的描述是：“对目标 SDK 为 C 及以上的应用，忽略 XML 之外的应用标志 usesCleartextTraffic”。对应的 @ChangeId 位于 ManifestConfigSource：

// frameworks/base/packages/NetworkSecurityConfig/platform/src/android/security/net/config/ManifestConfigSource.java
@ChangeId
@Disabled
static final long DEPRECATE_USES_CLEARTEXT_TRAFFIC = 415007211L;

当配置源为没有 XML 配置的应用构建默认配置时，它会读取该清单标志；若兼容性变更与 aconfig 标志同时开启，则把该标志清零：

boolean usesCleartextTraffic =
        (mApplicationInfo.flags & ApplicationInfo.FLAG_USES_CLEARTEXT_TRAFFIC) != 0
        && !mApplicationInfo.isInstantApp();
if (CompatChanges.isChangeEnabled(DEPRECATE_USES_CLEARTEXT_TRAFFIC) &&
    deprecateUsesCleartextTraffic2()) {
    usesCleartextTraffic = false;
}

对于受影响的应用，无论该清单属性声明为何值，都会被当作 false 处理。若应用仍需对特定主机使用明文，必须在网络安全配置中显式声明（对这些主机使用 <domain-config cleartextTrafficPermitted="true">）。这正是本次废弃希望推动应用转向的更细粒度、更可审计的机制。DEFAULT_CLEARTEXT_TRAFFIC_PERMITTED 本身并未改变（仍为 true）。因此下表所示“按目标 SDK 默认拒绝”的行为，管辖的是既未提供该清单标志、也未提供 XML 配置的应用。

35.10 VCN（虚拟运营商网络）

虚拟运营商网络（Virtual Carrier Network，VCN）子系统在任意可用传输（蜂窝或 Wi-Fi）之上提供运营商级 IPsec 隧道，并把结果作为一个单一、无缝的移动网络呈现给平台其余部分。传统 VPN 服务于用户隐私，而 VCN 服务于运营商：移动运营商可以配置设备，把所有流量包进回到运营商网关的 IKEv2/IPsec 隧道中。这实际上创建了一个“虚拟”的运营商网络，它跨物理传输跟随用户。

35.10.1 动机与设计目标

部署 Wi-Fi 分流（ePDG）或专网的运营商，需要一种机制把用户流量从设备安全地隧道化到运营商网关，并且无论设备处于 Wi-Fi、蜂窝还是二者之间切换时都必须可用。VCN 提供：

  1. 运营商绑定的隧道：与用户 VPN 不同，VCN 隧道绑定到某个运营商订阅组。 只有该运营商的配置应用（具备运营商特权）才能安装 VCN 配置。
  2. 无缝移动性：底层传输变化时（例如 Wi-Fi 切到蜂窝），VCN 通过 MOBIKE（RFC 4555）迁移 IKE/IPsec 会话， 从而避免应用可见的 TCP 连接重置。
  3. 安全模式回退：若隧道在超时内无法建立，VCN 回退到“安全模式”， 暴露原始底层网络，使设备绝不至于失去连接。
  4. 按能力的网关连接：单个 VCN 实例可以管理多条网关连接， 各自服务不同的 NetworkCapabilities（例如一条用于 INTERNET，另一条用于 DUN/网络共享）。

35.10.8 安全模式

安全模式是 VCN 的关键可靠性机制。若某个 VcnGatewayConnection 在 SAFEMODE_TIMEOUT_SECONDS（30 秒）内无法建立隧道，整个 Vcn 实例进入安全模式：

  1. 底层网络不再被标记为受限 （NET_CAPABILITY_NOT_VCN_MANAGED 能力被恢复）。
  2. 应用可以直接访问原始底层网络。
  3. VCN 继续在后台尝试建立隧道。
  4. 隧道重建成功后，VCN 退出安全模式。

这确保配置错误或不可达的运营商网关绝不会让设备失去网络连接。

35.11 Thread 网络

Thread 是一种基于 IPv6 的网状网络协议，面向低功耗物联网（IoT）设备，基于 IEEE 802.15.4 射频标准构建。Android 的 Thread 实现作为 Connectivity Mainline 模块的一部分加入，使 Android 设备可以充当 Thread 边界路由器，把 Thread 网状网络桥接到更广的 IP 基础设施（Wi-Fi／以太网）。

35.11.1 什么是 Thread？

Thread 是由 Thread Group 标准化的低功耗、低时延网状网络协议。关键特性：

  • IEEE 802.15.4：使用 2.4 GHz 频段，吞吐 250 kbps， 信道页 0（信道 11–26）。
  • 原生 IPv6：每个 Thread 设备都获得全局可路由的 IPv6 地址， 无需 NAT 或应用层网关。
  • 网状拓扑：设备自组织成网，由路由器转发 数据包，并由单一 Leader 协调网络。
  • 低功耗：终端设备（Child）可长时间休眠， 把数据包缓存委托给其父路由器。
  • Thread 1.3：当前版本，支持服务注册协议（SRP）、组播， 以及用于 IPv4 连通性的 NAT64。

Thread 网络中的设备角色：

角色 说明
Leader 经选举产生的路由器，负责路由器 ID 分配与网络数据管理
Router 完整参与者，转发数据包，可作为 Child 的父节点
Child 与某个父路由器关联的终端设备，可休眠省电
Border Router 具备到外部 IP 网络（Wi-Fi／以太网）连通性的路由器
Detached 当前不属于任何 Thread 分区的设备

  7. 处理排队消息：投递注册期间排队的消息

35.12.2 重新匹配算法

rematchAllNetworksAndRequests() 方法是网络选择的核心。凡是可能影响“哪个网络最能满足某个请求”的变化发生时，它都会运行。

// Source: packages/modules/Connectivity/service/src/com/android/server/ConnectivityService.java
private void rematchAllNetworksAndRequests() {
    rematchNetworksAndRequests(getNrisFromGlobalRequests());
}

private void rematchNetworksAndRequests(
        @NonNull final Set<NetworkRequestInfo> networkRequests) {
    ensureRunningOnConnectivityServiceThread();
    final long start = SystemClock.elapsedRealtime();
    final NetworkReassignment changes =
        computeNetworkReassignment(networkRequests);
    final long computed = SystemClock.elapsedRealtime();
    applyNetworkReassignment(changes, start);
    final long applied = SystemClock.elapsedRealtime();
    issueNetworkNeeds();
    final long end = SystemClock.elapsedRealtime();
    if (VDBG || DDBG) {
        log(String.format(
            "Rematched networks [computed %dms] [applied %dms] [issued %d]",
            computed - start, applied - computed, end - applied));
        log(changes.debugString());
    }
}

重新匹配分三个阶段：

阶段 1：计算重分配（computeNetworkReassignment）

  • 对每个网络请求，找出能满足它的最佳网络
  • 比较能力、评分及其他属性
  • 构建一个描述全部变更的 NetworkReassignment 对象

阶段 2：应用重分配（applyNetworkReassignment）

  • 若默认网络发生变化则更新之
  • 向应用发送回调（onAvailable、onLost 等）
  • 为本地网络配置转发规则
  • 更新停留计时器

阶段 3：发出网络需求（issueNetworkNeeds）

  • 把未被满足的请求告知网络工厂

  1. 识别绑定在旧网络上的 socket（依据 UID 范围与 fwmark）
  2. 通过 SockDiag 接口对 TCP socket 发送 RST

35.21.2 INTERNET 权限的执行

INTERNET 权限在 Android 中是独特的：它在内核层执行。现代 Android 上由 packages/modules/Connectivity/bpf/progs/netd.c 中的 cgroupsock/inet_create eBPF 程序负责。它会在每次创建 AF_INET/AF_INET6 socket 时运行，检查 BPF 映射表中按 UID 的 BPF_PERMISSION_INTERNET 位。该映射表通过 netd 的 trafficSetNetPermForUids() 填充：

// From system/netd/server/NetdNativeService.h
binder::Status trafficSetNetPermForUids(
    int32_t permission,
    const std::vector<int32_t>& uids) override;

加入 inet 组（AID_INET，GID 3003）并在 fork 时授予被许可的应用，是 BPF 之前的遗留机制。没有 INTERNET 权限的应用实际上无法创建 AF_INET 或 AF_INET6 socket——socket() 系统调用会返回 EPERM。

35.26 多代理与多 PAC 框架

35.26.1 为什么需要新的代理协议栈

历史上 Android 只支持单一的、全局的 HTTP 代理。该代理要么是静态的主机/端口，要么是一个 PAC（Proxy Auto-Config）URL。PAC 文件是一个 JavaScript 文件，其 FindProxyForURL(url, host) 函数返回针对给定请求应使用哪个代理（若有）。遗留实现在 packages/modules/Connectivity/service/src/com/android/server/connectivity/ProxyTracker.java 中，它持有一个全局 ProxyInfo，对 PAC 则把脚本交给单个进程外的 PAC 处理器。所有网络、所有应用共享这同一个代理决策。

这一模型在多网络设备上难以为继：受管的企业网络可能自带 PAC 脚本，而个人 Wi-Fi 根本不用代理；VPN 可能希望使用与底层传输不同的代理。Android 17 引入了重新设计的代理协议栈，可以同时运行多个独立的 PAC 脚本，并按上下文（网络、用户或应用 UID）选择。新 PAC 处理器的 AIDL 头文件直接说明了目标：支持“运行多个 PacProcessor，以便基于上下文（如网络、用户或应用 UID）使用不同的 PAC 脚本” （packages/modules/Connectivity/commercial/pac/multipacprocessor/src/com/android/multipacprocessor/IMultiPacService.aidl）。

这是 17 代码树中的脚手架式特性：接线、服务契约与协调器均已到位，但置于开关之后；若干叶子操作仍为桩实现（UnsupportedOperationException）。之所以在此记录，是因为架构才是持久的部分，也是集成者需要理解的内容。

35.26.2 两个协同服务：PacProcessor 与 ProxyServer

新协议栈把遗留单一 PAC 服务的职责拆分为两个协同的、驻留 APEX 的服务。每个服务各自运行一组配对的 {ProxyServer; PacProcessor} 实例：

  • MultiPacService —— 运行真正执行 PAC JavaScript 的 PacProcessor 实例。 包 com.android.multiproxyhandler 提供代理侧，包 com.android.multipacprocessor 提供 PAC 侧 （packages/modules/Connectivity/commercial/pac/multipacprocessor/src/com/android/multipacprocessor/MultiPacService.java）。
  • MultiProxyService —— 运行本地 HTTP 代理服务器。按其 AIDL 文档所述，其用途是“运行本地 HTTP 服务器[…]， 为无法直接访问 PacProcessor 的应用提供 PAC 支持” （packages/modules/Connectivity/commercial/pac/multiproxyhandler/src/com/android/multiproxyhandler/MultiProxyService.java）。

两者均通过 AIDL stub 暴露—— packages/modules/Connectivity/commercial/pac/multipacprocessor/src/com/android/multipacprocessor/IMultiPacService.aidl 与 packages/modules/Connectivity/commercial/pac/multiproxyhandler/src/com/android/multiproxyhandler/IMultiProxyService.aidl。 在 17 代码树中，这两个接口体被有意留为空的占位符：绑定、生命周期与 intent 契约已定，RPC 方法随实现落地逐步补入。两个应用都位于 Connectivity （com.android.tethering）APEX 内，这也是协调器把服务查找范围限制在 /apex/com.android.tethering/ 下包的原因。

35.26.3 PacCoordinator

编排者是 PacCoordinator （packages/modules/Connectivity/service/src/com/android/server/connectivity/proxy/PacCoordinator.java）。 其类注释描述了它的角色：协调“PAC 脚本的下载并[管理] MultiPacService 与 MultiProxyService 服务[…]，跟踪当前正在使用的 PAC 脚本，并确保为这些脚本提供服务的对应 PAC 组件正在运行。”

它完全运行在 ConnectivityService 的 handler 线程上。每个公开方法都以 ensureRunningOnHandlerThread() 开头，服务绑定回调通过 mConnectivityServiceHandler::post 投回该 handler，因此所有状态变更都是单线程的。两个关键入口点是：

// PacCoordinator.java
public void startServingPacScript(ProxyInfo proxy, Optional<Integer> netId) {
    ensureRunningOnHandlerThread();
    bindToPacComponentsIfNeeded();
    mPacDownloader.downloadPacScript(
            new PacKey(proxy.getPacFileUrl(), netId), this::onPacScriptDownloaded);
}

public void stopServingPacScript(ProxyInfo proxy, Optional<Integer> netId) { ... }

startServingPacScript() 在需要时绑定这两个服务，随后安排下载 PAC 脚本。下载完成后，它要求两个服务为该脚本建立一对 {ProxyServer; PacProcessor}。若该键对应的配对已在运行，则本次调用为空操作。

该键是一个 PacKey （packages/modules/Connectivity/commercial/pac/common/src/com/android/commercial/PacKey.java）， 由 PAC 的 Uri 与 Optional<Integer> 网络 id 构成的 parcelable 对。 Optional.empty()（序列化为 -1）表示默认网络。

下载本身委派给 PacDownloader （packages/modules/Connectivity/service/src/com/android/server/connectivity/proxy/PacDownloader.java）， 它通过所请求的网络抓取脚本，从而使按网络的 PAC 经由该网络取得。

绑定使用 BIND_AUTO_CREATE | BIND_NOT_FOREGROUND。NOT_FOREGROUND 标志是刻意为之：代理服务器在解析 URL 时会对 PAC 处理器发起阻塞调用，而耗时较长或阻塞式的 PAC 求值不应把系统进程拖入前台优先级状态。

35.26.4 MultiProxyTracker 与 ConnectivityService 的接线

ConnectivityService 通过 IProxyTracker 接口抵达新协议栈。遗留的 ProxyTracker 与新的 MultiProxyTracker （packages/modules/Connectivity/service/src/com/android/server/connectivity/proxy/MultiProxyTracker.java） 都实现该接口，因此 ConnectivityService 其余部分对具体实现无感。选择发生在构造阶段，并由一个开关控制：

// ConnectivityService.java
final boolean multiProxyEnabled =
        mDeps.isMultiProxyEnabled()
                && mResources.get().getBoolean(R.bool.config_enable_multi_proxy_system);
mProxyTracker = multiProxyEnabled
        ? mDeps.makeMultiProxyTracker(mContext, mHandler)
        : /* legacy ProxyTracker */ ...;

isMultiProxyEnabled() 返回 com.android.tethering.flags.Flags.enableMultiProxySystem()。因此，必须同时置位 aconfig 开关与资源 overlay（config_enable_multi_proxy_system），才会启用多代理路径；否则 ConnectivityService 回落到经典的单 ProxyTracker。

MultiProxyTracker 声明了 updateNetworkProxy(network, newProxy, oldProxy) 与 updateDefaultNetworkState(...) 回调，意在按网络驱动 PacCoordinator.startServingPacScript()。PacCoordinator 还在构造函数中接收一个 MultiPacProxyInstalledListener， 该监听器在代理服务器启动且其 PAC 脚本加载完成后收到通知。但在 Android 17 代码树中，MultiProxyTracker 尚未实现该监听器，其 updateNetworkProxy／updateDefaultNetworkState 覆写仍是空的 // TODO: Implement 桩。

35.27 Mainline supplicant

35.27.1 动机

传统的 wpa_supplicant 是厂商组件：它位于 vendor 分区，通过 Wi-Fi supplicant HAL 访问。因此修复 supplicant 缺陷或交付新的 Wi-Fi 特性都需要 OEM 参与构建。Android 17 新增了第二个、可更新 的 supplicant——mainline supplicant——它随 Wi-Fi APEX（com.android.wifi）一同交付，使 Google 可以通过 Play 系统更新自行更新。

mainline supplicant 并不取代厂商 supplicant。它与后者并行运行，充当一层薄薄的前门：其根 AIDL 接口把绝大部分 STA/P2P 工作交回厂商 supplicant。mainline 二进制自身只负责一组小而仍在演进的能力（目前是 Wi-Fi Aware / NAN 接口管理与当前用户身份）。这样一来，新的 supplicant 侧代码可以随模块交付，而既有厂商行为不受影响。

35.27.3 IMainlineSupplicant

AIDL 契约是 packages/modules/Wifi/aidl/mainline_supplicant/android/system/wifi/mainline_supplicant/IMainlineSupplicant.aidl， 包名为 android.system.wifi.mainline_supplicant。它是一个明确标注为不稳定的接口（随模块而非平台交付），并且很小：

interface IMainlineSupplicant {
    @PropagateAllowBlocking ISupplicant getVendorSupplicant();
    @PropagateAllowBlocking ISupplicantNanIface addNanInterface(in String ifaceName);
    void removeNanInterface(in String ifaceName);
    void setCurrentUserIdentity(in int userId);
}
  • getVendorSupplicant() 返回标准的厂商 ISupplicant 根——STA 与 P2P 操作正是经此路由回厂商 supplicant。
  • addNanInterface() / removeNanInterface() 注册与拆除 Wi-Fi Aware（NAN）接口（例如 aware0）。它们返回 mainline 的 android.system.wifi.mainline_supplicant.ISupplicantNanIface。这是由 mainline supplicant 自身拥有的 NAN 接口面，而非厂商的 NAN 接口。
  • setCurrentUserIdentity() 告知 supplicant 当前处于前台的用户， 以便加载该用户的凭据加密（CE）配置。

35.27.4 MainlineSupplicantAidlManager

框架侧是 MainlineSupplicantAidlManager （packages/modules/Wifi/service/java/com/android/server/wifi/MainlineSupplicantAidlManager.java）。 它通过一个小的 JNI 适配层 packages/modules/Wifi/service/java/com/android/server/wifi/mainline_supplicant/ServiceManagerWrapper.java 按名称解析 binder：

startDaemon() 取得 binder，缓存 getVendorSupplicant() 返回的厂商 ISupplicant，并挂接死亡通知接收器。terminate() 请求 supplicant 退出，随后在一个闩锁上等待 binder 死亡确认。NAN 接口获取（getWifiNanIface()）包裹 addNanInterface()，并把结果作为 AwareIfaceAidlSupplicantImpl 交给 Aware 协议栈。死亡回调被投递到 WifiThreadRunner，从而保持管理器状态单线程。

是否启用 mainline supplicant 完全由 isServiceAvailable() 决定，它要求以下条件全部成立：

// MainlineSupplicantAidlManager.java
public static boolean isServiceAvailable(WifiContext context) {
    boolean isEnabledInOverlay = context.getResourceCache().getBoolean(
            com.android.wifi.resources.R.bool.config_wifiMainlineSupplicantEnabled);
    return isEnabledInOverlay && (Environment.isSdkAtLeastC() || hasPcFeature(context))
            && Flags.mainlineSupplicant()
            && Environment.isMainlineSupplicantBinaryInWifiApex()
            && !isUnsupportedDevice(context);
}

具体是：

  • 资源 overlay（config_wifiMainlineSupplicantEnabled）启用它。
  • 平台为 Android 17 及以上（或 PC 形态）。
  • mainlineSupplicant aconfig 开关开启。
  • 该二进制确实存在于 Wi-Fi APEX 内。
  • 设备不属于 isUnsupportedDevice() 排除的资源受限形态（手表、 嵌入式、leanback/TV、汽车）。

35.27.5 HAL 选择：mainline、厂商还是 HIDL

35.3.5 节提到 SupplicantStaIfaceHal.createStaIfaceHalMockable() 按优先级顺序选择后端。mainline supplicant 位于该顺序的顶端：

35.28 NSD 服务访问选择器与本地网络权限

35.28.1 问题：本地网络可见性

此前，任何持有 INTERNET 权限的应用都可以使用 NSD API 列出本地网络上的所有 mDNS 服务（例如打印机、智能家居中枢、电视以及其他手机）。这是一处实实在在的隐私泄漏，因为某人家庭网络上的服务集合具有可识别性。Android 17 用新的运行时权限 ACCESS_LOCAL_NETWORK 封堵了这一缺口，并新增了服务访问选择器：一个由用户驱动的允许名单，让应用能够访问它没有整体发现权限的特定服务。

35.28.2 DiscoveryRequest 标志

DiscoveryRequest （packages/modules/Connectivity/framework-t/src/android/net/nsd/DiscoveryRequest.java） 新增了三个标志，用于告诉 NsdService 在应用没有 ACCESS_LOCAL_NETWORK 却要发现服务时应如何行为：

  • FLAG_NO_PICKER —— 绝不显示选择器；若应用缺少权限则失败。
  • FLAG_SHOW_PICKER —— 强制显示选择器界面；用户选定后，即使应用没有权限， 也被授予对所选择服务的访问。
  • FLAG_USER_APPROVED_ONLY —— 不做任何展示；只返回用户已为该应用 批准过的服务。

若既未设置 FLAG_NO_PICKER 也未设置 FLAG_SHOW_PICKER，默认行为取决于应用的权限以及 USE_NSD_PICKER_WHEN_NO_LOCAL_NET_PERMISSION 兼容性变更。

35.28.3 NsdService 中的执行

NsdService （packages/modules/Connectivity/service-t/src/com/android/server/NsdService.java） 以 aconfig 开关 FLAG_NSD_SERVICE_PICKER 控制该特性 （mEnablePicker = mDeps.isAconfigFlagEnabled(FLAG_NSD_SERVICE_PICKER)）。有两个关键的执行点：

  • 发现：checkDiscoveryPermissionsAndPicker() 依据请求标志与调用方权限， 决定是直接发现、拒绝，还是拉起选择器。走选择器路径时，NsdService 不会把原始结果交给应用， 而是经 PickerListener 传递，由后者的 startPicker() 显示系统界面。
  • 解析／注册回调：checkQueryServicePermissions() 在调用方持有 ACCESS_LOCAL_NETWORK 或该服务位于按应用的允许名单中时允许相应操作 （mAccessRepository.isServiceAllowed(uid, packageName, serviceName, serviceType)）。

用户选定某服务时，handleServiceSelected() 会记录之： mAccessRepository.addAllowedService(uid, packageName, serviceName, serviceType)。 在客户端连接／断开时，NsdService 调用 loadPackage() 与 unloadPackage()，使允许名单仅在客户端活动期间被分页载入。

35.28.4 ServiceAccessRepository 与 ServiceAccessDb

允许名单本身分为内存中的仓库与基于 SQLite 的存储，两者都位于 packages/modules/Connectivity/service-t/src/com/android/server/connectivity/mdns/internal/ 之下：

  • ServiceAccessRepository.java 是内存缓存与编排者。它把每个 (uid, packageName) 映射到用户批准的 (serviceName, serviceType) 元组集合；保存“最近访问”时间戳用于 LRU 淘汰， 并对每个客户端的条目数设上限。它完全运行在 NsdService 的 handler 线程上，并明确不是线程安全的。其主要方法有 addAllowedService()、isServiceAllowed()、 loadPackage()、unloadPackage()，以及一个 maybeScheduleDatabaseMaintenance()， 用于清理已卸载软件的条目。
  • ServiceAccessDb.java 是持久化层。它是一个小型 SQLite 数据库 （NsdServiceAccess.db），其中 package 表跟踪已知软件包， service_access 表保存已批准的 (uid, package, serviceName, serviceType, last_seen_time) 行。级联删除意味着卸载某个软件包会移除其全部授予。

35.28.5 NsdManager API

对应用而言，NsdManager （packages/modules/Connectivity/framework-t/src/android/net/nsd/NsdManager.java） 新增了 checkPermissionForService(serviceName, serviceType, executor, resultReceiver)， 使应用可以在解析之前询问某个此前批准过的服务是否仍可访问。结果为 SERVICE_PERMISSION_GRANTED 或 SERVICE_PERMISSION_DENIED 之一。它与 DiscoveryRequest 标志配合，让应用可以驱动整个流程：先以 FLAG_USER_APPROVED_ONLY 发现；若它关心的服务缺失，再以 FLAG_SHOW_PICKER 重新发现以提示用户。

35.29 Wi-Fi USD：非同步服务发现

NSD/mDNS（§35.28）在既有的 IP 网络上发现服务。Android 17 新增了一个互补的发现机制，它运行在协议栈更低的位置、发生在任何 IP 连通性建立之前：Wi-Fi 非同步服务发现（Unsynchronized Service Discovery，USD）。

USD 属于本章已介绍的 Wi-Fi Aware（NAN）家族 （§35.25.1 把 aware0 映射到 WifiAwareNetworkAgent）。它让两台设备在空中广播并发现服务——无需网络、无需 IP 地址，也如名称所示，无需事先的时间与信道同步。这使它非常适合快速发现刚进入范围的新设备上的服务。

其模型是发布／订阅：发布者设备广播一个具名服务，订阅者设备搜索它。订阅者收到匹配的广播后，会与发布者交换后续消息，这些消息携带服务特定的配置信息。实现遵循 Wi-Fi Aware 规范 4.0 版。

该特性以 Wi-Fi mainline 模块中的新系统服务形式出现，而不是放在 frameworks/base。管理器类是 packages/modules/Wifi/framework/java/android/net/wifi/usd/UsdManager.java， 注册在 Context.WIFI_USD_SERVICE 常量下（字符串值为 "wifi_usd"，声明于 frameworks/base/core/java/android/content/Context.java:5484）。由于该 API 随 mainline 模块交付，管理器受三重门控：

  • UsdManager 上的 @FlaggedApi(Flags.FLAG_USD) 注解与 @SystemApi 可见性 （UsdManager.java:65-66），因此它仅是系统应用可用、受开关保护的 API。
  • 最低 SDK 门控：类上标注 @RequiresApi(Build.VERSION_CODES.BAKLAVA)， 而 packages/modules/Wifi/framework/java/android/net/wifi/WifiFrameworkInitializer.java 中的注册仅在 Flags.usd() && Environment.isSdkAtLeastB() 时注册该服务。
  • 设备能力门控：除非设备资源 config_deviceSupportsWifiUsd 为 true，注册返回 null，因此在无法支持 USD 的硬件上 getSystemService() 不会返回 UsdManager。

android.net.wifi.usd 中的配套类描述了发现的形态： PublishConfig/SubscribeConfig 说明要广播或查找什么， PublishSession/SubscribeSession 附带各自回调， DiscoveryResult 保存结果，Characteristics 保存设备的 USD 限制 （经 UsdManager.getCharacteristics() 读取）。 UsdManager 还暴露 publish(...)、subscribe(...) 以及发布者／订阅者可用性监听 （registerPublisherStatusListener/registerSubscriberStatusListener），因为 USD 的可用性取决于射频的并发使用情况。

服务端位于同一模块的 packages/modules/Wifi/service/java/com/android/server/wifi/usd/ 下，包含 UsdService（把 binder 发布到 Context.WIFI_USD_SERVICE 下的 SystemService）、UsdServiceImpl、UsdRequestManager，以及负责把发现下推到 Wi-Fi HAL 的 UsdNativeManager。

NSD 回答的是“我已接入的网络上哪些服务可达”；USD 回答的是更早的问题——“在任何网络存在之前，空中附近有哪些设备与服务”。二者处在服务发现故事中相邻的两个层次。

35.30 APF：Android 数据包过滤器

到目前为止本章的一切都假定应用处理器（AP）处于唤醒状态以查看数据包。而这个假定正是空闲设备耗电的元凶。

一部放在口袋里、连着 Wi-Fi 的手机，仍会持续收到并不发给它的组播与广播流量——例如 mDNS 服务公告、SSDP/UPnP 发现、其他主机的 ARP 探测以及 IPv6 路由通告；网络上每多一台设备，噪声就更多。NIC 收到的每一帧通常都会把 AP 从低功耗睡眠中唤醒，好让网络协议栈看一眼，然后判定无趣并丢弃。

在一个繁忙的家庭或办公网络上，这可能意味着每分钟数百次无谓的唤醒。而唤醒是移动 SoC 在功耗上最昂贵的操作之一。

Android 数据包过滤器（APF）正是为了夺回这部分功耗而存在。APF 把一小段数据包过滤程序下推到 Wi-Fi（或以太网）NIC 固件，让固件自己判断某个到来的帧是否值得唤醒 AP。无趣的组播与广播在 AP 继续睡眠时就被丢弃；只有程序判定为 PASS 的帧才会冒上来唤醒主机。

驻留固件的解释器与字节码定义位于 Google 的 APF 硬件项目 hardware/google/apf/。负责生成程序的框架侧编译器位于 NetworkStack mainline 模块的 packages/modules/NetworkStack/src/android/net/apf/。

35.30.1 两半：解释器与生成器

APF 分属两套代码，二者必须就字节码契约达成一致：

  • 解释器 是一个极小的、自包含的 C 虚拟机，被编译进 NIC 固件（或厂商 HAL 适配层）。其参考实现是 hardware/google/apf/next/apf_interpreter.c，字节码与机器模型定义在 hardware/google/apf/next/apf.h。系统保留带版本的快照 （v2/、v4/、v6/、v6.1/），以便固件锁定某个已知版本。
  • 生成器 是 NetworkStack 模块中的 Java 代码。它在运行时依据当前网络状态编译APF 程序—— 这些状态包括设备自身地址、组播过滤设置、RA 过滤器与 mDNS 卸载规则—— 随后把生成的字节数组安装进固件。

设备从不携带固定过滤器：程序把设备当前的 IP 地址及其他实时值以字面字节内嵌其中。因此，只要相关状态变化，框架就会重新生成并重新安装程序。

35.30.2 字节码机器模型

hardware/google/apf/next/apf.h 中的头注释精确地定义了这台抽象机器。一台 APF 机器包含：

  1. 一段只读的字节码指令程序。
  2. 两个 32 位寄存器，R0 与 R1。
  3. 十六个 32 位临时内存槽，数据包之间清零。
  4. 数据包的一份只读副本。
  5. 一个可选的读写发送缓冲区（APFv6 及以上），用于构造应答。

每条指令以一个字节开始：高 5 位是操作码，接下来 2 位编码立即数的长度（0、1、2 或 4 字节），最低位选择寄存器。指令集被刻意做得很小：

  • 数据包加载（ldb/ldh/ldw 及其索引变体 *x）从数据包的某个偏移处 取出 1/2/4 字节放入寄存器。
  • 算术与位运算（add、and、or、sh 等）把寄存器与立即数或另一寄存器组合。
  • 条件跳转（jeq、jne、jgt、jlt、jset，以及字节序列匹配 jbsmatch）把 R0 与某值比较后分支。

apf.h 中的 *_OPCODE 定义枚举了这些操作码（例如 LDB_OPCODE、JEQ_OPCODE、JBSMATCH_OPCODE）。 packages/modules/NetworkStack/src/android/net/apf/BaseApfGenerator.java 中的 Opcodes 枚举 在 Java 侧与之对应。

解释器在每次运行前会预填十六个内存槽中的若干个，使程序不必重复计算常用值。apf.h 中的槽位表 （以及 apf_interpreter.c 顶部的 memory_type 联合体）定义了它们。槽 13 保存计算得到的 IPv4 头长度，槽 14 保存数据包总长度，槽 15 保存自程序安装以来的过滤器存活秒数。过滤器可用它在 N 秒内对该数据包限速一次，或让陈旧规则失效。

PASS 与 DROP 被编码为跳出程序末尾的跳转，这使核心循环无分支且极其简单。头注释明确了这一约定：跳到程序末尾之后一个字节表示“放行该数据包”，跳过后两个字节表示“丢弃它”。解释器在其 apf_interpreter.c 分发循环顶部把它转换为返回码：PASS/DROP/EXCEPTION 宏分别对应 1/0/2， apf_run() 返回其中之一。

任何内部错误或断言失败都被刻意转换为 PASS：ASSERT_RETURN 返回 EXCEPTION，运行器在返回前把 EXCEPTION 改写为 PASS。因此有缺陷或对抗性的程序绝不可能导致数据包被静默丢失——拿不准时就唤醒 AP。

APFv6 新增了发送路径：程序可以 allocate 一个发送缓冲区、把字节复制进去并 transmit 它。固件正是以此在不唤醒 AP 的情况下，代 AP 应答 ARP 请求、IPv6 邻居请求以及卸载的 mDNS 查询。主机侧的分配／发送回调是声明在 hardware/google/apf/next/apf_interpreter.h 中的 apf_allocate_tx_buffer() / apf_transmit_tx_buffer() 函数。

配套的反汇编器（hardware/google/apf/disassembler.c）与汇编器库 （hardware/google/apf/apflib.c）让开发者能把已安装的程序读回为可读的汇编，这在排查某个数据包为何被丢弃或未被丢弃时价值极高。

35.30.3 能力协商

在安装任何程序之前，框架必须先了解固件实际能运行什么。这一契约是 packages/modules/Connectivity/framework/src/android/net/apf/ApfCapabilities.java 中的 ApfCapabilities 类， 它携带三个字段：

  • apfVersionSupported：固件实现的 APF 指令集版本，其中 0 表示完全不支持 APF。
  • maximumApfProgramSize：可用于程序及其数据区的 NIC RAM 字节数。
  • apfPacketFormat：固件交给过滤器的链路层帧格式（ARPHRD_* 常量之一）。 生成器目前只为 ARPHRD_ETHER 以太网帧生成代码。

IpClient.maybeCreateApfFilter()（位于 packages/modules/NetworkStack/src/android/net/ip/IpClient.java 约第 2936 行）读取这些能力并决定是否以及如何构建过滤器。其中逻辑值得注意：若设备声称支持 APFv3+ 但暴露的 RAM 少于 1024 字节，IpClient 会把配置版本降为 2，因为 APF 在 RAM 末尾保留的计数区会使实际程序空间过小；它对除 ARPHRD_ETHER 之外的任何 apfPacketFormat 也拒绝构建过滤器，因为生成器中硬编码的数据包偏移假定为以太网帧。随后，填充完整的 ApfConfiguration（组播过滤状态、RA 最短生命周期、ARP/ND/mDNS/IGMP/MLD 卸载标志以及 RAM 大小）被交给 ApfFilter.maybeCreate()。

35.30.4 解释器与生成器的版本同步契约

解释器驻留固件，生成器位于可更新的 mainline 模块中。正因如此，二者对同一操作码含义的理解绝不能出现分歧。在固件侧，该契约是 apf_interpreter.c 中 apf_version() 返回的版本号（当前为带日期戳的值 20250228）。框架侧则把它与 BaseApfGenerator.java 中的版本常量做匹配：

// This version number syncs up with APF_VERSION in hardware/google/apf/apf_interpreter.h
public static final int APF_VERSION_2 = 2;
public static final int APF_VERSION_3 = 3;
public static final int APF_VERSION_4 = 4;
public static final int APF_VERSION_6 = 6000;
public static final int APF_VERSION_61 = 6100;

生成器会选择固件所能运行的最强程序格式。 ApfFilter.createApfGenerator()（ApfFilter.java 约第 4187 行）依据协商出的版本实例化 ApfV61Generator、ApfV6Generator 或 ApfV4Generator。这一选择通过 useApfV61Generator() / useApfV6Generator() 把关，它们各自调用对应生成器的 supportsVersion() 检查（例如 ApfV6Generator.supportsVersion() 仅在 version >= APF_VERSION_6 时返回 true）。三者的共同基类是 ApfV4GeneratorBase， 而 BaseApfGenerator.requireApfVersion() 会在生成器代码试图发射目标固件版本无法执行的指令时抛出 IllegalInstructionException。正是这一编译期护栏，防止较新的 NetworkStack 把 APFv6 操作码发给只会 APFv4 的固件。

35.30.5 编译与安装程序

ApfFilter.installNewProgram()（ApfFilter.java 约第 4302 行）是“编译并安装”循环的核心。每当相关状态发生变化（新的 IP 地址、组播过滤开关切换、新的路由通告、更新的 mDNS 卸载规则）它都会运行。流程如下：

  1. 为协商版本创建生成器（createApfGenerator()）。
  2. 发射序言，随后在程序预算允许的范围内逐步塞入尽可能多的过滤逻辑。代码对优先顺序是明确写出的：先为 mDNS 卸载规则预留空间（使设备能由固件代为应答服务查询而不必被唤醒），再为 RA 过滤器预留空间；各项尺寸都以 mMaximumApfProgramSize 为准，放不下的部分会被从本次程序中丢弃，而不是撑爆 NIC RAM。
  3. 调用 gen.generate() 把指令列表汇编成最终的 byte[] 程序。
  4. 把字节交给 installPacketFilter()，它经 IApfController 接口调用 Wi-Fi HAL，由后者把程序写入 NIC RAM。IpClient 接入了两个控制器实现（mIpClientApfController 与 mNonHalApfController，位于 IpClient.java 约第 1144 行），用哪一个取决于程序是经 IpClient 回调路径安装，还是直接通过非 HAL API 安装。任何安装失败都会记录一条 QE_APF_INSTALL_FAILURE 网络异常指标。

有一个微妙但重要的细节是活性。该程序并非通用程序：

它把设备当前的单播 IPv4/IPv6 地址写死进 jeq 比较中，于是发往这些地址的广播／组播放行，其余一概丢弃。地址一变化，旧程序即失效，installNewProgram() 必须重新运行。解释器预填了“过滤器存活时间”槽（槽 15），让对时间敏感的规则（例如 RA 生命周期检查与限速）能推知当前程序已运行多久，框架无需按定时器重新安装程序。

净效果是清晰的分工：框架对网络状态有完整可见性，且拥有可更新的代码路径，由它思考并编译出量身定制的程序；固件在 AP 睡眠状态下，每帧只运行数百字节的无分支字节码并判定 PASS 或 DROP。空闲的 Android 设备正是以此留在网络上，而不为它根本不需要的流量支付唤醒税。

35.31 Wi-Fi RTT 与 802.11az 安全测距

Wi-Fi RTT（往返时间）让设备测量自身到某台 Wi-Fi 接入点或另一台设备的距离，做法是对 IEEE 802.11mc 定义的精细定时测量（FTM）帧交换进行计时。

该 API 自 Android 9 起就已存在：应用构建 RangingRequest 并通过 WifiRttManager 提交，随后得到一组 RangingResult 对象，每个对象携带以毫米为单位的距离与距离标准差。Android 17 保留该 API，并新增对更新的 IEEE 802.11az 测距修正案的支持，包括其安全变体。

框架类位于 Wifi mainline 模块的 packages/modules/Wifi/framework/java/android/net/wifi/rtt/ 下。

35.31.1 测距请求路径

WifiRttManager （packages/modules/Wifi/framework/java/android/net/wifi/rtt/WifiRttManager.java） 取自 Context.getSystemService(WifiRttManager.class)，并以 android.hardware.wifi.rtt 特性为前提。一次测距请求可用两种方式指定对端：

  • 通过 ScanResult（或 ResponderConfig），对某台接入点测距。
  • 通过 PeerHandle，对另一个 Wi-Fi Aware（NAN）对端测距。该 PeerHandle 即本章前文 Aware 部分所述的不透明 Aware 对端标识符，测距复用了它。这使得已经通过 Aware 发现对端的应用，无需另建关联即可测量到它的距离。

ResponderConfig （.../rtt/ResponderConfig.java）描述单个对端。针对 802.11az 它新增了 supports80211azNtb 字段及 is80211azNtbSupported() / Builder set80211azNtbSupported()（NTB 即 non-trigger-based ranging，非触发式测距），还新增了面向 Aware 场景的 getPeerHandle() / setPeerHandle() 以及 getSecureRangingConfig() 访问器。fromScanResult() 工厂会检查扫描结果的能力：一旦发现支持 PASN，便自动填入安全配置。

35.31.2 802.11az 安全测距：PASN 与帧保护

802.11mc 的帧交换未经认证，附近攻击者可以伪造 FTM 帧并谎报距离。802.11az 增加了预关联安全协商 （PASN）：两台设备在测距前先完成一次轻量级的认证密钥交换，随后对测距帧加以保护。Android 17 通过两个新类暴露该能力，二者都由 secure_ranging aconfig 开关 （packages/modules/Wifi/flags/wifi_flags.aconfig）保护：

  • SecureRangingConfig（.../rtt/SecureRangingConfig.java）携带按会话的安全选项： isSecureHeLtfEnabled()（加密的 HE-LTF 长训练字段，可防止旁听者重放测距波形）、 isRangingFrameProtectionEnabled()，以及要使用的 PasnConfig。
  • PasnConfig（.../rtt/PasnConfig.java）保存认证参数：一组基础 AKM （AKM_PASN、AKM_SAE、AKM_FT_*、 AKM_FILS_*）与成对密码套件（CIPHER_CCMP_128、CIPHER_GCMP_256 等），还包含可选的口令或 SSID 以及 PASN 回访 cookie。静态辅助方法 getBaseAkmsFromCapabilities() 与 getCiphersFromCapabilities() 从扫描结果的能力字符串推导出 AKM 与密码套件位掩码。

PASN 密钥缓存让重复的测距会话跳过完整握手。当响应方无法立即接纳请求方时，它返回一个 回访 cookie 与退避时延，请求方在下次尝试时把两者原样回送。RangingResult 通过 getPasnComebackCookie() 与 getPasnComebackAfterMillis() 暴露它们，另提供 isRangingAuthenticated() isRangingFrameProtected() 与 isSecureHeLtfEnabled()。借助这些，调用方可以判断某次测量是否真正得到了安全保护。

35.31.3 选择安全模式

RangingRequest （.../rtt/RangingRequest.java）新增了安全模式，请求方通过 Builder.setSecurityMode() 设置：

模式 行为
SECURITY_MODE_OPEN 普通 802.11mc/az 测距，不做认证
SECURITY_MODE_OPPORTUNISTIC 双方都支持时使用安全测距，否则回落到开放模式
SECURITY_MODE_SECURE_AUTH 要求使用基础 AKM 的 PASN 认证；不支持的对端被剔除

WifiRttManager.getRttCharacteristics() 通过新的布尔键公布本机射频能力： CHARACTERISTICS_KEY_BOOLEAN_NTB_INITIATOR、 CHARACTERISTICS_KEY_BOOLEAN_SECURE_HE_LTF_SUPPORTED、 CHARACTERISTICS_KEY_BOOLEAN_RANGING_FRAME_PROTECTION_SUPPORTED，以及整型的 CHARACTERISTICS_KEY_INT_MAX_SUPPORTED_SECURE_HE_LTF_PROTO_VERSION。应用可以读取一次，据此决定是请求 SECURITY_MODE_SECURE_AUTH 还是接受机会性安全。

小结

Android 的网络与连接协议栈是一个层次极深的系统：它把 Java 框架服务、本地守护进程、eBPF 程序与 Linux 内核子系统组合成一个有机整体。关键的架构洞见如下：

  1. ConnectivityService 是编排者：所有网络管理都流经这一个服务，它持有全部网络、请求及其匹配关系的全局视图。

  2. NetworkAgent 是网络的抽象：每种传输（Wi-Fi、蜂窝、VPN）都通过这一统一接口与 ConnectivityService 通信，该接口使与传输类型无关的网络管理成为可能。

  3. Mainline 模块化带来敏捷性：关键的网络组件（Connectivity、NetworkStack、Wi-Fi、DnsResolver）以可独立更新的 APEX 模块交付，从而把安全修复与平台 OTA 解耦。

  4. eBPF 正在取代 iptables：现代 Android 越来越多地使用 BPF 程序做流量控制；相比传统 iptables 链，它们性能更好、策略执行更灵活。

  5. 按网络隔离是基础：netId/fwmark 机制确保路由、DNS 与防火墙规则被正确限定在单个网络范围内，从而使按应用 VPN、多网络连接等特性成为可能。

  6. 安全是分层叠加的：Android 以纵深防御保护网络通信，层次从网络安全配置（应用层）经加密 DNS（传输层）一直延伸到防火墙规则（网络层）。

网络协议栈仍在快速演进：近期的增强包括 Wi-Fi 7 MLO 支持、卫星连接、Thread 网状组网以及用于加密 DNS 的 DoH。

Android 17 还把模块化推进到本地代码——引入 mainline supplicant（一个随 Wi-Fi APEX 交付、可更新的 wpa_supplicant）。它同时重新设计了代理协议栈：新协议栈通过 PacCoordinator 以及驻留 APEX 的 MultiPacService/MultiProxyService，支持按网络／用户／UID 并发的多个 PAC 脚本。此外，Android 17 在新的 ACCESS_LOCAL_NETWORK 权限背后新增了按应用、由用户驱动的 NSD 服务访问选择器。模块化架构确保这些特性无需等待完整平台升级即可交付给用户。

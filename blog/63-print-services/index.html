第 63 章：打印服务

第 63 章：打印服务

Android 的打印框架提供了一套完整系统，用于发现打印机、渲染文档、假脱机（spool）打印作业，并把它们投递给实体或虚拟打印机。该框架采用分层架构：一个系统服务（PrintManagerService）管理按用户划分的状态并在应用之间协调；一个打印假脱机进程管理打印队列；可插拔的打印服务负责与特定打印机或协议通信。

本章从公开 API 一路讲到系统服务内部，覆盖打印作业生命周期、文档渲染、打印机发现与假脱机架构。

63.2.1 发起一次打印作业

应用在 Activity 中调用 PrintManager.print() 发起打印：

// Application code
PrintManager printManager = (PrintManager) getSystemService(Context.PRINT_SERVICE);
PrintJob job = printManager.print("My Document", new MyPrintDocumentAdapter(), null);

print() 方法会：

  1. 为跨进程通信创建一个 PrintDocumentAdapterDelegate 代理
  2. 经 Binder IPC 把打印请求送给 PrintManagerImpl
  3. 读取系统在 EXTRA_PRINT_DIALOG_INTENT 下返回的 IntentSender，并用它启动打印 UI（来自 com.android.printspooler 包）
  4. 返回用于跟踪状态的 PrintJob 句柄；若打印不可用则返回 null

Android 17 的实现加固了这条路径。print() 会构建带 MODE_BACKGROUND_ACTIVITY_START_ALLOWED 的 ActivityOptions，使假脱机对话框被允许从打印请求启动；同时它现在会捕获对话框 Activity 无法解析时的 ActivityNotFoundException，在这种情况下返回 null（文档化的失败模式），而不是把异常泄漏给调用方：

// frameworks/base/core/java/android/print/PrintManager.java
try {
    ActivityOptions activityOptions = ActivityOptions.makeBasic()
            .setPendingIntentBackgroundActivityStartMode(
                    ActivityOptions.MODE_BACKGROUND_ACTIVITY_START_ALLOWED);
    mContext.startIntentSender(intent, null, 0, 0, 0, activityOptions.toBundle());
    return new PrintJob(printJob, this);
} catch (SendIntentException sie) {
    Log.e(LOG_TAG, "Couldn't start print job config activity.", sie);
} catch (ActivityNotFoundException anfe) {
    Log.e(LOG_TAG, "Print preview activity not found: ", anfe);
}
return null;

63.3 PrintDocumentAdapter —— 渲染契约

PrintDocumentAdapter 是应用为实现“为打印提供内容”而重写的抽象类，它在应用与打印框架之间定义了一套严格的生命周期契约。

63.3.1 生命周期

stateDiagram-v2
    [*] --> onStart: 发起打印
    onStart --> onLayout: 提供打印属性
    onLayout --> onWrite: 布局完成、内容变化
    onLayout --> onLayout: 属性变化
    onWrite --> onLayout: 属性变化
    onWrite --> onFinish: 所有页面写完
    onLayout --> onFinish: 用户取消
    onFinish --> [*]: 释放资源

生命周期回调：

// frameworks/base/core/java/android/print/PrintDocumentAdapter.java
public abstract class PrintDocumentAdapter {
    public static final String EXTRA_PRINT_PREVIEW = "EXTRA_PRINT_PREVIEW";

    // 1. Called once when printing starts
    public void onStart() { /* stub */ }

    // 2. Called when print attributes change (page size, density, etc.)
    public abstract void onLayout(PrintAttributes oldAttributes,
            PrintAttributes newAttributes,
            CancellationSignal cancellationSignal,
            LayoutResultCallback callback,
            Bundle extras);

    // 3. Called to render specific pages as PDF
    public abstract void onWrite(PageRange[] pages,
            ParcelFileDescriptor destination,
            CancellationSignal cancellationSignal,
            WriteResultCallback callback);

    // 4. Called once when printing finishes
    public void onFinish() { /* stub */ }
}

63.3.2 布局—写入协议

系统与适配器之间的交互遵循一套回调协议：

sequenceDiagram
    participant System as 打印系统
    participant Adapter as PrintDocumentAdapter
    participant Callback as LayoutResultCallback

    System->>Adapter: onStart()
    System->>Adapter: onLayout(oldAttrs, newAttrs, cancel, callback, extras)

    alt 布局成功
        Adapter->>Callback: onLayoutFinished(info, contentChanged=true)
        System->>Adapter: onWrite(pages, fd, cancel, writeCallback)
        Note over Adapter: 把页面作为 PDF 渲染到 fd
        Adapter->>System: writeCallback.onWriteFinished(writtenPages)
    else 布局失败
        Adapter->>Callback: onLayoutFailed("reason")
    else 布局被取消
        Adapter->>Callback: onLayoutCancelled()
    end

    System->>Adapter: onFinish()

关键规则：

  • onLayout() 在调用其中一个回调方法之前不算完成
  • onWrite() 在调用其中一个回调方法之前不算完成
  • 当前方法完成之前，不会调用其他生命周期方法
  • 适配器必须关闭传给 onWrite() 的 ParcelFileDescriptor
  • extras bundle 中含 EXTRA_PRINT_PREVIEW，用于指示预览模式

63.3.3 取消

CancellationSignal 参数让系统得以请求取消：

cancellationSignal.setOnCancelListener(new OnCancelListener() {
    @Override
    public void onCancel() {
        // Stop layout or write work
    }
});

当用户在一次进行中的布局过程中改变打印选项时，这一点很重要 —— 系统会取消当前布局并请求一次新的布局。

63.3.4 PrintDocumentInfo

布局之后，适配器报告文档元数据：

PrintDocumentInfo info = new PrintDocumentInfo.Builder("document.pdf")
        .setContentType(PrintDocumentInfo.CONTENT_TYPE_DOCUMENT)
        .setPageCount(pageCount)
        .build();
callback.onLayoutFinished(info, contentChanged);

contentChanged 标志至关重要：为 false 时，系统可以复用先前已渲染的页面并跳过 onWrite() 调用。

一个打印作业会经历七个状态，由 PrintJobInfo 跟踪：

63.4.3 内部状态分组

系统用聚合状态常量做过滤：

常量 包含的状态 用途
STATE_ANY 所有状态 不过滤
STATE_ANY_VISIBLE_TO_CLIENTS 实际上只有 BLOCKED（见下文） 对创建该作业的应用可见
STATE_ANY_ACTIVE CREATED、QUEUED、STARTED、BLOCKED 非终态状态
STATE_ANY_SCHEDULED QUEUED、STARTED、BLOCKED 已投递给打印服务

STATE_ANY_VISIBLE_TO_CLIENTS 过滤器只在一个地方被消费，即 PrintSpoolerService.isStateVisibleToUser()。该方法要求 isActiveState(state)（CREATED、QUEUED、STARTED 或 BLOCKED）并且是 FAILED、COMPLETED、CANCELED 或 BLOCKED 之一。这两个条件的交集只有 STATE_BLOCKED —— 而不是名字可能暗示的“除 CREATED 之外的所有状态”。

63.4.4 PrintJob 包装类

PrintJob 类为应用提供了一层方便的包装：

// frameworks/base/core/java/android/print/PrintJob.java
public final class PrintJob {
    private final @NonNull PrintManager mPrintManager;
    private @NonNull PrintJobInfo mCachedInfo;

    public void cancel() {
        final int state = getInfo().getState();
        if (state == PrintJobInfo.STATE_QUEUED
                || state == PrintJobInfo.STATE_STARTED
                || state == PrintJobInfo.STATE_BLOCKED
                || state == PrintJobInfo.STATE_FAILED) {
            mPrintManager.cancelPrintJob(mCachedInfo.getId());
        }
    }

对于活动作业，缓存的 PrintJobInfo 在每次 getInfo() 调用时刷新；对终态（已完成/已取消）则直接返回缓存，因为这些状态不会再变。

// Typical implementation in a PrintDocumentAdapter
@Override
public void onWrite(PageRange[] pages, ParcelFileDescriptor destination,
        CancellationSignal cancel, WriteResultCallback callback) {

    PrintedPdfDocument document = new PrintedPdfDocument(context, printAttributes);

    for (int pageNum : pagesToWrite) {
        PdfDocument.Page page = document.startPage(pageNum);

        // Get the Canvas and draw content
        Canvas canvas = page.getCanvas();
        drawPageContent(canvas, pageNum);

        document.finishPage(page);
    }

    // Write to the file descriptor
    document.writeTo(new FileOutputStream(destination.getFileDescriptor()));
    document.close();

    callback.onWriteFinished(new PageRange[] { PageRange.ALL_PAGES });
}

63.7.2 权限强制

PrintManagerImpl 中的 print() 方法会校验：

  1. 适配器非空
  2. 打印已启用（未被设备策略禁用）
  3. 调用用户是当前前台用户（或它的某个配置文件用户）

打印由 UserManager.DISALLOW_PRINTING 用户限制门控 —— 管理员禁用打印时，DevicePolicyManager 会设置该限制：

// frameworks/base/services/print/java/com/android/server/print/PrintManagerService.java
private boolean isPrintingEnabled() {
    return !mUserManager.hasUserRestriction(UserManager.DISALLOW_PRINTING,
            Binder.getCallingUserHandle());
}

打印被禁用时，print() 会经 DevicePolicyManagerInternal.getPrintingDisabledReasonForUser() 取到人类可读的原因并以 toast 展示；它还会驱动适配器走过 start()/finish()，以便释放应用资源；然后返回 null，不创建作业。

63.14 print() 方法的内部

UserState.print() 方法揭示了作业创建的内部机制：

// frameworks/base/services/print/java/com/android/server/print/UserState.java
public Bundle print(@NonNull String printJobName, @NonNull IPrintDocumentAdapter adapter,
        @Nullable PrintAttributes attributes, @NonNull String packageName, int appId) {
    // Create print job place holder.
    final PrintJobInfo printJob = new PrintJobInfo();
    printJob.setId(new PrintJobId());
    printJob.setAppId(appId);
    printJob.setLabel(printJobName);
    printJob.setAttributes(attributes);
    printJob.setState(PrintJobInfo.STATE_CREATED);
    printJob.setCopies(1);
    printJob.setCreationTime(System.currentTimeMillis());

    // Track this job so we can forget it when the creator dies.
    if (!mPrintJobForAppCache.onPrintJobCreated(adapter.asBinder(), appId, printJob)) {
        return null; // Client is dead
    }

    Intent intent = new Intent(PrintManager.ACTION_PRINT_DIALOG);
    intent.setData(Uri.fromParts("printjob", printJob.getId().flattenToString(), null));
    intent.putExtra(PrintManager.EXTRA_PRINT_DOCUMENT_ADAPTER, adapter.asBinder());
    intent.putExtra(PrintManager.EXTRA_PRINT_JOB, printJob);
    intent.putExtra(Intent.EXTRA_PACKAGE_NAME, packageName);

    ActivityOptions activityOptions = ActivityOptions.makeBasic()
            .setPendingIntentCreatorBackgroundActivityStartMode(
                    ActivityOptions.MODE_BACKGROUND_ACTIVITY_START_DENIED);
    IntentSender intentSender = PendingIntent.getActivityAsUser(
            mContext, 0, intent, PendingIntent.FLAG_ONE_SHOT
                    | PendingIntent.FLAG_CANCEL_CURRENT | PendingIntent.FLAG_IMMUTABLE,
            activityOptions.toBundle(), new UserHandle(mUserId)).getIntentSender();

    Bundle result = new Bundle();
    result.putParcelable(PrintManager.EXTRA_PRINT_JOB, printJob);
    result.putParcelable(PrintManager.EXTRA_PRINT_DIALOG_INTENT, intentSender);
    return result;
}

关键实现细节：

  1. 死亡跟踪：适配器的 Binder 经 PrintJobForAppCache 被监视 —— 创建作业的应用一旦死亡，其打印作业会被清理。

  2. PendingIntent：打印对话框经一个 PendingIntent 启动，该 PendingIntent 被包在 EXTRA_PRINT_DIALOG_INTENT 下的 Bundle 里。客户端（63.2.1 节中的 PrintManager.print()）读取那个 IntentSender 并启动它。这样，对话框就能跨进程边界以正确的安全上下文运行。

  3. 后台 Activity 限制：该 PendingIntent 用 setPendingIntentCreatorBackgroundActivityStartMode(MODE_BACKGROUND_ACTIVITY_START_DENIED) 构建，因此创建方应用无法借这个 intent 启动后台 Activity。

  4. 初始状态：每个打印作业都以 STATE_CREATED、1 份副本开始。

63.21.2 日志

63.23 打印机设置 Activity（Android 17）

Android 17 允许打印服务为打印机发布一个设置（setup）Activity，与长期存在的信息（info）Activity 并列。触发场景是：服务能发现某台打印机，但在用户完成一次性设置步骤之前无法向其打印 —— 这类步骤包括认领打印机、输入凭据、安装厂商配置文件。该特性由 android.print.flags.enable_setup_activity aconfig 标志门控：

# frameworks/base/core/java/android/print/flags/flags.aconfig
flag {
    name: "enable_setup_activity"
    namespace: "printing"
    description: "Enable PrintService implementations to provide a printer setup activity"
    is_exported: true
}

63.23.1 PrinterInfo 上的 setup intent

PrinterInfo 在既有的 mInfoIntent 之外新增了一个可空的 mSetupIntent（PendingIntent）。打印服务经 PrinterInfo.Builder.setSetupIntent() 附上它：

// frameworks/base/core/java/android/print/PrinterInfo.java
@FlaggedApi(Flags.FLAG_ENABLE_SETUP_ACTIVITY)
public @NonNull Builder setSetupIntent(@NonNull PendingIntent setupIntent) {
    mSetupIntent = Objects.requireNonNull(setupIntent);
    return this;
}

每一个触及该字段的地方 —— 构造函数、序列化、hashCode()、equals() 与 toString() —— 都包在 if (Flags.enableSetupActivity()) 里。于是这个额外的 PendingIntent 只在标志打开时才从 parcel 读写，从而与按标志关闭版本编译的服务保持线格式兼容。访问器 getSetupIntent() 被刻意标为 @hide —— 只有框架自己的打印 UI 才应启动设置界面，第三方应用即便经其他 API 拿到 PrinterInfo 也无法启动它。

63.23.2 假脱机器如何在设置完成前阻止打印

打印对话框（假脱机器中的 PrintActivity）把带 setup intent 的打印机视作“尚不可打印”。needsSetup() 仅在标志打开且所选打印机带 setup intent 时返回 true：

// frameworks/base/packages/PrintSpooler/src/com/android/printspooler/ui/PrintActivity.java
private static boolean needsSetup(PrinterInfo printer) {
    return android.print.flags.Flags.enableSetupActivity()
            && printer != null
            && printer.getSetupIntent() != null;
}

用户尝试打印时，setupAndPrint() 先检查 needsSetup()。若需要设置，它会为“取结果”而启动服务的 setup PendingIntent（而不是确认打印作业），从而让该 Activity 借 MODE_BACKGROUND_ACTIVITY_START_ALLOWED 从假脱机器启动。只有不需要设置（或设置已完成）时，假脱机器才落到 confirmPrint()：

flowchart TB
    PRESS["用户按下打印"]
    NEEDS{"needsSetup 打印机<br/>（标志开 且<br/>setupIntent != null）？"}
    LAUNCH["startIntentSenderForResult<br/>（打印机设置 Activity）"]
    DONE{"设置结果为 OK？"}
    UPDATE["onSetupActivityResult：<br/>采用返回的打印机，<br/>回到对话框"]
    CONFIRM["confirmPrint<br/>（假脱机作业，STATE_QUEUED）"]
    STAY["停留在打印对话框"]

    PRESS --> NEEDS
    NEEDS -->|"否"| CONFIRM
    NEEDS -->|"是"| LAUNCH
    LAUNCH --> DONE
    DONE -->|"是"| UPDATE
    DONE -->|"否"| STAY

设置成功并不会直接假脱机作业。onSetupActivityResult() 只是采用设置 Activity 返回的打印机 —— 如果用户在设置过程中另选了打印机，这可能是另一台 —— 然后按该打印机的能力更新打印属性并回到对话框。用户再次按下打印，此时该打印机不再需要设置，假脱机器便落到 confirmPrint()。

63.24.2 事件在哪里被记录

作业进入最终假脱机状态时，PrintSpoolerService.logPrintJobFinalState() 发出一个 FrameworkPrintJob。它解析打印服务的 UID，读取可选的属性（PrintAttributes）与文档信息（PrintDocumentInfo），交给异步记录器：

// frameworks/base/packages/PrintSpooler/src/com/android/printspooler/model/PrintSpoolerService.java
private void logPrintJobFinalState(PrinterId printerId, PrintJobInfo printJob) {
    if (!Flags.printingTelemetry()) {
        return;
    }
    // ... resolve serviceUId, read PrintAttributes + PrintDocumentInfo ...
    StatsAsyncLogger.INSTANCE.PrintJob(serviceUId, state, colorMode, size,
            resolution, duplexMode, docType, savedPdf, pageCount);

proto 的注释点名了每个 atom 的确切来源文件：FrameworkPrintJob 从 PrintSpoolerService.java 记录，FrameworkPrinterDiscovery 从 PrinterDiscoverySession.java 记录，两个 UI 启动 atom 从 PrintActivity.java 记录。为支持这些 atom，Android 17 还加了一些供记录器使用的小访问器，包括从 PrintAttributes 与 PrintDocumentInfo 读取纸张尺寸与文档类型的查询。

63.25 假脱机器不再处处预装（Android 17）

早先的版本假定 com.android.printspooler 存在于每个用户上。Android 17 把这项预装改成显式的 install-in-user-type 白名单：假脱机器只为列出的用户类型交付（完整用户，加上 clone、managed 与 private 配置文件），而不是无条件地给每个用户都装。

<!-- build/make/target/product/sysconfig/preinstalled-packages-platform-handheld-system.xml -->
<install-in-user-type package="com.android.printspooler">
    <install-in user-type="FULL" />
    <install-in user-type="android.os.usertype.profile.CLONE" />
    <install-in user-type="android.os.usertype.profile.MANAGED" />
    <install-in user-type="android.os.usertype.profile.PRIVATE" />
</install-in-user-type>

既然假脱机器在某个用户上可能不存在，与它打交道的代码就必须容忍这一点。dumpsys print 路径是最显眼的例子：一个过时的实现会对每个用户状态都调用 RemotePrintSpooler.dump()，而当假脱机包未安装时该调用会失败。Android 17 加了一道安装检查来短路转储：

// frameworks/base/services/print/java/com/android/server/print/RemotePrintSpooler.java
public void dump(@NonNull DualDumpOutputStream dumpStream) {
    synchronized (mLock) {
        if (!isInstalled()) {
            return;
        }
        // ... write is_destroyed / is_bound ...
    }
}

private boolean isInstalled() {
    try {
        mContext.createPackageContextAsUser(PRINT_SPOOLER_PACKAGE_NAME, 0, mUserHandle);
        return true;
    } catch (PackageManager.NameNotFoundException e) {
        return false;
    } catch (Exception e) {
        Slog.e(LOG_TAG, "Failed to check if print spooler is installed", e);
        return false;
    }
}

isInstalled() 经 createPackageContextAsUser() 在代理自己的 mUserHandle 上探测假脱机包。返回 false 时，对该用户的转储被跳过 —— 于是 adb shell dumpsys print 在某些用户没有假脱机器的设备上也能成功。

动手试试

用一台运行 Android 17 的设备或模拟器观察打印框架的实际行为。

  1. 查看活动打印状态。 打开任一支持打印的应用（Chrome、Files、Photos），发起一次打印，然后转储框架状态：

    adb shell dumpsys print
adb shell dumpsys print --proto > print_state.pb

    留意逐用户的 UserState 区段、已安装与活动的打印服务，以及缓存的打印作业。在有次要用户的设备上，确认该命令不会失败 —— 即便某些用户上可能没有假脱机器（63.25 节）也是如此。

  2. 观察“禁用集合”模型。 列出打印服务，然后在设置里切换其中一个，再读取真正持久化该选择的 secure 设置：

    adb shell settings get secure disabled_print_services

    在设置中禁用一个服务，观察它出现在冒号分隔的列表里的 ComponentName。而启用设置保持为空（63.8.2 节）。

  3. 追踪打印作业的生命周期。 跟随一个作业从 STATE_CREATED 经 STATE_QUEUED 到终态。框架的各个类把 verbose 日志门控在编译期常量 DEBUG = false 上（63.21.2 节），所以 setprop log.tag.* 帮不上忙。取而代之，在作业推进过程中轮询 dumpsys print，观察缓存作业的 state 字段变化；同时观察那些无条件进入 logcat 的消息：

    adb shell dumpsys print | grep -A3 "print jobs"
adb logcat | grep -i print

    在自建镜像上，把 UserState.java 与 RemotePrintSpooler.java 中的 DEBUG 改为 true，即可记录每一次状态迁移。

  4. 切换新增的标志。 查看 Android 17 的打印标志及其当前状态：

    adb shell device_config get printing android.print.flags.enable_setup_activity
adb shell device_config get printing com.android.printspooler.flags.printing_telemetry

    aconfig 标志对应的 DeviceConfig 键以其 aconfig 包名限定（android.print.flags 与 com.android.printspooler.flags）。在较新的构建上，adb shell aflags list | grep printing 会列出两个标志及其当前状态。

    在 printing_telemetry 打开时完成一次打印，确认记录了一个 FrameworkPrintJob atom（63.24 节）。

  5. 实现一个最小打印服务。 构建一个 PrintService 子类，在 onCreatePrinterDiscoverySession() 中报告一台假打印机，并在 onPrintJobQueued() 中完成作业。用 PrinterInfo.Builder.setSetupIntent() 附上一个 setup intent，观察打印对话框在作业被允许之前如何因设置而阻塞（63.23 节）。

小结

Android 的打印框架是一个结构良好的系统，建立在四层之上：客户端 API（PrintManager）、系统服务（PrintManagerService 加逐用户的 UserState）、打印假脱机进程（com.android.printspooler），以及可插拔的打印服务（PrintService）。

应用与打印框架之间的 PrintDocumentAdapter 契约确保内容能针对不同打印属性重新布局，而框架始终要求 PDF 输出。七状态的打印作业生命周期（CREATED -> QUEUED -> STARTED -> COMPLETED/FAILED/CANCELED，BLOCKED 作为中间状态）提供了对打印进度的细粒度跟踪。

打印机发现经 PrinterDiscoverySession 处理，支持惰性能力加载与实时的打印机状态跟踪。这种会话式设计确保打印服务只在系统需要时才执行昂贵的网络发现。

假脱机与打印服务代理（RemotePrintSpooler 与 RemotePrintService）处理跨进程通信的各种复杂性，包括绑定生命周期、超时、崩溃恢复与延迟命令排队。多用户架构在共享底层框架基础设施的同时，确保用户之间完全隔离。

Android 17 精化其中若干层：打印服务现在可以发布逐打印机的设置 Activity（enable_setup_activity），由假脱机器启动它，从而在用户完成设置之前阻止打印。

新的遥测层（printing_telemetry）为作业结果、打印机发现与打印对话框使用情况发出结构化 statsd atom。持久化的服务状态继续在 Settings.Secure.DISABLED_PRINT_SERVICES 中跟踪禁用集合，遗留的启用列表设置仅作为一次性迁移输入存活。假脱机器不再在每个用户上预装，因此像 dumpsys print 这样的框架代码现在用安装检查来守卫对假脱机器的访问；此外，当对话框 Activity 无法解析时，PrintManager.print() 返回 null 而不是泄漏 ActivityNotFoundException。

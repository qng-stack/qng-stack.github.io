第 65 章：自定义 ROM 指南

第 65 章：自定义 ROM 指南

本章是全书的收束篇。我们把前面 62 章讲过的内容 —— 构建系统、init、HAL、系统服务、SystemUI、模拟器、安全与签名 —— 汇总成一次完整的端到端演练，演示如何构建、裁剪、签名并发布一个功能完备的自定义 ROM。

目标设备是 AOSP 的 Goldfish 模拟器（sdk_phone64_x86_64）。这是刻意选的：本书每位读者都有一台能跑模拟器的笔记本或工作站，不需要真实硬件。而这里构建的一切同样适用于真实设备 —— 自定义设备树、overlay、应用、服务、开机动画、内核调优与 HAL 改造，唯一需要变化的是 BoardConfig.mk 与内核二进制。

本章里每个文件路径、每条命令、每个代码片段都对照 Android 17（android17-release）AOSP 源码树验证过。引用源文件时我们给出完整的树内相对路径，方便你在自己的检出里对照。

65.1 规划你的自定义 ROM

65.1.1 什么是“自定义 ROM”？

自定义 ROM 是 Android 的一个改造构建，它改动了下列一层或多层：

层次 示例 复杂度
产品配置 品牌、预置应用、壁纸 低
资源 overlay 状态栏颜色、快捷设置布局、配置开关 低
预置应用 增删随镜像打包的 APK 低
框架行为 新系统服务、修改 API 中
SystemUI 自定义状态栏、导航、主题 中
开机动画 自定义开机画面 低
内核 自定义模块、调度器调优 高
HAL 自定义硬件抽象层 高
签名与分发 发布密钥、OTA 包 中

流行的社区 ROM（LineageOS、/e/OS、GrapheneOS、CalyxOS、PixelExperience）都在所有这些层次上组合了各自的裁剪。本章我们会触及每一层。

65.1.2 定义你的 ROM 目标

动手写代码之前，先回答这些问题：

  1. 目的是什么？ 主打隐私？主打性能？企业管控？还是纯粹的学习练手？

  2. 目标设备是什么？ 我们用模拟器（goldfish/ranchu）；真实设备需要厂商 blob 与内核源码。

  3. 基于哪个 Android 版本？ 我们基于 AOSP main 构建 —— 撰写时为 Android 17（平台 SDK 37，last-stable 版本 17）。固定这些取值的发布配置位于 build/release/：build/release/flag_values/trunk_staging/RELEASE_PLATFORM_VERSION_LAST_STABLE.textproto 中写 "17"，RELEASE_PLATFORM_SDK_VERSION.textproto 中写 "37"。

  4. 品牌是什么？ ROM 名称、型号字符串、构建指纹。

  5. 默认预置哪些应用？ 保留哪些 AOSP 应用、移除哪些、加入哪些第三方 APK？

  6. 框架要改什么？ 新服务、行为改动、配置变更。

65.2 搭建构建环境

65.2.1 硬件要求

构建 AOSP 很吃资源，要求如下：

资源 最低 推荐 本书配置
磁盘（源码） 250 GB 400 GB 500 GB SSD
磁盘（含构建产物） 400 GB 600 GB+ 1 TB NVMe
内存 32 GB 64 GB+ 64 GB
CPU 核心 4 16+ 16 核
操作系统 Ubuntu 22.04+ Ubuntu 24.04 LTS Ubuntu 24.04
文件系统 ext4（区分大小写） ext4 ext4

构建高度并行，每多一个核都能从完整构建里省下几分钟。内存是第二关键因素 —— 链接器（lld）与 javac/d8 编译阶段每个并行任务可吃掉 2–4 GB。

关于工具链有一点说明：AOSP 自带宿主机工具链预编译包，因此你不需要从发行版安装 JDK 或 C/C++ 编译器 —— 构建会使用树内的 OpenJDK 与树内的 clang。全局默认是 jdk21，树内另有 jdk25 供可选的工具链使用（见 build/soong/ui/build/config.go 的 ConfigJavaEnvironment）。下面这些宿主包只是构建脚本会调用的支撑库与工具。

65.2.3 安装 repo 工具

repo 工具负责协调 AOSP 数百个 Git 仓库：

# Create a bin directory in your home directory

# Download the repo launcher

# Make it executable

repo 启动器是一个 Python 脚本，会从 Google 的仓库引导出完整的 repo 工具，要求 Python 3.6+。

65.2.4 初始化 AOSP 源码树

# Create your working directory
mkdir -p ~/aosp && cd ~/aosp

# Initialize the repo with the main branch
repo init -u https://android.googlesource.com/platform/manifest \
    -b main \
    --partial-clone \
    --clone-filter=blob:limit=10M

# Sync all repositories (this takes 1-3 hours on a fast connection)
repo sync -c -j$(nproc) --no-tags --no-clone-bundle

关键参数说明：

参数 用途
-b main 跟踪 main 开发分支
--partial-clone 启用 Git 部分克隆（省磁盘）
--clone-filter=blob:limit=10M 初始只下载 10 MB 以下的 blob
-c 只同步当前分支
-j$(nproc) 按 CPU 核数并行
--no-tags 跳过 Git 标签（省时省空间）
--no-clone-bundle 跳过 bundle 文件（有时更快）

65.2.6 配置 ccache

编译器缓存 ccache 能大幅缩短重编时间。首次完整构建（约 2–4 小时）之后，只改动少数文件时的增量构建可在几分钟内完成。

# Set cache size (50 GB is reasonable for AOSP)
export USE_CCACHE=1
export CCACHE_EXEC=/usr/bin/ccache
export CCACHE_DIR=$HOME/.ccache
ccache -M 50G

# Add to ~/.bashrc for persistence
cat >> ~/.bashrc << 'EOF'
export USE_CCACHE=1
export CCACHE_EXEC=/usr/bin/ccache
export CCACHE_DIR=$HOME/.ccache
EOF

65.2.7 初始化构建环境

每次开新 shell 都要初始化构建环境：

cd ~/aosp

# Source the environment setup script
# Real file: build/make/envsetup.sh
source build/envsetup.sh

# This provides:
#   lunch    - Select a build target
#   m        - Build (make) from the tree root
#   mm       - Build from the current directory
#   mmm      - Build from a specified directory
#   croot    - cd to the tree root
#   godir    - Go to the directory containing a file

envsetup.sh 脚本（位于 build/make/envsetup.sh）用构建所需的函数与环境变量配置 shell。它会扫描所有 device/*/ 与 vendor/*/ 目录下的 vendorsetup.sh 并 source 它们，从而注册额外的 lunch 目标。

65.2.8 理解 lunch 目标

# Run lunch with no arguments for an interactive menu, or list the pieces
# of a target with the envsetup helpers:
list_products   # every product (TARGET_PRODUCT) the tree knows about
list_releases   # release configs (trunk_staging, next, ...)
list_variants   # user, userdebug, eng

# Select the emulator target (what we will base our ROM on)
lunch sdk_phone64_x86_64-trunk_staging-userdebug

list_products、list_releases 与 list_variants 是 build/soong/bin/ 下的独立脚本，build/make/envsetup.sh 通过 set_global_paths 辅助函数把它们放进 PATH。lunch 本身接受完整拼写的 <product>-<release>-<variant> 字符串；不带参数时它会打印菜单。

lunch 目标的格式是 <product>-<release>-<variant>：

组成 取值 描述
Product sdk_phone64_x86_64 由 AndroidProducts.mk 定义
Release trunk_staging 发布配置
Variant userdebug user、userdebug 或 eng

三种构建变体决定可调试程度：

变体 ro.debuggable adb Root 使用场景
user 0 默认关闭 无 生产/发布
userdebug 1 开启 adb root 行为接近生产环境的开发
eng 1 开启 始终 root 完整开发/调试

我们的自定义 ROM 会创建自己的 lunch 目标，取代 sdk_phone64_x86_64。

在 Android 17 中，最后一步默认经 Siso 而非经典 Ninja 执行 —— build/soong/ui/build/config.go 把 NINJA_DEFAULT = NINJA_SISO。所以 m 会让 Soong 生成的构建图由 Siso 驱动，除非你覆盖它：设 SOONG_NINJA=ninja 可退回经典 Ninja，macOS 上的 CI 构建器也会自动退回。

Siso 与 Soong 产出的 Ninja manifest 在协议上兼容，因此从 ROM 作者角度看，构建依然“像 Ninja” —— 同样的 m、同样的 out/ 布局，但它额外提供了更好的远程执行与缓存钩子。本章的一切在两种执行器下表现一致。

65.3.10 继承机制

$(call inherit-product, ...) 函数是产品配置的基石：它把被包含 makefile 的变量值追加到包含方的同名变量上：

# In parent.mk:
PRODUCT_PACKAGES += ParentApp

# In child.mk:
$(call inherit-product, parent.mk)
PRODUCT_PACKAGES += ChildApp

# Result: PRODUCT_PACKAGES = ParentApp ChildApp

这与简单的 include 语句不同：inherit-product 使用命名空间机制，避免多个 makefile 定义同名变量时相互覆盖。

另有 $(call inherit-product-if-exists, ...)，文件不存在时静默成功 —— 适合可选的厂商 overlay。

65.3.11 通用系统镜像与设备导入

我们的 bookphone 产品构建完整设备镜像。Android 同时还提供通用系统镜像（GSI）：一个按 Treble 接口契约构建的 system.img，可运行在任何符合 Treble 的 vendor 分区之上。GSI 正是你用来把新设备的 vendor 实现与纯 AOSP 做对照检查的手段；GSI 上的兼容性测试（CTS-on-GSI）与供应商测试套件（VTS）也用它验证 vendor/system 切分。

GSI 产品位于 build/make/target/product/：

lunch aosp_arm64-trunk_staging-userdebug   # arm64 GSI
lunch aosp_x86_64-trunk_staging-userdebug  # x86_64 GSI

build/make/target/product/aosp_arm64.mk 自述“aosp_arm64-userdebug 的 system 镜像就是一个 GSI”，并引入 generic_system.mk 与 gsi_release.mk；其板级配置来自 build/make/target/board/BoardConfigGsiCommon.mk。Android 17 还提供 aosp_arm64_fullmte.mk —— 一个强制打开 Arm 内存标记扩展（MTE）的 GSI 变体，用于堆破坏测试。

用 GSI 给真实设备做导入的流程是：

graph TD
    A["来自 OEM 的 vendor 分区（vendor.img）"] --> D["启动 Treble 设备"]
    B["m aosp_arm64 -> system.img（GSI）"] --> D
    D --> E["fastboot flash system system.img"]
    E --> F["重启；AOSP system 运行在 OEM vendor 上"]
    F --> G["运行 CTS-on-GSI / VTS 验证切分"]

    style B fill:#fff3e0
    style G fill:#e8f5e9

刷入 GSI 通常要经 fastbootd（用户态 fastboot），因为 system 是动态分区：

fastboot reboot fastboot          # enter fastbootd
fastboot flash system system.img  # the GSI
fastboot -w                        # wipe userdata (required on a different system)
fastboot reboot

GSI 是调试与一致性验证工具，不是日常使用的 ROM：它不带厂商应用，完全依赖设备已有的 vendor 分区。我们的自定义 ROM 走的是完整设备镜像路线，但当你把自定义 ROM 带到一块新硬件上时，必须了解 GSI 这条路。

Android.bp 文件定义一个预置应用：

// device/AospBook/bookphone/apps/prebuilt/BookReader/Android.bp
//
// Prebuilt APK for BookReader PDF viewer.
// This is included in the system image via PRODUCT_PACKAGES += BookReader.

android_app_import {
    name: "BookReader",

    // The APK file in this directory
    apk: "BookReader.apk",

    // Install to the /product partition (not /system)
    product_specific: true,

    // Other modules this APK replaces (removed from PRODUCT_PACKAGES)
    overrides: [],

    // Signature: presigned means keep the APK's existing signature
    presigned: true,

    // Optional: mark as privileged if it needs privileged permissions
    // privileged: true,

    // Optimize DEX code during build
    dex_preopt: {
        enabled: true,
    },
}

android_app_import 的关键属性：

属性 取值 描述
apk 文件名 APK 文件路径
presigned true/false 保留原有签名 vs. 重新签名
certificate "platform"、"shared"、"media"、路径 签名密钥
privileged true/false 安装到 priv-app/
product_specific true/false 安装到 /product 分区
vendor true/false 安装到 /vendor 分区
dex_preopt.enabled true/false 构建时预优化 DEX

如果你的 APK 并非已用正确密钥签名，就用 certificate 而不是 presigned：

android_app_import {
    name: "BookReader",
    apk: "BookReader.apk",
    product_specific: true,
    certificate: "platform",   // Re-sign with the platform key
    dex_preopt: {
        enabled: true,
    },
}

签名密钥名映射到 build/make/target/product/security/ 下的文件：

密钥名 文件 用途
platform platform.pk8、platform.x509.pem 声明 android:sharedUserId="android.uid.system" 的系统应用
shared shared.pk8、shared.x509.pem 共享数据的应用（Contacts、Phone）
media media.pk8、media.x509.pem 媒体/下载类系统应用
testkey testkey.pk8、testkey.x509.pem 默认开发签名密钥

65.4.4 移除默认应用

AOSP 本身没有“移除某包”的产品变量。你在 LineageOS 的树里可能见过 PRODUCT_PACKAGES_REMOVE，但那是厂商扩展；build/make/core/product.mk 只声明了 PRODUCT_PACKAGES 及其 _DEBUG/_ENG/_TESTS 变体。在原版 AOSP 中，去掉一个默认应用有两条路：

  1. 不继承添加它的 makefile —— 多数默认应用是经 $(call inherit-product, ...) 链进入 PRODUCT_PACKAGES 的；换用更精简的父 makefile，它们就整个不进来。
  2. 用替代模块覆盖它 —— 在 Soong 中声明 overrides: ["Browser2"]（Make 中为 LOCAL_OVERRIDES_PACKAGES）的模块会把被指名的模块从 PRODUCT_PACKAGES 中移除；这发生在两个模块都会被安装的场合：
// In your replacement app's Android.bp
android_app {
    name: "BookBrowser",
    // Removes Browser2 from PRODUCT_PACKAGES when both would be installed
    overrides: ["Browser2"],
    // ...
}

用了 overrides 之后，被替换的应用仍会被构建（它可能是其他模块的依赖），但不会安装进镜像。

第一种做法 —— 不继承某些 makefile，从而排除整类 AOSP 应用 —— 形如这样。例如不想要电话类应用：

# Instead of inheriting full_base_telephony.mk, inherit full_base.mk
$(call inherit-product, $(SRC_TARGET_DIR)/product/full_base.mk)

65.5 修改框架行为

65.5.1 Runtime Resource Overlay（RRO）

Runtime Resource Overlay 是在不改框架源码的前提下裁剪框架行为的推荐方式。RRO 是一个只含资源的小 APK，用其中的取值覆盖目标包的默认值。

框架的可配置行为定义在：

frameworks/base/core/res/res/values/config.xml

这个文件包含数百个配置取值，RRO 可以覆盖其中任何一个。

RRO 的工作方式：

sequenceDiagram
    participant PMS as PackageManagerService
    participant OMS as OverlayManagerService
    participant RRO as RRO APK
    participant Target as 目标包（例如 framework-res）
    participant App as 应用

    participant AM as AssetManager（应用进程内）

    PMS->>OMS: 注册 overlay APK
    OMS->>RRO: 解析 AndroidManifest.xml
    OMS->>OMS: 把 targetPackage 匹配到已安装的包
    OMS->>OMS: 启用 overlay，生成 idmap
    OMS->>AM: 加载时挂入 overlay 的 ApkAssets + idmap

    App->>AM: getResources().getBoolean(R.bool.config_foo)
    AM->>RRO: 经 idmap 解析资源
    RRO-->>App: 返回覆盖后的取值

注意 OverlayManagerService 只在安装/启用阶段参与：它驱动 idmap 生成，并告知应用的 ResourcesManager 该加载哪些 overlay 的 ApkAssets。逐资源的查找完全发生在应用进程内的 AssetManager 里（frameworks/base/libs/androidfw/），资源读取路径上没有任何到 system_server 的 IPC。

package com.aospbook.service;

import android.content.Context;
import android.os.RemoteException;
import android.os.SystemProperties;
import android.util.Log;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/**
 * System service implementation for AospBook ROM.
 *
 * This service is registered with ServiceManager under the name
 * "aospbook" and can be accessed by apps via BookServiceManager.
 *
 * Registration happens in SystemServer.java during the
 * startOtherServices() phase.
 */
public class BookService extends IBookService.Stub {
    private static final String TAG = "BookService";
    private static final String SERVICE_NAME = "aospbook";

    private final Context mContext;
    private final Map<String, String> mPreferences;

    public BookService(Context context) {
        mContext = context;
        mPreferences = new HashMap<>();
        Log.i(TAG, "BookService initialized");
    }

    @Override
    public String getRomVersion() throws RemoteException {
        return SystemProperties.get("ro.aospbook.version", "unknown");
    }

    @Override
    public long getBuildTimestamp() throws RemoteException {
        String timestamp = SystemProperties.get("ro.build.date.utc", "0");
        try {
            return Long.parseLong(timestamp);
        } catch (NumberFormatException e) {
            return 0;
        }
    }

    @Override
    public void setPreference(String key, String value) throws RemoteException {
        // In a production implementation, this would persist to disk
        // and enforce permission checks.
        enforceCallerPermission();
        synchronized (mPreferences) {
            mPreferences.put(key, value);
        }
        Log.d(TAG, "Preference set: " + key + " = " + value);
    }

    @Override
    public String getPreference(String key) throws RemoteException {
        synchronized (mPreferences) {
            return mPreferences.get(key);
        }
    }

    @Override
    public List<String> getEnabledFeatures() throws RemoteException {
        List<String> features = new ArrayList<>();

        if (SystemProperties.getBoolean(
                "ro.aospbook.features.dark_mode_default", false)) {
            features.add("dark_mode_default");
        }
        if (SystemProperties.getBoolean(
                "ro.aospbook.features.custom_qs", false)) {
            features.add("custom_qs");
        }

        return features;
    }

    /**
     * Returns the service name for ServiceManager registration.
     */
    public static String getServiceName() {
        return SERVICE_NAME;
    }

    private void enforceCallerPermission() {
        // In production, check a custom permission here:
        // mContext.enforceCallingOrSelfPermission(
        //     "com.aospbook.permission.MANAGE_PREFERENCES",
        //     "BookService");
    }

import android.os.RemoteException;
import android.os.ServiceManager;
import android.util.Log;

import java.util.Collections;
import java.util.List;

/**
 * Client-side manager for the AospBook system service.
 *
 * Usage:
 *     BookServiceManager manager = BookServiceManager.getInstance();
 *     String version = manager.getRomVersion();
 */
public class BookServiceManager {
    private static final String TAG = "BookServiceManager";
    private static volatile BookServiceManager sInstance;

    private final IBookService mService;

    private BookServiceManager(IBookService service) {
        mService = service;
    }

    /**
     * Gets the singleton instance of BookServiceManager.
     * Returns null if the service is not available (e.g., on non-AospBook ROMs).
     */
    public static BookServiceManager getInstance() {
        if (sInstance == null) {
            synchronized (BookServiceManager.class) {
                if (sInstance == null) {
                    IBinder binder = ServiceManager.getService("aospbook");
                    if (binder != null) {
                        IBookService service =
                            IBookService.Stub.asInterface(binder);
                        sInstance = new BookServiceManager(service);
                    }
                }
            }
        }
        return sInstance;
    }

    public String getRomVersion() {
        try {
            return mService.getRomVersion();
        } catch (RemoteException e) {
            Log.e(TAG, "Failed to get ROM version", e);
            return "unknown";
        }
    }

    public long getBuildTimestamp() {
        try {
            return mService.getBuildTimestamp();
        } catch (RemoteException e) {
            Log.e(TAG, "Failed to get build timestamp", e);
            return 0;
        }
    }

    public void setPreference(String key, String value) {
        try {
            mService.setPreference(key, value);
        } catch (RemoteException e) {
            Log.e(TAG, "Failed to set preference", e);
        }
    }

    public String getPreference(String key) {
        try {
            return mService.getPreference(key);
        } catch (RemoteException e) {
            Log.e(TAG, "Failed to get preference", e);
            return null;
        }
    }

    public List<String> getEnabledFeatures() {
        try {
            return mService.getEnabledFeatures();
        } catch (RemoteException e) {
            Log.e(TAG, "Failed to get enabled features", e);
            return Collections.emptyList();
        }
    }
}

65.6.1 开机动画格式

开机动画是一个 ZIP 文件，放在下列位置之一（frameworks/base/cmds/bootanimation/BootAnimation.cpp 按顺序查找）：

  1. /apex/com.android.bootanimation/etc/bootanimation.zip
  2. /product/media/bootanimation.zip（文件名可通过 ro.product.bootanim.file 属性覆盖）
  3. /oem/media/bootanimation.zip
  4. /system/media/bootanimation.zip

格式在 frameworks/base/cmds/bootanimation/FORMAT.md 中有详细定义（注意该文档里只有两项的旧位置列表已过时，上面的查找顺序才是代码实现）。

ZIP 内包含：

bootanimation.zip (store compression, no deflate)
    desc.txt          # Animation descriptor
    part0/            # First animation part (frames)
        00000.png
        00001.png
        ...
    part1/            # Second animation part
        00000.png
        00001.png
        ...
    audio.wav         # Optional audio (per-part)

65.6.2 desc.txt 文件

第一行定义全局参数：

WIDTH HEIGHT FPS [PROGRESS]

后续行定义动画片段：

TYPE COUNT PAUSE PATH [FADE [#RGBHEX [CLOCK1 [CLOCK2]]]]

类型取值：

类型 行为
p 一直播放到开机完成，然后停止
c 无论开机状态如何都播放到结束
f 类似 p，但被打断时带淡出

desc.txt 示例：

1080 1920 30
c 1 0 part0
p 0 0 part1

含义是：

  • 分辨率为 1080x1920，30 FPS
  • part0：完整播放一次（c 1），无停顿
  • part1：无限循环（p 0）直到开机结束

    convert -size 1080x1920 xc:black \
        -fill white -gravity center \
        -pointsize 72 -annotate 0 "AospBook" \

# Part 1: Pulsing dots (looping animation, 60 frames = 2 seconds)

    phase=$(echo "scale=4; $i / 60 * 3.14159 * 2" | bc)

第 2 步：编写 desc.txt

# device/AospBook/bookphone/bootanimation/desc.txt
1080 1920 30
c 1 10 part0
p 0 0 part1

说明：

  • 1080 1920 30 —— 1080x1920，30 FPS
  • c 1 10 part0 —— part0 完整播放一次，停顿 10 帧（0.33 秒）
  • p 0 0 part1 —— part1 循环到开机结束，循环之间不停顿

第 3 步：打包动画

ZIP 必须使用 store 压缩（不做 deflate），因为 PNG 本身已经压缩过：

# Verify the contents
unzip -l bootanimation.zip

-0 参数至关重要：若使用默认压缩，开机动画播放器读帧效率低下，会造成卡顿甚至播放失败。

第 4 步：纳入构建

65.8.9 16 KB 页大小

一项影响 Android 17 ROM 里每个原生二进制的改动，是转向 16 KB 内存页大小。现代 arm64 SoC 可以让 MMU 以 16 KB 基础页（而非历史悠久的 4 KB）运行，从而减少 TLB 缺失、提升吞吐；但所有原生代码（.so 文件、可执行文件）的布局必须让可加载段按 16 KB 对齐。

构建系统在 64 位目标上已默认如此。build/make/core/config.mk 把 arm64 与 x86_64 支持的最大页大小设为 16384：

# build/make/core/config.mk (key excerpt)
else ifeq (,$(filter arm64 x86_64,$(TARGET_ARCH)))
  # > 4096 only supported on arm64 and x86_64
  TARGET_MAX_PAGE_SIZE_SUPPORTED := 4096
else
  # The default binary alignment for userspace is 16384.
  TARGET_MAX_PAGE_SIZE_SUPPORTED := 16384
endif

所以你经 Soong 从源码构建出来的二进制已经兼容 16 KB。可能出问题的是预置 APK 或厂商 blob 里的预编译 .so —— 它们由旧工具链按 4 KB 对齐链接，在 4 KB 内核上能正常加载，在 16 KB 内核上却映射失败。

开发与测试时有两个旋钮值得关注：

机制 位置 作用
TARGET_MAX_PAGE_SIZE_SUPPORTED build/make/core/config.mk（自动） 原生模块的段对齐，arm64/x86_64 上默认 16384
TARGET_BOOTS_16K BoardConfig.mk 标记该板级实际以 16 KB 内核启动（build/make/core/android_soong_config_vars.mk）
PRODUCT_16K_DEVELOPER_OPTION 产品 makefile 暴露运行时的“以 16KB 页大小启动”开发者开关；设置 ro.product.build.16k_page.enabled（build/make/core/sysprop_config.mk）

模拟器自带专门的 16 KB 产品，不必真实硬件即可验证对齐。device/generic/goldfish/64bitonly/product/sdk_phone16k_x86_64.mk（及其 arm64 兄弟）继承 16 KB 板级细节（device/generic/goldfish/board/emu64x16k/details.mk）与 16 KB 命令行内核（device/generic/goldfish/board/kernel/x86_64_16k.mk）。构建并启动其中一个目标，即可确认你的预置库能否干净映射：

lunch sdk_phone16k_x86_64-trunk_staging-userdebug
m
emulator
# On the device, confirm the live page size:
adb shell getconf PAGE_SIZE        # prints 16384 on a 16 KB build

这项检查只以 getconf PAGE_SIZE 为准。相关的属性 ro.product.build.16k_page.enabled 只反映产品是否设置了 PRODUCT_16K_DEVELOPER_OPTION（那个双启动开发者开关），并不能说明镜像是否按 16 KB 对齐。在 sdk_phone16k_x86_64 上因为没有设置该选项，它读出来是 false，尽管构建确实是 16 KB 的。

若某个预置库在 16 KB 目标上加载失败，就从源码重编 —— 它会自动带上 16 KB 对齐；或者用 16 KB 的 max-page-size 重新链接。把 ROM 推进到 Android 17 时，审计预置库的 16 KB 就绪度已是标准步骤。

65.10 分发

65.10.1 签名总览

Android 用代码签名保证每个 APK 与系统镜像的完整性和真实性。AOSP 中使用的密钥有四种：

密钥 文件对 用途
testkey testkey.pk8 / testkey.x509.pem 默认开发签名
platform platform.pk8 / platform.x509.pem 具有 android.uid.system 的系统应用
shared shared.pk8 / shared.x509.pem 共享数据的应用（Contacts、Phone）
media media.pk8 / media.x509.pem 媒体/下载类应用

这些默认密钥位于：

build/make/target/product/security/

关键警告：该目录里的密钥是公开已知的测试密钥。任何用这些密钥发布的 ROM 都形同虚设 —— 谁都可以用同一把密钥签名恶意 APK，而系统会把它当作合法系统更新接收。

build/make/target/product/security/README 中明确警告：

“本目录中的测试密钥仅用于开发，绝不可用于为公开发布的镜像中的包签名。”

65.10.2 生成发布密钥

生成你自己独有的密钥：

# Create a directory for your keys
mkdir -p device/AospBook/bookphone/keys
cd device/AospBook/bookphone/keys

# The make_key tool is provided by AOSP:
SUBJECT='/C=US/ST=California/L=Mountain View/O=AospBook/OU=ROM/CN=AospBook/emailAddress=rom@aospbook.example.com'

# Generate each key pair
# This will prompt for a password -- use a strong one for release keys
# For development, you can press Enter for no password
../../../../../../development/tools/make_key releasekey "$SUBJECT"
../../../../../../development/tools/make_key platform "$SUBJECT"
../../../../../../development/tools/make_key shared "$SUBJECT"
../../../../../../development/tools/make_key media "$SUBJECT"

# Verify the generated files
ls -la
# Expected:
#   releasekey.pk8
#   releasekey.x509.pem
#   platform.pk8
#   platform.x509.pem
#   shared.pk8
#   shared.x509.pem
#   media.pk8
#   media.x509.pem

每次调用 make_key 都会生成两个文件：

  • *.pk8 —— PKCS#8 DER 格式的私钥
  • *.x509.pem —— X.509 PEM 格式的公钥证书

development/tools/make_key 接受可选的第三个参数选择密钥类型：rsa（默认）或 ec。APK Signature Scheme v3/v4 与现代 AVB 都接受 EC 密钥，所以若你偏好椭圆曲线密钥，make_key platform "$SUBJECT" ec 是合法选择。无论选哪种，下面的签名工具都以同样的方式消费这对 .pk8 / .x509.pem。

65.10.3 配置构建使用发布密钥

告诉构建系统用你的密钥替代测试密钥：

# In device/AospBook/bookphone/bookphone.mk (or device.mk)

# Use our custom signing keys
PRODUCT_DEFAULT_DEV_CERTIFICATE := device/AospBook/bookphone/keys/releasekey

# Map APK signing to our keys
PRODUCT_CERTIFICATE_OVERRIDES := \
    testkey:device/AospBook/bookphone/keys/releasekey \
    platform:device/AospBook/bookphone/keys/platform \
    shared:device/AospBook/bookphone/keys/shared \
    media:device/AospBook/bookphone/keys/media

65.10.4 为构建签名

签名有两种做法：

做法一：构建过程中签名（开发用）

设置 PRODUCT_DEFAULT_DEV_CERTIFICATE 后，所有 APK 在构建时自动签名。这是最省事的做法。

做法二：构建之后再签名（发布用）

生产发布时，先构建，再单独签名：

# Step 1: Build target-files package
m dist

# The target-files ZIP is at:
# out/dist/bookphone-target_files-<build_id>.zip

# Step 2: Sign all APKs in the target-files.
#   -d <dir> is the short form of --default_key_mappings: every APK that the
#            stock build signed with testkey/platform/shared/media is re-signed
#            with the matching key name found in <dir>.
#   -o       also re-signs (replaces) the OTA verification keys with the
#            release key in that directory.
python3 build/make/tools/releasetools/sign_target_files_apks.py \
    -o \
    -d device/AospBook/bookphone/keys \
    out/dist/bookphone-target_files-*.zip \
    out/dist/bookphone-target_files-signed.zip

# Step 3: Generate signed images from the signed target-files
python3 build/make/tools/releasetools/img_from_target_files.py \
    out/dist/bookphone-target_files-signed.zip \
    out/dist/bookphone-img-signed.zip

65.10.5 生成 OTA 包

OTA（Over The Air，空中升级）包用于向既有用户分发更新。

完整 OTA 包（含完整镜像）：

# Generate from target-files
python3 build/make/tools/releasetools/ota_from_target_files.py \
    --package_key device/AospBook/bookphone/keys/releasekey \
    out/dist/bookphone-target_files-signed.zip \
    out/dist/bookphone-ota-full.zip

增量 OTA 包（只含相对上一构建的差异）：

# Generate incremental OTA (from v1 to v2)
python3 build/make/tools/releasetools/ota_from_target_files.py \
    --package_key device/AospBook/bookphone/keys/releasekey \
    -i out/dist/bookphone-v1-target_files-signed.zip \
    out/dist/bookphone-v2-target_files-signed.zip \
    out/dist/bookphone-ota-v1-to-v2.zip

build/make/tools/releasetools/ 里还提供了一些更窄的 OTA 辅助脚本，在 ROM 导入阶段很好用：

  • ota_from_raw_img.py 直接从一组 .img 文件构建 A/B payload，而不需要完整 target-files 包 —— 当你只想发布一两个重新分区的镜像时很方便。
  • create_brick_ota.py 生成一个 recovery 包，清掉 AVB/vbmeta 分区，从而“故意变砖”设备（用于 RMA/安全擦除流程）。它提醒我们：OTA payload 不过是一组针对各分区的、已签名的指令集。

这些脚本是对本节其余部分所用的 ota_from_target_files.py 路径的补充，而非替代。

// device/AospBook/bookphone/hal/booklight/default/BookLight.h
#pragma once

#include <aidl/com/aospbook/hardware/light/BnBookLight.h>
#include <aidl/com/aospbook/hardware/light/BookLightState.h>

namespace aidl::com::aospbook::hardware::light {

/**
 * Default implementation of the BookLight HAL.
 *
 * For the emulator, this is a software-only implementation that
 * stores state in memory. On a real device, this would interface
 * with kernel drivers via sysfs or ioctl.
 */
class BookLight : public BnBookLight {
public:
    BookLight();

    ndk::ScopedAStatus getState(BookLightState* _aidl_return) override;
    ndk::ScopedAStatus setBrightness(int32_t brightness) override;
    ndk::ScopedAStatus setColorTemperature(int32_t kelvin) override;
    ndk::ScopedAStatus setEnabled(bool enabled) override;
    ndk::ScopedAStatus getSupportedTemperatureRange(
        std::vector<int32_t>* _aidl_return) override;

private:
    std::mutex mLock;
    BookLightState mState;

    static constexpr int32_t kMinTemperature = 2700;
    static constexpr int32_t kMaxTemperature = 6500;
    static constexpr int32_t kDefaultTemperature = 4000;
    static constexpr int32_t kMaxBrightness = 255;
};

}  // namespace aidl::com::aospbook::hardware::light

BookLight.cpp：

// device/AospBook/bookphone/hal/booklight/default/BookLight.cpp
#include "BookLight.h"

#include <android-base/logging.h>

namespace aidl::com::aospbook::hardware::light {

BookLight::BookLight() {
    mState.enabled = false;
    mState.brightness = 0;
    mState.colorTemperature = kDefaultTemperature;
    LOG(INFO) << "BookLight HAL initialized";
}

ndk::ScopedAStatus BookLight::getState(BookLightState* _aidl_return) {
    std::lock_guard<std::mutex> lock(mLock);
    *_aidl_return = mState;
    return ndk::ScopedAStatus::ok();
}

ndk::ScopedAStatus BookLight::setBrightness(int32_t brightness) {
    if (brightness < 0 || brightness > kMaxBrightness) {
        return ndk::ScopedAStatus::fromExceptionCode(
            EX_ILLEGAL_ARGUMENT);
    }

    std::lock_guard<std::mutex> lock(mLock);
    mState.brightness = brightness;
    LOG(DEBUG) << "BookLight brightness set to " << brightness;

    // On a real device, write to hardware:
    // write_to_sysfs("/sys/class/leds/booklight/brightness", brightness);

    return ndk::ScopedAStatus::ok();
}

ndk::ScopedAStatus BookLight::setColorTemperature(int32_t kelvin) {
    if (kelvin < kMinTemperature || kelvin > kMaxTemperature) {
        return ndk::ScopedAStatus::fromExceptionCode(
            EX_ILLEGAL_ARGUMENT);
    }

    std::lock_guard<std::mutex> lock(mLock);
    mState.colorTemperature = kelvin;
    LOG(DEBUG) << "BookLight color temperature set to " << kelvin << "K";

    // On a real device, write to hardware:
    // write_to_sysfs("/sys/class/leds/booklight/color_temp", kelvin);

    return ndk::ScopedAStatus::ok();
}

ndk::ScopedAStatus BookLight::setEnabled(bool enabled) {
    std::lock_guard<std::mutex> lock(mLock);
    mState.enabled = enabled;
    LOG(DEBUG) << "BookLight " << (enabled ? "enabled" : "disabled");

    // On a real device:
    // write_to_sysfs("/sys/class/leds/booklight/enable", enabled ? 1 : 0);

    return ndk::ScopedAStatus::ok();
}

ndk::ScopedAStatus BookLight::getSupportedTemperatureRange(
        std::vector<int32_t>* _aidl_return) {
    _aidl_return->clear();
    _aidl_return->push_back(kMinTemperature);
    _aidl_return->push_back(kMaxTemperature);
    return ndk::ScopedAStatus::ok();
}

}  // namespace aidl::com::aospbook::hardware::light

// device/AospBook/bookphone/hal/booklight/default/service.cpp
#include "BookLight.h"

#include <android-base/logging.h>
#include <android/binder_manager.h>
#include <android/binder_process.h>

using aidl::com::aospbook::hardware::light::BookLight;

int main() {
    // Configure logging
    android::base::SetDefaultTag("booklight-hal");
    android::base::SetMinimumLogSeverity(android::base::DEBUG);

    LOG(INFO) << "BookLight HAL service starting";

    // Start the binder thread pool
    ABinderProcess_setThreadPoolMaxThreadCount(0);

    // Create the HAL instance
    std::shared_ptr<BookLight> bookLight =
        ndk::SharedRefBase::make<BookLight>();

    // Register with the service manager
    const std::string instance =
        std::string() + BookLight::descriptor + "/default";
    binder_status_t status = AServiceManager_addService(
        bookLight->asBinder().get(), instance.c_str());

    CHECK_EQ(status, STATUS_OK)
        << "Failed to register BookLight HAL service";

    LOG(INFO) << "BookLight HAL service registered: " << instance;

    // Join the binder thread pool (blocks forever)
    ABinderProcess_joinThreadPool();

    // Should never reach here
    LOG(FATAL) << "BookLight HAL service died unexpectedly";
    return EXIT_FAILURE;
}

65.14 案例研究：MaruOS 作为融合型自定义 ROM

上面十三节搭出了一个通用的“自定义 ROM”：AOSP 的一个分支，加上定制应用、框架调整、品牌化的 SystemUI、自定义内核，以及一套发布/分发流程。要看看这个模板在实践中能延伸到多远，可以看 MaruOS（https://github.com/maruos）—— 一个开源自定义 ROM，其明确目标是“手机即电脑”。项目对该目标的表述是：“在路上时，Maru 是你的手机；在桌前时，Maru 是你的桌面。”

受支持的 Pixel 或 HTC 10 可以通过 USB-C/HDMI 接到显示器上，外接屏幕上会起一个完整的 Debian GNU/Linux 桌面会话；与此同时，手机屏幕仍在跑原生 Android。同一个内核，同一台设备，两套同时面向用户的操作系统。

MaruOS 不是典型的自定义 ROM。它之所以有意思，恰恰是因为它偏离了本章其余部分所铺陈的模板。它是个很有用的收尾展品：一个不同寻常但已真正投入生产的范例，说明 AOSP 的 overlay 模型究竟给 ROM 作者留下多大余地。

65.14.1 MaruOS 为何是个不寻常的自定义 ROM

经典的自定义 ROM（LineageOS、GrapheneOS、/e/OS、ParanoidAndroid）保持 AOSP 的形态不变，只变化内容 —— 差异在 APK、框架默认值、SystemUI、安全策略与内核 加固 —— 用户感受到的运行时模型依然是 zygote → activity → SystemUI → 桌面启动器。

MaruOS 对手机这一面保持该模型不变，同时在上面叠加第二套运行时模型：一个跑在 LXC 容器里的 Debian 系统。Android 侧按需启动该容器；容器有自己的 X11 桌面环境、自己的包管理器、自己的启动与登录流程。README 中明确写道：

“它使用轻量级操作系统虚拟化（容器）按需拉起虚拟系统” —— maruos/maruos README。

所以除了普通 ROM 都会带的东西（device 仓库、厂商 blob、品牌化应用），MaruOS 还带：

  • 一个 LXC 容器管理守护进程及配套的 Android 侧服务。
  • 一个“Perspective”层，把 Android 的显示、输入与音频管线接到容器上，使容器能在外接屏上呈现一个连贯的桌面。
  • 一套独立于 AOSP 构建的 Debian 容器镜像构建流水线。
  • 一个设备接入钩子，决定何时启动容器、把桌面放到哪块屏幕上。
  • 新的 SELinux 策略，防止容器内的 Linux 进程冲撞 Android 的域模型。

设备列表刻意做得很窄：较新的分支只跟几代 Pixel 与 HTC 10。设备仓库是从 LineageOS 分出来的，所以 Maru 借用硬件使能层而不从零维护 —— 当前集合见 maruos/manifest 中的清单，受支持设备在各 maru-0.x 发布间有变化。

整个组织采用 Apache-2.0 许可，与 AOSP 本身一致。

有三处架构要点值得单独挑出：

  1. 一个内核。 Android 与 Debian 共享 /proc/version。容器通过命名空间隔离 PID、挂载、网络、IPC 与用户 ID 来运行，并不引导自己的内核镜像。这就是 LXC 的交易：开销远低于虚拟机，但对跨越容器边界的内核漏洞毫无防御。
  2. Maru 桥接守护进程常驻 Android。 它作为普通 Android 进程（原生 C/C++ 之上的 Java/JNI）跑在 AOSP 用户空间里，监听显示接入事件，并用普通 Linux API 启动 LXC 容器。它不是容器内的代码 —— 容器只知道自己被启动了。
  3. 两块屏，两个归属方。 手机屏继续在内屏上渲染 Android 的 SystemUI；外接屏不是在跑另一个 Android UI，而是一块呈现面，由 SurfaceFlinger 经 mflinger 交给 Linux 侧（65.14.8）。X.org 与容器的桌面环境（Xfce 或该 Debian 镜像配置的任意环境）渲染用户在显示器上看到的一切。桌面起来的过程中，用户的手机始终在跑原生 Android。

这与原版 Android 内置的“桌面模式”功能（Samsung DeX、Android 12+ 的外接屏窗口化）有本质区别：那些仍只有一个 Android 运行时，而 MaruOS 在同一内核上跑两套操作系统。

65.14.3 为 LXC 定制内核配置

LXC 正是让 MaruOS 能在没有第二个内核的前提下，与 Android 并行运行 Debian rootfs 的机制。但它依赖一些原版 Android 内核通常会关掉的 Linux 内核特性。基于 LXC 的自定义 ROM，必须先确认它发布的镜像里具备这些特性。

Maru 所运行的那种非特权 LXC 容器所需的内核特性：

特性 内核配置 MaruOS 为何需要
用户命名空间 CONFIG_USER_NS=y 把容器内的“root” UID 映射到宿主上一个高位非特权 UID；非特权 LXC 的基础
PID 命名空间 CONFIG_PID_NS=y 让容器的 init 在内部看到 PID 1，而不是宿主机的 init
挂载命名空间 CONFIG_NAMESPACES=y（隐含 mount NS） 每个容器独立的 /proc、/sys 与根文件系统视图
网络命名空间 CONFIG_NET_NS=y 每个容器独立的网络栈
UTS 命名空间 CONFIG_UTS_NS=y 每个容器独立的主机名
IPC 命名空间 CONFIG_IPC_NS=y 每个容器独立的 System V IPC 与 POSIX 消息队列
Cgroups CONFIG_CGROUPS=y 及 memory、cpu、devices、freezer 子系统 容器内的资源统计与限额
Seccomp CONFIG_SECCOMP_FILTER=y 让 LXC 限制容器可发起的系统调用
uinput（可选） CONFIG_INPUT_UINPUT=y 输入桥在某事件需跨屏缩放时使用的合成注入路径（65.14.9）；在“每个设备直连一侧”的常见情形下不需要
可选 overlay FS CONFIG_OVERLAY_FS=y 分层容器 rootfs，免于整盘复制

麻烦在于 CONFIG_USER_NS。Android 的内核团队历来在生产内核上关闭该选项，因为用户命名空间在各 Linux 版本中反复成为 CVE 的来源 —— 用户命名空间内的特权边界比标准的 root/非 root 划分更难收窄。Android 的安全原则是去掉平台本身不需要的攻击面，LineageOS 的设备内核通常沿用这个默认。要跑 LXC，MaruOS 必须在它的内核构建里把 CONFIG_USER_NS 改回 y，并明知如此地接受额外攻击面。

表里其他特性在 Android 内核里通常已打开：ActivityManager 使用 cgroups（memory、freezer），低内存杀手使用 cgroup v2 的内存控制器；Android 沙箱需要 seccomp 过滤器；命名空间属于每个现代 Linux 内核的默认配置。所以 Maru 需要的内核改动比乍看要窄：打开 CONFIG_USER_NS，确认其余命名空间与 cgroup 控制器已启用，然后重编。若想用 65.14.9 的合成注入输入路径，还可打开 CONFIG_INPUT_UINPUT。

这就是为什么 Maru 的设备构建从自己的 device_* 仓库拉一份 Maru 修改过的内核，而不是原样复用 LineageOS 的内核。65.11 节介绍的通用的内核定制流程正是 MaruOS 所走的：把所需选项写成 defconfig 片段叠在设备基础 defconfig 之上，然后重编 boot 镜像，与 system 镜像一并刷入。

这一取舍非常直接：打开 CONFIG_USER_NS 会暴露一个原版 AOSP 刻意关闭的攻击面。对 Maru 而言这是融合模型的已知代价。任何考虑基于 LXC 或命名空间扩展的自定义 ROM，都应刻意做出这一选择，并把威胁模型写下来 —— 没有该开关就得不到非特权 LXC，而打开该开关就必然扩大内核攻击面。

perspective/ 是概念中心。这个名字体现了抽象：设备有多个“视角”（手机屏、桌面屏，也许还有仅耳机），Maru 的职责就是在它们之间切换。该目录里的 C++ 与 Java 混合体就是监听显示事件、判定用户“桌面视角”何时激活并编排下游一切的守护进程。

container/ 承载 LXC 集成：围绕 lxc-start 的生命周期封装、rootfs 挂载逻辑、cgroup 设置、把宿主资源暴露给容器的 bind mount，以及拆除路径。这是直接与 LXC 对话的一层。

overlay/ 使用 AOSP 标准 overlay 机制（见 65.5 节）替换框架或应用中的特定资源，典型目标包括设备的 config.xml 设置、语言区域默认值、品牌字符串以及预装应用的启动默认值。

overrides/ 与 overlay/ 并列，处理 overlay 系统无法表达的文件级覆盖：overlay 只改 APK 内的资源取值，而 overrides/ 替换整个文件或脚本。

sepolicy/ 是 SELinux 策略增量，让容器守护进程能对话 LXC、挂载 rootfs、操作 cgroups、转发输入并抓取帧缓冲。原版 AOSP 策略一条都不允许，因为没有原版 AOSP 组件做这些事。

prebuilts/ 存放 AOSP 构建本身不会产出的预编译产物，通常是 LXC 工具链二进制、不按设备构建的辅助 shell 脚本，以及各类第三方 Debian 支撑件。

mlogwrapper/ 是个小工具，把 Maru 守护进程的日志重定向进 Android 的日志基础设施（logd/logcat），这样调试 Maru 的开发者可以用与任何 Android 服务相同的工具。

scripts/ 包含仓库级 setup 辅助脚本，在常规 m/make 流程之外调用。例如某个辅助脚本从 blueprints 的构建输出取回 Debian rootfs，并在系统镜像打包之前把它放进按产品划分的路径。

65.14.6 blueprints 容器构建器

容器运行的 Debian rootfs 不是由 Soong 构建的，而是由独立仓库 maruos/blueprints 构建。该仓库是一套自洽的 shell 流水线：

  • build.sh —— 主构建入口：读取 blueprint、调用其按 blueprint 划分的钩子、产出输出 tarball。
  • build-with-docker.sh —— 在 Docker 镜像里运行 build.sh 的包装器，适用于构建主机没有 debootstrap 或其他 Debian 工具的场合。
  • plugin.sh —— 任何 blueprint 都要 source 的样板文件，它强制每个 blueprint 提供两个 shell 函数：blueprint_build 与 blueprint_cleanup。
  • blueprint/debian/ —— 规范 blueprint。README 确认：“镜像构建逻辑被分离成独立的插件，称为 blueprint。规范实现是 blueprint/debian。”

这种拆分是刻意的。AOSP 构建系统擅长产出 Android 系统镜像与已签名的 boot 镜像，但它对 Debian rootfs 一无所知。与其教 Soong 懂 debootstrap，Maru 干脆跑两套构建：Android 侧用 Soong/Make，Debian 侧用 Shell/debootstrap，最后由一个装配步骤把 rootfs 输出折进相应的产品目录。

这里有一课给 ROM 作者：如果你的定制引入了一个完全异质的运行环境（容器、虚拟机、不同的 libc），正确答案往往是一个平级的构建系统 —— 它导出一个 tarball，而不是一个试图建模那个异世界的 Soong 模块。

65.14.7 “Perspective”桥接层

perspective/ 与 include/perspective/ 目录承载了设计中最难归类的一部分：驱动整个融合流程的、常驻 Android 的守护进程。我们从它的结构位置（Android 用户空间、C++/Java 混合、与源码并列的 include/）以及整棵树对它的角色预期，推断出它的职责。它至少负责：

  1. 显示接入检测。 监听 DisplayManager 的 onDisplayAdded 回调（或更底层的等价物），判断接入的显示器是否“桌面级”—— 足够大且足够外接 —— 从而值得启动桌面视角。
  2. 容器生命周期。 在首次桌面接入时调用 container/ 启动 LXC 容器，在最后一次桌面断开时停止它；若 Maru 策略要求，还会在息屏时让容器静默。
  3. 输入路由。 把 Android 输入系统的键盘、鼠标乃至触摸事件转发进容器，让使用外接键盘的用户看到按键落在 Debian 里。
  4. 音频路由。 在手机扬声器与桌面显示器经 HDMI 提供的音频设备之间协商音频输出。
  5. 权限与认证。 提供某种方式让用户确认“这块外接屏被允许承载桌面会话”—— Maru 不会对任何插上接口的人都暴露一个 Debian 会话。

仓库的组织方式表明：perspective 层是“导演”，container/ 是“舞台工作人员”。一个决定该发生什么，另一个实际搬运 LXC 机器。这个拆分对任何编写长驻 Android 服务、驱动非 Android 用户空间资源的 ROM 作者都是有用的模式。

65.14.8 mflinger 与 mclient：图形桥

当 Debian 容器内的 X11 服务器绘制到它的帧缓冲时，那些像素位于容器的地址空间里 —— 容器有独立的挂载命名空间、独立的 /dev，以及对 GPU 内存的独立视图。而拥有外接屏呈现权的 Android SurfaceFlinger 对那块缓冲一无所知。必须有软件在两者之间架桥。Maru 的设计异常优雅：它让 LXC 命名空间边界对 GPU 实际上不可见。

mflinger 在其独立仓库 https://github.com/maruos/mflinger 中，与 vendor_maruos 分开。README 只有一句：“Maru OS 的图形缓冲桥。” 代码以 C 为主（约 64% C、21% C++），目录为 src/、include/、lib/、tests/、scripts/ —— 一个小型 Linux 系统服务的典型布局。

名字体现了类比：Android 的 SurfaceFlinger 是消费者，它按标准 ANativeWindow/BufferQueue 生产者协议，接收来自应用、相机 HAL、视频解码器等的逐生产者图形缓冲，再把它们合成为显示内容。mflinger 为容器的帧扮演生产者角色：向 SurfaceFlinger 申请一个基于 ANativeWindow 的 Surface，把底层缓冲交给 Linux 侧直接渲染，然后在缓冲可呈现时通知 SurfaceFlinger。

mflinger 架构分成两半：

  • mflinger（守护进程，Android 侧）作为 init.maru.rc 启动的 Android 用户空间服务运行。它创建挂到外接屏的 Android Surface，用标准 ANativeWindow C API 取出 GraphicBuffer 槽位；每个缓冲由一次 gralloc 分配支撑 —— 在现代 AOSP 设备上通常是 dma-buf。mflinger 可以把这次分配的文件描述符交给另一个命名空间中的进程。
  • mclient（容器侧客户端）随 Debian rootfs 发布。它经 Unix 域套接字从 mflinger 接收 dma-buf 文件描述符，传输使用 SCM_RIGHTS 辅助数据 —— 在进程间传递内核管理 fd 的标准 Linux 机制。这能跨越 LXC 命名空间边界，因为内核按底层对象而非路径做引用计数。随后 mclient 对 dma-buf mmap（或经 DRI3 作为 pixmap 导入），并把所得内存区域作为根窗口的后备存储暴露给 X.org。

关键事实：X.org 直接渲染进 SurfaceFlinger 将要呈现的同一块物理 GPU 内存。 当 X 服务器提交一帧，mclient 通知 mflinger 缓冲就绪，mflinger 在 ANativeWindow 上调用 queueBuffer；SurfaceFlinger 取走该缓冲并在外接屏的下一次合成中包含它，用户于是看到桌面。跨界复制不存在中间的“容器帧缓冲” —— fd 就是边界，GPU 内存是共享的。

这正是 Android 内部为每个相机、编解码器与 OpenGL 表面所用的同一套生产者/消费者模式 —— mflinger 把它泛化，把生产者端交给位于另一个挂载命名空间的进程。

这个设计有两点后果值得挑出：

  • 跨 LXC 边界零拷贝。 从没有像素在 Android 与容器的地址空间之间被搬运，跨桥传递的只有文件描述符与少量协议消息。端到端成本由 GPU 渲染决定，而不受内存带宽或跨命名空间开销限制。
  • 每帧只合成一次。 因为 X.org 直接绘制进 SurfaceFlinger 将要呈现的那块缓冲，所以不存在额外的“容器帧缓冲 → 宿主帧缓冲”合成步骤 —— 合成次数与任何普通 Android 表面相同。这正是该设计能扩展到 1920×1080 外接显示器、且在中低端硬件上不会成为瓶颈的原因。

vendor_maruos/sepolicy/ 中的 Android 侧 SELinux 策略（65.14.11）允许 mflinger 获取 ANativeWindow 表面并经 binder 与 SurfaceFlinger 通信，也允许它通过自己的 UDS 传出文件描述符。没有这些规则，守护进程在启动时就会被拒。vendor_maruos/container/ 里的容器模块（65.14.5）在 LXC 启动时建立 bind mount，把 mclient↔mflinger 的套接字跨容器边界暴露出来。

65.14.9 Linux 与 Android 之间的输入映射

图形桥的对应物是输入桥，但它比图形桥小得多 —— 原因相同：Android 与 LXC 容器共享同一个内核。

键盘、鼠标与触摸硬件位于内核的 input 子系统，经 /dev/input/event* 节点暴露。因为只有一个内核，也就只有一套这样的节点 —— 不存在每件硬件一对“Linux 输入设备”与“Android 输入设备”。Android 的 InputReader（在 system_server 内，见第 22 章）经 Android 的 /dev/input/ 打开它们。

容器通过它自己的 /dev/input/ 命名空间看到同样的节点 —— Maru 在 LXC 启动时从宿主 bind mount 过去。容器内的 X.org 经 evdev 输入驱动读取它们，与在原生 Debian 桌面上用的是同一条 evdev 路径。没有像素拷贝，因为 GPU 内存是共享的；也没有事件拷贝，因为内核设备节点是共享的。

那么这座桥实际做的是路由 —— 决定每台设备“归”哪一侧。所用机制全是标准 Linux 手段：

  1. 设备枚举。 USB 或蓝牙键盘、鼠标、触摸屏接入时，内核创建 /dev/input/eventN；udev 式的热插拔事件同时传播到 Android 输入层与（经 bind mount）容器。

  2. 按设备归属。 Maru 的 perspective 守护进程（65.14.7）依据当前“视角”决定每台设备归谁：

    • 手机内屏触摸面板永远归 Android —— 那些触摸要驱动内屏上的 SystemUI 与应用，绝不能给桌面。
    • 硬件按键（电源、音量）永远归 Android。
    • 外接 USB/蓝牙键鼠在桌面起来时通常归桌面，否则归 Android。
    • 外接触摸显示器的输入设备在桌面起来期间归桌面。

  3. 经 EVIOCGRAB 实现独占。 当归属方需要成为设备的唯一读取者时，相关进程在事件节点上发起 ioctl(fd, EVIOCGRAB, 1)。否则 evdev 的读取路径是多播的：同一个 /dev/input/eventN 上每个打开的 fd 都会收到每个事件，Android 与 X.org 会各自派发同一次按键。用了 EVIOCGRAB，内核在抓取释放前只把事件投给抓取者。

  4. 跨屏触摸的坐标换算。 触摸事件使用按源面板分辨率缩放的绝对坐标 —— Android 内屏 1080×1920 上的一次触摸，对绘制在 1920×1080 外接屏上的 X 服务器毫无意义。

    常见情形不会碰到这点，因为 Android 拥有内屏、桌面拥有外接触摸显示器。少见情形是“把手机屏当桌面的触摸板”：此时 perspective 守护进程读取内屏事件，把坐标重缩放到桌面空间，再在虚拟设备上合成新事件。CONFIG_INPUT_UINPUT（65.14.3）正是启用这条合成注入路径的开关，常见路径并不需要它。

整条管线对两端都是不可见的：Android 的 InputReader 枚举它拥有的设备并正常派发，容器的 X 服务器对它拥有的设备同样如此，只有中间的 perspective 守护进程知道当前谁拥有什么。

与图形桥的对比就是这里的架构课：当两个用户空间栈共享内核时，内核已经抽象掉的东西（输入事件、网络套接字、fd、字符设备）可以用“路由”而非“转发”来共享；而内核没有抽象的东西（支撑 Surface 的 GPU 内存）就必须像 65.14.8 那样用显式 fd 传递来架桥。Maru 的输入桥小，是因为内核替它干活；图形桥小，是因为它搭了内核既有 dma-buf fd 传递的便车，而不是自己发明像素传输通道。

65.14.10 Init 与启动集成

init.maru.rc 是声明启动集成的地方。Android 的 init 在启动时处理 /system/etc/init/ 与 /vendor/etc/init/ 里的 *.rc 文件，定义服务与触发器。对 MaruOS，该文件概念上包含：

  • perspective 守护进程的 service 条目，带正确的 user、group 与 seclabel —— 让 SELinux 把它放进 Maru 域，并让 init 监督其重启。
  • 一个或多个 on 触发器 —— on boot、on property:sys.boot_completed=1，也许还有 on property:maru.container.requested=1 —— 决定守护进程何时启动、先跑哪些辅助设置。
  • 为 perspective 守护进程可能从自身进程外调用的任何辅助命令声明 socket 或 oneshot。

65.14.11 SELinux 方面的影响

原版 AOSP 的 SELinux 策略假定没有任何 Android 进程需要启动 LXC 容器或挂载 rootfs，也假定没有任何进程需要操作 Android 的 lmkd/freezer 所辖之外的 cgroups。Maru 的 sepolicy/ 目录承载这份增量：

  • 新域 —— 姑且称为 maru_perspective 与 maru_container —— 给守护进程与任何辅助进程用。
  • 允许该域 execute LXC 工具链、把容器 rootfs mount 到 Maru 专属路径、写入容器所用 cgroups 的规则。
  • 允许守护进程绑定外接屏上的帧缓冲（或 surfaceflinger 等价物）的规则 —— 容器内的 X11 得有个可见的地方绘制。
  • 允许输入管道从 Android 的 input 域跨进 perspective 域的规则，使输入转发生效。

有志于做 ROM 的作者应从中得到这样一条：任何引入带更高能力的新系统服务的自定义 ROM，都必须编写新的 SELinux 策略，没有例外。代价不在写 *.te 文件本身（Maru 的 sepolicy/ 很小），而在开发期间逐条二分定位拒绝：每条新拒绝只在首次命中时记录一次，之后就静默了。这就是为什么在不同设备上首次安装 Maru 构建时常常需要跑一遍审计。

65.14.12 Maru 系统应用的特权权限

privapp-permissions-maru.xml 位于厂商 overlay 作用域，由 Android 的特权权限白名单机制处理（参见 65.4 节关于添加自定义应用的内容）。Maru 需要这个文件，是因为其 perspective 守护进程的配套 APK 位于 /system/priv-app/，并声明了必须由白名单显式授予的权限。该 APK 是面向用户的 UI：确认桌面访问、管理容器设置、显示“桌面已激活”通知。

形态对 ROM 作者来说很熟悉：

65.14.13 构建流程

把各部分拼起来，为受支持设备从源码构建 MaruOS 大致如下：

# 1. Set up the AOSP-style tree using Maru's manifest
mkdir maru && cd maru
repo init -u https://github.com/maruos/manifest.git -b maru-0.7
repo sync -j$(nproc)

# 2. Build the Debian rootfs separately (sibling build system)
cd vendor/maruos/blueprints   # (path depends on manifest layout)
./build.sh blueprint/debian
# Produces a rootfs tarball — Maru's scripts move it into the right
# product directory so it gets packaged into the system image.

# 3. Standard AOSP build flow for the chosen device
cd $TOP
source build/envsetup.sh
lunch maru_<device>-userdebug
m

与 65.8 节构建流程相比，有三点突出：

  • 两套构建系统。 Soong/Make 流水线不运行 blueprints 流水线；ROM 作者手工或用包装脚本编排二者。
  • 容器镜像是构建产物，不是源码。 Debian rootfs 每个发布构建产出一次、签名，并随 Maru 系统镜像一起发布 —— 设备在安装时不会跑 debootstrap。
  • lunch 组合内含 Maru。 maru_<device> 组合意味着该产品 makefile 继承了 device-maru.mk（并经由它继承 maru_build.mk），后者引入 vendor_maruos 并打开 Maru 专属构建标志。标准 lineage_<device> lunch 会构建同一设备但不带 Maru 层。

65.14.14 MaruOS 给 ROM 作者的启示

把 MaruOS 当作范本而非孤例来读，有三条教训可超出这个具体项目：

  1. overlay 模型的弹性很大。 65.3–65.5 节把 overlay 讲成改资源取值、塞几个 APK 的手段，而 MaruOS 展示了它的上限：你可以通过厂商 overlay + sepolicy + init.rc + 一套平级构建系统，加进整套第二操作系统，而完全不必 fork AOSP 源码树。你的定制可以表达为落在 /system/、/vendor/、/product/ 或 /system_ext/ 的文件，加上 init 规则与 SELinux 策略 —— 这样就不需要打 AOSP 补丁。

  2. 把硬件使能委托出去。 Maru 分支 LineageOS 设备树，而不维护自己的按设备 HAL 分支。结果 Maru 维护者可以专注融合层，同时享受 LineageOS 每季度的设备节奏。任何与硬件使能较劲的自定义 ROM 都是在签一份永无休止的工作量清单；交给上游去做。

  3. 把异世界与 Soong 分开。 Debian 容器的构建流水线基于 shell、住在独立仓库，Soong 永远不必知道 debootstrap 是什么，两套系统在一个 tarball 产物处交汇。

    有时你的自定义 ROM 需要发布并非 Android 系统镜像的东西。那就把该产物建模为一套平级的构建，只交出一个文件 —— 例如容器 rootfs、单独许可的固件 blob，或给配套微控制器的 Buildroot 镜像。

65.14.15 局限与取舍

MaruOS 也是一个很有用的案例，用来研究这种做法代价几何。诚实读来的取舍：

  • 设备支持很窄。 跨多设备维护融合层，意味着跟踪每个 LineageOS 设备分支、在每个设备上验证 LXC 所需的内核特性集、反复重测显示路由。真实的 Maru 发布每次只覆盖少量设备 —— 对小队团队而言大致合适，但离“任何 Android 手机都能跑”的承诺相去甚远。
  • 共享内核，共享风险。 LXC 比虚拟机便宜得多，但共享内核：从 Debian 容器内部可达的内核漏洞，同样能触及 Android 用户空间与 bootloader。在隔离性上，Maru 很难与虚拟化桌面方案竞争。
  • 与 Android 文件系统之间的隔离。 默认情况下 LXC 容器可被配置成暴露宿主的大部分文件系统。Maru 的 container/perspective 桥必须谨慎决定 bind mount 哪些宿主路径、屏蔽哪些 —— 判断失误就会把 Android 用户数据暴露给 Debian 应用。
  • 维护债。 两套构建系统、两套用户空间栈、一层自定义桥，在 AOSP 版本跃迁时要维持的东西很多。Android 每年的字母版本都会在 DisplayManager、输入派发与 SELinux 上带来行为变化，perspective 守护进程必须随之适配。
  • 上游的不确定性。 Maru 的设计早于 Android 的 Computer Control 框架（51.3 节）以及原版 Android 中桌面模式的正式化。融合式 UI 如今已更接近上游的一等关切，这既可能让 Maru 的路子过时，也可能抬高它的地基。请把上面的案例当作一份快照来读：它展示了一个已投产的自定义 ROM 在 Android 12 时代可用的 AOSP 原语下落到了哪里。

这里的教训与 65.14.14 对称：同一套 overlay 机制的弹性，既让一个小团队能发布手机到桌面的融合 ROM，也把成本分摊到每一处。每多一层野心就多一层维护。权衡要把模型推到多远的 ROM 作者，应先规划一份现实的设备清单与现实的发布节奏。

65.15 动手试试

请在 Android 17（android17-release）检出上完成这些练习，它们走完本章从注册产品到签名、页大小正确的镜像的整条弧线。前面的练习是后面的前提。

  1. 注册并 lunch 你自己的产品。 用 65.3 节的四个文件（AndroidProducts.mk、bookphone.mk、device.mk、BoardConfig.mk）创建 device/AospBook/bookphone/，source build/envsetup.sh，然后运行 list_products | grep bookphone 与 lunch bookphone-trunk_staging-userdebug。确认 printconfig 报告的 TARGET_PRODUCT=bookphone。

  2. 确认构建执行器。 运行 m nothing 并观察输出：Android 17 的默认执行器是 Siso。再用 SOONG_NINJA=ninja m nothing 重跑，注意构建仍以经典 Ninja 成功。对照 build/soong/ui/build/config.go 中的默认值（NINJA_DEFAULT = NINJA_SISO）。

  3. 验证平台版本三元组。 lunch 之后，在已启动的镜像上运行 adb shell getprop ro.build.version.sdk 确认是 37，用 getprop ro.build.version.release 确认是 17。把这两个取值追溯到 build/release/flag_values/trunk_staging/RELEASE_PLATFORM_SDK_VERSION.textproto 与 RELEASE_PLATFORM_VERSION_LAST_STABLE.textproto。

  4. 构建 16 KB 页大小镜像。 构建 sdk_phone16k_x86_64-trunk_staging-userdebug 并启动模拟器。运行 adb shell getconf PAGE_SIZE（应为 16384）。注意此处 ro.product.build.16k_page.enabled 读出 false，因为该产品未设置 PRODUCT_16K_DEVELOPER_OPTION。然后加一个按 4 KB 对齐的预置 .so，观察它在 16 KB 目标上加载失败；从源码重编后再看它成功加载。

  5. 签名并打包发布构建。 用 development/tools/make_key 生成密钥，设置 PRODUCT_DEFAULT_DEV_CERTIFICATE / PRODUCT_CERTIFICATE_OVERRIDES，运行 m dist，再用 build/make/tools/releasetools/sign_target_files_apks.py -o -d <keys> 重签，并用 ota_from_target_files.py 产出完整 OTA。用 build/make/tools/releasetools/check_ota_package_signature.py 校验 OTA 包的签名。

  6. 用 Kleaf 构建自定义内核。 同步 common-android-mainline，运行 tools/bazel run //common:kernel_x86_64_dist -- --dist_dir=out/x86_64/dist，把产出的 bzImage 放进 prebuilts/qemu-kernel/x86_64/6.12/，用你的内核启动模拟器。确认你的 printk 一行出现在 adb logcat -b kernel 中。

  7. 添加并让框架发现自定义 AIDL HAL。 实现 65.12 节的 IBookLight HAL 及其 VINTF 片段与 SELinux 策略，然后用 adb shell lshal | grep booklight 验证框架能看到它，同时确认 logcat 中没有与它相关的 avc: denied 行。

关键要点：

  1. 先考虑 overlay，再考虑改源码。 RRO 与产品配置能在不碰框架代码的前提下给你巨大的裁剪能力，也让 ROM 在 AOSP 更新中更易维护。

  2. 设备树是你的地盘。 device/AospBook/bookphone/ 下的一切都与 AOSP 隔离，repo sync 后能干净存活。

  3. SELinux 不可省。 每个自定义服务、HAL 与守护进程都需要 SELinux 策略。用 audit2allow 从拒绝记录生成初版策略，再把它们收敛到尽可能严格。

  4. 绝不用测试密钥发布。 向任何人分发 ROM 之前先生成独有的签名密钥。

  5. 模拟器是你最好的朋友。 95% 的 ROM 定制都能在模拟器上开发与测试，完全不必碰真实硬件。

本章的技术构成所有主流自定义 ROM 项目的基础。你可以做一个主打隐私的 ROM、一套企业管控方案，或者单纯从内到外理解 Android 如何运作。无论哪种，能够构建、裁剪、签名并分发一套完整的 Android 系统镜像，都是 AOSP 精通程度的终极体现。

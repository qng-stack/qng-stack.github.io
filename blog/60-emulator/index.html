第 60 章：模拟器架构

第 60 章：模拟器架构

Android 模拟器是 AOSP 生态中最关键的开发者工具之一。它远不止一个简单的模拟器，而是一台完整的系统级虚拟机，在改造过的 QEMU hypervisor 里运行生产环境的 Android 系统镜像；在 Linux 上通过 KVM 获得硬件加速，在其他平台上则借助 HAXM/Hypervisor Framework。

本章由内而外剖析模拟器，涵盖 QEMU 执行引擎，以及 Goldfish 与 Ranchu 两套虚拟硬件平台；涵盖把虚拟设备接到模拟器宿主的客户机侧 HAL 实现；也涵盖面向云端的 Cuttlefish 替代方案，以及快照、多屏、折叠屏模拟等一大批让模拟器不可或缺的开发者功能。

模拟器背后的设备树位于 AOSP 源码的 device/generic/goldfish/ 下。另一套虚拟设备平台 Cuttlefish 位于 device/google/cuttlefish/。两个目录合计含有数十万行 C++、shell 脚本、SELinux 策略与 Makefile 配置。正是这些文件在没有真实硬件时定义了“一台 Android 设备”意味着什么。

60.1 模拟器架构概览

60.1.1 软件栈

Android 模拟器构建在 QEMU 的自定义分支之上 —— QEMU 是开源的机器模拟器与虚拟化工具。当开发者在命令行敲下 emulator 时，下面这套分层架构就开始运转：

Host machine (Linux/macOS/Windows)
  |
  +-- Android Emulator binary (emulator, qemu-system-*)
       |
       +-- QEMU core (TCG for software emulation, or KVM/HAXM for HW accel)
       |    |
       |    +-- Virtual CPU (vCPU) executing ARM/x86/RISC-V instructions
       |    +-- Virtual memory management (shadow page tables / EPT)
       |    +-- Interrupt controller (GICv2/v3 for ARM, IOAPIC for x86)
       |
       +-- Goldfish/Ranchu virtual hardware
       |    +-- goldfish-pipe: host<->guest communication channel
       |    +-- virtio-gpu: GPU passthrough / host rendering
       |    +-- virtio-net: virtual networking
       |    +-- virtio-input: touch, keyboard, sensors
       |    +-- virtio-blk: block device emulation
       |    +-- virtio-console: serial/console ports
       |
       +-- Emulator UI / gRPC control interface
            +-- Skin rendering, Extended Controls
            +-- Snapshot management
            +-- Location / Telephony / Battery simulation

60.1.2 执行模式

模拟器支持两种基本执行模式：

  1. KVM 加速模式（Linux）：客户机代码通过基于内核的虚拟机（KVM）模块在宿主 CPU 上原生执行。这是最快的模式；只要客户机与宿主架构一致（x86 客户机跑在 x86 宿主，或 ARM 客户机跑在 ARM 宿主），就总应优先选它。在 KVM 下，绝大多数客户机指令以接近原生的速度执行，只有特权操作（I/O、页表操作）才会陷入到模拟器中处理。

  2. 软件翻译模式（TCG）：QEMU 的 Tiny Code Generator（小型代码生成器）即时把客户机指令翻译为宿主指令。架构不一致时（例如在 x86 宿主上跑 ARM 客户机镜像）就用它。虽然比 KVM 慢得多，但 TCG 让跨架构开发成为可能。

在 macOS 上，Apple 的 Hypervisor Framework 取代 KVM；在 Windows 上，Intel HAXM（Hardware Accelerated Execution Manager，硬件加速执行管理器）或 Windows Hypervisor Platform（WHPX）承担同样角色。

60.2 Goldfish 设备平台

“Goldfish” 是 Android 模拟器最初的虚拟硬件平台。这个名字指的是 QEMU 呈现给客户机内核的那一组虚拟设备（定时器、中断控制器、I/O 总线等）。随着时间推移，Goldfish 已大幅演进：在现代的 “Ranchu” 平台里，标准 virtio 设备替换了绝大多数原有的自定义 Goldfish 设备，但这个名字在 AOSP 源码树中保留了下来。

60.2.3.1 音频 HAL

位置： device/generic/goldfish/hals/audio/

音频 HAL 实现 android.hardware.audio@7.1。它通过 TinyALSA 与 QEMU 提供的虚拟声卡交互。该实现包括：

  • primary_device.cpp —— 主音频设备，负责音量控制、麦克风静音与流创建。

  • stream_out.cpp / stream_in.cpp —— 输出与输入流的实现。

  • talsa.cpp —— TinyALSA 封装层。

  • device_port_sink.cpp / device_port_source.cpp —— 音频路由用的端口抽象。

摘自 device/generic/goldfish/hals/audio/primary_device.cpp：

60.2.3.2 摄像头 HAL

位置： device/generic/goldfish/hals/camera/

摄像头 HAL 实现 AIDL 的 Camera Provider 接口，支持多种摄像头来源：

    e = qemuReceiveMessage(fd, &reply);
    if (e < 0) {

bool MultihalSensors::setSensorsReportingImpl(SensorsTransport& st,
                                              const int sensorHandle,
                                              const bool enabled) {
    char buffer[64];
    int len = snprintf(buffer, sizeof(buffer),
                       "set:%s:%d",
                       getQemuSensorNameByHandle(sensorHandle),
                       (enabled ? 1 : 0));

    if (st.Send(CONTROL, buffer, len) < 0) {
        ALOGE("%s:%d: send for %s failed", __func__, __LINE__, st.Name());
        return false;
    } else {
        return true;
    }
}

60.2.3.4 GNSS HAL

位置： device/generic/goldfish/hals/gnss/

GNSS（全球导航卫星系统）HAL 提供虚拟 GPS 数据。关键类是 GnssHwConn，它打开一条通往 “gps” 服务的 QEMU pipe：

// Source: device/generic/goldfish/hals/gnss/GnssHwConn.cpp
GnssHwConn::GnssHwConn(IDataSink& sink) {
    mDevFd.reset(qemu_pipe_open_ns("qemud", "gps", O_RDWR));
    if (!mDevFd.ok()) {
        ALOGE("%s:%d: qemu_pipe_open_ns failed", __func__, __LINE__);
        return;
    }

    unique_fd threadsFd;
    if (!::android::base::Socketpair(AF_LOCAL, SOCK_STREAM, 0,
                                     &mCallersFd, &threadsFd)) {
        ALOGE("%s:%d: Socketpair failed", __func__, __LINE__);
        mDevFd.reset();
        return;
    }

    std::promise<void> isReadyPromise;
    const int devFd = mDevFd.get();
    mThread = std::thread([devFd, threadsFd = std::move(threadsFd), &sink,
                           &isReadyPromise]() {
        GnssHwListener listener(sink);
        isReadyPromise.set_value();
        workerThread(devFd, threadsFd.get(), listener);
    });

    isReadyPromise.get_future().wait();
}

工作线程用 epoll 在 QEMU 设备 fd（接收宿主发来的 GPS 数据）与一条命令 fd（用于关停信号）之间做多路复用。模拟器的 Extended Controls 窗口下发一次定位时，数据经 QEMU 的 GPS 服务与 pipe 传出，进入 GnssHwListener 解析 NMEA 语句，最终交给 Android 的 LocationManager。

std::array<std::int8_t, 16> ToLibyuvColorMatrix(
        const std::array<float, 16>& in) {
    // Converts HAL color matrix to libyuv format
    std::array<std::int8_t, 16> out;
    for (int r = 0; r < 4; r++) {
        for (int c = 0; c < 4; c++) {
            int indexIn = (4 * r) + c;
            int indexOut = (4 * c) + r;
            float clampedValue = std::max(-128.0f,
                std::min(127.0f, in[indexIn] * 64.0f + 0.5f));
            out[indexOut] = static_cast<std::int8_t>(clampedValue);
        }
    }
    return out;
}

客户机侧 API： pipe 通过 libqemupipe.ranchu 库访问（源码在 hardware/google/gfxstream/guest/qemupipe/），它提供如下函数：

  • qemu_pipe_open_ns(namespace, name, flags) —— 打开通往某个宿主服务的具名 pipe

  • qemu_pipe_write_fully(fd, data, size) —— 向 pipe 写数据

  • qemu_pipe_read_fully(fd, data, size) —— 从 pipe 读数据

在底层，非图形 pipe 如今走 vsock socket，只有图形 pipe 仍回退到已废弃的字符设备，其节点为 /dev/goldfish_pipe_dprctd。

qemud 层在裸 pipe 之上加了多路复用：一条 pipe 连接上可以打开多个逻辑通道。摘自 device/generic/goldfish/hals/lib/qemud/qemud.cpp：

// Source: device/generic/goldfish/hals/lib/qemud/qemud.cpp
int qemud_channel_open(const char* name) {
    return qemu_pipe_open_ns("qemud", name, O_RDWR);
}

int qemud_channel_send(int pipe, const void* msg, int size) {
    char header[5];
    if (size < 0)
        size = strlen((const char*)msg);
    if (size == 0)
        return 0;

    if (size >= 64 * 1024) { // use binary encoding
        uint32_t length32be = htonl(size | (1U << 31));
        memcpy(header, &length32be, 4);
    } else { // use hex digit encoding
        snprintf(header, sizeof(header), "%04x", size);
    }

    if (qemu_pipe_write_fully(pipe, header, 4)) {
        return -1;
    }
    if (qemu_pipe_write_fully(pipe, msg, size)) {
        return -1;
    }
    return 0;
}

int qemud_channel_recv(int pipe, void* msg, int maxsize) {
    char header[5];
    int size;
    if (qemu_pipe_read_fully(pipe, header, 4)) {
        return -1;
    }
    header[4] = 0;
    if (sscanf(header, "%04x", &size) != 1) {
        return -1;
    }
    if (size > maxsize) {
        return -1;
    }
    if (qemu_pipe_read_fully(pipe, msg, size)) {
        return -1;
    }
    return size;
}

该协议采用简单的长度前缀分帧：

  • 小于 64KB 的消息用 4 字符十六进制长度前缀（例如 "001a"）
  • 64KB 及以上的消息用 4 字节网络序二进制长度，并置高位标志

60.3.2 传感器 HAL 的线程模型

传感器 HAL 具有一套值得细看的多线程架构。MultihalSensors 类的头文件（device/generic/goldfish/hals/sensors/include/multihal_sensors.h）揭示了其内部结构：

        int64_t timeBiasNs = -500000000;
        int32_t sensorsUpdateIntervalMs = 200;

        float lastHingeAngle2Value = kSensorNoValue;

    };

    // batching
    struct BatchEventRef {
        int64_t  timestamp = -1;
        int      sensorHandle = -1;
        int      generation = 0;

        bool operator<(const BatchEventRef &rhs) const {
            // not a typo: we want top() to be smallest timestamp

        Event       event;
        int64_t     samplingPeriodNs = 0;

    };

    std::thread                          m_batchThread;
    std::atomic<bool>                    m_batchRunning = true;
    mutable std::mutex                   m_mtx;
};

线程模型包含三个线程：

  1. 主线程 —— 处理来自 SensorService 的 HIDL/AIDL 调用（activate、batch、flush、injectSensorData_2_1）。

  2. 传感器监听线程（qemuSensorListenerThread）—— 从 QEMU 传输通道读取传感器数据并分派事件。用 epoll 在传输 fd 与命令 fd 之间做多路复用。

  3. 批量线程（batchThread）—— 实现连续模式传感器的批量上报。用按时间戳排序的优先队列来决定下一次事件该在何时递交。

基于 epoll 的监听线程实现摘自 device/generic/goldfish/hals/sensors/multihal_sensors_epoll.cpp：

// Source: device/generic/goldfish/hals/sensors/multihal_sensors_epoll.cpp
bool MultihalSensors::qemuSensorListenerThreadImpl(
        const int transportFd) {
    const unique_fd epollFd(epoll_create1(0));

    epollCtlAdd(epollFd.get(), transportFd);
    epollCtlAdd(epollFd.get(), m_sensorThreadFd.get());

    while (true) {
        struct epoll_event events[2];
        const int kTimeoutMs = 60000;
        const int n = TEMP_FAILURE_RETRY(epoll_wait(
            epollFd.get(), events, 2, kTimeoutMs));

        for (int i = 0; i < n; ++i) {
            const struct epoll_event* ev = &events[i];
            const int fd = ev->data.fd;

            if (fd == transportFd) {
                if (ev->events & EPOLLIN) {
                    std::unique_lock<std::mutex> lock(m_mtx);
                    parseQemuSensorEventLocked(&m_protocolState);
                }
            } else if (fd == m_sensorThreadFd.get()) {
                const int cmd = qemuSensortThreadRcvCommand(fd);
                switch (cmd) {
                case kCMD_QUIT: return false;
                case kCMD_RESTART: return true;
                }
            }
        }
    }
}

批量间隔变化、传输通道需要重配时下发 kCMD_RESTART 命令；关停时下发 kCMD_QUIT。这样的设计让传感器监听线程可以被重启，而无需拆掉整个 HAL。

60.3.6 QEMU 属性服务

qemu-props 服务（device/generic/goldfish/qemu-props/qemu-props.cpp）是模拟器启动过程中最先拉起的一批服务之一。它从模拟器宿主读取属性并设为 Android 系统属性：

// Source: device/generic/goldfish/qemu-props/qemu-props.cpp
constexpr char kBootPropertiesService[] = "boot-properties";
constexpr char kHeartbeatService[] = "QemuMiscPipe";

int setBootProperties() {
    unique_fd qemud;
    for (int tries = 5; tries > 0; --tries) {
        qemud = unique_fd(qemud_channel_open(kBootPropertiesService));
        if (qemud.ok()) break;
        else if (tries > 1) sleep(1);
        else return FAILURE(1);
    }

    if (qemud_channel_send(qemud.get(), "list", -1) < 0) {
        return FAILURE(1);
    }

    while (true) {
        char temp[PROPERTY_KEY_MAX + PROPERTY_VALUE_MAX + 2];
        const int len = qemud_channel_recv(qemud.get(), temp, sizeof(temp) - 1);
        if (len < 0 || len > (sizeof(temp) - 1) || !temp[0]) break;

        temp[len] = '\0';
        char* prop_value = strchr(temp, '=');
        if (!prop_value) continue;
        *prop_value = 0;
        ++prop_value;

        // Properties are prefixed with "vendor." unless already prefixed
        // or in the system properties list
        if (need_prepend_prefix(temp, "vendor.")) {
            snprintf(renamed_property, sizeof(renamed_property),
                     "vendor.%s", temp);
            final_prop_name = renamed_property;
        }

        property_set(final_prop_name, prop_value);
    }
    return 0;
}

设置完属性后，该服务进入心跳循环，周期性向 QemuMiscPipe 服务发送 “heartbeat” 消息。这让模拟器宿主能判断客户机是否存活且响应正常：

// Source: device/generic/goldfish/qemu-props/qemu-props.cpp
int main(const int argc, const char* argv[]) {
    if ((argc == 2) && !strcmp(argv[1], "bootcomplete")) {
        sendMessage("bootcomplete");
        return 0;
    }

    int r = setBootProperties();
    parse_virtio_serial();
    sendHeartBeat();

    while (s_QemuMiscPipe >= 0) {
        if (android::base::WaitForProperty(
                    "vendor.qemu.dev.bootcomplete", "1",
                    std::chrono::seconds(5))) {
            break;
        }
        sendHeartBeat();
    }

    while (s_QemuMiscPipe >= 0) {
        usleep(30 * 1000000);  // 30 seconds
        sendHeartBeat();
    }
    // ...
}

60.4.4 端口转发与 ADB 连接

模拟器支持宿主与客户机之间的 TCP、UDP 端口转发，ADB 正是靠端口转发与客户机通信：

  • 控制台端口：5554（第一个实例）、5556（第二个），依此类推
  • ADB 端口：5555（第一个实例）、5557（第二个），依此类推

端口转发通过模拟器控制台配置：

# Forward host port 8080 to guest port 80
redir add tcp:8080:80

# Forward host port 5000 to guest port 5000
redir add tcp:5000:5000

客户机内的 ADB 守护进程监听一个众所周知的端口。模拟器自动建立转发，因此 adb devices 会把该模拟器实例显示为一台已连接设备。

60.4.6 蓝牙网络

蓝牙通过 VirtIO console 设备模拟。init 脚本为蓝牙设备创建软链接：

# Source: device/generic/goldfish/init/init.ranchu.rc
on property:vendor.qemu.vport.bluetooth=*
    symlink ${vendor.qemu.vport.bluetooth} /dev/bluetooth0

service bt_vhci_forwarder \
    /vendor/bin/bt_vhci_forwarder \
    -virtio_console_dev=/dev/bluetooth0
    class main
    user bluetooth
    group root bluetooth

bt_vhci_forwarder 服务在 VirtIO console 设备与蓝牙 VHCI（Virtual Host Controller Interface，虚拟主机控制器接口）驱动之间架桥，让客户机可以使用模拟器的蓝牙栈。

60.5 Ranchu 与 Goldfish 内核

60.5.1 历史背景

模拟器经历了两个主要的内核世代：

  1. Goldfish 内核（遗留）：经过定制修改的 Linux 内核，带有面向最初模拟器虚拟硬件的 Goldfish 专属驱动（goldfish_timer、goldfish_fb、goldfish_audio、goldfish_battery 等）。

  2. Ranchu 内核（现代）：标准的 GKI（Generic Kernel Image，通用内核镜像）内核，用标准 VirtIO 设备取代自定义 Goldfish 设备。名字 “ranchu” 本身就是一种金鱼，暗喻两者的演化关系。

60.5.3 内核模块配置

现代 Ranchu 内核为 VirtIO 设备使用可加载内核模块。Goldfish 保留自己的内核板级配置，第一阶段模块列表很短。在 device/generic/goldfish/board/kernel/arm64.mk 中只点名了 virtio_dma_buf.ko、virtio_mmio.ko 与 virtio-rng.ko，外加一组 RAMDISK_SYSTEM_KERNEL_MODULES，来源于 prebuilts/qemu-kernel/。Cuttlefish 的板级配置 —— 它使用 kernel/prebuilts/ 下独立的一套预编译内核树 —— 则给出了更完整的一批必需 ramdisk 模块：

# Source: device/google/cuttlefish/shared/BoardConfig.mk
RAMDISK_KERNEL_MODULES ?= \
    failover.ko \
    nd_virtio.ko \
    net_failover.ko \
    virtio_dma_buf.ko \
    virtio-gpu.ko \
    virtio_input.ko \
    virtio_net.ko \
    virtio-rng.ko \

这些模块必须在第一阶段 init 中加载，系统才能启动。稍后加载的其他模块包括：

  • virtio_blk.ko —— 块设备模拟

  • virtio_console.ko —— 串口控制台与虚拟端口

  • virtio_pci.ko —— VirtIO 的 PCI 传输

  • vmw_vsock_virtio_transport.ko —— 客户机与宿主通信用的 vsock 传输

  • mac80211_hwsim.ko —— WiFi 模拟

  • cfg80211.ko、mac80211.ko —— 无线网络栈

60.5.4 内核版本选择

在 Android 17 中，Cuttlefish 的内核版本不再是单一硬编码值。device/google/cuttlefish/shared/BoardConfig.mk 先定义一个默认值，再按产品逐个选择，其中若干目标从 release-config 变量读取自己的版本：

# Source: device/google/cuttlefish/shared/BoardConfig.mk
DEFAULT_TARGET_KERNEL_USE := 6.12

ifneq (,$(findstring cf_gwear_arm,$(PRODUCT_NAME)))
TARGET_KERNEL_USE ?= 6.6
else ifeq (true,$(CLOCKWORK_EMULATOR_PRODUCT))
TARGET_KERNEL_USE ?= 6.1
else ifneq (,$(findstring x86_tv,$(PRODUCT_NAME)))
TARGET_KERNEL_USE ?= 6.1
else ifneq (,$(filter cf_x86_64_desktop,$(PRODUCT_NAME)))
TARGET_KERNEL_USE ?= $(RELEASE_KERNEL_CUTTLEFISH_X86_64_VERSION)
TARGET_KERNEL_DIR ?= $(RELEASE_KERNEL_CUTTLEFISH_X86_64_DIR)
else ifneq (,$(filter cf_arm64_desktop,$(PRODUCT_NAME)))
TARGET_KERNEL_USE ?= $(RELEASE_KERNEL_CUTTLEFISH_ARM64_VERSION)
TARGET_KERNEL_DIR ?= $(RELEASE_KERNEL_CUTTLEFISH_ARM64_DIR)
else
TARGET_KERNEL_USE ?= $(DEFAULT_TARGET_KERNEL_USE)
endif

通用手机目标的默认值是 6.12。较老的形态被钉在长期内核上（Wear OS 用 6.6，clockwork 模拟器与 x86 TV 用 6.1）。最值得注意的是 桌面 目标：它从 RELEASE_KERNEL_CUTTLEFISH_* release-config 变量读取版本与目录，然后从独立的桌面专属树（而非共享的预编译目录）取内核与模块。

注意下面这些 filter 判断精确匹配非 AOSP 的产品名 cf_x86_64_desktop / cf_arm64_desktop，因此 AOSP 的 aosp_cf_x86_64_desktop 产品会落进共享的 kernel/prebuilts/ 分支：

# Source: device/google/cuttlefish/shared/BoardConfig.mk
ifneq (,$(filter cf_x86_64_desktop cf_arm64_desktop,$(PRODUCT_NAME)))
SYSTEM_DLKM_SRC ?= device/google/desktop/cuttlefish-$(TARGET_KERNEL_ARCH)-kernels/$(TARGET_KERNEL_USE)/$(TARGET_KERNEL_DIR)/system_dlkm
KERNEL_MODULES_PATH ?= device/google/desktop/cuttlefish-$(TARGET_KERNEL_ARCH)-kernels/$(TARGET_KERNEL_USE)/$(TARGET_KERNEL_DIR)/vendor_dlkm
else
SYSTEM_DLKM_SRC ?= kernel/prebuilts/$(TARGET_KERNEL_USE)/$(TARGET_KERNEL_ARCH)
KERNEL_MODULES_PATH ?= \
    kernel/prebuilts/common-modules/virtual-device/$(TARGET_KERNEL_USE)/$(subst _,-,$(TARGET_KERNEL_ARCH))
endif

TARGET_KERNEL_PATH ?= $(SYSTEM_DLKM_SRC)/kernel-$(TARGET_KERNEL_USE)

除桌面之外，预编译内核都存放在 kernel/prebuilts/ 下，而 common-modules/virtual-device/ 目录存放专为虚拟设备构建的内核模块。

60.5.5 ZRAM 与内存配置

Ranchu 内核启用 zram 做内存压缩：

# Source: device/generic/goldfish/init/init.ranchu.rc
on early-init
    exec u:r:modprobe:s0 -- /system/bin/modprobe -a -d \
        /system/lib/modules zram.ko

on init
    write /sys/block/zram0/comp_algorithm lz4
    write /proc/sys/vm/page-cluster 0

on sys-boot-completed-set && property:persist.sys.zram_enabled=1
    swapon_all /vendor/etc/fstab.${ro.hardware}

zram 压缩使用 LZ4，以获得快速的压缩与解压。page-cluster 0 设置让内核每次从 swap 读一页，这对 zram 最优，因为不存在寻道开销。

#   Instance 1: CID=3, TAP cvd-mtap-01, port 6520
#   Instance 2: CID=4, TAP cvd-mtap-02, port 6521
#   Instance 3: CID=5, TAP cvd-mtap-03, port 6522

实例专属路径由 CuttlefishConfig::InstanceSpecific 管理，它为每个实例生成唯一的 socket 路径、FIFO 路径与日志目录。这让 CI/CD 环境中的大规模并行测试成为可能。

快照类型：

  1. QuickBoot 快照 —— 模拟器关闭时自动保存，下次打开时自动恢复。由此获得近乎瞬时的启动（通常 2–5 秒，而不是冷启动的 60 秒以上）。

  2. 具名快照 —— 用户通过 Extended Controls 界面或命令行手动创建，用于保存特定设备状态（例如“已登录”、“已装应用”、“特定界面”）。

快照存放在模拟器的 AVD（Android Virtual Device）目录中，通常在 ~/.android/avd/<name>.avd/snapshots/。

快照内容：

  • snapshot.pb —— Protobuf 元数据（机器配置、时间戳）
  • ram.bin —— 客户机完整内存内容
  • textures.bin —— GPU 纹理与缓冲区数据
  • <disk>-snapshot.img —— 写时复制的磁盘覆盖层

60.8 Android 17 的 Cuttlefish 变更

每版发布里，虚拟设备的大部分变动都落在 Cuttlefish 上，Android 17 也不例外。本节汇总对平台开发者有意义的变更：新增的桌面产品、客户机侧的 VKMS 显示控制器、沙箱化的宿主进程模型、新的 NPU HAL，以及宿主启动工具迁出 AOSP 树。

60.8.1 桌面产品目标

Android 17 往 Cuttlefish 产品目录中加入了 aosp_cf_x86_64_desktop。板级配置里也为非 AOSP 的 cf_arm64_desktop 产品名保留了一条内核分支，但 AOSP 中并无 ARM64 桌面产品。与手持目标不同，桌面产品继承一套桌面专属 vendor 栈（见 60.5.4 与 60.6.3 节）。它是桌面 Android 形态的虚拟参考设备，用于演练大屏窗口管理、ndk_translation_only 模式下的二进制翻译，以及不压缩的 Chrome WebView。该产品与长期存在的手机、折叠、TV、Wear 目标，以及扩展后的车机目标集合（auto、auto_md、auto_mdnd、auto_dd、auto_portrait）一同注册在 device/google/cuttlefish/AndroidProducts.mk 中。

60.8.2 vkms_controller：客户机侧虚拟显示管理

早前的 Cuttlefish 版本把虚拟显示配置逻辑散落在宿主命令与临时客户机脚本之间。Android 17 把它整合进单个客户机二进制 vkms_controller，直接驱动内核的 VKMS（Virtual Kernel Mode Setting，虚拟内核模式设置）ConfigFS 接口。宿主 CLI 则退化为薄薄的无状态代理，只负责执行 adb shell vkms_controller ...。

// Source: device/google/cuttlefish/guest/commands/vkms_controller/main.cpp
namespace cuttlefish {
namespace vkms_controller {

constexpr std::string_view kUsage = R"(
Usage: vkms_controller <command> [options]

A guest-side utility for Virtual Kernel Mode Setting (VKMS).
It manages virtual displays by interacting directly with the kernel's VKMS
ConfigFS interface.

Commands:
  setup
  hotplug
  reset
  list-presets
  list-displays

这个二进制负责把虚拟硬件（VKMS ConfigFS 的 connector 索引）与 Android SurfaceFlinger 的显示 ID 对应起来，状态存放在 /data/vendor/vkms 下。它支持四条命令：

  • setup —— 用指定的 EDID 与 plane 定义显示。
  • hotplug —— 插入或拔出某个 connector。
  • list-presets —— 枚举客户机内置的显示器预设。
  • list-displays —— 解析当前的显示拓扑。

60.8.3 process_sandboxer：给宿主守护进程加沙箱

Cuttlefish 一个反复被提及的顾虑是：宿主上跑着一批拥有宽泛宿主权限的辅助守护进程，包括 VMM、调制解调器模拟器、GNSS 代理、secure_env 等等。对策是 device/google/cuttlefish/host/commands/process_sandboxer/：它于 2024 年初引入，此后按可执行文件划分的策略覆盖范围不断扩大。它把这些宿主进程包进基于 Google sandboxed-api / sandbox2 库的 seccomp 沙箱。

#include "host/commands/process_sandboxer/policies.h"
#include "host/commands/process_sandboxer/sandbox_manager.h"

absl::Status ProcessSandboxerMain(int argc, char** argv) {

沙箱器为每个可执行文件准备一份策略。policies/ 目录为每个在沙箱下运行的宿主工具备一个专属源文件，例如 run_cvd.cpp、assemble_cvd.cpp、gnss_grpc_proxy.cpp、secure_env.cpp、logcat_receiver.cpp、modem_simulator.cpp、socket_vsock_proxy.cpp 等。此外还有一份共享的 baseline.cpp 策略和一个 no_policy.cpp 逃生门。

每份策略声明某个守护进程可以使用的系统调用与文件路径，因此被攻破的辅助进程无法越出其声明的边界。配套的 sandboxer_proxy 让沙箱内进程可以向管理器申请特权操作。

这是平台其他部分进程内隔离工作在宿主侧的对应物：并非每个 Cuttlefish 辅助进程都享有启动器的全部权限，每个都在最小权限策略下运行。

60.8.4 NPU 调度 HAL

Android 17 的 Cuttlefish 新增一套客户机 NPU（Neural Processing Unit，神经网络处理单元）HAL，位于 device/google/cuttlefish/guest/hals/npu/，用 Rust 编写。它注册一个 android.hardware.npu 调度服务，给框架的 NPU 通路提供可演练的虚拟面（源码片段见 60.6.15 节）。该 HAL 作为独立的 APEX 包服务发布，附带一个声明 IScheduling/default 的 VINTF 片段。它与 virtio_media/ 一起，构成本版中两个值得关注的新客户机 HAL 目录。

60.9.9 理解产品配置的继承链

构建模拟器镜像时，产品配置沿着一条特定的继承链展开。以 x86_64 phone 目标为例追踪：

sdk_phone64_x86_64.mk
  -> phone.mk
       -> handheld.mk
            -> base_handheld.mk
                 -> multidisplay.mk
            -> generic_system.mk
            -> handheld_system_ext.mk
            -> aosp_product.mk
       -> base_phone.mk
            -> generic.mk
                 -> versions.mk
            -> phone_overlays.mk

每一层都补齐特定功能：

  1. versions.mk —— 设置版本代号与 API 级别
  2. generic.mk —— 模拟器核心设备：HAL、包、属性
  3. base_handheld.mk —— 手持设备专属设置（dalvik 堆等）
  4. handheld.mk —— 完整手持产品，含 system、system_ext、product
  5. base_phone.mk —— 手机专属 overlay
  6. phone.mk —— 把一切串起来，并加上 config.ini

这种分层设计意味着新的模拟器产品（例如新形态）只需要一个轻薄的顶层 makefile，继承自合适的基类即可。

60.9.10 测试 HAL 实现

对平台开发者来说，模拟器最有用的能力之一就是测试 HAL 实现。下面是以修改过的传感器 HAL 为例的工作流：

# Step 1: Make changes to the sensors HAL
# Edit device/generic/goldfish/hals/sensors/multihal_sensors.cpp

# Step 2: Rebuild just the sensors module
m android.hardware.sensors@2.1-impl.ranchu

# Step 3: Push the updated library
adb root
adb remount
adb push $ANDROID_PRODUCT_OUT/vendor/lib64/hw/\
    android.hardware.sensors@2.1-impl.ranchu.so \
    /vendor/lib64/hw/

# Step 4: Restart the sensors HAL
adb shell stop
adb shell start

# Step 5: Verify
adb shell dumpsys sensorservice

# Rebuild camera provider

# Push and restart

    /vendor/bin/hw/

60.9.13 在模拟器上跑 CTS

模拟器是受支持的 CTS（Compatibility Test Suite，兼容性测试套件）目标：

# Step 1: Launch emulator with CTS-compatible settings
emulator -gpu host -memory 4096 -cores 4

# Step 2: Wait for boot to complete
adb wait-for-device
adb shell getprop sys.boot_completed  # should return "1"

# Step 3: Run CTS
cd /path/to/cts
./android-cts/tools/cts-tradefed
> run cts --plan CTS

# Or run specific modules
> run cts -m CtsMediaTestCases
> run cts -m CtsSensorTestCases

部分 CTS 用例需要特定传感器值或硬件能力，模拟器通过其虚拟 HAL 提供。传感器 HAL 中的数据注入支持（所有传感器上的 SensorFlagBits::DATA_INJECTION 标志）正是为满足 CTS 合规而设计。

小结

Android 模拟器是一套精密的虚拟化平台，在虚拟硬件上运行真实的 Android 系统镜像。本章覆盖了它的分层架构：

  1. QEMU 核心 —— 经 KVM（硬件）或 TCG（软件翻译）提供 CPU 虚拟化，并负责内存管理与设备模拟。

  2. Goldfish/Ranchu 虚拟平台 —— 一组虚拟设备，包括 VirtIO（gpu、net、blk、input、console、rng）以及用于高带宽宿主-客户机通信的 goldfish-pipe。

  3. HAL 实现 —— 九个 HAL 模块（音频、摄像头、传感器、GNSS、无线电、指纹、HWC3、gralloc，外加支撑库）。它们把 Android 的硬件接口桥接到模拟器的虚拟设备。

  4. GPU 模拟 —— 命令流架构：客户机的 GLES/Vulkan 调用被序列化，经 goldfish-pipe 送往宿主，再在宿主真实 GPU 上重放。

  5. 网络 —— 虚拟路由器、VirtIO WiFi、端口转发与模拟器间网络。

  6. Cuttlefish —— 面向云的替代方案，用相同的内核与 VirtIO 设备，但不带桌面 GUI，因而非常适合 CI/CD 与服务器侧测试。

  7. 开发者特性 —— 可瞬时恢复的快照、多屏支持、折叠模拟、位置/电池/电话模拟，以及丰富的控制台命令。

  8. Android 17 的 Cuttlefish 变更 —— 新增 aosp_cf_x86_64_desktop 产品与客户机侧 vkms_controller 显示工具；通过 process_sandboxer 扩大了对宿主守护进程按可执行文件划分的 seccomp 沙箱覆盖；新增 Rust 版 NPU 调度 HAL 与 20 端口 HVC 映射（传感器拆为控制/数据两路）；cvd 启动器与 Debian 打包也迁到了外部 github.com/google/android-cuttlefish 仓库。

贯穿始终的关键架构原则是：模拟器运行的是真实的 Android —— 同样的内核、同样的框架、同样的系统镜像格式。虚拟硬件层被设计成对上层软件透明，从而让应用与平台代码无论跑在物理设备还是模拟器上都表现一致。

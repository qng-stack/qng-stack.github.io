第 53 章：NPU 管理器

第 53 章：NPU 管理器

现代手机都配备 NPU（neural processing unit，神经网络处理单元）。NPU 是一种固定功能加速器，它以远高于 CPU 或 GPU 的效率，运行为端侧语音、视觉与生成式模型提供支撑的矩阵乘法。

直到 Android 17，平台并不管控哪些应用可以使用 NPU。应用自行加载模型、映射权重，并把工作直接交给厂商的 NPU 驱动。如果两个应用都想在同一时刻驻留一个数 GB 的模型，它们会在同一个固定内存池里相互冲突：输的一方要么得到内存不足错误，要么被静默驱逐。这里没有优先级，没有准入控制，也没有“这段缓冲区装的是模型权重，应当保护起来”这种共识。

Android 17 引入 NPU 管理器（NPU Manager）：一个新的主线 APEX 模块（com.android.npumanager），外加一个配套的厂商 HAL（android.hardware.npu）。二者合力把 NPU 变成一项受管理的多租户资源。应用不再想加载模型就直接加载，而是向 NPU 管理器询问自己是否可以加载。服务依据可插拔的策略、发起请求的应用的优先级以及内存预算给出答复。

新增的 Rust NDK 让原生 AI 运行时得以分配受保护的 NPU 缓冲区。新增的内核原语 /dev/wrapfd 为这些缓冲区提供底层支撑：即便文件描述符在进程之间流转，内核仍可强制这些缓冲区的内存保护状态。

本章自上而下讲解该模块：先说明它为何是 Android 17 的新增内容，并描述 APEX 与其模块 SDK 的结构；然后讲模型加载的准入控制状态机及其三种策略；接着讲服务与 HAL 共享的优先级模型、Rust NDK 的缓冲区接口，以及 android.hardware.npu v1 契约；最后讲 libwrapfd 如何实施缓冲区保护。

53.1 为什么需要管理器，为什么做成模块

53.1.1 问题所在：一台无人管理的共享加速器

NPU 拥有少量专用（或划出）内存和一条命令队列。仅一个大语言模型的权重就可能有 1-2 GB。若一个前台助手应用和一个后台照片分类应用都想常驻各自的模型，设备就会耗尽 NPU 可访问的内存。厂商驱动随后会按请求到达的先后顺序把其中一个弄失败。平台没有任何机制规定前台助手应当胜出，也没有机制规定平台应当先礼貌地请后台任务释放它的模型。

NPU 管理器补上的正是这一缺失的层次。它不亲自执行推理，也不取代厂商的 NPU 驱动。它是一个仲裁与记账服务，位于应用与硬件之间：它决定应用何时可以加载模型、在压力下驱逐谁的模型，还决定如何分配并保护存放这些模型的缓冲区。

53.1.2 为什么以主线模块形式交付

该管理器是一个可更新的 APEX，而不属于平台镜像的一部分。这让 Google 得以脱离年度 OS 发布节奏，独立迭代准入控制策略——加载策略、预算启发式与 NDK 都可以通过模块更新改变。文件 packages/modules/NpuManager/apex/Android.bp 把该 APEX 定义为 com.android.npumanager，并设置 min_sdk_version: "36"。有两个标志为其把关：

  • 一个构建期发布标志 RELEASE_NPUMANAGER_MODULE，决定构建系统是否构建该 APEX、其 bootclasspath 与 systemserver 片段，以及它的模块 SDK。APEX 中每个 Soong 模块都把自己的 enabled: 字段包在 select(release_flag("RELEASE_NPUMANAGER_MODULE"), ...) 里。
  • 一个运行期 aconfig 标志 npumanager_enabled，通过 @FlaggedApi 为框架 API 界面把关，还决定服务是否连接 HAL。文件 packages/modules/NpuManager/flags/npumanager_flags.aconfig 在命名空间 machine_learning 中声明该标志。

该 APEX 在两个 classpath 层级贡献代码，二者都可在 apex/Android.bp 中看到。第一层是一个 bootclasspath_fragment（com.android.npumanager-bootclasspath-fragment），承载框架库 framework-npumanager；第二层是一个 systemserverclasspath_fragment，承载服务 service-npumanager。对于一个既对外暴露框架侧 @SystemApi、又在 system_server 内运行逻辑的模块，这是标准拆分方式。

53.1.3 自带的模块 SDK

由于厂商代码与其他模块代码需要针对该管理器的接口进行构建，同一个 apex/Android.bp 还定义了一个模块 SDK：

// Source: packages/modules/NpuManager/apex/Android.bp
sdk {
    enabled: select(release_flag("RELEASE_NPUMANAGER_MODULE"), {
        true: true,
        false: false,
    }),
    name: "npumanager-module-sdk",
    apexes: [
        "com.android.npumanager",
    ],
}

该模块交付 npumanager-module-sdk，这使 com.android.npumanager 成为一个自包含、可独立构建的模块。使用方对 SDK 做快照，并针对导出的 classpath 片段编译，而不是针对活动源码树编译。

53.2 框架侧界面

53.2.1 NpuManager 系统服务

应用通过 NpuManager 类访问该管理器 （packages/modules/NpuManager/framework/java/android/npumanager/NpuManager.java）。 框架把该 @SystemApi 类注册在 Context.NPU_SERVICE（字符串 "npu"）下。 注解 @FlaggedApi(Flags.FLAG_NPUMANAGER_ENABLED) 为整个类把关。该类是 binder 接口 INpuManagerService 之上的薄客户端。注册发生在 NpuManagerFrameworkInitializer.registerServiceWrappers() 中，经 SystemServiceRegistry.registerContextAwareService(Context.NPU_SERVICE, ...) 完成。

binder 契约很小，且刻意不是一个“跑我的模型”式的接口。以下取自 packages/modules/NpuManager/framework/java/android/npumanager/INpuManagerService.aidl：

// Source: framework/java/android/npumanager/INpuManagerService.aidl
interface INpuManagerService {
    void canLoadModel(in ModelLoadRequestParcelable request, in IModelLoadCallback callback);
    void cancelModelLoad(in ModelLoadRequestParcelable request);
    void notifyModelLoaded(in ModelLoadRequestParcelable request);
    void notifyModelUnloaded(in ModelLoadRequestParcelable request);
    void setPolicy(int policy, in PersistableBundle policyParams);

    /** For memory management. */
    INpuAllocator createAllocator(INpuAllocatorCallback callback);
}

其中三个属于准入控制（canLoadModel、cancelModelLoad、 setPolicy）。两个是诚实性通知，应用必须回传（notifyModelLoaded、notifyModelUnloaded）。一个返回内存管理分配器（createAllocator）。

模型管理相关调用需要 android.Manifest.permission.ACCESS_NPU_MODEL_MANAGER_API 权限。框架侧的 NpuManager 方法带有注解 @RequiresPermission(ACCESS_NPU_MODEL_MANAGER_API)。在服务侧，目前只有 setPolicy() 会调用 NpuManagerServiceImpl.enforceModelManagerPermissions()。其他入口点虽带 @PermissionManuallyEnforced 注解，但目前自身尚未做任何校验。

53.2.2 请求、尺寸与优先级

应用用 ModelLoadRequest 描述一个模型 （framework/java/android/npumanager/ModelLoadRequest.java）。应用在请求中给出一个 id、一个粗粒度尺寸档和一个优先级。尺寸不是字节数，而是三档之一。NpuModelSize 枚举 （framework/java/android/npumanager/NpuModelSize.aidl）用无前缀的裸名定义这些档位（LESS_THAN_1GB、BETWEEN_1GB_AND_2GB、GREATER_THAN_2G）。 NpuManager 把它们重新导出为带前缀的常量：

  • NPU_MODEL_SIZE_LESS_THAN_1GB（NpuModelSize.LESS_THAN_1GB）
  • NPU_MODEL_SIZE_BETWEEN_1GB_AND_2GB（NpuModelSize.BETWEEN_1GB_AND_2GB）
  • NPU_MODEL_SIZE_GREATER_THAN_2G（NpuModelSize.GREATER_THAN_2G）

模型优先级是请求自身上一个两值档位： NPU_MODEL_PRIORITY_NORMAL 与 NPU_MODEL_PRIORITY_BACKGROUND。这个模型优先级不同于服务从 ActivityManager 重要性导出的 0-1000 细粒度 UID 优先级（见 53.4 节），也不同于 NDK 侧的缓冲区优先级。本模块中存在三种不同的优先级概念，阅读代码时请把它们区分开。

53.2.3 异步准入协议

canLoadModel() 不返回“是”或“否”的答复。应用传入一个回调，服务稍后再作答，且可能作答不止一次，通道是 IModelLoadCallback。框架侧由 NpuManager.ModelLoadCallbackWrapper 包装该回调。NpuManager 定义了这些状态值：

  • NPU_MODEL_LOAD_STATUS_CAN_LOAD_NOW（0）：现在可以加载。
  • NPU_MODEL_LOAD_STATUS_WAIT_FOR_UNLOAD（1）：服务正在为你腾出内存。 等待后续通知。
  • NPU_MODEL_LOAD_STATUS_NOT_PRIORITIZED（2）：另一个应用优先级高于你， 不要加载。

应用加载模型之后必须调用 notifyModelLoaded()。当应用用完模型，或服务经回调的 onRequestUnloadModel() 提出要求时，它必须调用 notifyModelUnloaded()。服务信任应用会做这两件事。终结性回调 onModelLoadRequestComplete() 会投递 NPU_MODEL_LOAD_REQUEST_STATUS_CANCELLED（3）或 NPU_MODEL_LOAD_REQUEST_STATUS_COMPLETE（4），此后该请求不再有任何更新。

策略驱动应用请求所经历的状态机：

stateDiagram-v2
    [*] --> PendingLoad : canLoadModel
    PendingLoad --> Loaded : CAN_LOAD_NOW 后 notifyModelLoaded
    PendingLoad --> NotPrioritized : NOT_PRIORITIZED
    PendingLoad --> WaitForUnload : WAIT_FOR_UNLOAD
    WaitForUnload --> Loaded : CAN_LOAD_NOW 后 notifyModelLoaded
    NotPrioritized --> PendingLoad : 更高优先级的槽位腾出
    Loaded --> Unloading : onRequestUnloadModel
    Unloading --> [*] : notifyModelUnloaded 后 COMPLETE
    PendingLoad --> [*] : cancelModelLoad 后 CANCELLED
    NotPrioritized --> [*] : cancelModelLoad 后 CANCELLED

53.3 准入控制与三种策略

服务实现 （packages/modules/NpuManager/service/java/com/android/server/npumanager/NpuManagerServiceImpl.java） 持有单个 NpuModelLoadingPolicy，并把每次 canLoadModel、 notifyModelLoaded、notifyModelUnloaded 与 cancelModelLoad 直接转发给它。 setPolicy() 通过在三个策略常量上做 switch，在运行期替换策略对象。NpuModelLoadingPolicy 是抽象基类，另有三个具体实现。

53.3.1 StatusQuo：不做仲裁

StatusQuoModelLoadingPolicy （service/java/com/android/server/npumanager/StatusQuoModelLoadingPolicy.java） 是默认策略。它的 canLoadModel() 对所有人都立即答复 CAN_LOAD_NOW，只为在取消或卸载时能触发 onModelLoadRequestComplete() 而跟踪回调。它是一条旁路，用于在无人改动策略时保持 17 之前的行为。该策略“模仿 NpuModelManager 引入之前的行为”。

53.3.2 Budget：在加权上限内允许多个模型

BudgetModelLoadingPolicy （service/java/com/android/server/npumanager/BudgetModelLoadingPolicy.java） 是真正的仲裁者。它给每个模型尺寸分配一个权重，只要已加载与待决模型的权重之和不超过最大预算，就允许并发加载。默认权重把小块模型映射为 1、中块为 2、大块为 4：

// Source: service/java/com/android/server/npumanager/BudgetModelLoadingPolicy.java
private static final Map<Integer, Integer> DEFAULT_MODEL_WEIGHTS =
        Map.of(
                NPU_MODEL_SIZE_LESS_THAN_1GB, 1,
                NPU_MODEL_SIZE_BETWEEN_1GB_AND_2GB, 2,
                NPU_MODEL_SIZE_GREATER_THAN_2G, 4);

各尺寸权重与上限都可通过调用方传给 setPolicy() 的 PersistableBundle 配置，使用的键为 NpuManager.KEY_MODEL_SIZE_WEIGHTS 与 NpuManager.KEY_MAX_BUDGET。

当新请求超出预算时，策略最先从最不重要的 UID 开始遍历（getLeastImportantUids()）。对于重要性不高于调用方的任何 UID，若其模型已加载，策略请其卸载；若仍处于待决，则取消之。策略持续这一过程，直到腾出足够预算。

若调用方在这场竞争中无法胜出，它得到 NOT_PRIORITIZED；若策略确为调用方要求了模型卸载，调用方得到 WAIT_FOR_UNLOAD。当某个模型终于卸载时，evaluateAndLoadHighestPriorityModels() 会重跑整轮排序，并通知下一批胜出者。

有两个决胜规则值得注意，因为它们塑造了公平性。当两个 UID 重要性相同时，策略偏向最近没有完成工作的那个 UID；它把这一点记录在 mTimeUidLastCompleted 中，由 handleWorkEnded() 打时间戳。策略还为每个发起调用的 UID 注册 binder 死亡接收器，从而能回收崩溃客户端的模型并重新评估预算。

53.3.3 TurnTaking：一次只允许一个模型

TurnTakingModelLoadingPolicy （service/java/com/android/server/npumanager/TurnTakingModelLoadingPolicy.java） 是预算策略的薄子类：它把每个尺寸权重都设为 1，最大预算设为 1。这个子类是预算机制有多通用的最清晰示范。

// Source: service/java/com/android/server/npumanager/TurnTakingModelLoadingPolicy.java
super(
        priorityManager,
        Map.of(
                NPU_MODEL_SIZE_LESS_THAN_1GB, 1,
                NPU_MODEL_SIZE_BETWEEN_1GB_AND_2GB, 1,
                NPU_MODEL_SIZE_GREATER_THAN_2G, 1),
        1);

因为预算为 1 且每个模型都花费 1，所以同一时刻只能有一个模型驻留。优先级最高的 UID 占用该槽位，重要性更高的 UID 可以抢占它。全部工作都由预算策略的驱逐与重评估逻辑完成。

53.4 优先级与 HAL 桥接

53.4.1 PriorityManager 与 0-1000 刻度

各策略给 UID 排序，但原始优先级数值来自 PriorityManager （service/java/com/android/server/npumanager/PriorityManager.java）。它监听 ActivityManager.OnUidImportanceListener，把进程重要性映射为按 UID 的优先级。HAL 的 parcelable SchedulingConfig 定义了该优先级的刻度。在这个刻度上，MIN_PRIORITY = 0 是最高优先级，MAX_PRIORITY = 1000 是最低。该类把系统与 root UID 固定为静态优先级 100，把未知 UID 视为 MAX_PRIORITY。

NDK 缓冲区优先级（0-1000，默认 500）与 HAL 的 WorkInfo.jobPriority 使用同一刻度。因此整个模块遵循同一种优先级约定：0 意味着“最重要”。

53.4.2 按特性为应用把关

PriorityManager 还强制一项新的平台要求：应用必须声明 PackageManager.FEATURE_NEURAL_PROCESSING_UNIT 特性才能获得 NPU 访问权限。一个 NpuPackageMonitor 按包跟踪这一点，对安装、移除与修改事件做出反应。

对目标版本为 Android 17（Build.VERSION_CODES.CINNAMON_BUN）却未声明该特性的应用，当 npumanager_block_missing_feature 标志开启时，管理器会把 SchedulingConfig.hasDirectAccess 设为 false；标志关闭时，管理器只记一条警告，说明该访问“很快会被阻断”。

53.4.3 android.hardware.npu HAL v1 契约

厂商侧是一个位于 hardware/interfaces/npu/aidl/android/hardware/npu/ 的新 AIDL HAL，版本号为 v1（冻结快照位于 aidl_api/android.hardware.npu/1/）。它刻意不是一个“执行推理”的接口。该 HAL 的 README.md 指出，实际工作仍通过厂商 SDK 运行；该 HAL 只管优先级与观测。

NpuManagerServiceImpl 经 ServiceManager.waitForDeclaredService(IScheduling.DESCRIPTOR + "/default") 连接 IScheduling（IScheduling.aidl）。该接口有三个方法：

  • setSchedulingConfigs(SchedulingConfig[]) 整体替换优先级表。
  • updateSchedulingConfigs(SchedulingConfig[]) 增量添加或更新条目。
  • setCallback(ISchedulingCallback) 注册管理器的观察者。

SchedulingConfig（SchedulingConfig.aidl）携带 uid、其 priority、 hasDirectAccess，以及 canAttributeOtherUid（即某个中介服务能否代表另一个应用提交工作）。NPU 应尽力先运行数值更小的优先级。

反方向是 ISchedulingCallback（ISchedulingCallback.aidl），一个由 HAL 调用来上报 NPU 活动的 oneway 接口：

  • onWorkRequested(WorkInfo)
  • onWorkStarted(WorkInfo, StartReason)，其中 StartReason 为 INITIAL 或 RESUMED
  • onWorkEnded(WorkInfo, EndReason)，其中 EndReason 为 CANCELLED_USER、CANCELLED_SYSTEM、PAUSED、FAILED、COMPLETED 之一

HAL 用 DEBOUNCE_DURATION_MS = 50 对这些事件做去抖。

WorkInfo（WorkInfo.aidl）描述一个 NPU 工作单元。它有一个单调递增的 id；一个可选的 groupId（Uuid）把属于同一件更大工作的多次推理关联起来。该 parcelable 还含请求方的 uid、用于归因工作的 originalUid，以及 jobPriority。合成的 effectivePriority 是 UID 优先级加作业优先级，最大可达 MAX_PRIORITY * 2。

在 NpuManagerServiceImpl 中，onWorkRequested 流入 PriorityManager.handleWorkRequested()，为新出现的 UID 赋予优先级； onWorkEnded 流入当前活动策略的 handleWorkEnded()，让预算策略打上公平性时间戳。当同级优先级的对端在等待时，策略还可以要求刚完成的 UID 卸载。真正的重评估稍后发生，即卸载经 notifyModelUnloaded 到达之时。

该连接具备自愈能力：服务对 HAL binder 调用 linkToDeath，若厂商进程死亡则在 ensureHalService() 中重连。

53.5 Rust NDK 与 ANpuBuffer

53.5.1 原生分配接口

原生 AI 运行时（真正映射模型权重的那类）使用 C NDK。头文件 packages/modules/NpuManager/ndk/include/android/npumanager/buffer.h 声明它。不透明句柄是 ANpuBuffer。运行时用 ANpuManager_AllocRequest 构建分配一个缓冲区的请求。

这一头文件背后的实现是 Rust。文件 ndk/Android.bp 构建 libnpumanager_rust（crate 根为 buffer_impl.rs），并把它包装成共享库 libcom.android.npumanager.so。该共享库随 APEX 一起交付。由于 libandroid.so 可能在 APEX 就绪之前即被加载，调用方经一个惰性 dlopen() 垫片 （ndk/npumanager_dlopen.h / .cpp）抵达公开入口点。

运行时用这些函数配置请求：

  • ANpuManager_AllocRequest_setDeviceNumber() —— 指定哪个 NPU（对厂商不透明，必须非负）。
  • ANpuManager_AllocRequest_setBufferType() —— 取 ANPUBUFFER_TYPE_* 之一： MODEL_EXECUTABLE、MODEL_WEIGHTS、CACHE、AUXILIARY（输入／输出缓冲区改用 AHardwareBuffer）。
  • ANpuManager_AllocRequest_setSize()、setBufferPriority()（0-1000 刻度，默认 ANPUBUFFER_PRIORITY_DEFAULT = 500）与 setProtectionFlags()（默认 PROT_READ）。
  • ANpuManager_AllocRequest_setFileSegmentToLoad() —— 可选地给一个文件 fd 加偏移，好让管理器把权重直接加载进缓冲区。
  • setCookie()、setOnAlloc()、setOnPreempt() —— 回调接线。

所有入口点都标有 __INTRODUCED_IN(37)。分配是异步的： ANpuManager_allocAsync() 接收一批请求，结果经每个请求自己的 ANpuManager_AllocCallback 抵达。

分配之后，运行时用 ANpuBuffer_map() 与 ANpuBuffer_unmap() 映射与取消映射缓冲区。这些函数类同 mmap，但 prot 必须是分配后即固定的保护标志的子集。运行时可以调用 ANpuBuffer_setPriority() 调整缓冲区优先级，也可以调用 ANpuBuffer_loadAsync() 在分配之后流式装入一段文件。运行时必须用 ANpuBuffer_free() 释放每一个缓冲区，即使是已被抢占的缓冲区。

53.5.2 缓冲区状态机

Rust 客户端（ndk/npu_buffer_state.rs）用一个小的状态机跟踪每个缓冲区，镜像服务的异步响应。缓冲区起始于 Allocating；服务返回其 fd 时变为 Allocated；分配失败则变为 Gone。

在 ANpuBuffer_loadAsync() 期间缓冲区转入 Loading，完成时回到 Allocated。抢占可以在任何时点把缓冲区强制变为 Gone。NpuBufferState 直接编码这些转移：

stateDiagram-v2
    [*] --> Allocating : allocAsync
    Allocating --> Allocated : onGetBuffer 返回 fd
    Allocating --> Gone : onGetBuffer 出错或被抢占
    Allocated --> Loading : loadAsync
    Loading --> Allocated : onLoad
    Allocated --> Gone : onNotifyPreempted
    Loading --> Gone : onNotifyPreempted
    Gone --> [*] : ANpuBuffer_free

抢占是 NDK 的驱逐信号：服务调用 INpuAllocatorCallback.onNotifyPreempted()，客户端把缓冲区推进到 Gone，可选的 ANpuManager_PreemptCallback 随之触发。此后任何 ANpuBuffer_map() 都会以 errno == ENOENT 失败，因为内核已清空底层缓冲区（见 53.6 节）。

53.5.3 分配器的 binder 路径

在 C API 之下，Rust 客户端经 INpuAllocator（framework/java/android/npumanager/INpuAllocator.aidl）与服务对话。客户端从 INpuManagerService.createAllocator() 取得该接口。客户端一侧（ndk/npu_allocator_client.rs）把请求批进 getBuffers()、检查 isSupported()，并用 putBuffers() 归还缓冲区。Rust 客户端经 ndk/npu_manager_delegate.rs 中的 setPriority() 调整缓冲区优先级，经 ndk/npu_buffer_impl.rs 中的 loadFileSegmentToBuffer() 流式传输数据；调用走 NpuAllocatorClient::load_async。

回复经 INpuAllocatorCallback 异步返回（onGetBuffer、 onLoad、onNotifyPreempted）。分配器的服务实现是 NpuAllocator（service/java/com/android/server/npumanager/NpuAllocator.java）， 是一个 INpuAllocator.Stub，在后台线程池上完成真正的堆分配与包装。

53.6 libwrapfd 与缓冲区保护

53.6.1 /dev/wrapfd 原语

NPU 管理器提供的缓冲区不是单纯的 dma_heap 分配。管理器把它们包装起来，使内核能够强制规定进程可以如何映射它们、以及它们归谁所有。这是 libwrapfd （system/memory/libwrapfd）的职责——一个新的 Rust 库兼 LLNDK 共享库，建立在新的 /dev/wrapfd 内核驱动之上。构建文件 system/memory/libwrapfd/rust/Android.bp 把该库同时定义为 rust_library（libwrapfd_rust）与 cc_library_shared（libwrapfd）。该库还对 com.android.npumanager 设置 apex_available。

libwrapfd 接收一个既有 fd（此处为 dma-buf），返回一个新的 wrapfd：它委托给原 fd，但附加了保护状态。核心操作是 WrapfdDriver::wrap(fd, prot)（system/memory/libwrapfd/rust/lib.rs）。它把被包装的 fd 钉在 PROT_NONE 或 PROT_READ 与 PROT_WRITE 组合的保护掩码上；自此内核便约束进程如何映射该缓冲区。更多操作包括：

  • acquire_ownership() / release_ownership() —— 拥有者修改缓冲区期间的独占所有权；RAII 守卫 WrapfdOwnershipGuard 在 drop 时释放。
  • load(wrapfd, file, file_offset, buf_offset, len) —— 以 DMA 方式把一段文件复制进缓冲区；需要所有权，且偏移须页对齐。
  • rewrap(prot) —— 把底层缓冲区迁入一个保护掩码不同的新 wrap。
  • allow_guests() / prohibit_guests() —— 控制非拥有者进程能否映射该缓冲区。
  • empty() —— 释放被包装的缓冲区；正是它使被抢占缓冲区其后的映射失败。

头文件 system/memory/libwrapfd/rust/include/wrapfd.h 记录了 C 接口，以及 wrapfd_get_state() 上报的 WrapfdState 枚举（EMPTY、RDONLY、RDWR）。

53.6.2 分配、包装、加载

NpuAllocator 在其 JNI 层 （service/jni/com_android_server_npumanager_NpuAllocator.rs，crate 为 libnpumanager_service_jni）把 dma-buf 堆、libwrapfd 与缓冲区类型串起来。单个缓冲区的处理序列在 Java 侧名为 allocWrapLoad，步骤为：

  1. 依据每台设备各自的 DMA-buf 堆配置，按 (deviceNumber, bufferType) 选择一个 DMA-buf 堆 （nativeGetHeapName）。这让不同的 NPU 与缓冲区类型映射到不同的堆。
  2. 用 BufferAllocator::alloc() 在该堆上分配。为便于调试给缓冲区命名 （npubuf-<pid>-<appReqId>）。
  3. 用请求中的保护标志对该 dma-buf 调用 WrapfdDriver::wrap()。
  4. 若应用请求了文件段，则用 WrapfdOwnershipGuard 获取所有权，调用 wrapfd::load() 以 DMA 方式把权重复制进来， 然后释放所有权。
  5. 把 wrapfd（而非裸 dma-buf）返回给客户端，客户端经 onGetBuffer 收到它。

由于 wrapfd 在内核中携带保护状态，应用可以只读地映射权重；而管理器仍可撤销它们：发生抢占时，它会把该 wrap 置空。应用与服务无需信任彼此的用户态。

分配器在构造时探测驱动 （nativeInitWrapfdDriver()）。在没有 /dev/wrapfd 的设备上，分配器抛出 UnsupportedOperationException。管理器就是这样在不支持被包装缓冲区的硬件上优雅降级。

flowchart TB
    Get["getBuffers(request)"] --> Heap["nativeGetHeapName(deviceNumber, bufferType)"]
    Heap --> AllocBuf["在 /dev/dma_heap 上 BufferAllocator.alloc()"]
    AllocBuf --> WrapBuf["WrapfdDriver.wrap(dmabuf, protectionFlags)"]
    WrapBuf --> LoadQ{"是否设置了 fileSegmentToLoad？"}
    LoadQ -->|"是"| Own["WrapfdOwnershipGuard，随后 wrapfd::load()"]
    LoadQ -->|"否"| Reply
    Own --> Reply["onGetBuffer(appReqId, wrapfd)"]

53.7 动手试试

以下命令可在设备或模拟器上演练该模块。开始前，请确认构建标志 RELEASE_NPUMANAGER_MODULE 与 aconfig 标志 npumanager_enabled 都已开启。该服务以 npu 之名可访问。

  • 先确认服务出现在服务列表中，再确认 APEX 存在：

    adb shell service list | grep npu
adb shell ls /apex/com.android.npumanager

  • 用 info 子命令查看当前策略、请求与优先级表（该子命令由 NpuManagerServiceImpl.handleShellCommand 实现）：

    adb shell cmd npu info

  • 在运行期切换准入控制策略，然后重新查看 info：

    adb shell cmd npu set-turn-taking-policy
adb shell cmd npu set-budget-policy
adb shell cmd npu set-status-quo-policy

  • 临时停止服务向 HAL 推送优先级更新，随后重新开启。只有 root 可以这样做：

    adb root
adb shell cmd npu disable
adb shell cmd npu enable

  • 检查某设备是否通告 NPU HAL 与特性：

    adb shell dumpsys package | grep android.hardware.npu
adb shell pm list features | grep android.hardware.npu

  • 阅读冻结的 v1 HAL 接口，看清厂商必须实现什么：

    ls hardware/interfaces/npu/aidl/aidl_api/android.hardware.npu/1/

本章小结

  • Android 17 新增了 NPU 管理器，一个主线 APEX （com.android.npumanager），负责仲裁对端侧神经加速器的访问。它由两个标志把关：构建标志 RELEASE_NPUMANAGER_MODULE 与 aconfig 标志 npumanager_enabled。它自带模块 SDK （npumanager-module-sdk），外加 bootclasspath 与 systemserver 片段。
  • 应用使用 @SystemApi 的 NpuManager（Context.NPU_SERVICE）来询问某个模型是否可以加载， 而不是直接加载模型。异步协议答复 CAN_LOAD_NOW、WAIT_FOR_UNLOAD 或 NOT_PRIORITIZED，应用必须如实上报 notifyModelLoaded 与 notifyModelUnloaded。
  • 准入控制可插拔。StatusQuo 为默认且不做仲裁；Budget 允许在上限内按权重并发加载， 并按优先级驱逐模型；TurnTaking 即权重为 1、预算为 1 的预算策略，一次只允许一个模型。
  • PriorityManager 把 ActivityManager 的重要性映射到共享的 0-1000 优先级刻度（0 = 最高）， 把这些优先级下发给厂商 HAL，并阻断未声明 FEATURE_NEURAL_PROCESSING_UNIT 的 Android 17 应用。
  • 配套的 android.hardware.npu HAL v1（IScheduling 与 ISchedulingCallback）向下传递按 UID 的 SchedulingConfig 优先级，向上回传 WorkInfo 的起止回调（StartReason、EndReason）。它本身不执行推理。
  • 一个 Rust NDK（ANpuBuffer、ANpuManager_AllocRequest，位于 libcom.android.npumanager.so 之后）让原生运行时得以分配、映射、加载与 释放受保护的 NPU 缓冲区，并提供用于驱逐的抢占回调。
  • 建立在新 /dev/wrapfd 内核驱动之上的 libwrapfd 为这些缓冲区提供支撑。服务在 DMA-buf 堆上分配， 以保护掩码对 fd 调用 wrap()，可调用 load() 复制权重进来；发生抢占时，它可对 wrap 调用 empty()，使被撤销缓冲区的映射以 ENOENT 失败。

附录 D：Android 17 的更新

本附录汇总 Android 16（android-16.0.0_r4 标签）到 Android 17（android17-release 分支）之间的重要平台变化。内容来自对两个版本逐仓库的差异分析，并对照 Android 17 源码树核实过。重点是新项目、新代码模块与架构变更。对 external/* 依赖，本附录只讲它们如何被集成；例行缺陷修复与版本号升级则略过不提。若某项变更在 17 中仍受 flag 控制、或虽已搭好骨架但尚未成为默认，文中会明确指出这一状态。

D.1 如何阅读本附录

本附录按书的“篇”（子系统）组织，并遵循章节顺序。每一篇内部，变更按类别分组。

新项目指新的顶层仓库。新模块指既有仓库中新增的代码模块、APEX 或 HAL 包。架构变更是结构性重构。重要集成说明新出现的或外部的部件如何接入平台。

每一条论断都引用真实的 AOSP 路径；第 D.16 节的 关键源文件参考表按篇汇总最值得关注的若干文件。

D.2 内核与启动

Android 17 把 USB 配件处理独立成自己的顶层仓库；把基于快照的 OTA 转向用户空间块设备（UBLK）后端；并首次给出 android17-6.18 的 GKI 配置。init 第一阶段挂载路径也完成了把 Android 特有逻辑与 Microdroid 分离的工作。

新项目

system/usb（platform/system/usb） 是一个全新的顶层仓库，存放 USB 栈的用户空间组件。它的第一个住户是 aoad，一个用户空间守护进程，实现 Android 开放配件（AOA，Android Open Accessory） 协议——该协议历史上住在内核的 f_accessory USB function 驱动里。该仓库交付：

  • 一份 AIDL 契约 android.hardware.usb.aoa（system/usb/aoa/aidl/android/hardware/usb/aoa/IUsbAoa.aidl），暴露 openAccessory()、openAccessoryForInputStream/OutputStream()、getMaxPacketSize()、getAccessoryStrings()、getInitializationStatus() 与 isStartRequested()。UsbDeviceManager 之类的客户端会调用 getInitializationStatus() 以确认用户空间 AOA 路径健康。
  • 守护进程本身（system/usb/aoa/daemon/main.cpp），注册 aoad Binder 服务，另有 UsbAoaService.cpp、VendorControlRequestMonitor.cpp 与 AccessoryLegacyBridgeThread.cpp（按 system/usb/aoa/daemon/Android.bp 编入 libaoad_core）。

架构上的迁移是从内核 gadget function 走向 FunctionFS（FFS）+ 用户空间 模型。VendorControlRequestMonitor（system/usb/aoa/daemon/VendorControlRequestMonitor.h）打开 FFS 控制端点 ep0 并做 epoll 等待，完全在用户空间解码 AOA 厂商控制请求（ACCESSORY_GET_PROTOCOL=51、..._SEND_STRING=52、..._START=53、HID 请求 54..57、..._SET_AUDIO_MODE=58）。HID-over-AOA 被桥接到 /dev/uhid。该守护进程默认关闭，仅在显式启用后才启动。

架构变更

OTA 快照转向 UBLK 后端（system/core + system/update_engine）。 原先由 snapuserd 通过内核 dm-user 设备提供的 Virtual A/B 快照合并，现在可以跑在 UBLK（用户空间块驱动）之上。第一阶段 init 在启动时选择模式：system/core/init/first_stage_mount_android.cpp 调用 sm->UpdateUsesUblk()，随后调用 LaunchFirstStageSnapuserd(use_ublk) 并初始化 /dev/block/ublkb* / /dev/ublk* misc 设备。新增的 manifest 字段 disable_ublk（system/update_engine/update_metadata.proto:385-387）让 OEM 即便在已配置 UBLK 的设备上也能强制使用 dm-user。旧的 system snapuserd 代码路径与 ro.virtual_ab.userspace.snapshots.enabled 一类属性已从 snapuserd/第一阶段这一侧删除（system/core）；update_engine 的 payload_consumer/vabc_partition_writer.cc 仍在读取 ro.virtual_ab.userspace.snapshots.enabled。

update_engine 的 COW/压缩更新。 Android 17 为 REPLACE 操作新增 zstd 压缩（外加一个 zstd_extent_writer 单元测试），并提供禁用 REPLACE 压缩的 flag。它还移除 squashfs 支持与 retrofit 动态分区的逻辑，去掉 SnapshotMergeStats，并停止保存 manifest 字节、用完即释放 manifest 分区内存，以压低内存峰值。大补丁现在会写入文件并通过 fd 施加，而不再整块留在内存里。

第一阶段 init：Microdroid 与 Android 的分离。 第一阶段挂载逻辑经过重构，Android 特有的挂载不再编入 Microdroid（反之亦然）。system/core/init/first_stage_mount_android.cpp/.h 与 first_stage_mount_microdroid.cpp 现在与共享的 first_stage_mount.cpp 并列。FirstStageMount 虚基类被移除；第二阶段 init 也不再引入第一阶段的 mount/main。

其他 init/启动变更。 重做过的 boot monitor 落地，但本周期内“默认启用”又被回退了一次。启动分析新增 ro.boottime.event.* 属性与更丰富的 bootchart 采集（通过内核命令行做早期 bootcharting、完整命令行采集、从 /proc/cpuinfo 检测 CPU 型号）。init 现在在重启时把关机原因传给内核，并为长按电源键新增重启原因；它还挂载 securityfs，并去掉 TPM 已清除时的交互式 FDR 提示。ueventd 在 sysfs 属性规格中支持通配符匹配，并能在完整 APEX 集合就绪之前从 bootstrap APEX 中取固件。

ION 分配器移除（只剩 dma-buf heaps）。 BufferAllocator（system/memory/libdmabufheap/BufferAllocator.cpp）现在只从 /dev/dma_heap/* 分配。旧式 ION 路径（system/memory/libion）被削减为标记为废弃的空壳。于是 DMA-buf heaps 成为唯一的图形/媒体缓冲分配器。

构建期只读的 AOSP 源码树。 Soong 现在在沙箱构建期间以只读方式挂载检出。SandboxConfig.SrcDirMountFlag() 返回 -R（build/soong/ui/build/sandbox_config.go）。因此构建动作无法回写源码树，所有生成输出都被限制在 out/ 内。

Memory Limiter 系统服务。 新增的 MemoryLimiter 服务（frameworks/base/services/core/java/com/android/server/am/MemoryLimiter.java、JNI com_android_server_am_MemoryLimiter.cpp、flag memory_limiter_enable）对应用 UID 施加 cgroup-v2 的逐进程限额。它在 memory.high 处软限流，并杀死 anon+swap 合计持续超出预算的进程。它与系统级的 mmd swap 守护进程、以及面向厂商进程的 pmgd（见 D.7）互为补充。

重要集成

  • GKI 内核：首批 android17-6.18 配置。 kernel/configs 新增 android17-6.18 分支，目标是 Linux 6.18 GKI 内核。它还裁掉了 Android R 的配置，刷新了 OGKI 批准构建清单与 kernel-lifetimes.xml。
  • init/fastboot/recovery 共用 OTA 头文件。 libupdate_engine_headers 被导出，使 init、fastboot 与 recovery 的 libinstall 都能找到 file_descriptor.h（system/core 与 bootable/recovery）。这收紧了 OTA 引擎与给它输送数据的启动/recovery 工具之间的耦合。
  • Recovery（bootable/recovery）。 接入 F2FS 的 packed_ssa 支持、MISC_KCMDLINE 中的 binder=c 位，以及可配置的 recovery_ui 图形超时。

D.3 原生基础层

Android 17 的原生层由两条主线主导。其一是显著扩大的 AIDL HAL 面（hardware/interfaces 中 820 个提交、一份新的框架兼容性矩阵、若干新的设备契约）。其二是动态二进制翻译器 berberis 的结构性成熟（439 个提交）：它从“x86_64 上跑 riscv64”长成一个多客户机引擎，并把 arm64 搭好了骨架。bionic 与 libcore 补足了这一图景：页大小/内存标记方面的加固，以及一次指向 jdk-25 的 OpenJDK 升级。

新项目

本篇没有全新的仓库进入。值得注意的新增是 hardware/interfaces 内的新HAL 包，以及 berberis 内的新子目录（分别在“新模块”与“架构变更”中讲述）。

新模块

hardware/interfaces 中新增了一批 AIDL HAL 契约，并在 Android 17 的框架兼容性矩阵 compatibility_matrices/compatibility_matrix.202704.xml（FCM level="202704"）中声明：

  • Motion Context HAL — hardware/interfaces/motioncontext/aidl/android/hardware/motioncontext/ 定义 IMotionContext、IMotionContextClient、IMotionContextCallback，以及 MotionState、MotionEvent、MotionSubscription、EventDeliveryReason：向框架客户端提供基于订阅的设备运动状态流。
  • NPU HAL — hardware/interfaces/npu/aidl/android/hardware/npu/ 新增 IScheduling 与 ISchedulingCallback，以及 SchedulingConfig、WorkInfo、StartReason、EndReason、Uuid。按 npu/README.md，第一版让 Android 能把应用优先级（0-1000，0 为最重要）告知神经处理单元，也能在其工作开始/结束时收到回调。
  • libwrapfd（system/memory/libwrapfd） —— 一个新的 Rust/LLNDK 库（rust/lib.rs、cc_library_shared libwrapfd），under 一个新的 /dev/wrapfd 内核驱动。它包装一个既有 fd 并控制它可被怎样 mmap。wrapfd_driver_wrap() 钉住一个 PROT_READ/PROT_WRITE/PROT_NONE 掩码，另有若干 ioctl 用于查询状态与获取/释放所有权。它对 com.android.npumanager 为 apex_available，为 NPU 缓冲保护提供支撑。
  • 安全执行环境（SEE，Secure Execution Environment）家族 —— 一棵很大的新 hardware/interfaces/security/see/ 树，全部在 202704 矩阵中声明：
    • security/see/hwcrypto/aidl/.../hwcrypto/ —— IHwCryptoOperations、IOpaqueKey、ICryptoOperationContext（及 CryptoOperation、CryptoOperationSet、KeyPolicy、MemoryBufferParameter）：一个 TEE 侧、使用不透明密钥句柄的加密操作面。
    • security/see/storage/aidl/.../storage/ —— ISecureStorage、IStorageSession、IDir、IFile（及 CreationMode、Integrity、Availability、Filesystem、OpenOptions）：一份可检测篡改、防回滚的安全文件系统契约。
    • security/see/devicestate/.../IDeviceState、security/see/authmgr/，以及 security/see/ext/.../ITrustedHalExt.aidl —— 一个让可信 HAL 可从 SEE 侧到达的扩展点。
  • 既有 HAL 的版本升级：health AIDL V5（电池厂商/型号/设计最低电压）与 Weaver V3。蓝牙音频 V6 新增 LE Audio 外设/广播接收端、over HDT phy 的 LE Audio，以及 ISO 参数更新。其他变更包括 Channel Sounding 增补（UpdateChannelSoundingConfig、GetVelocity）、Wi-Fi Proximity Ranging、USB 的 PortPartnerStatus/Bc12Type，以及一个新的“timestamp HAL”。

berberis 新增一个 cpu_emulation/ 伞状模块（见下），并把 riscv64 翻译器拆成自己的库（translator_riscv64、runtime_library）。

架构变更

berberis：从 riscv64 翻译器到多客户机、多层引擎。 Android 16 的树实际上只做 x86_64 上的 riscv64。到 17，引擎重组到 frameworks/libs/binary_translation/cpu_emulation/ 之下，汇聚三个执行层与共享基础设施：

  • cpu_emulation/interpreter/ —— 第一层解释器（riscv64）。
  • cpu_emulation/lite_translator/ —— 快速、低优化的 JIT（lite_translator/riscv64_to_x86_64）。
  • cpu_emulation/heavy_optimizer/ —— 优化型 JIT（heavy_optimizer/riscv64），17 周期的重点。全局客户机上下文优化已实现并默认启用；该层还新增了针对不可归约循环的 LoopGuestContextOptimizer，以及 LocalGuestContextOptimizer 中的寄存器生命周期工作。
  • 共享支撑：cpu_emulation/{decoder,assembler,backend/x86_64,code_gen_lib,intrinsics}/。

arm64 客户机现在已在整棵树中搭好骨架。新架构目录出现在 runtime/arm64/ 与 runtime/arm64_to_x86_64/、guest_loader/arm64/、guest_state/arm64/（含 get_cpu_state.cc）、guest_abi/arm64/、guest_os_primitives/arm64/、kernel_api/arm64/，另有 cpu_emulation/insn_tests/arm64/ 与 intrinsic 映射目录（intrinsics/riscv64_to_arm64/、code_gen_lib/arm64_to_x86_64/、arm64_to_all/）。所以，尽管 README.md 仍只宣传 x86_64 上的 riscv64，17 的代码已把这些抽象泛化，以承载不止一种客户机 ISA。同周期的运行时加固把翻译宿主栈提升到 1 MB 并带保护页，同时新增 clone3 系统调用模拟。

AIDL 工具链。 system/tools/aidl（78 个提交）新增接口注解 @VersionSupport(version=N)，注册在 system/tools/aidl/aidl_language.cpp（AidlAnnotation::Type::VERSION_SUPPORT），并由 aidl_language.h:372 中的 AidlInterface::VersionSpecificCheckValid() 与 GetVersionSupportVersion() 执行。该注解把一个声明的版本钉在接口的实际版本上。Rust 后端新增 no_std 变体，Soong 规则逐步沙箱化，生成代码中的 C++ tracing 现在默认关闭。

VINTF。 system/libvintf 很安静（8 个提交，无契约变更）。不过兼容性面借新的 compatibility_matrix.202704.xml FCM 以及为下一“甜点”版本预留的占位值而向前推进。

重要集成

  • bionic 的内存/页大小加固。 16 KB 页大小的迁移继续推进：带来一个带填充的 ELF 测试库、16 KB 向后兼容模式的保护页（先加后撤），以及 RWX_MiddlePageProtection 的回归覆盖。动态链接器在 linker 二进制中重新启用只执行内存（XOM），补齐缺失的 BTI 指令/ELF 注解。它还细化了 MTE 处理：只对可读段调用 get_tagged_address。字符串例程转向可移植 SIMD（来自 psimd 的 strlen.cpp，rustlib 的 x86_64 strlen 换成 psimd），另加优化的 wmemset/wmemcpy/memccpy。
  • libcore 的 OpenJDK 升级。 libcore（205 个提交）较大范围地从 jdk-25.0.1-ga 与 jdk-25+26 导入。导入面包括 java.util.concurrent（及 .locks、.atomic）、java.time.chrono、Character、ClassValue、Collections，以及 Invokers/NamedParameterSpec。libcore 还导入了 OpenJDK 21 新增的 3 个 String API 方法。libcore-openjdk-analyzer 工具中新增了 OpenJDK 25 条目。这标志着类库正朝 JDK 25 前进。

D.4 原生服务与媒体

Android 17 的原生服务与媒体层在几个方向上推进。SurfaceFlinger 获得**进程外渲染（OOPR，out-of-process rendering）**的骨架——OOPR 是一条共享内存渲染命令通道，让客户端录制绘制命令，而不是推送已画好的缓冲。SurfaceFlinger 还获得重做过的多显示模式设置路径；libbinder 长出一条通用 netlink 诊断通道。

媒体侧，codec2 为 media APEX 拆出一份稳定的 NDK 编解码器面（libapexcodecs）。相机服务新增多客户端共享会话模式。照片选择器新增搜索与分类网格。

新模块

  • libapexcodecs —— 面向 media APEX 的稳定 C2 编解码器 NDK。 frameworks/av/media/module/libapexcodecs/include/apex/ApexCodecs.h 定义一套 C ABI（ApexCodec_ComponentStore、ApexCodec_Component、ApexCodec_Buffer，以及 ApexCodec_Component_create/start/flush/reset/process，全部带 __INTRODUCED_IN(36)）。这套 ABI 让可更新的 media（swcodec）APEX 能跨 APEX 边界暴露 Codec2 软件组件。17 周期把真实解码器接了上去（C2ApexAacDec、C2ApexOpusDec），Codec2Client 也学会枚举并排序基于 ApexCodecs 的组件。
  • 供 OOPR 使用的 libgui 无锁 IPC 原语。 frameworks/native/libs/gui/include/gui/ 下一簇新头文件支撑下文那条渲染命令通道：RenderCommandBuffer{,Producer,Consumer}.h，加上无锁构建块 MagicRingBuffer.h、LocklessStaticQueue.h、LocklessTripleBuffer.h、LocklessQueue.h 与 RPointer.h（用于共享内存的相对指针）。

架构变更

SurfaceFlinger 的进程外渲染（OOPR）。 这是本周期 SF 最大的主题。客户端不再渲染进 GraphicBuffer 并把它入队，而是把 Skia 绘制操作录进一块由 ashmem 支撑的 RenderCommandBuffer，由 SurfaceFlinger 在合成时回放。

RenderCommandBufferProducer（frameworks/native/libs/gui/include/gui/RenderCommandBufferProducer.h）持有 ashmem 的 IpcRenderRegion，暴露 startRecording()/finishRecordingAndPostFrame()，并通过 SurfaceComposerClient::Transaction 上新增的 setter 挂到某个图层。批量上传走无锁的 MagicRingBuffer。SF 侧的支持包括 RenderResourceCache（frameworks/native/services/surfaceflinger/RenderResourceCache.{h,cpp}）、合成着色器、端到端贯通的 frameId 用于同步，以及 OOPR 感知的统计。该路径位于一个 aconfig flag 之后；在 17 中它是基础设施，还不是默认渲染路径。

D.5 运行时

Android 17 重塑了托管运行时的最底层。最抢眼的是把 Zygote 用 Rust 从头重写为一个新的顶层项目；Android 17 还在 ART 中新增一个 x86 微架构目标。挂在 APEX 上的运行时面继续收缩。

新项目

system/zygote（Native Zygote / zygote_next）。 Android 17 引入一个全新的顶层仓库，用 Rust 实现 Zygote 进程服务器。它构建 zygote_next 守护进程（system/zygote/zygote/src/bin/zygote.rs），并拆成若干职责单一的 crate（system/zygote/Android.bp，edition: "2024"）：

  • zygote-sys 把裸系统调用（fork、clone3、epoll_wait、setresuid/setresgid、prctl）与 /proc 内省封在安全的 Rust 之后（system/zygote/zygote-sys/src/）。
  • zygote-messages 用 FlatBuffers schema（system/zygote/zygote-messages/schemas/messages.fbs）定义 system_server ↔ Zygote 的 IPC，并用 zygote-proc-macros 的派生宏做编组。
  • zygote-core 集中日志/tracing 的初始化，并挂进 atrace。
  • zygote 持有 Server 事件循环与 Species 抽象。

frameworks/base 中经典的 ZygoteInit Java 路径仍然存在；zygote_next 是平台正迁移过去的原生继任者。它在启动时打出一条 NativeZygoteStarted statsd atom，以 nice -20 运行，并用 ASYNC MTE 构建（system/zygote/zygote/Android.bp 中的 Soong sanitize: { memtag_heap: true }）。

架构变更

Species / subspecies 进程模型。 zygote_next 不再沿用旧的“fork 后特化”流程，而是把每个预加载并孵化环境建模为一个 Species（system/zygote/zygote/src/species.rs）。Species trait（第 82-181 行）是一张回调 vtable（gather_reinitialization_data、speciate、gestate、set_seccomp_filters、sync_fd_state、文件/socket 允许清单检查）。静态注册了三个实现：AndroidNative（.../species/android_native.rs）、LibApp，以及测试用的 Mock “Turtle”。

一项关键的新能力是 subspecies。schema 定义了 SpawnSubspecies 与 SpawnSubspeciesAndroidNative 载荷（messages.fbs 第 31-43、87-93 行）。服务器可以按需孵化一个原生子 Zygote，让它把自己重新初始化为 subspecies（speciate() 在 re_initialize_as_subspecies() 之前运行）。这把旧的“子 zygote”想法泛化为一条一等公民的、按载荷触发的孵化命令。该命令携带自己的库路径、ABI 列表、预加载函数与 UID/GID 范围。

FD 继承现在由每个 species 中显式、带日期的允许清单掌管（android_native.rs 第 41-77 行）。每个 AllowListEntry 记录审阅者与审阅日期。有一个单元测试（species.rs 的 allow_list_audit）会在条目过期（> 365 天）时让构建失败。传输层也从手写循环换成了 epoll，对 SIGCHLD 做合并处理，子进程退出状态则经非请求的 Zygote socket 转发给 ActivityManager。

ART：pantherlake x86 目标。 ART 把 Intel Panther Lake 加为可识别的 x86 / x86-64 指令集变体（art/runtime/arch/x86/instruction_set_features_x86.cc 第 43-115 行）。Panther Lake 是 Intel 的客户端（消费/移动）CPU 世代，比 ART 已知的 Kaby Lake / Alder Lake 更新。

与其他 Intel 客户端芯片一样，它提供 AVX/AVX2 但不提供仅限服务器的 AVX-512。因此该变体按 SSSE3、SSE4.1/4.2、POPCNT 与 AVX/AVX2 注册（特性串 ssse3,sse4.1,sse4.2,avx,avx2,popcnt，位图 63），与 alderlake/kabylake 处于同一 AVX2 档。X86FeaturesFromPantherlakeVariant 单元测试在 32 位与 64 位下都验证了它。有了这个具名变体，在模拟器及 x86 形态等 x86-64 Android 目标上，dex2oat 就能为这些 CPU 生成 256 位 AVX2 向量化代码。

DEX 容器格式 V41。 运行时把 DEX 版本 41 视为容器格式（art/libdexfile/dex/dex_file.h 第 112 行，kDexContainerVersion = 41；第 181 行的 HeaderV41）。V41 文件携带容器偏移/大小，使多个逻辑 DEX 文件共享同一块后备缓冲。profile 机制已针对仅 V41 的位置语法更新。HasDexContainer() / ContainerSize()（第 165-174 行）是这一新行为的关口。

值类与 record 类。 mirror::Class 新增一等的 IsValueClass()/SetValueClass() 与 IsRecordClass()/SetRecordClass() 访问器（art/runtime/mirror/class.h 第 341-357 行），背后是新的 mirror::Class flag（kClassFlagValue/kClassFlagRecord）。这是 Valhalla 式值类的地基；record 现在被当作携带 record 标记的普通类处理。

GC 调优。 收集器在并发复制 GC 下重新启用基于 MADV_FREE 的积极页释放，回退了此前一次临时禁用（art/runtime/gc/collector/garbage_collector.cc 约第 465 行）。GC 旋钮现在通过 ArtDeviceStatus pulled atom 上报，供机群级遥测使用。

分代标记压缩（CMC）GC。 标记压缩收集器在 use_generational_cmc aconfig flag（art/build/flags/art-flags.aconfig，art_performance 命名空间）之后新增分代模式，运行时由 ShouldUseGenerationalGC()（art/runtime/gc/collector/mark_compact.cc）把关。一次 minor GC 只追踪并压缩最近分配的对象而非整个堆，并按年龄晋升存活对象。

SDK 37 起 static final 字段不再可反射改写。 对目标为 SDK 37 的应用，ArtField::IsUnmodifiable()（art/runtime/art_field-inl.h）对普通 static final 字段返回 true。于是反射（java_lang_reflect_Field.cc）与 JNI（jni_internal.cc）写入会抛出 IllegalAccessException，而不是悄悄改动常量。

SDK 37 的无锁 MessageQueue。 Android 17 新增一套并发 MessageQueue 重实现，由 release_package_messagequeue_implementation 这个 Soong 配置选择。默认的 CombinedMessageQueue（frameworks/base/core/java/android/os/CombinedMessageQueue/MessageQueue.java，即该配置的 conditions_default）在运行时从传统 synchronized 队列与 VarHandle-CAS 的 “DeliQueue” 之间选一个。它会对系统进程、以及受 USE_NEW_MESSAGEQUEUE 兼容性变更（@EnabledAfter(BAKLAVA)，SDK 37+）控制的应用切到无锁路径。

重要集成

APEX：收缩运行时挂载面。 apexd 继续把运行时组件移出 bootstrap APEX 集合。com.android.runtime APEX 现在在 bootstrap 清单中被 RELEASE_DEPRECATE_RUNTIME_APEX 挡住（system/apex/apexd/apexd.cpp 第 169-180 行）。flag 一旦置上，runtime APEX 就消失，其内容并入基础系统镜像。

EROFS 文件直挂（无需 loop 设备）。 一项重要的挂载变更让 apexd 直接从文件挂载 EROFS 格式的 APEX 载荷，完全跳过 loop 设备（system/apex/apexd/apexd.cpp 第 522-534 行）。启用文件直挂后，载荷以一个指向 APEX 内镜像的 fsoffset= 选项挂载。这由 erofs_file_backed_mount aconfig flag 与若干运行时属性控制（apexd_mount.cpp 第 38-120 行）。

配套的 microdroid_no_loop_device flag 让 Microdroid 用 dm-linear 而非 loop 设备激活块设备 APEX。随着 Mainline 模块集合不断增长，两者共同削减每个 APEX 的 loop 设备开销。apexd 还在 loop 设备上启用 Direct I/O，并在 tasklet 中对 APEX 载荷做 dm-verity 校验。

自定义通知视图的内存上限。 SystemUI 现在通过 NotificationCustomContentMemoryVerifier（frameworks/base/packages/SystemUI/src/com/android/systemui/statusbar/notification/row/NotificationCustomContentMemoryVerifier.kt）校验通知的自定义 RemoteViews 是否低于内存上限（config_notificationStripRemoteViewSizeBytes，约 5 MB）。对 SDK 37 应用，超限视图会被丢弃并撤掉通知，而不是仅在日志里留一条警告。

D.7 框架服务

Android 17 重组了若干与框架服务相邻的子系统。最醒目的是一个全新的原生内存守护进程（mmd），它从 system_server 接管 ZRAM 管理，并新增逐进程写回/预取。Permission/Privacy 模块长出代理活动面与 Private Compute Core（PCC）感知能力，UprobeStats 与 Profiling 则以预编译模块 SDK 形式交付。

新项目

system/memory/mmd（Modern Memory Daemon，现代内存守护进程）。 Android 17 引入 mmd，一个新的原生 Rust 守护进程（system/memory/mmd/README.md）。它集中管理内存配置与 ZRAM 可调参数，把原先散落在 swapon_all、config.xml overlay 与 ro.zram.* 属性中的东西统一起来，同时把 swap 管理从 system_server 里剥离。

它注册名为 mmd 的 Binder 服务（system/memory/mmd/src/main.rs:203-205），暴露 IMmd AIDL 接口（system/memory/mmd/aidl/android/os/IMmd.aidl）。专设的 mmd_setup 服务（system/memory/mmd/src/mmd_setup.rs）由 init 启动，负责首次开机时的 ZRAM 激活。当 mmd.zram.enabled 置位时，swapon_all 内的 ZRAM 设置变为空操作，旧式 overlay 配置被忽略。

新模块

UprobeStats 预编译模块 SDK。 基于 uprobe 的追踪模块（把 BPF uprobe 挂到方法调用上，并把结果作为 statsd atom 发出）现在交付预编译模块 SDK：sdk { name: "uprobestats-module-sdk" }（packages/modules/UprobeStats/apex/Android.bp:87-88）。到 A17，其 Rust core crate 新增类型化的 UprobeStatsError，以及携带 MAP_PATH/PROG_PATH 常量的 Handler trait；还新增细粒度 BPF 挂载错误上报，以及 UprobeStatsBridgeServiceImpl 中的批量事件投递。新的 BPF 处理器覆盖无障碍与“干扰性应用”检测，另有能从寄存器解析原始调用参数的通用插桩。

Profiling 预编译模块 SDK + 异常检测器。 设备端 Profiling 模块同样交付 sdk { name: "profiling-module-sdk" }（packages/modules/Profiling/apex/Android.bp:103-104）。A17 新增 AnomalyDetectorService（.../anomaly-detector/service/java/com/android/os/profiling/anomaly/AnomalyDetectorService.java），受 anomaly_detector_core_c flag 控制，评估基于规则的信号（例如 BinderSpamAnomalyDetector）并触发 Perfetto trace。专设的 MemoryAnomalyRateLimiter 在请求到达 ProfilingService 之前对内存超限异常剖析做限流。

Web App（PWA）服务。 新的 com.android.webapp APEX 安装/管理渐进式 Web 应用，通过 AIDL 系统服务在 Context.WEB_APP_SERVICE（"web_app"）下发布 WebAppManager，由 enable_web_app_service_v2 控制（命名空间 lse_desktop_experience）（packages/modules/WebApp/framework/java/android/content/pm/webapp/WebAppManager.java）。

有线串口 API + 原生守护进程。 一套有线串口 API（Context.SERIAL_SERVICE，"serial"），与 USB 串口不同：frameworks/base/core/java/android/hardware/serial/ 中的 SerialManager/SerialPort，由 SystemServer.java 中的 SerialManagerService 支撑。一个 Rust 守护进程在 enable_wired_serial_api flag 之后注册惰性 binder native_serial（frameworks/native/services/serialservice/rust/service.rs:53）。

进程内存守护进程（pmgd）。 原生 Rust 的逐进程守护进程。它监视每个目标进程的 cgroup-v2 memory.high 压力与 anon_limit_in_mb，在回收宽限期后杀死越界者，并把击杀遥测作为 statsd atom 发出（system/memory/guardian/README.md）。它以细粒度的逐进程执法补充 mmd。

新的 system_server 服务。 三个管理器加入 SystemServer.java，各带一个 Context.*_SERVICE 常量：MultisensoryService（音频-触觉，MULTISENSORY_MANAGER_SERVICE）、ContentRestrictionService（CONTENT_RESTRICTION_SERVICE）与 PccSandboxManagerService（Private Compute Core，PCC_SANDBOX_SERVICE）（frameworks/base/core/java/android/content/Context.java）。

架构变更

mmd 的 ZRAM 生命周期与逐进程写回/预取。 开机后，mmd_setup 激活 ZRAM 并以可选 swap 优先级调用 swapon。A17 新增显式的 swap 优先级与多设备支持（mmd.zram.num_devices，以及逐设备属性）。优先级通过 SWAP_FLAG_PREFER 打入 swap flags（system/memory/mmd/src/zram/setup.rs:40-73）。ZRAM 维护（空闲写回、重压缩）不再由 system_server 自己的逻辑驱动；system_server 通过 Binder 发 doZramMaintenanceAsync() 提示，由 mmd 施加自己的策略。

真正新的低内存路径是 逐进程 的 ZRAM 操作。IMmd 新增 supportsProcessMemoryZramOps()、asyncWritebackProcessZramMemory(pidfd, callback) 与 asyncPrefetchProcessZramMemory(pidfd)（system/memory/mmd/aidl/android/os/IMmd.aidl:51-80）。写回按 pidfd 锁定单一进程，把其驻留 ZRAM 的页推到后备设备，并通过 IMmdProcessWritebackCallback 回报 WritebackStatus 与已写字节数。预取是其反面：在一份被缓存的应用恢复之前，把它已写回的页拉回压缩池。这些走新的 zram 内核 ioctl（ZRAM_ANDROID_IOC_PROCESS_WRITEBACK_CMD、..._PREFETCH_CMD），封装在 system/memory/mmd/src/zram/per_process_ioctls.rs 中。

内部上，MmdService 跑两级工作队列（system/memory/mmd/src/service.rs:68-146）：预取进高优先级的 prefetch_work 双端队列，写回与周期维护进低优先级的 other_work。对某 pid 的预取请求会取消该进程仍在等待的写回（用 pidfds_likely_equals 匹配）。于是恢复过程不会与一次正要驱逐“待预取页”的写回相互竞争。

D.8 连接性

Android 17 的连接性面被一个横切主题主导：通用测距（generic ranging）。新的系统服务把 UWB、蓝牙 Channel Sounding、Wi-Fi RTT 与 BLE RSSI 统一在单一 RangingManager API 之下；蓝牙、Wi-Fi 与 UWB 的控制器级栈都长出喂给它的原语。与测距并列，Wi-Fi 新增不同步服务发现（USD）服务，NFC 新增用于 tap-to-X 的手势交换 API，电话侧继续铺开卫星/NTN 支持。

集成式 VoIP 通话记录。 自管理 VoIP 应用可以写进共享的系统通话记录（CallLog.Calls，新增 UUID 列），由 telecom_integrated_call_log 系列 flag 控制。CallAttributes.setLogExcluded()/setContactUri()（frameworks/base/telecomm/framework/java/android/telecom/CallAttributes.java）按通话控制是否纳入。拨号器通过 INCLUDE_VOIP_CALLS_PARAM_KEY 查询 VoIP 通话。

OTT 通话自动路由到优质切片。 当一笔事务性自管理 VoIP 通话开始时，系统代表应用请求一个优质 5G 切片，经 NET_CAPABILITY_PRIORITIZE_UNIFIED_COMMUNICATIONS（值 38，packages/modules/Connectivity/framework/src/android/net/NetworkCapabilities.java）。ConnectivityService 把请求映射到调制解调器的 URSP 规则上。应用可通过 PhoneAccount.CAPABILITY_OPT_OUT_OF_PREMIUM_NETWORK 退出。

SIM 工具箱应用（Stk）。 随包的 SIM Toolkit UI（packages/apps/Stk，包名 com.android.stk）跑在 phone 进程内，渲染主动式 SIM 命令。CatService 把 CAT_CMD_ACTION（受 RECEIVE_STK_COMMANDS 保护）广播给 StkAppService。该服务按 CommandType 分支并拉起对应的 activity（StkDialogActivity、StkMenuActivity、StkInputActivity、tone 播放器）。

D.9 安全

Android 17 围绕两条主线重塑硬件支撑的安全栈。第一条把安全服务（KeyMint、SecureClock、SharedSecret、RKP、Gatekeeper）搬进受保护虚拟机。第二条引入通用的进程内沙箱原语（LFI），让不可信原生代码能在可信进程内运行。几个新仓库随之出现：一个专门的 Weaver 实现、SEE AuthMgr，以及一个树外的密钥证明校验库。

新项目

system/lfi —— 轻量级故障隔离（LFI，Lightweight Fault Isolation）运行时支撑。 新仓库，存放编译并加载 LFI 沙箱库所需的共享胶水。按 system/lfi/README.md，它包含三部分。boxrt 提供链入沙箱库的运行时桩，例如 boxrt/boxrt_minimal.c 中以裸 svc 系统调用实现的 abort/brk/pause。allocator 是线程安全的自旋锁极简分配器（allocator/alloc.c）。relocator 是为 lfi-bind 做重定位的极简 -static-pie 加载器（relocator/relocate.c + start.S）。

LFI 源自斯坦福/LLVM 的软件故障隔离方案。它不靠独立地址空间，而是通过经过验证的机器码把库的内存访问与控制流限制在沙箱区域内。system/lfi/Android.bp 定义 cc_defaults system_lfi_defaults（lfi_supported: true、nocrt、stl: "none"、静态链接 libc_lfi/libm_lfi、仅 arm64、apex_available: ["com.android.media.swcodec"]）。首个生产消费者是 swcodec APEX。

system/weaver —— Weaver 防回滚密钥存储 TA。 新 Rust workspace（Cargo.toml 成员为 ta、wire），实现由安全环境可信应用支撑的 IWeaver HAL。Weaver 按槽位存储键/值密钥，用于凭据尝试限流。每个 Slot（ta/src/lib.rs）持有 slot_key、slot_value、last_checked_timestamp 与 failure_counter。TA 返回 Error::IncorrectKey(ms) / Error::Throttle(ms)，以施加能在重启后存活的硬件支撑重试退避。

HAL 服务（hal/src/lib.rs）是薄薄的 IWeaver binder 外壳：把请求编成 CBOR，经 SerializedChannel 序列化送到 TA，复用共享的 system/security/hals/* channel 与 wire crate。

system/see/authmgr —— 安全执行环境（SEE）认证管理器。 Rust crate 分为前端（authmgr-fe）、后端（authmgr-be、authmgr-be-impl、authmgr-be-storage-impl）、authmgr-common，外加 secure-storage-aidl-wrapper。AuthMgr 实现 hardware/interfaces/security/see/authmgr/IAuthMgrAuthorization.aidl（在 authmgr-fe/src/authorization.rs 中被引用）。它用 DICE 证书链与策略，把受保护虚拟机（pVM）认证到安全侧可信应用。AuthMgrFe::authenticate 提交 ExplicitKeyDiceCertChain + SignedConnectionRequest；后端按 instance-id 与 DICE 模式去重实例，并实施回滚保护。

42 个提交为每个 instance id 增加两种 DICE 链模式、DICE 策略的覆盖点，以及安全存储的暂存/提交与 read_file/write_file API。

新模块

external/lfi/* —— LFI 工具链（外部，仅集成）。 上游组件被 vendor 进来支撑进程内沙箱，包括 lfi-verifier（校验 ELF 只发出沙箱安全指令）与 lfi-runtime（liblfi：保留/映射沙箱地址空间、进出控制转移、模拟宿主调用）。其余为 lfi-bind（Go 跳板生成器）、rlbox/rlbox-lfi（带 LFI 后端的 RLBox API），以及供校验器使用的 disarm/fadec（AArch64/x86 解码器）。

只集成、不修改。构建把 liblfi 与沙箱化的 libopus_lfi 链入 frameworks/av/media/module/libapexcodecs。当 android.media.codec.in_process_sw_codec_lfi 置位时，Codec2 走进程内路径（frameworks/av/media/codec2/hal/client/client.cpp:1909,2034）。于是不可信的软件解码器在 codec 进程内运行，内存安全由经过验证的代码保证，而不是靠独立进程。

external/keyattestation —— Android 密钥证明校验器（外部，仅集成）。 Kotlin 库（Android.bp 构建 java_library "keyattestation"，对 //frameworks/base/core/java 与厂商可见），校验由 KeyMint/RKP 产出的密钥证明证书链。其 Verifier 接受信任锚、吊销序列号与时间源，返回 VerificationResult，暴露被证明的公钥、安全等级、验证启动状态与设备信息。它支持可插拔的 ChallengeChecker，自带根证书集（roots.json、keyattestation_roots filegroup），镜像自 github.com/android/keyattestation。

架构变更

KeyMint 及其同伴搬进受保护虚拟机（keymint-in-vm）。 本周期最大的 sepolicy 主题（system/sepolicy，452 个提交）是把硬件安全 HAL 从虚拟机内部暴露出来。新的 accessor 服务支持被定义，为 IRemotelyProvisionedComponent、ISecureClock、ISharedSecret、IProvisioning 增加 accessor 权限，并（单独地）为 IGatekeeper 增加 gatekeeper-in-vm。service_contexts 新增 ISharedSecret/security_vm 与一个 KeyMint provisioning 服务上下文。

效果是 KeyMint、RKP、SecureClock、SharedSecret 与 Gatekeeper 都可以跑在 security_vm（Microdroid/pVM）中，平台经 accessor 服务抵达它们，而不是宿主上的厂商 HIDL/AIDL HAL。这正是 AuthMgr 的 pVM 认证所支撑的格局。

KeyMint 参考 TA 获得 ML-DSA（后量子）密钥。 system/keymint（63 个提交）为 Rust 参考 TA 增加 ML-DSA 签名支持，含 ML-DSA-87 与 PKCS#8 种子导入。Keystore2 跟进：system/security/keystore2/src/key_parameter.rs 与 security_level.rs 处理 ML-DSA，指标记录 ML-DSA 变体，Algorithm.aidl 增加对应枚举。

KeyMint 还重做了证明。证明 ID 从 KeyParam 列表中解析出来；Cow 字符串持有应用证明 id 与编码后的信任根。HAL v5 / AIDL >= 500 中移除了销毁证明 ID 的路径。时间戳接口并入 KeyMint HAL（hal_timestamp_service 从 hal_keymint 移除）。

重要集成

ANGLE 作为默认 GLES 驱动。 Android 17 在每个基础系统镜像中都带上 ANGLE（GLES-over-Vulkan）驱动：base_system.mk 无条件把 libEGL_angle、libGLESv1_CM_angle 与 libGLESv2_angle 加入 PRODUCT_PACKAGES（build/make/target/product/base_system.mk:493）。

壁纸/主题化 UI 中的 Theme Service。 WallpaperPicker2 现在经平台 Theme Service 施加颜色 overlay，由框架 flag android.server.Flags.enableThemeService 控制（packages/apps/WallpaperPicker2/src/com/android/wallpaper/config/BaseFlags.kt，isThemeServiceEnabled()）。同一批工作还包括壁纸轮播的桌面形态适配，以及主屏的命名自定义图标主题。

D.12 AI 与设备

Android 17 把设备端 AI 更深地推入平台。新的 NPU Manager mainline 模块仲裁对神经加速器的访问；新的 PersonalContext 系统应用构建设备端个人上下文面；Khronos OpenXR SDK 头文件首次被 vendor 进来，同时出现受 flag 控制的 Android XR API 面（覆盖头显与 MicroXR 眼镜）；CHRE 长出面向常开感知的高吞吐数据流子系统。

新项目

packages/modules/NpuManager 是一个新发布的 APEX（com.android.npumanager，min_sdk_version: 36），17 中交付自己的模块 SDK（apex/Android.bp 定义 npumanager-module-sdk）。它由 RELEASE_NPUMANAGER_MODULE 发布 flag 与 npumanager_enabled aconfig flag 控制（machine_learning 命名空间，flags/npumanager_flags.aconfig）。它同时贡献一个 bootclasspath 片段（framework-npumanager）与一个 systemserver 片段（service-npumanager）。细节见下文“新模块”。

packages/apps/PersonalContext（com.android.personalcontext）是一个新的特权、平台签名、product_specific 系统应用（Android.bp 的 PersonalContext_defaults：privileged: true、certificate: "platform"），构建一层设备端个人上下文，喂给助手类表面。其 AndroidManifest.xml 声明 ContextUnderstanderService 实现（src/com/android/personalcontext/understander/ 下的 ChatUnderstanderService、NotificationUnderstanderService、ContextMenuUnderstanderService），绑定在 android.service.personalcontext.UnderstanderService 下，由 BIND_CONTEXT_COMPONENT_SERVICE 保护。

它的工作组件打上 android:privateComputeCore 标记，应用持有新的 PERSONAL_CONTEXT_* 权限（PUBLISH_INSIGHTS、READ_SETTINGS、RECEIVE_HINTS）与 USE_ON_DEVICE_INTELLIGENCE。于是它跑在 Private Compute Core 沙箱内，与设备端模型对话而非走网络。源码子包（memorygeneration/、magicrecall/、magicactions/、appfunctions/、aicore/、AppSearch 支撑的 storage/appsearch/）指向一个个人记忆库，由它驱动回忆与“魔法操作”建议。该特性由 enable_osi aconfig 总开关控制（personal_context 命名空间）。

新模块

NpuManager 在相互竞争的应用之间复用设备端神经加速器。框架面是 @SystemApi、@FlaggedApi 控制的 NpuManager 类（Context.NPU_SERVICE），位于 framework/java/android/npumanager/NpuManager.java。应用拿不到裸的 NPU 访问权，而是申请加载模型的许可，由服务在适合时予以答复。binder 契约（framework/java/android/npumanager/INpuManagerService.aidl）就是准入控制加内存管理：

  • canLoadModel、cancelModelLoad、notifyModelLoaded、notifyModelUnloaded、setPolicy
  • createAllocator(INpuAllocatorCallback)，返回一个 INpuAllocator。

system_server 侧（service/java/com/android/server/npumanager/，NpuManagerService / NpuManagerServiceImpl）在抽象类 NpuModelLoadingPolicy 之后实现可插拔的模型加载策略：BudgetModelLoadingPolicy（按 KEY_MAX_BUDGET 与粗粒度 NpuModelSize 分桶 <1GB / 1-2GB / >2GB 做内存预算仲裁）、TurnTakingModelLoadingPolicy 与 StatusQuoModelLoadingPolicy。三者共用 PriorityManager。原生缓冲管理基于 Rust（service/jni/lib.rs、ndk/*.rs），并暴露 C NDK 面（ndk/include/android/npumanager/buffer.h），其中 ANpuBuffer 的优先级范围为 0-1000。

该模块配有一个新的厂商 HAL android.hardware.npu（hardware/interfaces/npu/，AIDL v1）。NpuManager 经此 HAL 把按应用的优先级告知 NPU，并接收工作回调（IScheduling、ISchedulingCallback、WorkInfo、StartReason、EndReason、SchedulingConfig）。

架构变更

CHRE（system/chre，536 个提交）新增 数据流（data-flow） 子系统，用于单一源与多接收端（nanoapp 及其他端点）之间的高吞吐流式传输。它用共享内存区域把拷贝降到最低。公开 API 是 chre_api/include/chre_api/chre/data_flow.h（事件 CHRE_EVENT_DATA_FLOW_CREATED、_SINK_CREATED、_ALERT、_SINK_CONFIGURE_DONE；调用如 chreDataFlowSinkEnable()）。

packages/modules/OnDevicePersonalization 在 17 中被重新打包/迁移，仍保留其 Private Compute 模型：框架 + 系统服务（framework/、systemservice/）、pluginlib/ 沙箱，以及一个 federatedcompute/ 子树用于联邦学习/分析，使个性化信号留在设备端。

重要集成

Android XR：仅有 API 骨架。 external/openxr-sdk（Khronos OpenXR SDK，release-1.1.50）被新 vendor 进来、只读。其 Android.bp 在 include/ 之上只构建一个 cc_library_headers { name: "openxr_headers" }。这些就是 OpenXR 头文件，没有加载器，也没有树内消费者。frameworks/base/core/api/current.txt 中对应的框架面同样处于惰性状态。

它包含 FEATURE_XR_API_OPENXR（“android.software.xr.api.openxr”）与 FEATURE_XR_API_SPATIAL，以及 FEATURE_XR_INPUT_* 系列字符串（手柄、眼动追踪、手部追踪）；还包含 XrWindowProperties 及其全空间与主空间的 activity 启动模式，以及 DisplayManager.DISPLAY_CATEGORY_XR_PROJECTED；进一步还有危险级的身体/环境追踪权限与 AppOps（EYE_TRACKING_COARSE/FINE、FACE_TRACKING、HAND_TRACKING、HEAD_TRACKING、SCENE_UNDERSTANDING_COARSE/FINE）。所有这些都由 android.xr.xr_manifest_entries aconfig flag 以 @FlaggedApi 控制（core/java/android/content/pm/xr.aconfig）。该 flag 默认关闭。

定位表述得很明确：运行时、合成器、OpenXR 加载器与场景/空间 SDK 都不在 AOSP 里，而由厂商运行时加树外的 Jetpack XR SDK 提供。上游唯一的 XR 行为代码是头显侧的录制器 statsd atom（frameworks/proto_logging/stats/atoms/xr/recorder/，XrRecorderSessionStatusReported）。

MicroXR：XR 眼镜外设类。 与头显面不同，轻量可穿戴 XR 眼镜走另一个 flag：com.android.microxr 的 xr_glasses_feature（frameworks/base/core/java/android/content/pm/glasses.aconfig，同样默认关闭）。它控制 FEATURE_XR_PERIPHERAL（android.hardware.type.xr_peripheral）——一个设备类标记，与 FEATURE_PC / FEATURE_WATCH 同级。PackageManager 的 javadoc 把 XR 外设定义为可穿戴、完整栈的 Android 设备，不能安装用户应用，很可能需要配套设备进行交互。

与那些惰性的头显特性不同，这个标记在树内确实被读取。WiFi（WifiGlobals）、蓝牙音频（Util.isXrDevice()）与 MediaProvider 都按 hasSystemFeature(FEATURE_XR_PERIPHERAL) 分支，把眼镜当作受约束的设备类处理。其眼镜遥测位于 frameworks/proto_logging/stats/atoms/microxr/（MicroXrDonDoffStateChanged 表示戴上/摘下状态，MicroXrPhotoCaptured / MicroXrVideoCaptured 区分按键触发与语音触发的拍摄，MicroXrMcuCrashOccurred 表示独立 MCU 崩溃）。AOSP 中不交付任何 MicroXR 模块、服务、HAL 或设备目标。

Health Connect（packages/modules/HealthFitness，689 个提交）主要是渐进性的 API/UX 工作：新的批量 grantHealthPermissions / revokeHealthPermissions API、从步数数据推导距离与卡路里、Changelogs API 中减少转换层；还包括跨设备“匹配”/设备数据提供者流程的继续铺设（service/.../onboarding/matchmaking/、apk/src/.../controller/matchmaking/、.../newDevices/DeviceDataProvider*）。

CompanionDeviceManager：设备信任与电源豁免处理器。 CDM 服务在 17 中新增两个处理器包，都在 frameworks/base/services/companion/java/com/android/server/companion/ 下。devicetrust/（TrustedDeviceProcessor、TrustedDeviceStore）用于可信设备密钥交换；powerexemption/（CompanionExemptionProcessor、CompanionExemptionStore）用于电源与自动撤销豁免。既有的 actionrequest/ 处理器（自 16 就在）新增了若干结果常量。AssociationRequest 中的 DEVICE_PROFILE_FITNESS_TRACKER / DEVICE_PROFILE_MEDICAL 关联档案（frameworks/base/core/java/android/companion/AssociationRequest.java，flag FLAG_BAND_DEVICE_PROFILE / FLAG_ENABLE_MEDICAL_PROFILE）在 Android 16 就已交付，因此不算 16 到 17 的新增。

Handoff（Task Continuity）：跨设备活动接续。 Android 17 在 CDM 传输之上新增面向用户的 Handoff 特性。activity 通过 Activity.setHandoffEnabled() 选择加入，并经 onHandoffActivityDataRequested()（frameworks/base/core/java/android/app/Activity.java:7789/10240）提供可恢复状态。该方法返回 HandoffActivityData，即一个 ComponentName 加点附加数据的 PersistableBundle，再加一个可选的 Web fallbackUri（HandoffActivityData.java:48）。

新的 TaskContinuityManager 系统服务（@SystemService(Context.TASK_CONTINUITY_SERVICE)）及其 RemoteTask 描述符，让启动器能呈现来自配对设备的任务。载荷以 MESSAGE_ONEWAY_TASK_CONTINUITY（CompanionDeviceManager.java:361）在两端真实、用户拥有的设备之间的安全 CDM 信道上传输。由 task_continuity aconfig flag（frameworks/base/core/java/android/companion/flags.aconfig:69，命名空间 companion）/ CompanionDeviceManager.FLAG_TASK_CONTINUITY 控制。见第 52 章 52.3.9-52.3.11 节。

D.13 基础设施

Android 17 的构建与虚拟化底层在两条战线上推进。Soong 构建系统长出一等公民的机器可读“API/合规”数据库，并继续从 Kati 时代的 Make 逻辑迁出。AVF（Android Virtualization Framework，Android 虚拟化框架）把受保护虚拟机做成多租户、支持 Trusty 的平台。新的顶层仓库 tools/mainline 携带开源的 mainline-train 构建工具。

新项目

tools/mainline（mainline-train 构建工具）。 Android 17 新增顶层仓库，用于装配 mainline“train”（作为整体交付的 APEX/APK 模块包）。其 train_build/ 目录是一组 Python 宿主二进制与库（tools/mainline/train_build/Android.bp），实现把逐模块产物变成已签名、带版本的 train：

  • trim_action.py 把打包的 APEX 裁剪到目标所需的架构，将模块 ABI 映射到 DCLA 架构集合（DCLA_ARCH_BY_MODULE_ARCH）。
  • dcla_build_action.py 构建共享的“DCLA”库 APEX（com.google.mainline.primary.libs / ...go.primary.libs），用于在模块间去重通用原生库（BIG_ANDROID_DCLA/GO_DCLA）。
  • versioning_action.py 递增模块版本码；pack_action.py 打包结果。
  • generic_train_build_action.py 与 primary_train_build_action.py 是编排器。它们把每个 train 建模为 TrainBuildSpec，并按 TrainType（TELEMETRY、ADSERVICES、NPU、NONUPDATABLE、TIMEZONE、PRELOAD、Go 变体）分派。

大部分旧式 mock 数据与专有脚本移到了 vendor/google/train_build。AOSP 中保留的是可复用的裁剪/DCLA/版本/打包机制，以及宿主单元测试。

新模块

cipd_package（build/soong/android/cipd/cipd_package.go）。 新的 Soong 模块类型，在构建时从 CIPD（Chrome Infrastructure Package Deployment）拉取预编译产物。它发布 CipdPackageInfoProvider，携带完整包名与钉住的版本。有界的 cipdPool（深度 8）限制并发拉取。许多 prebuilt_* 模块类型现在记录其 CIPD 来源，使其流入合规元数据。

android_filesystem_prebuilt（build/soong/filesystem/prebuilt.go）。 通用预编译镜像模块，把既有的系统镜像文件（Src）包进常规 filesystem 机制。于是厂商提供的分区镜像能与 Soong 构建的镜像一样参与打包/AVB。

trusty_vm_signing_tool（packages/modules/Virtualization/guest/trusty/tools/Android.bp）。 新的 Rust 宿主工具，为 pvmfw 签名 Trusty pVM 载荷。

架构变更

Soong API / 合规数据库（soong_api）。 最大的构建系统变更是新的 singleton soong_api_db（build/soong/soong_api/soong_api.go）。它遍历每个模块代理，为每个模块发出 SoongApiModuleRecord（身份/类型、安装/构建文件、许可证元数据、trendy_team_id、Java/CC/Rust 依赖边、CIPD 来源）。该 singleton 在 out/soong/soong_api/<product>/ 下导出 soong_api.json/.zip 与 SQLite 的 soong_api.db。它承接旧的 metadata.db/metadata_db_loader 家族，支撑 SBOM/来源生成，取代已移除的原生 gRPC 查询路径。

重要集成

AVF 多租户。 从 Android 26Q2 起，单个受保护虚拟机可以承载多个彼此隔离的租户（packages/modules/Virtualization/docs/multitenancy.md）。VM 持有人交付已签名的 TenancyConfig（APK 内的 JSON 载荷配置，经 VirtualMachineConfig#setPayloadConfigPath 设置），声明各租户的 package、位于 [10000, 65534] 的唯一 uid、min_version，以及按构建风味给出签名哈希的 expected_authority 映射。

virtmgr 依据 OS 签名状态校验每个租户的 authority，并反映到 pVM 的 DICE 证书中。按租户的 cgroup 与 SELinux 域隔离租户；不匹配的载荷被丢弃。

Trusty 作为 pVM。 Trusty OS 现在作为 AVF 管理的受保护虚拟机运行（packages/modules/Virtualization/guest/trusty/docs/trusty_vm.md）。Trusty 内核新增基于 PCI 的 virtio-vsock 用于宿主/VM IPC；还新增 virtio-vsock over virtio-msg over FF-A，用于进入安全世界 TEE 的宿主不透明通道；以及解析 crosvm 生成的设备树（含 pvmfw DICE 区域）、PSCI CPU 开关与 ARM TRNG 熵源。载荷经 Soong genrule 构建、签名（通过新的 trusty_vm_signing_tool）并为 pvmfw 打包，在 .../guest/trusty/ 下产出 security_vm/test_vm 镜像。

Linux/Terminal VM 的 guest 内代理与 pVM TEE 服务。 AVF 新增 linux_vm_manager，即 Linux/Terminal VM 的 guest 内 Rust 代理（packages/modules/Virtualization/guest/linux_vm_manager/）。该代理经 vsock 回连宿主（src/main.rs），注册 IGuestAgent binder，其处理器（例如 shutdownAsync）位于 src/guest_agent.rs。libavf LLNDK 还暴露 AVirtualMachineRawConfig_addTeeService（libs/libavf/include/android/virtualization.h，introduced=37），让受保护虚拟机声明它可触及的 TrustZone/TEE 服务。

D.14 设备支持

Android 17 在设备支持上的招牌变化是**软件定义车辆（SDV，Software Defined Vehicle）**平台。SDV 不是单个仓库，而是以新的顶层树（system/software_defined_vehicle/）出现，并附带参考设备（device/google/sdv）、新的 HAL 接口包（hardware/sdv/interfaces）与车用显示安全服务（packages/services/display_safety）。其模型是无头车辆 Android OS：SDV “Core” 在自己的 VM 中运行车辆服务、没有 UI，并经 SOME/IP 与一个或多个 AAOS 车载信息娱乐（IVI）VM 以及非 Android 的车用 ECU 通信。

新项目

manifest-snapshots/_compare/android-16.0.0_r4-to-android17-release/added-removed.txt 列出 84 个 ADDED 项目，SDV 集群占了大头：

  • 16 个新的 system/software_defined_vehicle/* 仓库：middleware、orchestration、some_ip、vsidl、telemetry、update_manager、sdv_gateway、lifecycle_management、health_monitor、service_bundles_registry、automotive_services、platform、common、samples、tools、vpm。
  • device/google/sdv（sha f4bfa128，组 swcar, pdk）—— 带全部 SDV lunch 目标的参考设备。
  • device/google/sdv_display_safety（sha 0971a467）—— 显示安全的产品 overlay。
  • hardware/sdv/interfaces —— 新的 SDV HAL/AIDL 契约包。
  • packages/services/display_safety —— 车用显示安全（“HARry”）服务。

packages/services/Car（Android Automotive 的 CarService）是迁移/扩展的既有仓库（561 个提交），不是新项目。

新模块

逐设备的 makefile device/google/sdv/sdv_core_arm64/sdv_core_arm64.mk 通过 SDV_SOMEIP_AGENT_MODULES / SDV_DIAGNOSTICS_AGENT_MODULE / SDV_VEHICLE_POWER_STATE_MANAGER_MODULE 变量提供 SOME/IP 栈、诊断与电源状态模块，由 sdv_packages_core_services.mk 消费。按 device/google/sdv/sdv_core_base/sdv_packages_core_services.mk，一个 SDV Core VM 安装这些代理与 APEX：

  • 通信栈（middleware/）：sdv_sd_agent（服务发现）、dt_agent（数据隧道 pub/sub，com.android.sdv.dt）、rpcagent（middleware/rpc_agent）；共享客户端库 libsdv_comms（middleware/sdv_comms），底层是 wire_format 与 transport（Rust）。
  • 生命周期与编排：sdv_lifecycle_agent、lifecycle_service_bundle_runner、sdv_orchestration_agent（com.android.sdv.orchestrator）、sdv_service_bundles_registry_agent —— 编排器按 orch_config.textproto 驱动 bundle 生命周期。
  • VSIDL 工具链（宿主）：vsidlc、vsidl_rc_generator、someip_translation_generator；设备端为 sdv_vsidl_provider_agent。
  • SOME/IP：sdv_someip_stack_agent + vsomeip_config.json（来自逐设备 makefile）、sdv_someip_broker_agent_comms。
  • 平台/运维：sdv_health_monitor、sdv_update_manager_agent、sdv_diagnostics_agent 与 vepsm（车辆电源状态管理器；后两者来自逐设备 makefile）。

hardware/sdv/interfaces 定义稳定的 AIDL 面：ISdvGateway/ISdvGatewaySession（sdv_gateway/google/sdv/gateway/）、IRpcAgent（middleware/rpc/）、IRegistry（service_bundles_registry/，aidl_api/ 下的 API v3），以及生命周期的 IService/IServiceManager；另有车辆电源管理器的 AIDL，以及特权级的 Service-Discovery / 身份代理。

packages/services/display_safety 是 Rust workspace（根 Cargo.toml），实现 HARry Driver-UI 运行时。它含 framework/（Impeller 图形、音频、布局、监控）、reference/（harry-app、safety-monitor、ADAS 可视化）与 service/har-sdv-service。该服务的 libhar_sdv_service_bundle 发布车辆数据，并经中间件以 gRPC 提供 Driver UI。

架构变更

SDV 栈在 AAOS 之下（以及旁边）垫上一层车辆服务织物。新树提供通信中间件与代理；device/google/sdv 把它们组合成 lunch 目标；hardware/sdv/interfaces 定义契约；CarService 与 IVI VM 经网关消费它们。

Lunch 目标的组合方式（device/google/sdv/AndroidProducts.mk、README.md）：OEM 产品继承自一个 SDV “base” 加一个厂商目标。base 有 sdv_base（仅通信栈）与 sdv_core_base（完整 SDV Core 服务），另有 sdv_media_base（Core + 媒体 API）与 sdv_ivi_base（一个 AAOS IVI，与其他 VM 上的 SDV 服务对话）。示例目标 sdv_core_cf、sdv_media_cf、sdv_ivi_cf（Cuttlefish）及其 *_arm64 同类会启动多个 VM 实例（cvd_config_sdv_core_instance{1,2,3}.json）。

VSIDL → 生成的 Rust。 服务在 .vsidl service-bundle 定义加目录中的 .proto 消息 schema 中描述。vsidlc（vsidl/vsidlc）遍历目录并把 Rust 中间件绑定生成到 generated_rs/。someip_translation_generator 为标记 INTERPRET_AS_BYTES（静态）或 DYNAMIC_LIBRARY（动态）的消息生成 SOME/IP↔proto 翻译代码。这是 SDV 对 AIDL stub 生成的对应物。

车辆服务接口分层。 在一个 VM 内部，通信栈分成服务发现、数据隧道（具名 pub/sub 主题）与 RPC（IRpcAgent）。跨 VM、跨 ECU 的流量经 SOME/IP 走 SOME/IP 栈代理与 broker-agent-comms 层，传输层用 vsomeip。

不认识 SDV 的原生/Java 应用经 SDV Gateway（sdv_gateway/）接入这层织物。网关的 vhal_proxy（libvhal_proxy）让 VHAL 服务调用 initComms 并发布车辆属性，由 sdv_gateway_config.json（/vendor/etc/sdv_gateway_config.json）控制——该文件按进程 UID 给 SDV 包名做允许清单。SDV-RPC 流量走专用 VLAN（androidboot.sdv.rpc.interface，默认 sdv_rpc）。

显示安全。 IVI 侧，packages/services/display_safety 把 HARry Driver-UI 作为 SDV service bundle（har-sdv-service）运行，并由 safety-monitor 施加分心/安全约束。此次迁移把 ADAS 框架 crate 与 DriverUI SEPolicy 搬到该仓库，并且只在 SDV 构建中交付 com.google.display_safety.har.apex。

重要集成

  • CarService ↔ SDV。 packages/services/Car（迁移来的仓库，561 个提交）新增 IVI 侧所需的 Driver-UI 管道：com.android.car.driverui privapp 权限与 ACCESS_LOCAL_NETWORK 默认授予，以及 SDV linter。IVI lunch 目标专门为 SDV 接线一个车辆 HAL：LOCAL_VHAL_PRODUCT_PACKAGE := android.hardware.automotive.vehicle@V1-sdv-emulator-service（device/google/sdv/sdv_ivi_cf/sdv_ivi_cf.mk）。于是 CarService 对话的车辆属性，最终由 SDV Core 经网关提供。
  • AIDL 迁入 hardware/sdv/interfaces。 若干接口集从 system/ 移到新的 HAL 包：SDV Gateway 接口、Service Bundles Registry 的 AIDL、vpm 稳定 AIDL，以及（在一次回退之后）Telemetry AIDL。这使 SDV 硬件契约成为带版本、VINTF 稳定、与代理实现无关的表面。
  • VHAL 代理桥与 OEM/PDK。 sdv_gateway/vhal_proxy（libvhal_proxy、config_loader）让未经修改的 VHAL 以允许清单内的 SDV 包名接入 SDV 织物。参考设备支持自定义 /oem_ab 分区（sdv_core_base/oem_ab/）用于 OEM service bundle。Core 目标可经 PDK 构建（SDV KeyMint 被强制加入，因为 PDK 测试时没有 system/software_defined_vehicle/ 源码）。
  • 安全模型。 VM 级权限是一个 APEX，id 为 com.oem.sdv.authz（参考实现 com.oem.sdv.authz.allow_all.{core,ivi}）。网关配置还按 UID 限制原生客户端。中间件交付 crypto_rpc 与 service_authz 用于带认证的 RPC。
  • 大屏应用兼容的 RRO 旋钮。 新的可运行时 overlay 配置布尔量用于调校大屏/折叠屏行为。config_isCameraCompatSimulateRequestedOrientationTreatmentEnabled（及横屏变体）经 AppCompatCameraSimReqOrientationPolicy（frameworks/base/services/core/java/com/android/server/wm/AppCompatConfiguration.java）驱动相机兼容的加黑边处理。config_enableSelfKillRecoveryBetweenInternalDisplays（frameworks/base/core/res/res/values/config.xml）让在折叠转场中自我结束的应用被重新拉起，以保住其会话。

D.15 实践工具

实践性开发/测试工具变化不大。Cuttlefish（290 个提交）新增一个桌面产品、统一的 VKMS 控制器、NPU HAL 与 AiSeal 接线。Traceur 新增两个 Perfetto trace 类别。

新项目

vsoc_x86_64_only/desktop/ 是新的 Cuttlefish 产品 aosp_cf_x86_64_desktop（在 AndroidProducts.mk:40 注册），面向 Android Desktop 形态。它仅支持 HSUM（PRODUCT_USE_HSUM := true）、只出 64 位，使用动态分区与 lz4 虚拟 A/B 压缩。它还交付 desktop_init_dev_config 服务，在首次启动时选择 APEX/设备配置（shared/desktop/common.mk）。该产品默认开启 verity + 加密，并启用 Trusty gatekeeper/keymint 与 pvmfw-cf（vsoc_x86_64_only/desktop/desktop.mk）。

新模块

  • guest/commands/vkms_controller/ 是新的 guest 侧二进制，用于虚拟内核模式设置（VKMS）（main.cpp）。它把原先零散的 VKMS 逻辑收拢起来：宿主 CLI 变成无状态的 adb shell vkms_controller ... 代理，各测试框架共用一条初始化路径；guest 负责把虚拟硬件（ConfigFS 索引）与 SurfaceFlinger 显示 ID 对应起来。以 vendor cc_binary 交付（guest/commands/vkms_controller/Android.bp）。
  • NPU 支持：shared/device.mk:489 安装 com.android.hardware.npu.cf HAL APEX，并把 android.hardware.npu.xml 复制为厂商特性权限，从而在虚拟设备上宣告新的 NPU HAL 面。

架构变更

  • AiSeal（设备端 AI 封存）现在为 Cuttlefish 接通，经 shared/aiseal/device_vendor.mk，受 RELEASE_AISEAL_FRAMEWORK 控制并可选 AppSearch。由于 Cuttlefish 不支持受保护虚拟机，它强制 service.aiseal.protected_vm=0，在非受保护 VM 中运行 AiSeal；aosp_cf_x86_64_only_phone 选择加入该特性。
  • 宿主工具清理：从 Cuttlefish 宿主包中删除 acloud 转换器；cvd-host-package 现在在沙箱（Sbox）中构建，并做增量遍历依赖跟踪，从而提升开发者宿主 tarball 的可复现性。
  • 变体广度在数量上不变，但在四个 minidroid 目标（vsoc_{arm64,arm,riscv64,x86_64}_minidroid）与页大小无关产品 vsoc_x86_64_pgagnostic / vsoc_arm64_pgagnostic 上均得到重申——后者用于验证 16 KB 页构建。

重要集成

Traceur 新增两个 Perfetto trace 类别，开发者可在系统追踪 UI 中开关（src_common/com/android/traceur/TraceUtils.java:127）：

  • wattson（“Wattson power estimation”）：启用时，Traceur 发一份最小 Perfetto 配置，含 linux.sys_stats（cpufreq/cpuidle 轮询）以及一个 linux.ftrace 块，采集 CPU 热插拔、devfreq、cpu_frequency/idle、suspend_resume 与 sched_switch 事件（src_common/com/android/traceur/PerfettoUtils.java:821）。
  • mq（“messagequeue tracing”）：为 Looper/MessageQueue 的分派追踪启用 mq track_event 类别（src_common/com/android/traceur/PerfettoUtils.java:851）。

Traceur 还把 targetSdk 升到 36，启用 R8 字节码优化，并移除已死的 bitmaps_in_traceur flag 与 WinscopeUtils/视图捕获路径。

DeviceDiagnostics（packages/apps/DeviceDiagnostics，包名 com.android.devicediagnostics）是 Settings > 重置选项 > 设备诊断背后的硬件健康与以旧换新应用。组件自检（屏幕、触控、电池、存储、传感器、铰链）收集 DeviceReport protobuf，其中携带一条密钥证明链。独立的 tradeinmode/ 组件以 persist.adb.tradeinmode 控制 adbd。于是合作伙伴可以经 adb 读取带证明的报告，而无需解锁设备。

第 54 章：主线模块

Android 历来以单体 OTA 镜像的形式交付操作系统更新。每一次安全补丁、每一个缺陷修复、每一项 API 改进，都必须经过设备厂商、等待运营商认证，最后才抵达用户手中。这条流水线常常要花上几个月。Project Mainline（主线项目）从根基上改变了这一模式：它把平台切分为可独立更新的模块，Google 可以通过 Google Play 基础设施把这些模块直接推送到设备。

本章剖析让这一切成为可能的架构，涵盖四个主题：第一是 APEX 容器格式；第二是在启动时激活模块的 apexd 守护进程；第三是 AOSP 中交付的 40 多个主线模块的清单；第四是 SDK 扩展（SDK Extensions）机制，它让应用在运行期得知设备上存在哪些模块版本。

Android 17（API 级别 37，代号 CINNAMON_BUN）延续这一趋势：它新增了一条 “C” SDK 扩展轴，并交付了新的模块（com.android.npumanager、com.android.webapp，以及若干 bootstrap APEX）。它还让 apexd 学会不经 loop 设备、直接从 APEX 文件挂载 EROFS 载荷。

新的顶层 tools/mainline 仓库现在承载开源“列车构建”（train build）工具，用它把这些模块组装成经 Google Play 交付的捆绑包。

54.1 主线项目

54.1.1 问题所在：碎片化与陈旧的安全修复

在 Android 10（Q）之前，每个平台组件的更新生命周期大体相同：

  1. Google 工程师向 AOSP 提交修复。
  2. 各 OEM 把该修复摘取（cherry-pick）到自己的 BSP 分支。
  3. OEM 构建完整的系统镜像。
  4. 运营商对镜像做认证。
  5. OTA 抵达终端用户设备。

对于某个关键 CVE——比如 DNS 解析器或媒体编解码栈中的漏洞——这条流水线可能需要三个月，也可能永远到不了。时间长短取决于 OEM 的投入程度与设备的机龄。结果是生态碎片化：数十亿台设备运行着危险地过时的平台代码。

54.1.2 解决方案：模块化、可更新的组件

Project Mainline 在 Android 10 引入，并在之后每个版本扩展，它把平台切成模块。每个模块都能独立于基础系统镜像更新，并以下述两种形式之一打包：

  • 一个 APEX（Android Pony EXpress）—— 一种用于原生代码、Java 库与配置文件的全新容器格式。

  • 一个标准 APK —— 用于纯 Java / Kotlin 的模块。

Google 通过 Google Play 系统更新机制推送模块更新（设备上标为“Google Play 系统更新”）。安全关键修复可以在数天内抵达所有受支持的设备，而不是数月。

54.2 APEX 格式

APEX 文件格式是 Project Mainline 的基石。它解决了一个 APK 无法解决的问题：把原生共享库、可执行文件、配置文件与Java bootclasspath 片段打包成一个经过签名、完整性校验的单一单元，并可持续更新。

54.2.1 为什么不用 APK 就好

APK 是为 Dalvik/ART 应用设计的 ZIP 归档，携带 DEX 字节码、资源与原生库（lib/<abi>/）。但它们缺少：

  • 对载荷镜像的 dm-verity 保护。

  • 让内核把载荷当作真实文件系统来对待的 loop 设备挂载。

  • 在 zygote 启动之前完成的启动期激活。

  • 替换 libc++ 或 libcrypto 这类平台级原生库的能力。

APEX 一并解决了这些问题。

54.2.2 文件结构

一个 APEX 文件（.apex）是包含下列内容的 ZIP 归档：

my_module.apex (ZIP)
+-- AndroidManifest.xml        # Standard APK manifest (for Play Store)
+-- apex_manifest.pb           # Protobuf: name, version, provideNativeLibs, ...
+-- apex_payload.img           # ext4/f2fs/erofs filesystem image
+-- apex_pubkey                # AVB public key (embedded for verification)
+-- META-INF/                  # JAR signing (v2/v3 APK signature)

关键组件是 apex_payload.img：一个真实的文件系统镜像——ext4、f2fs 或 erofs——其中该模块的文件按照挂载到 /apex/<module_name>/ 时的确切布局摆放。

system/apex/apexd/ 中的 apex_file.cpp 实现按魔数字节识别这三种文件系统类型：

// Source: system/apex/apexd/apex_file.cpp

constexpr const char* kImageFilename = "apex_payload.img";
constexpr const char* kCompressedApexFilename = "original_apex";
constexpr const char* kBundledPublicKeyFilename = "apex_pubkey";

struct FsMagic {
  const char* type;
  int32_t offset;
  int16_t len;
  const char* magic;
};
constexpr const FsMagic kFsType[] = {
    {"f2fs", 1024, 4, "\x10\x20\xf5\xf2"},
    {"ext4", 1024 + 0x38, 2, "\123\357"},
    {"erofs", 1024, 4, "\xe2\xe1\xf5\xe0"}
};

54.2.3 APEX 清单（Protobuf）

每个 APEX 都携带一个 protobuf 清单，定义于 system/apex/proto/apex_manifest.proto：

// Source: system/apex/proto/apex_manifest.proto

message ApexManifest {
  // Name used to mount under /apex/<name>
  string name = 1;

  // Version Number
  int64 version = 2;

  // Pre Install Hook
  string preInstallHook = 3;

  // Version Name
  string versionName = 5;

  // If true, apexd mounts with MS_NOEXEC
  bool noCode = 6;

  // Native libs provided to other APEXes or the platform
  repeated string provideNativeLibs = 7;

  // Native libs required from other APEXes or the platform
  repeated string requireNativeLibs = 8;

  // JNI libraries (used by linkerconfig/libnativeloader)
  repeated string jniLibs = 9;

  // Compressed APEX metadata
  CompressedApexMetadata capexMetadata = 12;

  // Can be updated without reboot
  bool supportsRebootlessUpdate = 13;

  // Whether activated in bootstrap phase
  bool bootstrap = 16;
}

provideNativeLibs 与 requireNativeLibs 两个字段尤为重要：它们让 apexd 与链接器配置系统得以在启动时构建正确的共享库命名空间。

54.2.4 压缩 APEX（CAPEX）

从 Android 11 起，APEX 可以在系统分区上以压缩形式存放以节省空间。压缩后的 APEX 后缀为 .capex，内部装的是压缩过的原始 APEX。启动时，apexd 把它解压到 /data/apex/decompressed/：

// Source: system/apex/apexd/apex_constants.h

static constexpr const char* kApexDecompressedDir = "/data/apex/decompressed";
static constexpr const char* kCompressedApexPackageSuffix = ".capex";
static constexpr const char* kDecompressedApexPackageSuffix =
    ".decompressed.apex";

ApexFile::IsCompressed() 方法检测某个 APEX 是否被压缩，ApexFile::Decompress() 负责解压。

Open() 工厂方法依次执行以下步骤：

  1. 用 libziparchive 把文件作为 ZIP 归档打开。

  2. 读取 apex_manifest.pb 条目并解析该 protobuf。

  3. 读取 apex_pubkey 条目（AVB 公钥）。

  4. 定位 apex_payload.img 条目，记录它在 ZIP 中的偏移与大小。

  5. 从载荷镜像读取魔数字节，识别文件系统类型。

  6. 检查这是否是压缩 APEX（内含 original_apex 而非 apex_payload.img）。

// Source: system/apex/apexd/apex_file.cpp (Open method, simplified)

Result<ApexFile> ApexFile::Open(const std::string& path) {
  // Open as ZIP archive
  ZipArchiveHandle handle;
  int ret = OpenArchiveFd(fd.get(), path.c_str(), &handle, false);

  // Try to find apex_payload.img
  ZipEntry entry;
  ret = FindEntry(handle, kImageFilename, &entry);
  if (ret == 0) {
    image_offset = entry.offset;
    image_size = entry.uncompressed_length;
    // Detect filesystem type (ext4, f2fs, erofs)
    fs_type = RetrieveFsType(fd, entry.offset);
  }

  // Read manifest
  FindEntry(handle, kManifestFilenamePb, &entry);
  // ... parse protobuf ...

  // Read public key
  FindEntry(handle, kBundledPublicKeyFilename, &entry);
  // ... read key ...

  return ApexFile(path, image_offset, image_size,
                  manifest, pubkey, fs_type, is_compressed);
}

54.2.6 签名

APEX 使用两层签名：

  1. 载荷签名（AVB）：用 Android Verified Boot 配合 avbtool 对 apex_payload.img 签名，公钥以 apex_pubkey 形式捆绑在 ZIP 内。

  2. 容器签名（APK Signature Scheme v2/v3）：外层 ZIP 像普通 APK 一样签名，好让 Google Play 基础设施校验它。

构建系统用 apex_key 模块类型定义密钥：

// Source: packages/modules/SdkExtensions/Android.bp

apex_key {
    name: "com.android.sdkext.key",
    public_key: "com.android.sdkext.avbpubkey",
    private_key: "com.android.sdkext.pem",
}

android_app_certificate {
    name: "com.android.sdkext.certificate",
    certificate: "com.android.sdkext",
}

build/soong/apex/key.go 中的 Soong 实现负责解析这些密钥：

// Source: build/soong/apex/key.go

type apexKeyProperties struct {
    // Path or module to the public key file in avbpubkey format.
    Public_key *string `android:"path"`
    // Path or module to the private key file in pem format.
    Private_key *string `android:"path"`
}

密钥解析遵循一条回退链：先是全局 apex 密钥目录（可配置），然后是本地模块目录。

apexer 工具（system/apex/apexer/apexer.py）是把一个内容目录组装成 APEX 文件的命令行工具：

调用 apexer 的 Soong 构建规则定义在 build/soong/apex/builder.go：

// Source: build/soong/apex/builder.go

apexRule = pctx.StaticRule("apexRule", blueprint.RuleParams{
    Command2: blueprint.NewCommand(
        android.Rm, ` -rf ${image_dir} && `, android.Mkdir, ` -p ${image_dir} && `,
        `(. ${out}.copy_commands) && `,
        `APEXER_TOOL_PATH=${tool_path} `,
        apexer, ` --force --manifest ${manifest} `,
        `--file_contexts ${file_contexts} `,
        `--canned_fs_config ${canned_fs_config} `,
        `--include_build_info `,
        `--payload_type image `,
        `--key ${key} ${opt_flags} ${image_dir} ${out} && `,
        android.SoongZip, ` -d -C ${image_dir} -D ${image_dir} -o ${image_zip}`,
    ),
    // ...
})

整个过程为：

  1. 收集全部原生库、可执行文件、Java 库与配置文件。

  2. 把它们复制进一个暂存目录（${image_dir}）。

  3. 用 mke2fs、make_f2fs 或 mkfs.erofs 创建文件系统镜像（ext4/f2fs/erofs）。

  4. 用 avbtool 对镜像签名。

  5. 用 soong_zip 把所有内容打包成 ZIP。

  6. 用 APK Signature Scheme 对 ZIP 签名。

    C --> D[apex_payload.img]
    D --> E["avbtool（dm-verity 签名）"]

启动期激活流程

apexd.cpp 中的 MountPackageImpl 函数实现五步挂载过程：

// Source: system/apex/apexd/apexd.cpp (MountPackageImpl)

// Steps to mount an APEX file:
//
// 1. create a mount point (directory)
// 2. create a block device for the payload part of the APEX
// 3. wrap it with a dm-verity device if the APEX is not on top of verity
//    device
// 4. mount the payload filesystem
// 5. verify the mount

第 2 步创建承载载荷的块设备。自 Android 17 起， MountPackageImpl 按优先级顺序选用三种策略之一：其一，为钉住（pinned）的 APEX 创建 dm-linear 设备；其二，文件承载的 EROFS 挂载，完全跳过块设备；其三，经典的 loop 设备：

// Source: system/apex/apexd/apexd.cpp (MountPackageImpl)

if (UsesPinnedApex() && GetImageManager()->IsPinnedApex(apex)) {
    linear_dev = OR_RETURN(CreateDmLinearForPayload(apex));
    mount_device = linear_dev.GetDevPath();
} else if (IsFileBackedMountEnabled() && fs_type == "erofs" &&
           !mount_on_verity) {
    mount_options = std::format("fsoffset={}", *apex.GetImageOffset());
    mount_device = apex.GetPath();
#if COM_ANDROID_APEX_FLAGS_MICRODROID_NO_LOOP_DEVICE
} else if (instance.IsBlockApex(apex)) {
    linear_dev = OR_RETURN(CreateDmLinearForBlockApex(apex, device_name));
    mount_device = linear_dev.GetDevPath();
#endif
} else {
    loop = OR_RETURN(CreateLoopForApex(apex, loop_id));
    mount_device = loop.name;
}

EROFS 文件承载分支是这里的头条改动（54.11 节详述）。当 erofs_file_backed_mount 标志开启、且某个预装的 EROFS APEX 无需自带的 dm-verity 层时，就走这一分支：apexd 直接从 .apex 文件挂载载荷，使用内核的 fsoffset= 挂载选项，全程不涉及 loop 设备。

第 3 步用 dm-verity 包装块设备以做完整性校验。位于受 dm-verity 保护分区（如 /system）的预装 APEX 可以跳过这一额外层：

// Source: system/apex/apexd/apexd.cpp

                             instance.IsDecompressedApex(apex) ||
                             instance.IsBlockApex(apex);

dm-verity 表构建

CreateVerityTable 函数依据 APEX 内嵌的 AVB hashtree 描述符构建 device-mapper verity 表：

// Source: system/apex/apexd/apexd.cpp

std::unique_ptr<DmTable> CreateVerityTable(
    const ApexVerityData& verity_data,
    const std::string& block_device,
    bool restart_on_corruption) {
  AvbHashtreeDescriptor* desc = verity_data.desc.get();
  auto table = std::make_unique<DmTable>();

  const uint64_t start = 0;
  const uint64_t length = desc->image_size / 512;  // in sectors

  const std::string& hash_device = block_device;
  const uint32_t num_data_blocks =
      desc->image_size / desc->data_block_size;
  const uint32_t hash_start_block =
      desc->tree_offset / desc->hash_block_size;

  auto target = std::make_unique<DmTargetVerity>(
      start, length, desc->dm_verity_version,
      block_device, hash_device,
      desc->data_block_size, desc->hash_block_size,
      num_data_blocks, hash_start_block,
      verity_data.hash_algorithm,
      verity_data.root_digest,
      verity_data.salt);

  target->IgnoreZeroBlocks();
  if (restart_on_corruption) {
    target->SetVerityMode(kDmVerityRestartOnCorruption);
  }
  table->AddTarget(std::move(target));
  table->set_readonly(true);

  return table;
}

关键的 dm-verity 参数：

  • 数据块大小与哈希块大小 —— 通常各为 4096 字节。
  • 哈希算法 —— 通常为 SHA-256。
  • 根摘要 —— 链接到全部数据块的顶层哈希。
  • 盐值 —— 混入哈希计算的随机数据。
  • restart_on_corruption —— 若设置，内核在检测到 verity 损坏时重启（而非返回 I/O 错误）。

对于 /system 上（本身已受 dm-verity 保护的）预装 APEX，会跳过这一额外 dm-verity 层，以免双重校验的开销。/data 上的更新 APEX 则一律拥有自己的 dm-verity 设备。

文件系统挂载

dm-verity 设备创建之后，载荷以只读文件系统形式挂载：

最后的 mount_options 参数正是文件承载 EROFS 路径把 fsoffset= 值交给内核的方式；对 loop 设备路径与 dm-linear 路径，它是空的。

挂载标志强制：

  • MS_RDONLY —— 只读（APEX 一旦激活即不可变）。
  • MS_NOATIME —— 不更新访问时间（性能）。
  • MS_NODEV —— 不允许设备节点。
  • MS_DIRSYNC —— 目录更新同步。
  • MS_NOEXEC —— 禁止执行（适用于 tzdata 这类 noCode APEX）。

54.2.10 OnBootstrap 与 OnStart 生命周期

apexd 守护进程有两个主要入口点，对应两个启动阶段。理解这一拆分对诊断启动失败至关重要。

阶段 1：OnBootstrap（在 /data 之前）

// Source: system/apex/apexd/apexd.cpp

int OnBootstrap() {
  ATRACE_NAME("OnBootstrap");
  auto time_started = boot_clock::now();

  ApexFileRepository& instance = ApexFileRepository::GetInstance();
  // Scan /system/apex, /system_ext/apex, /product/apex, /vendor/apex, /odm/apex
  if (auto st = AddPreinstalledData(instance); !st.ok()) {
    LOG(ERROR) << st.error();
    return 1;
  }

  ActivationContext ctx;
  std::vector<ApexFileRef> activation_list;

  if (IsMountBeforeDataEnabled()) {
    // New flow: wait for the /data block device, process sessions, scan data
    OR_RETURN(GetImageManager()->WaitForDataBlockDevice());
    ProcessSessions(ctx);
    auto data_apexes = ScanDataApexFiles(GetImageManager());
    instance.AddDataApexFiles(std::move(data_apexes));
    activation_list = instance.SelectApexForActivation();
  } else {
    // Legacy flow: only activate bootstrap APEXes
    const auto& pre_installed_apexes = instance.GetPreInstalledApexFiles();
    for (const auto& apex : pre_installed_apexes) {
      if (IsBootstrapApex(apex.get())) {
        LOG(INFO) << "Found bootstrap APEX " << apex.get().GetPath();
        activation_list.push_back(apex);
      }
    }
  }

  auto result = ActivateApexPackages(ctx, activation_list,
      ActivationMode::kBootstrapMode, ...);
  EmitApexInfoList(result.activated, /*is_bootstrap=*/true);
  LOG(INFO) << "OnBootstrap done, duration=" << time_elapsed;
  return 0;
}

Bootstrap APEX（清单中 bootstrap: true 的那些）必须在 /data 挂载之前就可用，因为其他早期服务依赖它们。例如：

  • com.android.art —— 运行时本身必须为 zygote 处于活动状态。
  • com.android.i18n —— 文本处理需要 ICU 数据。
  • com.android.tzdata —— 时钟显示需要时区数据。

阶段 2：OnStart（在 /data 之后）

// Source: system/apex/apexd/apexd.cpp

void OnStart() {
  ATRACE_NAME("OnStart");
  LOG(INFO) << "Marking APEXd as starting";
  SetProperty(gConfig->apex_status_sysprop, kApexStatusStarting);

  // Check if filesystem checkpointing needs a rollback
  if (gSupportsFsCheckpoints) {
    Result<bool> needs_revert = gVoldService->NeedsRollback();
    if (needs_revert.ok() && *needs_revert) {
      LOG(INFO) << "Exceeded number of session retries. "
                << "Starting a revert";
      RevertActiveSessions("", "");
    }
  }

  // Activate remaining APEXes (the ones not in bootstrap)
  if (!IsMountBeforeDataEnabled()) {
    ActivateApexesOnStart();
  }

  // Snapshot or restore DE_sys data for rollback support
  SnapshotOrRestoreDeSysData();
  LOG(INFO) << "OnStart done, duration=" << time_elapsed;
}

ActivateApexesOnStart() 函数先处理任何待决的分阶段会话，然后扫描 /data/apex/active/ 中的更新 APEX，并为每个模块激活最佳版本：

// Source: system/apex/apexd/apexd.cpp

void ActivateApexesOnStart() {
  ActivationContext ctx;
  // Process staged sessions first: revert or activate
  ProcessSessions(ctx);

  auto& instance = ApexFileRepository::GetInstance();
  // Scan /data/apex/active/ for updated APEXes
  instance.AddDataApex(gConfig->active_apex_data_dir);

  auto activate_status = ActivateApexPackages(
      ctx, instance.SelectApexForActivation(),
      ActivationMode::kBootMode,
      /*revert_on_error=*/true, /*fallback_on_error=*/true);
  EmitApexInfoList(activate_status.activated, /*is_bootstrap=*/false);
}

SelectApexForActivation() 方法比较预装 APEX 与 data 分区上的 APEX，为每个模块名挑出最高版本。

会话处理

ProcessSessions() 函数处理待决的分阶段会话：

// Source: system/apex/apexd/apexd.cpp

void ProcessSessions(ActivationContext& ctx) {
  auto sessions = gSessionManager->GetSessions();

  if (sessions.empty()) {
    LOG(INFO) << "No sessions to revert/activate.";
    return;
  }

  // If there's any pending revert, revert active sessions.
  if (std::ranges::any_of(sessions, [](const auto& session) {
        return session.GetState() == SessionState::REVERT_IN_PROGRESS;
      })) {
    RevertActiveSessions("", "");
  } else {
    // Otherwise, activate STAGED sessions.
    ActivateStagedSessions(ctx, std::move(sessions));
  }
}

正是这段核心逻辑让主线更新能跨重启生效：会话在重启前处于“分阶段”状态，下次启动时由 ProcessSessions 激活。

54.2.11 免重启更新路径

从 Android 13 起，清单中声明 supportsRebootlessUpdate: true 的 APEX 可以不重启设备而更新。AIDL 方法 installAndActivatePackage() 实现了这一点：

  1. 校验新的 APEX 包。
  2. 从 init 卸载当前 APEX（停止服务、卸载 init 脚本）。
  3. 取消挂载当前活动的 APEX。
  4. 把新 APEX 硬链接到 /data/apex/active/。
  5. 激活（挂载）新 APEX。
  6. 把 APEX 重新载入 init（重启服务、重读 init 脚本）。
// Source: system/apex/apexd/apexd.cpp (rebootless update, simplified)

// Scope guard: reload from init whether we succeed or fail

    LoadApexFromInit(module_name);
});

// 2. Unmount currently active APEX

// 3. Hard-link new APEX to /data/apex/active/

// 4. Activate new APEX

54.2.14 APEX 变体与衍生

Soong 构建系统会为所有被纳入 APEX 的模块创建 APEX 专用变体。这由 apexTransitionMutator 处理：

// Source: build/soong/apex/apex.go

func RegisterPostDepsMutators(ctx android.RegisterMutatorsContext) {
    ctx.BottomUp("apex_unique", apexUniqueVariationsMutator)
    ctx.BottomUp("mark_platform_availability",
        markPlatformAvailability)
    ctx.InfoBasedTransition("apex",
        android.NewGenericTransitionMutatorAdapter(
            &apexTransitionMutator{}))
}

该 mutator 为每个库创建彼此独立的构建变体：一个给平台，另外每个纳入它的 APEX 各一个。APEX 变体可能使用不同的编译标志，尤其是：

  • 不同的 min_sdk_version 限制。
  • 不同的符号可见性（为可更新模块满足 NDK 合规要求）。
  • 不同的链接行为（DCLA 场景下的静态与动态之别）。

例如 libc++ 可能有：

  • 一个链接系统 libc 的平台变体。
  • 一个按 min_sdk_version: 30 编译的 com.android.tethering 变体。
  • 一个按 min_sdk_version: 31 编译的 com.android.art 变体。

54.2.17 回滚与安全

若更新后的 APEX 激活失败，apexd 支持回滚：

  1. 备份：分阶段之前，BackupActiveApexes() 把当前活动的 APEX 复制到 /data/apex/backup/。

54.3.8 深入剖析：DnsResolver 模块

DNS 解析器是 Android 10 中最早的主线模块之一：

// Source: packages/modules/DnsResolver/apex/Android.bp

apex {
    name: "com.android.resolv",
    manifest: "manifest.json",
    key: "com.android.resolv.key",
    certificate: ":com.android.resolv.certificate",
    androidManifest: "AndroidManifest.xml",
    compressible: true,
    defaults: ["q-launched-dcla-enabled-apex-module"],
    // ...
}

注意哪里缺席：该定义完全没有声明 native_shared_libs、 binaries 或 classpath 片段。com.android.resolv 如今是一个空的遗留容器。libnetd_resolv.so 是处理设备上全部 DNS 解析的原生库，它随 Connectivity APEX（com.android.tethering，54.3.4 节）交付——该 APEX 的 native_shared_libs 列表把 libnetd_resolv 与 libnetd_updatable 并列（packages/modules/Connectivity/Tethering/apex/Android.bp）。因此 DNS 解析器特性如今通过 Connectivity 模块更新：

  • DNS-over-TLS（DoT）支持。
  • DNS-over-HTTPS（DoH）支持。
  • 私有 DNS 配置。
  • DNS 缓存投毒漏洞的修复。

空的 com.android.resolv APEX 仍会被构建与交付，以便出厂即带它的设备保留有效的挂载点与更新路径。

Profiling 模块在 Baklava 推出，展示了一个带条件启用的现代模块定义：

// Source: packages/modules/Profiling/apex/Android.bp

    enabled: select(
        release_flag("RELEASE_PACKAGE_PROFILING_MODULE"), {
            true: true,
            false: false,
        }),

    name: "com.android.profiling",
    manifest: "manifest.json",

  • 两个 classpath 片段：同时向 boot classpath 与 system server classpath 贡献内容。

  • B 起始：使用 b-launched-apex-module 默认值，即 min_sdk_version: "36"。

54.4 SDK 扩展

54.4.1 问题所在：运行期的 API 可用性

主线模块独立于平台更新。这意味着运行 Android 12（S）的设备上，某个模块可能停留在 R 时代，也可能早已更新到更新的版本。应用如何知道哪些 API 实际可用？

传统的 Build.VERSION.SDK_INT 检查告诉你平台版本，却对模块版本只字不提。SDK 扩展（SDK Extensions）机制补上了这块空白。

54.4.2 工作原理

每个 Android 版本定义一个扩展版本（extension version）—— 一个整数，随着该“列车”中各模块协同更新而递增。该版本在启动时由 derive_sdk 可执行文件推导得出，它会检查已安装模块的实际版本。

derive_sdk 的过程为：

  1. 从每个已挂载 APEX 读取 sdkinfo.pb（位于 /apex/<name>/etc/sdkinfo.pb）。

  2. 读取 extensions_db（一个记录版本要求的 protobuf 数据库）。

  3. 对每个扩展（R、S、T、U、V、B、C、ad_services），算出所有模块要求都得到满足的最高版本。

  4. 设置系统属性：build.version.extensions.r、.s、.t、…、 .c。

54.4.3 版本推导算法

GetSdkLevel 函数确定所有要求均得到满足的最高扩展版本：

// Source: packages/modules/SdkExtensions/derive_sdk/derive_sdk.cpp

int GetSdkLevel(const ExtensionDatabase& db,
                const std::unordered_set<SdkModule>& relevant_modules,
                const std::unordered_map<SdkModule, int>& module_versions) {
  int max = 0;
  for (const auto& ext_version : db.versions()) {
    if (ext_version.version() > max &&
        VersionRequirementsMet(ext_version, relevant_modules,
                               module_versions)) {
      max = ext_version.version();
    }
  }
  return max;
}

而 VersionRequirementsMet 逐个检查每个模块：

// Source: packages/modules/SdkExtensions/derive_sdk/derive_sdk.cpp

bool VersionRequirementsMet(
    const ExtensionVersion& ext_version,
    const std::unordered_set<SdkModule>& relevant_modules,
    const std::unordered_map<SdkModule, int>& module_versions) {
  for (const auto& requirement : ext_version.requirements()) {
    if (relevant_modules.find(requirement.module()) ==
        relevant_modules.end())
      continue;

    auto version = module_versions.find(requirement.module());
    if (version == module_versions.end()) return false;
    if (version->second < requirement.version().version())
      return false;
  }
  return true;
}

算法是：对每个扩展级别（R、S、T、……），遍历数据库中定义的全部版本；对每个版本号，检查每个必需模块是否达到最低版本阈值。通过检查的最高版本号即成为该扩展级别。

    public static final int AD_SERVICES = 1_000_000;

    private static final int T_EXTENSION_INT;

     * Return the version of the specified extensions.

        return ALL_EXTENSION_INTS;

54.4.6 实例演练：扩展版本如何算出

我们走一个具体例子，看 derive_sdk 如何计算 R 扩展版本。

输入：extensions_db 含下列（简化后的）条目：

version: 5
requirements:
  - module: CONSCRYPT,       min_version: 10
  - module: MEDIA,           min_version: 8
  - module: PERMISSIONS,     min_version: 12
  - module: TETHERING,       min_version: 6

version: 6
requirements:
  - module: CONSCRYPT,       min_version: 11
  - module: MEDIA,           min_version: 9
  - module: PERMISSIONS,     min_version: 14
  - module: TETHERING,       min_version: 7

已安装模块版本（来自各 APEX 中的 sdkinfo.pb）：

CONSCRYPT: 12
MEDIA: 9
PERMISSIONS: 14
TETHERING: 6

评估：

对版本 5：

  • CONSCRYPT 12 >= 10 —— 通过
  • MEDIA 9 >= 8 —— 通过
  • PERMISSIONS 14 >= 12 —— 通过
  • TETHERING 6 >= 6 —— 通过
  • 全部满足：版本 5 成为候选。

对版本 6：

  • CONSCRYPT 12 >= 11 —— 通过
  • MEDIA 9 >= 9 —— 通过
  • PERMISSIONS 14 >= 14 —— 通过
  • TETHERING 6 >= 7 —— 不通过（6 < 7）
  • 并非全部满足：版本 6 被拒。

结果：R 扩展版本 = 5。

TETHERING 模块停在版本 6，未达到扩展版本 6 所要求的最低 7。假设 Google 推送一次 Connectivity 模块更新，把 TETHERING 提到版本 7 或更高，那么 R 扩展版本会在下次重启后自动进阶为 6。

这一机制保证应用可以信任扩展版本检查：若 SdkExtensions.getExtensionVersion(R) >= 6，则 R 列车中所有模块都达到或超过所要求的版本，且 R 扩展 6 引入的全部 API 都可用。

54.4.8 SdkExtensions APEX

SdkExtensions 模块本身也打包成 APEX：

// Source: packages/modules/SdkExtensions/Android.bp

apex {
    name: "com.android.sdkext",
    defaults: ["com.android.sdkext-defaults"],
    bootclasspath_fragments: [
        "com.android.sdkext-bootclasspath-fragment"

它捆绑了：

  • derive_classpath —— 依据已安装模块的 classpath 片段生成 BOOTCLASSPATH、 DEX2OATBOOTCLASSPATH 与 SYSTEMSERVERCLASSPATH 环境变量的可执行文件。

  • extensions_db —— 记录版本要求的 protobuf 数据库。

  • framework-sdkextensions.jar —— Java API（SdkExtensions 类）。

extensions_db 的源码位于 packages/modules/SdkExtensions/gen_sdk/extensions_db.textpb。在 Android 17 中，定义的最高扩展是 版本 22。大多数模块都钉在这一版本上（ART、Conscrypt、Media、MediaProvider、Permissions、StatsD、 Tethering、AppSearch、OnDevicePersonalization、ConfigInfrastructure、 HealthFitness、NeuralNetworks 等）。

有两个模块被冻结在当前基线之下：gen_sdk/gen_sdk.py 把 AD_SERVICES 与 EXT_SERVICES 列入其 skipped_modules 集合，使二者都停在版本 20。AdServices 在 20 之后停止演进，ExtServices 在 20 之后也不再需要。

54.5 模块边界

主线模块必须与平台以及其他模块共存，同时维持严格的接口边界。本节说明界定“模块内可以放什么、不可以放什么”的规则。

54.5.1 apex_available 属性

任何希望被纳入某个 APEX 的库、可执行文件或应用，都必须声明它对哪些 APEX 可用：

// Source: build/soong/android/apex.go

type ApexProperties struct {
    // Availability of this module in APEXes. Only the listed APEXes
    // can contain this module.
    //
    // "//apex_available:anyapex" matches any APEX.
    // "//apex_available:platform" refers to non-APEX partitions.
    // Prefix pattern (com.foo.*) can match any APEX with that prefix.
    // Default is ["//apex_available:platform"].
    Apex_available []string
}

例如，一个既要供平台使用、又要供 Connectivity APEX 使用的库会这样声明：

cc_library {
    name: "libnetutils",
    apex_available: [
        "//apex_available:platform",
        "com.android.tethering",
    ],
}

构建系统强制要求：除非模块的 apex_available 列表允许，否则它不能被纳入某个 APEX。这避免了意外的依赖膨胀，并确保归属清晰。

54.5.3 Hidden API 强制

未标注上述任何标记的 API 被视为隐藏 API。主线模块和普通应用一样要受 hidden-API 强制的约束：

  • 构建系统通过 bootclasspath 片段定义中的 hidden_api 段来跟踪隐藏 API。

  • 在运行期，libnativeloader 与 ART 依据调用方模块的 API 级别实施访问限制。

bootclasspath 片段声明它拥有哪些包，以及这些包的 hidden API 标志：

    contents: ["framework-permission"],
    apex_available: ["com.android.permission"],
    hidden_api: {
        split_packages: ["*"],
        // annotation flags, metadata, index files
    },
}

54.5.5 模块内不可以有什么

并非一切都能模块化。存在以下约束：

  1. 内核模块 —— 内核代码通过 GKI 更新，而不是 APEX。

  2. HAL 实现 —— HAL 因厂商而异，使用 VINTF 清单，不在主线之列（尽管存在厂商 APEX）。

  3. 启动关键的 init 脚本 —— 最早期 init 阶段必须在未挂载任何 APEX 的情况下工作。

  4. SELinux 策略 —— 基础策略随平台交付；模块只为自己的挂载点贡献 file_contexts。

  5. 来自 framework-res 的资源 —— 核心框架资源不在 APEX 中（但可以用覆盖）。

54.5.6 模块依赖与 min_sdk_version

每个 APEX 都声明一个 min_sdk_version，它决定：

  • 该 APEX 可安装的最低平台版本。
  • 该模块原生代码可以使用哪些 NDK/SDK API。

packages/modules/common/sdk/Android.bp 文件为每个发布时间窗定义标准默认值。所支持的最低 min_sdk_version 本身在 Android 17 也是一个发布标志决定：APEX_LOWEST_MIN_SDK_VERSION 默认为 "30" （R），当 RELEASE_DEPRECATE_MAINLINE_R_SUPPORT 置位时翻转为 "31"（S）。这反映了对 R 时代模块支持的逐步退场：

// Source: packages/modules/common/sdk/Android.bp

APEX_LOWEST_MIN_SDK_VERSION = select(
    release_flag("RELEASE_DEPRECATE_MAINLINE_R_SUPPORT"), {
        true: "31",
        default: "30",
    })

apex_defaults {
    name: "r-launched-apex-module",
    defaults: ["any-launched-apex-modules"],
    min_sdk_version: APEX_LOWEST_MIN_SDK_VERSION,
}

apex_defaults {
    name: "s-launched-apex-module",
    defaults: ["any-launched-apex-modules"],
    min_sdk_version: "31",
    compressible: true,
}

apex_defaults {
    name: "t-launched-apex-module",
    defaults: ["any-launched-apex-modules"],
    min_sdk_version: "Tiramisu",
    compressible: true,
}

apex_defaults {
    name: "u-launched-apex-module",
    defaults: ["any-launched-apex-modules"],
    min_sdk_version: "UpsideDownCake",
    compressible: true,
}

apex_defaults {
    name: "v-launched-apex-module",
    defaults: ["any-launched-apex-modules"],
    min_sdk_version: "VanillaIceCream",
    compressible: true,
}

apex_defaults {
    name: "b-launched-apex-module",
    defaults: ["any-launched-apex-modules"],
    min_sdk_version: "36",
    compressible: true,
}

截至 Android 17，最高的发布窗默认值仍是 b-launched-apex-module（min_sdk_version: "36"），尚无 c-launched-apex-module。因此 Android 17 的新成员 NpuManager 与 WebApp 都继承 b-launched 默认值。

所有可更新 APEX 都继承 any-launched-apex-modules：

// Source: packages/modules/common/sdk/Android.bp

apex_defaults {
    name: "any-launched-apex-modules",
    updatable: true,
}

这设置了 updatable: true，从而触发额外的构建期检查：

  • 所有原生依赖必须使用稳定的 NDK API。
  • 所有 Java 依赖必须使用 sdk_version: "module_current" 或更低。
  • 共享库须实施符号版本化。

54.5.7 动态公共库 APEX（DCLA）

有些模块采用 DCLA（Dynamic Common Lib APEX，动态公共库 APEX）策略，在多个 APEX 之间共享原生库而不各自复制一份：

// Source: packages/modules/common/sdk/Android.bp

DCLA_MIN_SDK_VERSION = "31"

library_linking_strategy_apex_defaults {
    name: "r-launched-dcla-enabled-apex-module",
    defaults: ["r-launched-apex-module"],
    soong_config_variables: {
        library_linking_strategy: {
            prefer_static: {},
            conditions_default: {
                min_sdk_version: DCLA_MIN_SDK_VERSION,
            },
        },
    },
}

启用 DCLA 后，libc++、libcrypto 这类共享库从共享位置加载，而不再在每个 APEX 中重复一份。这减少了设备上的存储占用，但共享库加载基础设施要求 API 级别 31 及以上。

54.5.8 跨模块依赖

  2. java_sdk_library —— 提供稳定的 Java API stub，供其他模块编译时使用。

54.5.9 apex_available 强制机制

构建系统在 Soong 模块图层面强制 apex_available。build/soong/android/apex.go 中的 ApexModule 接口定义了该契约：

// Source: build/soong/android/apex.go

type ApexModule interface {
    // Returns true if this module is available in any APEX
    InAnyApex() bool

    // Returns true if the module is NOT available to the platform
    NotInPlatform() bool

    // Tests if this module can have APEX variants
    CanHaveApexVariants() bool

    // Tests if installable as a file in an APEX
    IsInstallableToApex() bool

    // Tests availability for a specific APEX or ":platform"
    AvailableFor(what string) bool

    // Returns the list of APEXes this module is available for
    ApexAvailableFor() []string

    // Returns the min SDK version the module supports
    MinSdkVersionSupported(ctx BaseModuleContext) ApiLevel
}

当一个 APEX 定义引用某个库（例如 native_shared_libs: ["libfoo"]）时，构建系统会：

  1. 经 apexTransitionMutator 创建 libfoo 的 APEX 变体。
  2. 检查 libfoo 的 apex_available 列表是否包含该 APEX 名。
  3. 校验 libfoo 的 min_sdk_version 与该 APEX 兼容。
  4. 传递性地检查 libfoo 的全部依赖。

任何一项检查失败，构建便中止，并给出清晰错误信息，指出哪个模块违反了边界。

54.5.10 链接器命名空间配置

  • APEX 内部的库彼此可见。

54.5.11 Bootclasspath 与 System Server Classpath

含 Java 的主线模块通过 bootclasspath 片段与 systemserverclasspath 片段参与 boot classpath。这些片段定义该模块中的哪些 JAR 文件应被加入 classpath。

一个 bootclasspath 片段声明：

bootclasspath_fragment {
    name: "com.android.tethering-bootclasspath-fragment",
    contents: [
        "framework-connectivity",
        "framework-connectivity-t",
    ],
    apex_available: ["com.android.tethering"],
    hidden_api: {
        split_packages: ["*"],
        // ...
    },
}

启动时，derive_classpath 可执行文件（来自 SdkExtensions 模块）读取活动 APEX 并生成：

  • BOOTCLASSPATH —— 供 boot class loader 使用的 JAR 列表。
  • DEX2OATBOOTCLASSPATH —— 由 dex2oat 做预编译的子集。
  • SYSTEMSERVERCLASSPATH —— 载入 system server 进程的 JAR。

这种动态生成至关重要：活动模块集合会随更新变化，而 classpath 必须始终反映实际安装的内容。

54.6.2 模块构建的组成

一个完整的模块定义通常涉及：

  1. APEX 定义（模块 apex/ 目录中的 Android.bp）
  2. APEX 密钥（apex_key 模块）
  3. 证书（android_app_certificate 模块）
  4. Bootclasspath 片段（含 Java 的模块需要）
  5. System server classpath 片段（含 system server 代码的模块需要）
  6. 框架库（通常为 java_sdk_library）
  7. 服务实现（通常为 java_library）

以 SdkExtensions 模块为例，最小结构如下：

packages/modules/SdkExtensions/
+-- Android.bp                    # APEX definition + key + certificate
+-- manifest.json                 # APEX manifest (JSON, converted to protobuf)
+-- com.android.sdkext.avbpubkey  # AVB public key
+-- com.android.sdkext.pem        # AVB private key
+-- com.android.sdkext.pk8        # Container signing private key
+-- com.android.sdkext.x509.pem   # Container signing certificate
+-- derive_sdk/
|   +-- derive_sdk.cpp            # Boot-time binary
|   +-- derive_sdk.rc             # init service definition
+-- java/
|   +-- android/os/ext/
|       +-- SdkExtensions.java    # Public API
+-- gen_sdk/                      # SDK version database generation
+-- javatests/                    # Tests

54.6.3 从零创建新模块

若要创建一个新的主线模块，步骤大体如下：

步骤 1：生成签名密钥。

# Generate AVB key pair
$ openssl genrsa -out com.android.mymodule.pem 4096
$ avbtool extract_public_key --key com.android.mymodule.pem \
    --output com.android.mymodule.avbpubkey

# Generate container signing key
$ development/tools/make_key com.android.mymodule \
    '/CN=com.android.mymodule'

步骤 2：编写 Android.bp。

apex {
    name: "com.android.mymodule",
    defaults: ["v-launched-apex-module"],  // launched in V
    manifest: "apex_manifest.json",
    key: "com.android.mymodule.key",
    certificate: ":com.android.mymodule.certificate",
    bootclasspath_fragments: [
        "com.android.mymodule-bootclasspath-fragment",
    ],
    native_shared_libs: ["libmymodule"],
    java_libs: ["mymodule-java-lib"],
}

apex_key {
    name: "com.android.mymodule.key",
    public_key: "com.android.mymodule.avbpubkey",
    private_key: "com.android.mymodule.pem",
}

android_app_certificate {
    name: "com.android.mymodule.certificate",
    certificate: "com.android.mymodule",
}

步骤 3：编写 APEX 清单。

{
    "name": "com.android.mymodule",
    "version": 1
}

步骤 4：创建 SELinux 文件上下文。

# system/sepolicy/apex/com.android.mymodule-file_contexts
(/.*)?       u:object_r:system_file:s0
/bin(/.*)?   u:object_r:mymodule_exec:s0
/lib(64)?(/.*)?  u:object_r:system_lib_file:s0

步骤 5：在所有依赖中声明 apex_available。

cc_library {
    name: "libmymodule",
    srcs: ["mymodule.cpp"],
    apex_available: [
        "com.android.mymodule",
    ],
    min_sdk_version: "VanillaIceCream",
}

54.6.9 APEX 服务接口（AIDL）

apexd 守护进程对外暴露一个 AIDL 服务接口，PackageManager 等系统组件用它管理 APEX 包。关键方法包括：

// Source: system/apex/apexd/aidl (simplified interface)

interface IApexService {
    void submitStagedSession(in ApexSessionParams params,
                             out ApexInfoList packages);
    void markStagedSessionReady(int session_id);
    void markStagedSessionSuccessful(int session_id);
    ApexSessionInfo getStagedSessionInfo(int session_id);
    void markBootCompleted();
    ApexInfo[] getActivePackages();
    ApexInfo[] getAllPackages();
    ApexInfo installAndActivatePackage(in @utf8InCpp String packagePath,
                                       boolean force);
    void revertActiveSessions();
}

installAndActivatePackage 方法是免重启更新的入口。它校验调用方（必须是 system 或 root）、校验该包，并执行 54.2.11 节所述的激活步骤。

54.6.10 持续集成与模块测试

主线模块遵循严格的测试流水线：

提交前（代码落地之前）：

  1. 单元测试（在 TEST_MAPPING 中指定）。
  2. 构建校验（模块必须干净通过构建）。
  3. API 兼容性检查（不得对稳定 API 做破坏性改动）。

提交后（代码落地之后）：

  1. 在多种设备类型上运行 MTS（主线测试套件）。
  2. 跑 CTS（兼容性测试套件）验证行为。
  3. 性能基准测试，捕捉回归。

模块发布之前：

  1. 在目标设备上通过完整 MTS。
  2. 在内部设备上做狗粮（dogfood）部署。
  3. 分阶段放量（1%、5%、25%、50%、100%）。
  4. 监控崩溃率、ANR 率与指标异常。

54.6.11 处理模块中的 API 演进

主线模块新增 API 的流程为：

  1. 以恰当的注解（@SystemApi、@TestApi 等）加入该 API。
  2. 更新 API 界面文件（current.txt / system-current.txt）。
  3. 运行 m update-api 重新生成 API 跟踪文件。
  4. 为新 API 添加 CTS 测试。
  5. 若该 API 应依据扩展版本把关，则把模块加入 derive_sdk.cpp 中恰当的扩展列车。

例如，若为 T 扩展列车版本 5 向 Permission 模块新增了一个 API，就会更新 extensions_db，要求一个包含该新 API 的最低 Permission 模块版本。

54.6.12 排查构建失败

主线模块的常见构建问题：

apex_available 违规：

error: "libfoo" is not available for "com.android.mymodule"
    Add "com.android.mymodule" to apex_available of "libfoo"

修复：把该 APEX 名加入该库的 apex_available 属性。

min_sdk_version 违规：

error: "libfoo" with min_sdk_version "current" cannot be used
    in "com.android.mymodule" with min_sdk_version "30"

修复：为依赖库设置具体的 min_sdk_version。

可更新模块限制：

error: "com.android.mymodule" is updatable but references "libbar"
    which uses unstable platform APIs

修复：确保所有依赖都使用稳定的 API 级别（NDK、SDK stub）。

54.6.13 模块版本化策略

在源码层面，APEX 只是在其 apex_payload.pb（见 54.2.3 节）中携带一个 int64 version，而 SelectApexForActivation() 总是优先选择数值更高者。AOSP 构建用平台构建号打这个版本号。因此在 Android 17（bp1a 风格）trunk-staging 构建上，本地构建的 APEX 会报告形如 370090000 的版本号。

Google 发布的各条已发布列车版遵循结构化的 XYYZZZNNN 约定，使更晚的列车总是排序更高。该约定分四段：列车类型的前导数字、平台 SDK 段、递增的构建段、末尾的变体段（发布 vs 开发）。

施加这套编码的是列车构建工具，而不是 AOSP 的 apexer。在 Android 17 中，该工具已迁入新的 tools/mainline/train_build/ 仓库（versioning_action.py 递增版本号，pack_action.py 打包结果 —— 见 54.10 节）。前导 SDK 段随每个平台版本递增，因此某模块的 Android 17 列车必定排在 Android 16 列车之上——这正是 Play 商店更新机制所需要的。

54.7.3 数据类型

Health Connect 在 android.health.connect.datatypes 包中定义了超过 45 种记录类型（46 个具体类）。每个记录类都继承两个基类之一：

基类 语义 示例
InstantRecord 单一时间点测量 RestingHeartRateRecord、BloodPressureRecord、BloodGlucoseRecord、OxygenSaturationRecord、BodyTemperatureRecord
IntervalRecord 一段时间区间内的测量 StepsRecord、HeartRateRecord（样本序列）、ExerciseSessionRecord、SleepSessionRecord、NutritionRecord、HydrationRecord、DistanceRecord

这些数据类型分属 HealthDataCategory 定义的八个类别 —— 六个稳定类别，外加两个由标志把关的新增类别：

  1. 活动（Activity） —— 步数、距离、卡路里、运动场次、踏频、爬楼层数、爬升高度、运动路线。

  2. 身体测量（Body measurements） —— 体重、身高、体脂、骨量、瘦体重、基础代谢率、体水质量。

  3. 周期追踪（Cycle tracking） —— 月经流量、宫颈黏液、排卵测试、经间出血、性行为。

  4. 营养（Nutrition） —— 营养记录（各营养素细节）、补水、餐食类型。

  5. 睡眠（Sleep） —— 带各阶段细分（清醒、浅睡、深睡、REM）的睡眠场次。

  6. 生命体征（Vitals） —— 心率、心率变异性（RMSSD）、血压、血糖、血氧饱和度、呼吸频率、体温。

  7. 身心健康（Wellness） —— 正念冥想场次（由 FLAG_MINDFULNESS 把关）。

  8. 症状（Symptoms） —— 症状追踪（由 FLAG_SYMPTOMS 把关）。

每条记录都携带 Metadata（数据来源、设备信息、客户端记录 ID、最后修改时间），从而支持去重与优先级排序。

54.8.6 trace 脱敏与隐私

所有剖析输出在交付给应用之前都由 trace_redactor 可执行文件脱敏。脱敏会剔除属于其他进程的数据，只保留请求应用自身 UID 的信息，从而让非特权应用安全地接收系统 trace。

脱敏流水线为：

  1. Perfetto 把原始 trace 写入 /data/misc/perfetto-traces/profiling/。

  2. ProfilingService 调用 trace_redactor 过滤该 trace。

  3. 脱敏后的输出经 Binder 传递的 ParcelFileDescriptor 写入应用的文件目录。

  4. 临时未脱敏 trace 被删除。

uci_hal_android.rs 是一个 binder 客户端，它针对 android.hardware.uwb AIDL HAL（IUwb / IUwbChip）实现 uwb_core 的 UciHal trait —— 而不是 JNI 桥。JNI 层单独放在 packages/modules/Uwb/service/uci/jni/（入口为 uci_jni_android_new.rs）。Java 服务经这一层进入 Rust 栈：它包装 uwb_core，而 uwb_core 又驱动 uci_hal_android 与硬件通信。

UCI 会话状态遵循标准状态机：

状态 值 说明
INIT 0x00 会话已初始化
DEINIT 0x01 会话已反初始化
ACTIVE 0x02 正在测距
IDLE 0x03 已配置但未测距

UCI 层之下是 android.hardware.uwb AIDL HAL（IUwb / IUwbChip）。Android 17 在 hardware/nxp/uwb 随附针对 NXP SR1XX 芯片的参考厂商实现。那个轻量 AIDL 服务可执行文件（android.hardware.uwb-service.nxp，注册为 init 服务 vendor.uwb_hal）桥接到 halimpl/ 下 NXP 的遗留 HAL 核心。该核心负责 HBCI 固件下载、SPI TML 传输、OTP 校准与会话/时间同步——正是它让上述协议栈能在 NXP 设备上完成硬件 UWB 测距。

54.9.7 带外测距规范（v2/v3）

两台设备相互测距时，必须先商定使用哪种技术，也必须商定如何配置它——这一切都发生在任何测距帧发出之前。通用测距栈经带外（out-of-band，OOB）通道——通常是 BLE GATT——用 packages/modules/Uwb/ranging/service/oob/oob_packets.pdl 中定义的小型消息协议完成该协商。该 .pdl 文件是一份包描述，pdlc 工具把它编译成 OOB 发起方与响应方所用的 Java 解析器 （packages/modules/Uwb/ranging/service/java/com/android/server/ranging/oob/）。 每条消息都以相同的两字节 OobMessage 头开始：一个 version 字节和一个 MessageId。

该协议是版本化的。Version 枚举声明 V1 = 1、V2 = 2、CURRENT = 3。因此设备会宣告自己支持哪个修订版，双方回退到最低公共版本。两个较晚的修订版在 v1 基线之上叠加了能力：

  • v2 —— 支持技术切换。 能力交换现在可以说明设备能否在会话中途切换测距技术，而不是拆掉会话重来。CapabilitiesResponseV2 新增了 supported_transitioning 字段，类型为 TechnologyTransitioning，取值 NOT_SUPPORTED 与 MAKE_BEFORE_BREAK。发起方读取该字段，以挑选“先建后断”引擎——即在新技起来之后再放弃当前技术。OOB 协议经 Technology / TechnologySet 类型协商多种技术：UWB、BLE 信道探测、Wi-Fi NAN RTT、BLE RSSI 与 Wi-Fi PD。PDL 把 Wi-Fi PD 标记为开发中的 v4 新增项。

  • v3 —— 运动通知。 新增的 MOTION_NOTIFICATION 消息 （MessageId = 0x8）携带 Motion 载荷，把检测到的运动报告为 NOT_DETECTED、SLIGHT、MODERATE 或 LARGE。其支持情况通过加到 ConfigurationRequestV3 的 supported_motion 字段（类型 MotionIndicator，取值 NOT_SUPPORTED / SUPPORTED）来宣告。发起方会话在 session/OobInitiatorRangingSession.java 中处理收到的 MotionNotification 消息（oob/ 包只存放协议构建器与解析器）。这样应用就能对报告自身在移动的对端做出反应。

完整消息集就是 MessageId 枚举：能力请求/响应、配置请求/响应、停止请求/响应，以及 v3 运动通知。每种消息类型在 PDL 中独立版本化（例如 CapabilitiesResponseV1 对比 CapabilitiesResponseV2，以及 ConfigurationRequestV1 对比 ConfigurationRequestV3）。因此生成的解析器依据头部版本选择正确布局——v3 设备就是这样与 v1 或 v2 对端保持互通。

54.10 tools/mainline 列车构建仓库

至此，本章都把每个模块当作自包含的 APEX 来讨论。实际上 Google 并不逐个交付模块：相关模块被打包成一条列车（train）—— 一组经 Google Play 一同发布、一同标注版本、一同放量的 APEX 与 APK 文件。Android 17 新增一个顶层仓库 tools/mainline，它承载组装这些列车的工具中的开源部分。

54.10.1 为何要独立仓库

各模块自己的 Android.bp 只描述如何构建单个 APEX。而要把它刚构建出的一堆模块产物变成一个已签名、版本正确的列车，是另一步跨模块的工作：它必须把每个模块裁到给定目标所需的架构、构建共享的公共库 APEX、重新打版本号使列车排序高于上一次发布，并把一切装进最终包。历史上这套逻辑放在 Google 内部脚本中。 Android 17 把可复用、可对 AOSP 开放的部分拆到 tools/mainline/train_build/，把专有的模拟数据与胶水代码留在 vendor/google/train_build。

54.10.2 train_build 流水线

tools/mainline/train_build/Android.bp 定义了一组 python_binary_host “worker”可执行文件与 python_library_host 的“action”库，各自实现流水线的一个阶段。该文件还为多数阶段（trim、versioning，以及两个编排器及其 worker）定义了 python_test_host 单元测试：

阶段 Action 模块 职责
Trim（裁剪） trim_action.py 把打包好的 APEX 裁到目标所需 ABI，并把模块 ABI 映射到 DCLA 架构集
DCLA build（DCLA 构建） dcla_build_action.py 构建共享公共库 APEX，跨模块去重原生库
Versioning（版本化） versioning_action.py 递增各模块版本号，使列车排序高于上一次发布
Pack（打包） pack_action.py 把裁剪、版本化后的模块打进最终列车产物

两个编排器把各阶段串起来：primary_train_build_action.py 构建主列车（及其 Go 变体），以共享 DCLA 库 APEX 为中心；generic_train_build_action.py 构建其他列车类型。每条列车建模为 TrainBuildSpec，由 TrainType 枚举派发：

  TELEMETRY = 1
  GO_TELEMETRY = 2
  ADSERVICES = 3
  NPU = 9
  GO_NONUPDATABLE = 4
  NONUPDATABLE = 5
  PRELOAD = 6
  TIMEZONE = 7
  UNKNOWN = 8

存在一个专门的 NPU 列车类型，本身就是 Android 17 的信号：新的 com.android.npumanager 模块（54.11 节）重要到值得按自己的列车节奏交付。

54.10.3 共享 DCLA 库 APEX

54.5.7 节在构建规则层面介绍过 DCLA（动态公共库 APEX）。真正为一条列车组装共享库 APEX 的地方是 primary_train_build_action.py。它命名两个已知的共享库 APEX —— 完整 Android 版与 Android Go 变体：

BIG_ANDROID_DCLA = 'com.google.mainline.primary.libs'

54.11 Android 17 的 apexd 与模块变更

Android 17 对主线的运行期侧做了两项显著改动。第一，apexd 获得了一种在无 loop 设备的情况下激活 EROFS APEX 载荷的方式。第二，模块集合本身扩大，新增 com.android.npumanager 与 com.android.webapp。

54.11.1 EROFS 文件承载挂载

每个被 APEX 占用的 loop 设备都是有限的内核资源。模块数量在攀升（54.3 节现在列出四十多个目录），启动时的 loop 设备压力也随之上升。Android 17 针对 EROFS 载荷用文件承载挂载（file-backed mounting）解决了该问题：若载荷是 EROFS 且不需要自己的 dm-verity 层，apexd 就直接从 .apex 文件挂载载荷，使用内核的 fsoffset= 挂载选项，中间不设 loop 设备。这就是前文 54.2.9 节所示 MountPackageImpl 中的 EROFS 分支：

// Source: system/apex/apexd/apexd.cpp (MountPackageImpl, EROFS branch)

} else if (IsFileBackedMountEnabled() && fs_type == "erofs" &&
           !mount_on_verity) {
    mount_options = std::format("fsoffset={}", *apex.GetImageOffset());
    mount_device = apex.GetPath();

该特性由 system/apex/apexd/apexd.aconfig 中的 aconfig 标志把关（包名 com.android.apex.flags）：

// Source: system/apex/apexd/apexd.aconfig

flag {
  name: "erofs_file_backed_mount"
  namespace: "treble"
  description: "This flag controls if file-backed mounting for EROFS APEXes"
}

flag {
  name: "microdroid_no_loop_device"
  namespace: "treble"
  description: "This flag controls if apexd activates apexes without loop devices"
}

由于并非所有内核都支持文件承载的 EROFS 挂载，apexd 不会盲信该标志。运行期它会用随包的空白 EROFS 镜像做一次性的测试挂载，把结果缓存在非持久的运行期属性 apexd.config.runtime.erofs_file_backed_mount 中，这样同一次启动内的后续检查会跳过探测。厂商可设置的覆盖项是 apexd.config.erofs_file_backed_mount：

// Source: system/apex/apexd/apexd_mount.cpp

static constexpr const char* kApexTestMountFolder = "/apex/.test@0.tmp";
static constexpr const char* kTestMountImage =
    "/system/etc/apexd/empty_erofs.img";

// ...
if (mount(kTestMountImage, kApexTestMountFolder, "erofs", mount_flags,
          "fsoffset=0")) {
    android::base::SetProperty(kFileBackedMountRuntimeProp, "false");
    PLOG(INFO)
        << "File-backed mount is disabled due to test mount failure (mount)";
    return false;
}

配套的 microdroid_no_loop_device 标志让 Microdroid 经 dm-linear 设备而非 loop 设备激活块 APEX。这就是 MountPackageImpl 的 CreateDmLinearForBlockApex 分支，仅在该标志被编译进去时才启用。随着模块集合持续增长，这两条路径共同降低了每 APEX 的 loop 设备开销。

54.11.2 NpuManager 模块

com.android.npumanager（packages/modules/NpuManager/apex/Android.bp）是两个真正新增的 Android 17 模块之一。它负责在争抢**神经网络处理单元（NPU）**的多个应用之间做仲裁。应用拿不到加速器的裸访问权：它们向该模块的服务询问此时加载模型是否合宜，服务依据内存预算与优先级作答。该 APEX 由 RELEASE_NPUMANAGER_MODULE 发布标志把关，并继承 b-launched-apex-module 默认值（min_sdk_version: "36"）：

// Source: packages/modules/NpuManager/apex/Android.bp

apex {
    enabled: select(release_flag("RELEASE_NPUMANAGER_MODULE"), {
        true: true,
        false: false,
    }),
    name: "com.android.npumanager",
    min_sdk_version: "36",
    defaults: ["b-launched-apex-module"],
    bootclasspath_fragments: ["com.android.npumanager-bootclasspath-fragment"],
    systemserverclasspath_fragments:
        ["com.android.npumanager-systemserverclasspath-fragment"],
    native_shared_libs: ["libcom.android.npumanager"],
    jni_libs: ["libnpumanager_service_jni"],
}

bootclasspath 片段贡献 framework-npumanager（对外公开的 NpuManager API 界面）。systemserver 片段贡献 service-npumanager（NpuManagerService）。该模块自带 npumanager-module-sdk，使其他组件可以编译其导出的 API。准入控制的详细架构见第 53 章，包括模型加载策略、Rust 支撑的原生缓冲区管理，以及配套的 android.hardware.npu 厂商 HAL。

54.11.3 WebApp 模块

com.android.webapp（packages/modules/WebApp/apex/Android.bp）是第二个 Android 17 新成员。它把**渐进式 Web 应用（PWA）**作为一等已安装实体来安装与管理，对外暴露 WebAppManager （packages/modules/WebApp/framework/java/android/content/pm/webapp/WebAppManager.java），背后由 APEX 内的 WebAppService APK 支撑。与 NpuManager 一样，它由标志把关（RELEASE_WEBAPP_MODULE）并继承 b-launched-apex-module 默认值：

        false: false,

随包的 aapt2 可执行文件与 webapp-template-res 预构建物让该模块在安装时编译资源，从而把一个 PWA 实体化为可安装的包。其包管理器集成讨论见第 26 章。

54.11.4 Bootstrap 与代码位置目录

packages/modules/ 下 Android 17 新增的内容并非都是可更新 APEX：

  • WebViewBootstrap（packages/modules/WebViewBootstrap/apex/Android.bp） 定义了 com.android.webview.bootstrap，一个本质上空的 bootstrap APEX（v-launched-apex-module 默认值），仅用于占位一个挂载点。它不捆绑任何应用、库或 classpath 片段。
  • ImsStack（packages/modules/ImsStack/）是一个代码位置，存放电话栈使用的 Java、原生库与特性标志，自身不产出 APEX。
  • GenericBootstrappingArchitecture （packages/modules/GenericBootstrappingArchitecture/）交付一个名为 GbaService 的 android_app（Generic Bootstrapping Architecture 运营商认证），而不是 APEX。

在推断 apexd 启动时究竟挂载了什么时，务必把这类目录与真正的 APEX 模块区分开：只有 Android.bp 中声明了 apex {（或 custom_apex { / virt_apex {）段的目录才会贡献一个 /apex/<name> 挂载。

关键源码文件

Project Mainline 是 Android 历史上最重大的架构变革之一。Google 把平台组件打包成可独立更新的 APEX 模块，借这些模块即可向数十亿设备交付安全修复与功能改进，而无需等待传统的 OEM 更新流程。

本章要点：

  • APEX 是一个 ZIP，内含经 dm-verity 签名的文件系统镜像，从而让原生代码、Java 库与配置作为一个原子单元被更新。

  • apexd 管理完整生命周期：启动时扫描各分区，创建 loop 设备（在 Android 17 则是 dm-linear / 文件承载 EROFS）与 dm-verity 表，bind mount 活动版本，处理分阶段更新，并支持回滚。

  • packages/modules/ 中四十多个模块覆盖网络、安全、媒体、电话、机器学习等。每个都有自己的 APEX 名、签名密钥与版本生命周期。Android 17 新增 com.android.npumanager 与 com.android.webapp（均由标志把关），以及新的 tools/mainline 列车构建仓库。

  • SDK 扩展解决了运行期 API 可用性问题：启动时依据实际安装的模块版本推导扩展版本号。Android 17（API 37，CinnamonBun）把扩展数据库基线提高到版本 22，并新增“C”这一扩展轴。

  • 模块边界经 apex_available、API 界面注解（@SystemApi）、min_sdk_version 与 hidden-API 策略强制。

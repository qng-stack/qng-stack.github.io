第 52 章：CompanionDeviceManager 与虚拟设备

Android 的 CompanionDeviceManager（CDM，设备伴侣管理）与 VirtualDeviceManager（VDM，虚拟设备管理）构成一套分层基础设施，让手机与外接硬件——智能手表、平板、车机、PC，甚至 AR 眼镜——配对，并把它们呈现为一等的计算界面。CDM 管理设备关联的生命周期、在场检测、安全传输通道与跨设备数据同步。VDM 建立在 CDM 关联之上，让远端伴侣设备承载虚拟显示器、虚拟输入设备、虚拟传感器、虚拟摄像头与虚拟音频管线。效果上，它把整套 Android 体验投射到外部硬件上。

本章走查这两个系统的完整服务端实现，从最初的 BLE／蓝牙发现握手开始，到一个正在运行、可注入触摸事件并重定向音频流的虚拟显示器为止。

所有源码路径均相对 AOSP 源码树根。

CDM 实施严格的权限模型。关键权限以 static import 的形式声明在 CompanionDeviceManagerService.java 顶部：

import static android.Manifest.permission.ACCESS_COMPANION_INFO;
import static android.Manifest.permission.ACCESS_COMPANION_MESSAGE_PCC;

import static android.Manifest.permission.BLUETOOTH_CONNECT;
import static android.Manifest.permission.DELIVER_COMPANION_MESSAGES;
import static android.Manifest.permission.MANAGE_COMPANION_DEVICES;
import static android.Manifest.permission.REQUEST_COMPANION_SELF_MANAGED;
import static android.Manifest.permission.REQUEST_OBSERVE_COMPANION_DEVICE_PRESENCE;

源码： frameworks/base/services/companion/java/com/android/server/companion/CompanionDeviceManagerService.java，第 20-28 行。

它们对应不同的能力：

  • ASSOCIATE_COMPANION_DEVICES —— 创建任何新关联所必需。

  • REQUEST_COMPANION_SELF_MANAGED —— 自管理关联所必需（此时由应用自己管理传输，而不依赖基于 MAC 地址的在场检测）。

  • REQUEST_OBSERVE_COMPANION_DEVICE_PRESENCE —— 注册在场回调（伴侣设备出现或消失时的 BLE／BT 通知）所必需。

  • USE_COMPANION_TRANSPORTS —— 为跨设备消息挂载系统数据传输通道（文件描述符）所必需。

  • DELIVER_COMPANION_MESSAGES —— 通过 CDM 传输通道发送消息所必需。

  • MANAGE_COMPANION_DEVICES —— 供 shell 命令与管理操作使用的系统级权限。

  • ACCESS_COMPANION_INFO —— 查询其他用户的伴侣信息所必需。

  • ACCESS_COMPANION_MESSAGE_PCC —— Android 17 新增；为受信任设备与 AI 智能体流程使用的私有计算核心消息路径把关。

52.1.3 启动时序

CompanionDeviceManagerService 是一个参与标准服务端启动生命周期的 SystemService。CompanionTransportManager、SystemDataTransferProcessor 及其他处理器都在服务构造函数中创建。在 onStart() 期间，服务会：

  1. 经 AssociationStore.refreshCache() 从磁盘读取已持久化的关联数据，并丢弃所有已被撤销的关联。
  2. 读取 UUID 观察存储，并发布 binder 与本地服务。

随后 onBootPhase() 完成与阶段相关的动作：

  1. 在 PHASE_SYSTEM_SERVICES_READY 时，注册跟踪包移除与变更的 PackageMonitor。
  2. 在 PHASE_BOOT_COMPLETED 时，初始化 DevicePresenceProcessor 以开始监控 BLE／BT 连接，安排 InactiveAssociationsRemovalService，并调用 CrossDeviceSyncController.onBootCompleted() 做通话元数据同步。

关联数据存放在设备加密（DE）存储中，因此在用户解锁设备之前即可用。AssociationStore.refreshCache() 的实现明确说明了这一点：

// The data is stored in DE directories, so we can read the data for all users now
// (which would not be possible if the data was stored to CE directories).
Map<Integer, Associations> userToAssociationsMap =
        mDiskStore.readAssociationsByUsers(userIds);

源码： frameworks/base/services/companion/java/com/android/server/companion/association/AssociationStore.java，第 177-180 行（位于第 164 行开始的 refreshCache() 内）。

52.2.2 设备配置

设备配置决定授予伴侣应用哪些权限与角色。需要用户确认的配置定义在 AssociationRequestsProcessor 中：

private static final Set<String> DEVICE_PROFILES_WITH_REQUIRED_CONFIRMATION = new ArraySet<>(
        Arrays.asList(
                AssociationRequest.DEVICE_PROFILE_APP_STREAMING,
                AssociationRequest.DEVICE_PROFILE_NEARBY_DEVICE_STREAMING));

源码： frameworks/base/services/companion/java/com/android/server/companion/association/AssociationRequestsProcessor.java，第 144-147 行。

完整的设备配置集合包括：

  • DEVICE_PROFILE_WATCH —— 智能手表伴侣
  • DEVICE_PROFILE_GLASSES —— AR／VR 眼镜
  • DEVICE_PROFILE_APP_STREAMING —— 远端显示／应用投屏
  • DEVICE_PROFILE_NEARBY_DEVICE_STREAMING —— 邻近设备投射
  • DEVICE_PROFILE_AUTOMOTIVE_PROJECTION —— 车机投射
  • DEVICE_PROFILE_COMPUTER —— 台式机／笔记本伴侣
  • DEVICE_PROFILE_WEARABLE_SENSING —— 可穿戴健康／传感器设备
  • DEVICE_PROFILE_VIRTUAL_DEVICE —— 受限的虚拟设备角色 （android.app.role.COMPANION_DEVICE_VIRTUAL_DEVICE）
  • DEVICE_PROFILE_FITNESS_TRACKER —— 健身手环／追踪器 伴侣（标志 FLAG_BAND_DEVICE_PROFILE）
  • DEVICE_PROFILE_MEDICAL —— 医疗设备伴侣（标志 FLAG_ENABLE_MEDICAL_PROFILE）

后两个是由标志门控的配置，Android 16 与 17 中都存在，一直留在各自的 aconfig 标志之后，并非 17 的新增。二者都声明在 frameworks/base/core/java/android/companion/AssociationRequest.java 中，各自以 @FlaggedApi 注解指向 frameworks/base/core/java/android/companion/flags.aconfig 中的 aconfig 标志。

DEVICE_PROFILE_FITNESS_TRACKER 映射到角色字符串 android.app.role.COMPANION_DEVICE_FITNESS_TRACKER，DEVICE_PROFILE_MEDICAL 映射到 android.app.role.COMPANION_DEVICE_MEDICAL。

每个配置都映射到一个 Android 角色。创建关联时，伴侣应用会自动被授予相应角色（若它尚未持有）：

addRoleHolderForAssociation(mContext, association, success -> {
    if (success) {
        Slog.i(TAG, "Added " + deviceProfile + " role to userId="
                + association.getUserId() + ", packageName="
                + association.getPackageName());
        mAssociationStore.addAssociation(association);
        sendCallbackAndFinish(association, callback, resultReceiver);
    } else {
        Slog.e(TAG, "Failed to add u" + association.getUserId()
                + "\\" + association.getPackageName()
                + " to the list of " + deviceProfile + " holders.");
        sendCallbackAndFinish(null, callback, resultReceiver);
    }
});

源码： AssociationRequestsProcessor.java，第 390-403 行。

每个配置的角色到权限映射位于 frameworks/base/services/companion/java/com/android/server/companion/utils/RolesUtils.java。 两个 Android 17 配置在那里有不同处理。DEVICE_PROFILE_FITNESS_TRACKER 是一个角色别名：ROLE_ALIASES 映射把它指向 DEVICE_PROFILE_WATCH。因此健身追踪器复用手表角色及其权限集（通知、电话、通话记录、短信、联系人、日历、邻近设备、媒体输出），而不定义单独的角色。

DEVICE_PROFILE_MEDICAL 是它自己的角色，在 PROFILE_PERMISSION_SETS 中权限集更窄：发布通知、邻近设备、精确闹钟调度与绕过免打扰。这反映出医疗伴侣需要投递时间关键的告警，而不需要手表那样广泛的消息访问。

processNewAssociationRequest() 中的完整流程实现：

public void processNewAssociationRequest(@NonNull AssociationRequest request,
        @NonNull String packageName, @UserIdInt int userId,
        @NonNull IAssociationRequestCallback callback) {
    // 1. Enforce permissions and other requirements.
    enforcePermissionForCreatingAssociation(mContext, request, packageUid);
    enforceUsesCompanionDeviceFeature(mContext, userId, packageName);

    // 2a. Check if association can be created without launching UI
    if (request.isSelfManaged() && !request.isForceConfirmation()
            && !DEVICE_PROFILES_WITH_REQUIRED_CONFIRMATION.contains(request.getDeviceProfile())
            && !willAddRoleHolder(request, packageName, userId)) {
        createAssociationAndNotifyApplication(request, packageName, userId,
                /* macAddress */ null, callback, /* resultReceiver */ null);
        return;
    }
    // ...
    // 2b. Build a PendingIntent for launching the confirmation UI
    request.setSkipPrompt(mayAssociateWithoutPrompt(packageName, userId));
    // ...
}

源码： AssociationRequestsProcessor.java，第 171-249 行。权限辅助方法 enforcePermissionForCreatingAssociation 与 enforceUsesCompanionDeviceFeature 是对 com.android.server.companion.utils.PermissionsUtils 与 PackageUtils 的 static import。这一重构是在 Android 17 引入的。

52.2.5 AssociationStore——持久化与变更通知

AssociationStore 是关联记录的中央 CRUD 接口。它维护一个内存缓存（mIdToAssociationMap），后端是经 AssociationDiskStore 实现的磁盘存储。

frameworks/base/services/companion/java/com/android/server/companion/association/
    AssociationStore.java
    AssociationDiskStore.java
    Associations.java

该存储支持两类变更监听器：

  1. 本地监听器（OnChangeListener）——供其他服务端组件使用 （DevicePresenceProcessor、TransportManager 等）。

  2. 远端监听器（IOnAssociationsChangedListener）——供应用 经 Binder 使用。

变更类型已枚举：

public static final int CHANGE_TYPE_ADDED = 0;
public static final int CHANGE_TYPE_REMOVED = 1;
public static final int CHANGE_TYPE_UPDATED_ADDRESS_CHANGED = 2;
public static final int CHANGE_TYPE_UPDATED_ADDRESS_UNCHANGED = 3;
public static final int CHANGE_TYPE_UPDATED_DATA_SYNC_TYPES = 4;

源码： AssociationStore.java，第 77-81 行。Android 17 新增 CHANGE_TYPE_UPDATED_DATA_SYNC_TYPES，在按关联的系统数据同步标志发生变化时触发（见 52.3.6 节的 DataSyncProcessor）。

通知逻辑区分改地址与不改地址的更新。远端监听器只在重大变更（增、删、地址变更）时收到通知，轻微配置调整不发：

这一分类决定消息的处理方式：

  • 请求消息（0x63xxxxxx）—— 等待远端的响应。发送方会得到一个 CompletableFuture<byte[]>，在响应到达时完成。

  • 单向消息（0x43xxxxxx）—— 发后即忘；future 在发送时立即完成。

  • 响应消息（0x33xxxxxx）—— 完成某个待决请求的 future。

        throws IOException {
    if (isOneway(message)) {
        processOneway(message, data);
    } else if (isRequest(message)) {
        try {
            processRequest(message, sequence, data);
        } catch (IOException e) {
            Slog.w(TAG, "Failed to respond to 0x" + Integer.toHexString(message), e);
        }

        processResponse(message, sequence, data);
    } else {
        Slog.w(TAG, "Unknown message 0x" + Integer.toHexString(message));
    }
}

整个 API 受 task_continuity aconfig 标志控制 （frameworks/base/core/java/android/companion/flags.aconfig:69，命名空间 companion， 导出为 android.companion.Flags.FLAG_TASK_CONTINUITY）。另一道门是相匹配的 CompanionDeviceManager.FLAG_TASK_CONTINUITY = 1 << 1 （CompanionDeviceManager.java:233）数据同步能力。该能力授权传输在 两台已关联设备之间承载交接载荷。没有 CDM 关联就没有交接：该特性搭乘 52.3.1–52.3.4 节所述的同一安全 CDM 通道。

两端都是真实的、用户自有的设备——手机与平板，或手机与 Chromebook——它们经 CompanionDeviceManager（52.2 节）配对。这与 52.4–52.6 节的虚拟显示器无关：那里是单台设备驱动一个投射出来的界面。在交接中，每台设备各自运行应用的一份副本，只有一段紧凑的描述符跨越链路，告诉接收方如何重建该 activity （52.3.11 节）。

HandoffActivityDataRequestInfo.isActiveRequest() 告诉 activity 为什么被索取。系统发出两类请求（见 52.3.10 节）：

  • 一类是缓存式请求（isActiveRequest() == false），在 activity 停止时被预先发起，使附近设备一开口就能立刻拿到快照；
  • 另一类是主动式请求（isActiveRequest() == true），在实际发生交接的时刻发出，用于捕获最新状态。

AOSP 交付框架与系统服务，但不交付那个列出邻近设备任务的启动器磁贴。该界面属于系统启动器／shell，后者通过 TaskContinuityManager 的监听器 API 消费远端任务。

52.3.11 应用到应用、应用到 Web，以及公开的管理器 API

HandoffActivityData（frameworks/base/core/java/android/app/HandoffActivityData.java:48） 携带接收方所需的全部信息，支持两种投递模式：

  • 应用到应用：由 ComponentName（getComponentName()，第 112 行）加一个 装 extras 的 PersistableBundle 构成。当同一原生应用已安装时，接收方直接深链进入。
  • 应用到 Web：HandoffActivityData.createWebHandoff(Uri)（第 61 行）产出一个 解析为 URL 的数据对象。任何应用到应用的载荷也可携带一个兜底 URI（setFallbackUri()），在接收方无法启动该组件时使用。

目标应用缺失是否阻断交接，由 HandoffActivityParams.isAllowHandoffWithoutPackageInstalled() （HandoffActivityParams.java:98）控制。置位后，即使另一台设备上没有目标应用，交接也会转向 Web 兜底。

交接能携带哪些数据。 HandoffActivityData 是一个小巧、完全可序列化的 描述符，而不是批量状态传输。其全部载荷只有三个字段 （HandoffActivityData.java:50-52）：一个可选的 ComponentName（要重新启动的 activity）、一个可选的兜底 Uri，以及一个装 extras 的 PersistableBundle（getExtras()， 默认为空）。

extras 刻意采用 PersistableBundle 而非完整的 Bundle。因此只有 PersistableBundle 能序列化的类型才跨越链路： boolean、int、long、double、String、它们的数组，以及嵌套的 PersistableBundle。 Parcelable、Binder 句柄、位图与文件描述符都不能放进去。

框架还要求 extras 可在设备间移植。Builder 的 setExtras() javadoc（HandoffActivityData.java:214）对此发出警告：extras “必须能安全地 传给另一台设备，因此不应引用任何设备专属信息，例如 文件路径。”

比原始状态更重的东西——半编辑的文档、已解码的媒体缓冲区、 已认证的会话——都不放进交接。接收方 activity 应依据组件加 extras 重建它们。例如，可以从用户账户或云端重新拉取。在线路上，该描述符被包进一个 HandoffActivityDataMessage。该消息还携带发送应用的 packageSignatureDigests，使接收方能确认自己启动的是同一个应用，而不是仿冒者。

想要观察并触发交接的应用与启动器，使用 TaskContinuityManager 系统服务（@SystemService(Context.TASK_CONTINUITY_SERVICE)， TaskContinuityManager.java:46）：

  • registerRemoteTaskListener(...) / unregisterRemoteTaskListener(...)，接收 已配对设备通告的 RemoteTask 描述符集合。每个 RemoteTask 暴露 getTaskId()、getCompanionDeviceAssociationId()、getLabel()、getIcon() 与 isHandoffEnabled()。
  • requestHandoff(...)，把某个任务拉取到本设备。

这些调用由专用权限把关，且在 AIDL stub 上强制 （ITaskContinuityManager.aidl）。所需权限为 READ_REMOTE_TASKS（列出远端任务，第 29 行）、 REQUEST_TASK_HANDOFF（拉取任务，第 35 行）、MODIFY_HANDOFF_SETTINGS （setHandoffForDeviceEnabled，第 39 行）与 READ_HANDOFF_SETTINGS（第 42 行）。

结果与可用性经 TaskContinuityManager 上的 HANDOFF_REQUEST_RESULT_* 与 HANDOFF_AVAILABILITY_STATUS_* 常量返回 （TaskContinuityManager.java:59-103）。例如，当设备缺少相应射频时，结果是 HANDOFF_AVAILABILITY_STATUS_UNSUPPORTED_HARDWARE；当发送方始终未上报数据时，结果是 HANDOFF_REQUEST_RESULT_FAILURE_TIMEOUT。

52.9 CrossDeviceSync 服务

前文所述的一切都运行在 system_server 内。52.3.7 节的 CrossDeviceSyncController 是一个框架组件，经 CDM 传输代理通话元数据。Android 17 还交付了一个独立的、体量大得多的应用层服务，它是 CDM 关联／传输机制用于通用数据同步的主要生产消费者。它在框架之外，是一个独立的平台应用：

每个特性在 NetworkManager 上创建一个具名 Network（例如飞行模式特性使用 NETWORK_ID = "apm_sync_network"），并把状态存放在 SharedDataStore 中。 该存储被描述为“一个与远端设备保持同步的数据存储……最终在其他已授权设备间同步” （SharedDataStore.java，第 30-37 行）。 其具体实现 SubmergeSharedDataStore，在按特性的 SQLite 数据库之上叠加 Google 的 Submerge 最终一致同步库。全局数据库为 cross_device_sync_global_db （SyncServiceInjectorImpl.java，第 77 行）。

飞行模式特性还回连到 52.2.1 节的按关联 systemDataSyncFlags：它以 CompanionDeviceManager.FEATURE_CROSS_DEVICE_SYNC 与 CompanionDeviceManager.FLAG_AIRPLANE_MODE 为键，用它们判断某条关联是否启用了同步（AirplaneModeSyncManager.java，import 见第 19-23 行）。 这正是框架侧 DataSyncProcessor （52.3.6 节）与 CHANGE_TYPE_UPDATED_DATA_SYNC_TYPES（52.2.5 节）所管理的那套标志位掩码。应用与框架借此就哪些特性处于活动状态达成一致。

最后，MetadataPublisher 写入按用户的 CDM 元数据 （putBooleanMetaData／putIntMetaData／putStringMetaData），远端设备可据此发现本设备支持哪些能力。这些元数据走 52.3.6 节的 DataSync 路径，经代理的 setLocalMetadata／ getLocalMetadata（MetadataPublisher.java，第 20-37 行）。

52.9.5 调试界面

SyncService.dump() 在可调试构建上兼作 shell 命令入口。SyncServiceShellCommand 支持一个维护命令 reset notifications，用于清掉被限流的同步通知：

adb shell dumpsys activity service com.android.crossdevicesync/.services.SyncService \
    reset notifications

在不可调试构建上，同一个 dump() 落到打印 NetworkManager、MetadataPublisher 与按特性的状态。源码： SyncService.java，第 125-140 行； packages/services/CrossDeviceSync/src/com/android/crossdevicesync/services/SyncServiceShellCommand.java， 第 33-67 行。

简言之，CrossDeviceSync 是 52.3.6 与 52.3.7 节那些进程内控制器在产品化层面的应用层对应物。它是一个特权可穿戴伴侣应用，把 CDM 原始的关联、传输、在场、动作与元数据原语，织成一张最终一致的多特性同步网。它本身并不向 system_server 添加任何东西。

52.10.4 使用 VirtualDeviceManager API

要以编程方式创建虚拟设备，应用需要：

  1. 一条具有合适设备配置的 CDM 关联。
  2. CREATE_VIRTUAL_DEVICE 权限 —— 在核心 manifest 中以 protectionLevel="internal|role" 声明，只授予持有相关角色的应用；普通应用无法申请。
  3. 某些特性还需额外权限：
    • ADD_TRUSTED_DISPLAY，用于剪贴板策略定制。
    • ADD_ALWAYS_UNLOCKED_DISPLAY，用于常解锁显示器。
    • ADD_MIRROR_DISPLAY，用于镜像显示器。
    • ACCESS_COMPUTER_CONTROL，用于计算机控制特性。

示例代码流程：

// Step 1: Create a CompanionDeviceManager association
CompanionDeviceManager cdm = getSystemService(CompanionDeviceManager.class);
AssociationRequest request = new AssociationRequest.Builder()
        .setDeviceProfile(AssociationRequest.DEVICE_PROFILE_APP_STREAMING)
        .setDisplayName("My Companion")
        .setSelfManaged(true)
        .build();
cdm.associate(request, callback, handler);

// Step 2: In the callback, create a virtual device
VirtualDeviceManager vdm = getSystemService(VirtualDeviceManager.class);
VirtualDeviceParams params = new VirtualDeviceParams.Builder()
        .setDevicePolicy(VirtualDeviceParams.POLICY_TYPE_AUDIO,
                VirtualDeviceParams.DEVICE_POLICY_CUSTOM)
        .setName("Streaming Device")
        .build();
VirtualDevice device = vdm.createVirtualDevice(associationInfo.getId(), params);

// Step 3: Create a virtual display (an Executor, then a VirtualDisplay.Callback)
VirtualDisplay display = device.createVirtualDisplay(
        new VirtualDisplayConfig.Builder("MyDisplay", 1920, 1080, 240)
                .build(),
        executor, displayCallback);

// Step 4: Create input devices
VirtualTouchscreenConfig touchConfig = new VirtualTouchscreenConfig.Builder(1920, 1080)
        .setAssociatedDisplayId(display.getDisplay().getDisplayId())
        .build();
device.createVirtualTouchscreen(touchConfig);

本章小结

CompanionDeviceManager 与 VirtualDeviceManager 共同构成了一套支持多设备 Android 体验的完整框架：

  • CDM 负责信任关系：发现、用户同意、关联持久化、在场检测、安全传输与数据同步。其模块化的处理器架构让各项关注点彼此隔离，而 AssociationStore 提供带变更通知的统一数据层。

  • VDM 负责虚拟表示。它创建带细粒度 activity 策略的虚拟显示器；注入来自远端硬件的输入，并把音频路由到伴侣设备或从伴侣设备路由回来；还提供虚拟传感器并控制摄像头访问。GenericWindowPolicyController 在 WindowManager 层面强制安全，确保只有经授权的 activity 能出现在虚拟界面上。

  • 传输层 把两者联系起来。带证明校验的 UKEY2 加密通道在已配对设备之间承载权限同步数据、通话元数据、任务交接消息与自定义应用数据。

  • 安全模型 是分层的。CDM 权限把关关联创建，设备配置控制角色授予，传输加密保护传输中的数据，摄像头注入阻断未授权的硬件访问，窗口策略防止敏感 activity 泄漏到远端显示器。

  • Android 17 的新增 拓宽了该框架。CDM 增加了持久化的受信任设备密钥（devicetrust/）与统一的电量豁免（powerexemption/），在既有的动作请求路径（actionrequest/，自 Android 16 延续）上增加了新的结果常量，并保留关联的备份／恢复。VDM 增加了计算机控制会话（virtual/computercontrol/），让获批的智能体在按智能体的明确同意下自动化虚拟显示器上的应用。

这套架构支撑了从智能手表配对到完整桌面级应用投屏的各种用例，而它们都使用同一套基础设施。

第 36 章：电话与 RIL

第 36 章：电话与 RIL

Android 的电话子系统是平台中最复杂、分层最重的部分之一：它横跨多个层次。最上层是任何应用都能调用的公开 SDK API（TelephonyManager、SmsManager）；其下是一个特权系统服务（PhoneInterfaceManager）与一套内部的「phone」对象层次；再往下是无线接口层（Radio Interface Layer，RIL），负责把请求序列化后送往蜂窝调制解调器；最底层则是硬件厂商实现的 AIDL HAL。

本章沿 AOSP 源码追踪这条链上的每一跳，解释 SIM、SMS、IMS、运营商配置与数据连接的运作机制，并提供在真机或模拟器上探查该协议栈的动手练习。

36.1 电话架构

36.1.1 全景视图

Android 电话功能被组织为四个主要层次，各自运行在不同的进程或地址空间中：

  1. 应用层 —— 第三方或系统应用，使用公开的 TelephonyManager、SmsManager、SubscriptionManager 或 TelecomManager API。
  2. 框架层 —— 运行在 com.android.phone 进程中的电话服务，包括 PhoneInterfaceManager（ITelephony 的 Binder 桩）与 Phone 对象层次。
  3. RIL 层 —— RIL.java 类，负责把高层命令转换为指向厂商无线电守护进程的 AIDL/HIDL 调用。
  4. HAL／调制解调器层 —— 厂商提供的无线电 HAL 实现 （IRadioModem、IRadioSim、IRadioNetwork 等），真正与基带处理器通信。

36.1.3 PhoneInterfaceManager——Binder 网关

PhoneInterfaceManager 位于 packages/services/Telephony/，继承 ITelephony.Stub。它是电话协议栈中最大的类之一（只有 TelephonyManager 本身更大）。它承担三项关键职责：

  1. 权限执行 —— 每个方法都会依据所需的权限（READ_PHONE_STATE、MODIFY_PHONE_STATE、 READ_PRIVILEGED_PHONE_STATE、运营商特权等）校验调用方 UID。
  2. Phone 选择 —— 对多 SIM 设备，它通过 PhoneFactory 把调用方的 订阅 ID 映射到正确的 Phone 对象。
  3. 委托 —— 调用内部 Phone 层次并返回结果。

权限检查的典型模式：

// packages/services/Telephony/src/com/android/phone/PhoneInterfaceManager.java
public String getImeiForSlot(int slotIndex, String callingPackage,
        String callingFeatureId) {
    Phone phone = PhoneFactory.getPhone(slotIndex);
    if (phone == null) {
        return null;
    }
    int subId = phone.getSubId();
    enforceCallingPackage(callingPackage, Binder.getCallingUid(), "getImeiForSlot");
    if (!TelephonyPermissions.checkCallingOrSelfReadDeviceIdentifiers(mApp, subId,
            callingPackage, callingFeatureId, "getImeiForSlot")) {
        return null;
    }

    final long identity = Binder.clearCallingIdentity();
    try {
        return phone.getImei();
    } finally {
        Binder.restoreCallingIdentity(identity);
    }
}

若无线电 HAL 进程崩溃，RIL 会通过 Binder 死亡通知接收器察觉，并尝试恢复：

收到死亡通知后，RIL 会：

  2. 清空代理引用。
  3. 通知 ServiceStateTracker 与 DataNetworkController。
  4. 尝试重新绑定到该 HAL 服务。

36.2.10 RilHandler——内部事件处理

RIL 拥有自己的内部 Handler 子类，用于处理超时与死亡事件：

// frameworks/opt/telephony/src/java/com/android/internal/telephony/RIL.java
public class RilHandler extends Handler {
    @Override
    public void handleMessage(Message msg) {
        RILRequest rr;
        switch (msg.what) {
            case EVENT_WAKE_LOCK_TIMEOUT:
                // Haven't heard back from the last request.  Assume we're
                // not getting a response and release the wake lock.
                synchronized (mRequestList) {
                    if (msg.arg1 == mWlSequenceNum && clearWakeLock(FOR_WAKELOCK)) {
                        if (mRadioBugDetector != null) {
                            mRadioBugDetector.processWakelockTimeout();
                        }
                        if (RILJ_LOGD) {
                            int count = mRequestList.size();
                            riljLog("WAKE_LOCK_TIMEOUT mRequestList=" + count);
                            for (int i = 0; i < count; i++) {
                                rr = mRequestList.valueAt(i);
                                riljLog(i + ": [" + rr.mSerial + "] "
                                        + RILUtils.requestToString(rr.mRequest));
                            }
                        }
                    }
                }
                break;

            case EVENT_ACK_WAKE_LOCK_TIMEOUT:
                if (msg.arg1 == mAckWlSequenceNum && clearWakeLock(FOR_ACK_WAKELOCK)) {
                    if (RILJ_LOGV) riljLog("ACK_WAKE_LOCK_TIMEOUT");
                }
                break;

            case EVENT_BLOCKING_RESPONSE_TIMEOUT:
                int serial = (int) msg.obj;
                rr = findAndRemoveRequestFromList(serial);
                if (rr == null) break;
                if (rr.mResult != null) {
                    Object timeoutResponse = getResponseForTimedOutRILRequest(rr);
                    AsyncResult.forMessage(rr.mResult, timeoutResponse, null);
                    rr.mResult.sendToTarget();
                }
                decrementWakeLock(rr);
                rr.release();
                break;

            case EVENT_RADIO_PROXY_DEAD:
                // HIDL radio proxy died
                ...
                resetProxyAndRequestList(service);
                break;

            case EVENT_AIDL_PROXY_DEAD:
                // AIDL radio proxy died
                ...
                resetProxyAndRequestList(aidlService);
                break;
        }
    }
}

36.2.12 Binder 死亡处理

依据 HAL 绑定类型，RIL 使用两种不同的死亡通知机制：

HIDL（遗留）：HwBinder.DeathRecipient

// frameworks/opt/telephony/src/java/com/android/internal/telephony/RIL.java
final class RadioProxyDeathRecipient implements HwBinder.DeathRecipient {
    @Override
    public void serviceDied(long cookie) {
        riljLog("serviceDied");
        mRilHandler.sendMessageAtFrontOfQueue(mRilHandler.obtainMessage(
                EVENT_RADIO_PROXY_DEAD,
                HAL_SERVICE_RADIO, 0, cookie));
    }
}

AIDL（现代）：IBinder.DeathRecipient

private final class BinderServiceDeathRecipient implements IBinder.DeathRecipient {
    private IBinder mBinder;
    private final int mService;

    @Override
    public void binderDied() {
        riljLog("Service " + serviceToString(mService) + " has died.");
        mRilHandler.sendMessageAtFrontOfQueue(mRilHandler.obtainMessage(
                EVENT_AIDL_PROXY_DEAD, mService, 0, mLinkedFlags));
        unlinkToDeath();
    }
}

任一服务死亡时，都会调用 resetProxyAndRequestList()，其作用是：

  1. 清空该服务代理引用。
  2. 为所有待处理请求发送错误响应。
  3. 释放所有持有的 wake lock。
  4. 触发重新连接尝试。

对 AIDL 服务而言，重置一个服务会导致所有 AIDL 服务一并重置，因为它们通常位于同一个厂商进程中。

36.7.12 集成的 VoIP 通话记录

在 Android 17 之前，系统通话记录实际上只是蜂窝通话记录。通过 Telecom 管理自身通话的 VoIP 应用（自管理的 ConnectionService 或 CallControl API）不得不自行维护应用内历史。其通话不会与蜂窝通话一起出现在系统拨号器的最近记录中。Android 17 引入了集成通话记录：VoIP 通话现在可以写入共享的 CallLog.Calls provider，并由系统拨号器展示。该特性提供了用户选项开关与逐通话的头像。

这项工作由两个 aconfig 开关控制，它们位于不同的 git 项目与包中。第一阶段开关是 integrated_call_logs （packages/services/Telecomm/flags/telecom_integrated_call_log.aconfig，包 com.android.server.telecom.flags）。第二阶段开关是 integrated_call_logs_stage2（packages/modules/Telephony/telecom/flags/26Q2_migration_flags.aconfig， 包 android.telecom.flags）。

VoIP 应用在创建通话时通过 CallAttributes （frameworks/base/telecomm/framework/java/android/telecom/CallAttributes.java）选择该通话是否纳入记录。其 Builder 新增了：

  • setLogExcluded(boolean)（开关 FLAG_INTEGRATED_CALL_LOGS）—— 把该通话完全排除在系统记录之外。
  • setIsGroupCall(boolean) 与新的通话类型 CallAttributes.MESSAGING （开关 FLAG_INTEGRATED_CALL_LOGS_STAGE2）—— 标记群组／会议呼叫以及回调式消息通话。
  • setContactUri(Uri)（开关 FLAG_INTEGRATED_CALL_LOGS_STAGE2）—— 指向应用 VoIP 通讯录或 CP2 联系人的 URI。拨号器用它解析参与者显示名与头像图像，用于记录条目。

通话记录契约在 CallLog.Calls （frameworks/base/core/java/android/provider/CallLog.java）中做了对应扩充：新增一个与 Telecom 通话关联的 UUID 列（开关 FLAG_INTEGRATED_CALL_LOGS）以及 FEATURES_GROUP_CALL 特性位。此外还提供了独立的 VoIP 行查询面，以免打扰旧版拨号器：包括 CONTENT_VOIP_URI、 INCLUDE_VOIP_CALLS_PARAM_KEY 查询参数，以及预构建的 CONTENT_URI_WITH_VOIP_CALLS；后两者由 FLAG_FILTER_VOIP_CALL_LOGS 控制。理解集成记录的新拨号器用「包含 VoIP 通话」的方式查询，而不理解的拨号器仍只看到蜂窝行。

用户偏好经由 TelecomManager （frameworks/base/telecomm/framework/java/android/telecom/TelecomManager.java）贯通。 ACTION_CONFIGURE_CALL_LOG_INTEGRATION 拉起设置界面，供用户为某个 VoIP 应用启用或停用记录。该选择变化时，Telecom 向受影响的应用广播 ACTION_VOIP_CALL_LOG_PREFERENCE，并通过 EXTRA_VOIP_CALL_LOG_PREFERENCE_STATUS 携带新状态。应用据此重新读取偏好，停止或恢复贡献记录。以上三者均由 FLAG_INTEGRATED_CALL_LOGS_STAGE2 控制。

36.8.20 把 OTT 通话自动路由到优质切片（Android 17）

网络切片（见 §36.8.19）为平台提供了一种把特定流量放到专用 5G 连接上的手段，但哪些流量应当获得切片仍是悬而未决的问题。Android 17 给出了一个具体答案：当一路 over-the-top（OTT）语音或视频通话进行中时，系统可代表通话应用请求一个优质切片，通话由此获得低时延路径，应用无需自行接入切片请求逻辑。

该机制位于 Connectivity Mainline 模块 （packages/modules/Connectivity）而非电话协议栈，但它建立在同一套 URSP／切片设施之上。关键能力是一个新的 NetworkCapabilities 常量， NET_CAPABILITY_PRIORITIZE_UNIFIED_COMMUNICATIONS（值 38，位于 packages/modules/Connectivity/framework/src/android/net/NetworkCapabilities.java）。其 javadoc 指出，该网络「可能为高优先级、低时延的数据路径提供专用切片」。javadoc 同时说明，OTT 应用可以直接通过 ConnectivityManager.requestNetwork() 请求该能力；系统也可在检测到活跃 OTT 通话时代表应用发起请求。

系统驱动路径是本次新增的部分。ConnectivityCallListenerService （packages/modules/Connectivity/framework/src/android/net/ConnectivityCallListenerService.java） 监听 Telecom 通话事件，并在 isCallEligibleForSlicing() 中判断某路通话是否符合条件。满足以下两个条件即视为合格：第一，它是一路事务性、自管理的 VoIP 通话（携带 Call.Details.PROPERTY_IS_TRANSACTIONAL 且为自管理）；第二，应用未设置 PhoneAccount.CAPABILITY_OPT_OUT_OF_PREMIUM_NETWORK 标志 （frameworks/base/telecomm/framework/java/android/telecom/PhoneAccount.java， 值 0x200000）。

这类通话开始时，该服务解析应用的 UID 并调用 ConnectivityManager.onOttCallStateChanged(uid, true)；通话结束时以 false 调用同一方法。整体行为由 ConnectivityManager.FEATURE_OTT_NETWORK_SLICING 特性位控制，未启用该位的构建或模块保持原有行为。

在 ConnectivityService 内部，该 UID 由 AppOptInDefaultNetworkController 跟踪，它在通话进行期间给该 UID 打上 POLICY_OTT 标记。对于每个此类 UID，服务在 getOttSlicingRequests() （packages/modules/Connectivity/service/src/com/android/server/ConnectivityService.java）中构造切片请求：

// ConnectivityService.getOttSlicingRequests()
// Layer 1: prefer unmetered (e.g. Wi-Fi) if available
new NetworkCapabilities.Builder()
        .addCapability(NET_CAPABILITY_INTERNET)
        .addCapability(NET_CAPABILITY_NOT_VCN_MANAGED)
        .addCapability(NET_CAPABILITY_NOT_METERED)
        .build();
// Layer 2: cellular premium slice for unified communications
new NetworkCapabilities.Builder()
        .addTransportType(TRANSPORT_CELLULAR)
        .addCapability(NET_CAPABILITY_NOT_VCN_MANAGED)
        .addCapability(NET_CAPABILITY_PRIORITIZE_UNIFIED_COMMUNICATIONS)
        .build();

这个两层请求在存在不计费网络时优先使用它，否则回落到蜂窝切片。蜂窝分支携带统一通信能力。数据协议栈通过前述 URSP 机制把该能力映射到切片：调制解调器的 URSP 规则与 TrafficDescriptor 的连接能力 CONNECTION_CAPABILITY_UNIFIED_COMMUNICATIONS （frameworks/base/telephony/java/android/telephony/data/TrafficDescriptor.java） 共同选定路由，DataNetworkController 随之建立对应的数据网络。

该能力的 javadoc 注明这只是一项提示：若运营商未开通统一通信切片，它就只是在其最佳可用网络上承载该请求。

36.10 WAP Push

WAP Push 是一种传统但仍被广泛使用的机制，用于过 SMS 向移动设备投递小型数据负载。其名称源自无线应用协议（Wireless Application Protocol）。然而它在当代最重要的作用是投递 MMS 通知指示——即通过短信承载、告知设备有待下载 MMS 的那类消息。每当你收到一条彩信，总是先到一个 WAP Push PDU。

36.10.1 什么是 WAP Push？

WAP Push 由开放移动联盟（OMA）的 WAP 规范（WAP-235、WAP-230-WSP）定义。一条 WAP Push 消息是一个二进制 PDU（协议数据单元），承载于一条或多条 SMS 之中。该 PDU 包含：

  1. 事务 ID（Transaction ID）：标识该 push 事务。
  2. PDU 类型：PUSH（0x06）或 CONFIRMED-PUSH（0x07）。
  3. 内容类型（Content-Type）：负载的 MIME 类型（例如 MMS 通知用 application/vnd.wap.mms-message）。
  4. 消息头：WSP（无线会话协议）消息头，其中可含用于路由的应用 ID。
  5. 消息体：实际的 push 数据负载。

常见 WAP Push 内容类型：

内容类型 用途
application/vnd.wap.mms-message MMS 通知（最常见）
application/vnd.wap.sic 服务指示（URL push）
application/vnd.wap.slc 服务加载（自动抓取 URL）
application/vnd.wap.coc 缓存操作
text/vnd.wap.si 服务指示（文本形式）

36.10.4 PDU 解码

decodeWapPdu() 方法执行二进制 PDU 解析。WSP 格式紧凑但复杂：

// Source: WapPushOverSms.java (simplified decode flow)
private DecodedResult decodeWapPdu(byte[] pdu, InboundSmsHandler handler) {
    int index = 0;

    // 1. Transaction ID (1 byte)
    int transactionId = pdu[index++] & 0xFF;

    // 2. PDU Type (1 byte) -- must be PUSH or CONFIRMED_PUSH
    int pduType = pdu[index++] & 0xFF;
    if (pduType != WspTypeDecoder.PDU_TYPE_PUSH &&
            pduType != WspTypeDecoder.PDU_TYPE_CONFIRMED_PUSH) {
        // Some carriers use non-standard PDU offsets
        index = mContext.getResources().getInteger(
                R.integer.config_valid_wappush_index);
        // Re-read transaction ID and PDU type at new offset
    }

    WspTypeDecoder pduDecoder = new WspTypeDecoder(pdu);

    // 3. Header Length (uintvar, up to 5 bytes per WAP-230-WSP 8.1.2)
    pduDecoder.decodeUintvarInteger(index);
    int headerLength = (int) pduDecoder.getValue32();

    // 4. Content-Type (well-known or extension media)
    pduDecoder.decodeContentType(index);
    String mimeType = pduDecoder.getValueString();

    // 5. Extract header and body
    byte[] header = Arrays.copyOfRange(pdu, headerStart,
            headerStart + headerLength);
    byte[] intentData = Arrays.copyOfRange(pdu,
            headerStart + headerLength, pdu.length);

    // 6. Check for MMS notification -- cache message size
    GenericPdu parsedPdu = new PduParser(intentData).parse();
    if (parsedPdu instanceof NotificationInd) {
        NotificationInd nInd = (NotificationInd) parsedPdu;
        WapPushCache.putWapMessageSize(
                nInd.getContentLocation(),
                nInd.getTransactionId(),
                nInd.getMessageSize());
    }

    // 7. Look for application ID in WSP headers
    if (pduDecoder.seekXWapApplicationId(index, headerEnd)) {
        result.wapAppId = pduDecoder.getValueString();
    }

    return result;
}

这种二进制格式虽紧凑，却折射出 21 世纪初移动网络处处字节珍贵的约束。

36.11 卫星与非地面网络（NTN）

Android 17 携带了一套完整的卫星消息与连接协议栈。这项工作最初是某家 OEM 设备上的紧急 SOS 特性，后发展为通用框架。该框架包括对外的 SatelliteManager API、frameworks/opt/telephony 中庞大的内部控制器群，以及面向厂商的 SatelliteService HAL。它还支持运营商漫游的「非地面网络」（NTN）模式——普通 SIM 驻留到运营商已开通的卫星网络上。本节自上而下梳理该架构，并指出 17 在 16 基础上新增了什么。

36.11.1 卫星的两种形态：OEM 开通 vs 运营商漫游

这里存在两种截然不同的连接模型，协议栈中几乎每个类都会依据当前生效的模式分支：

  • OEM 开通（P2P/SOS）：与卫星运营商的关系归设备而非运营商所有。调制解调器切换到专用卫星模式，交换的是数据报（SOS、短信形态或保活）而非 IP——这是最初的紧急消息路径。
  • 运营商漫游 NTN：普通运营商 SIM 在其运营商配置中列出卫星 PLMN。当地面覆盖消失时，设备「漫游」到该运营商的卫星网络，随后可承载 SMS 与 MMS，某些配置下还可承载数据与语音。连接行为取决于 CarrierConfigManager.KEY_CARRIER_ROAMING_NTN_CONNECT_TYPE_INT，其取值为 CARRIER_ROAMING_NTN_CONNECT_AUTOMATIC、 CARRIER_ROAMING_NTN_CONNECT_MANUAL 以及（新增的） CARRIER_ROAMING_NTN_CONNECT_HYBRID （frameworks/base/telephony/java/android/telephony/CarrierConfigManager.java）。

所使用的非地面无线技术是 NT_RADIO_TECHNOLOGY_NB_IOT_NTN、NT_RADIO_TECHNOLOGY_NR_NTN 或 NT_RADIO_TECHNOLOGY_EMTC_NTN 之一 （frameworks/base/telephony/java/android/telephony/satellite/SatelliteManager.java）。 Android 17 在 nr_ntn 开关之后补齐了 NR-NTN 路径（3GPP Release-17 的 5G-NR 卫星规范），与较早的 NB-IoT-NTN 路径并存。

SatelliteController 是这套协议栈的大脑，也是电话模块中最大的单个类——约一万二千行 （frameworks/opt/telephony/src/java/com/android/internal/telephony/satellite/SatelliteController.java）。 它是一个单例 Handler，拥有其余卫星对象，并裁决每一个启用／停用请求：

36.11.3 会话状态机

SatelliteSessionController 是一个 StateMachine，映照调制解调器的卫星模式并管控数据报传输。其状态对应 SatelliteManager.SATELLITE_MODEM_STATE_*：

Suspended 是 Android 17 新增的状态，位于 satellite_suspend 开关之后。该状态让框架可以把一路运营商漫游 NTN 会话挂起，调制解调器并不拆除。例如，框架可以挂起某会话，好让优先级更高的地面网络接管 （frameworks/opt/telephony/src/java/com/android/internal/telephony/satellite/SatelliteSessionController.java）。

Listening 状态之所以存在，是因为卫星链路半双工且代价高昂。在一次发送或接收之后，调制解调器会保持一个短暂的监听窗口 （DEFAULT_SATELLITE_STAY_AT_LISTENING_FROM_SENDING_MILLIS），随后退回空闲。

36.11.5 天线指向

在 NB-IoT-NTN 规范下，从手机视角看卫星并非对地静止，用户常常需要对准手机。PointingAppController 拉起 OEM 的指向界面并持续推送 PointingInfo。该数据包含天线方位角／俯仰角，来自 AntennaPosition 与 AntennaDirection。界面据此显示一个箭头，引导用户朝向卫星 （frameworks/opt/telephony/src/java/com/android/internal/telephony/satellite/PointingAppController.java）。 PointingUiAppLaunchIntentAttributes 描述启动 intent 的属性 （frameworks/base/telephony/java/android/telephony/satellite/PointingUiAppLaunchIntentAttributes.java）。

36.11.6 NTN 信号强度

卫星链路上报自己的信号度量，与蜂窝信号格相互独立。NtnSignalStrength 暴露五个等级——NTN_SIGNAL_STRENGTH_NONE、POOR、 MODERATE、GOOD、GREAT （frameworks/base/telephony/java/android/telephony/satellite/NtnSignalStrength.java）。 SatelliteController 向调制解调器注册 NTN 信号变化，并通过 INtnSignalStrengthCallback 通知应用回调。对运营商漫游 NTN，决定画几格信号的各 RAT 阈值来自运营商配置：KEY_NTN_LTE_RSRP_THRESHOLDS_INT_ARRAY、 KEY_NTN_LTE_RSRQ_THRESHOLDS_INT_ARRAY 与 KEY_NTN_LTE_RSSNR_THRESHOLDS_INT_ARRAY， 由 KEY_PARAMETERS_USED_FOR_NTN_LTE_SIGNAL_BAR_INT 选定 （frameworks/base/telephony/java/android/telephony/CarrierConfigManager.java）。

NtnCapabilityResolver 针对某次网络注册判定服务小区是地面还是非地面，并判定该小区使用哪种 NT 无线电技术。在调制解调器未直接上报这些事实时，这两项判定也由它完成 （frameworks/opt/telephony/src/java/com/android/internal/telephony/satellite/NtnCapabilityResolver.java）。

36.11.7 SatelliteService HAL 与公开 API

框架通过厂商的 SatelliteService 与调制解调器通信，该服务绑定在 android.telephony.satellite.SatelliteService action 上，并以 SatelliteImplBase 作为便捷基类 （frameworks/base/telephony/java/android/telephony/satellite/stub/SatelliteService.java、 SatelliteImplBase.java）。在框架侧，SatelliteModemInterface 封装该绑定。对于较旧的 HAL 版本，它把较新的请求走兼容路径，例如 SatelliteNetworkInfo 与带优先级的网络扫描 （frameworks/opt/telephony/src/java/com/android/internal/telephony/satellite/SatelliteModemInterface.java）。

应用通过 SatelliteManager 触及上述全部能力。PhoneInterfaceManager （packages/services/Telephony/src/com/android/phone/PhoneInterfaceManager.java） 在 SATELLITE_COMMUNICATION 权限之后执行并分发其入口点，例如 requestSatelliteEnabled、provisionSatelliteService、 sendDatagram、pollPendingDatagrams 以及各注册调用（名称相近的 sendSatelliteDatagram / pollPendingSatelliteDatagrams 属于面向厂商的 ISatellite HAL，而非 manager 层）。Android 17 新增了运营商开通入口点（requestEnableSatelliteForCarrier、自动运营商模式，以及 getManualConnectSatellitePlmnsForCarrier），还新增了更丰富的指标面（ControllerMetricsStats、 CarrierRoamingSatelliteSessionStats、独立的收发数据用量指标），位于 frameworks/opt/telephony/src/java/com/android/internal/telephony/satellite/metrics/。

36.12 ImsStack 模块——AOSP 的参考 IMS 实现

§36.5 介绍的是 IMS 框架——ImsResolver、ImsServiceController，以及运营商或 OEM 的 IMS 实现必须满足的 android.telephony.ims.ImsService 契约。历史上该实现一直是闭源的厂商 APK，AOSP 自己并未提供真正的实现。Android 17 填补了这一空缺：在 packages/modules/ImsStack 提供了一套完整的树内 IMS 协议栈——一个特权系统应用 com.android.imsstack，后端为原生 SIP 引擎 libimsstack。这是平台首次以开源形式携带端到端的 VoLTE/VoWiFi/RCS 协议栈。

36.12.1 打包形态：携带原生 SIP 引擎的特权 system_ext 应用

该模块把 ImsStack APK 构建为特权、平台签名、system_ext 应用。应用以 required 安装依赖的形式声明原生引擎，因此 libimsstack 随 APK 一同安装，而不是通过 jni_libs 打包进 APK （packages/modules/ImsStack/java/Android.bp）：

android_app {
    name: "ImsStack",
    privileged: true,
    certificate: "platform",
    system_ext_specific: true,
    // ...
    required: [
        "libimsstack",
        "privapp_permissions_com.android.imsstack",
        "sysconfig_com.android.imsstack",
    ],
}

其 manifest 声明包名 com.android.imsstack，并在自身进程中以 persistent 方式运行。该应用是 directBootAware 的，因此 IMS 可在用户解锁之前就起来（这对紧急呼叫很重要）。它请求了一大批普通应用绝无可能持有的特权权限，包括 MODIFY_PHONE_STATE、READ_PRIVILEGED_PHONE_STATE、 CONNECTIVITY_USE_RESTRICTED_NETWORKS、USE_ICC_AUTH_WITH_DEVICE_IDENTIFIER、 com.android.telephony.permission.USE_IMSMEDIA 等 （packages/modules/ImsStack/java/AndroidManifest.xml）。

36.12.2 接入 IMS 框架

该应用的服务声明在标准 IMS action 上，从而 ImsResolver 能像发现任何厂商 IMS 服务那样发现并绑定它：

36.12.4 libimsstack——原生 SIP 引擎

繁重工作位于 packages/modules/ImsStack/native/libimsstack 下的 C++ 代码。它被构建为单个名为 libimsstack 的 cc_library_shared，静态链接 engine、protocol、config、enabler、platform 与 JNI 各子库 （packages/modules/ImsStack/native/libimsstack/Android.bp）。libimsstack.cpp 中的 JNI_OnLoad 把原生命令接到 Java 的 jni 包 （packages/modules/ImsStack/native/libimsstack/libimsstack.cpp）。其中最重要的两个子树是：

  • protocol —— 从零实现的 SIP 与 SDP。它包含消息头解析器（SipCSeqHeader、SipContentTypeHeader、 SipGeolocationRoutingHeader 等）、SDP 模型（SdpDescription、 SdpMediaDescription、SdpAvCodec），以及用于 IMS XML 消息体的 DOM XML 解析器 （packages/modules/ImsStack/native/libimsstack/protocol/sip/、 .../protocol/sip/SipStackManager.cpp）。
  • engine —— SIP 事务与对话状态机，把这些消息转化为呼叫／注册逻辑。主要类是 SipStack、 SipStackTransaction 与 SipForkedTransactionManager，以及 CoreService/Connection 呼叫模型 （packages/modules/ImsStack/native/libimsstack/engine/sipcore/SipStack.cpp）。

platform 层抽象套接字、定时器与 TLS，使引擎得以运行在 Android 网络协议栈之上 （packages/modules/ImsStack/native/libimsstack/platform/）。

36.12.5 它的位置

ImsStack 只是 ImsResolver 所发现的又一个 ImsService（见 §36.5.2）。因此，出厂就带上它的设备无需任何专有二进制即可获得可用的 VoLTE、VoWiFi 与 RCS。运营商覆盖项仍可把 ImsResolver 指向厂商实现。§36.9 介绍的独立 ImsMedia 服务依然负责 IMS 的媒体面（RTP/RTCP）；ImsStack 通过 USE_IMSMEDIA 权限与 enabler 的媒体包请求它。

36.13 通用引导架构（GBA / BSF）

少数 IMS 与运营商服务（用于补充业务开通的 XCAP/Ut、部分 MBMS 与权益服务器）需要让设备对运营商网络完成认证，它们使用 3GPP 的通用引导架构：SIM 的 AKA 凭据与运营商的引导服务器功能（BSF）完成引导，产出一个共享密钥（Ks）与引导事务标识（B-TID）；再由它们为每个网络应用功能（NAF）计算出按应用区分的密钥（Ks_NAF）。Android 17 以独立模块的形式提供了这套机制的 AOSP 默认实现， packages/modules/GenericBootstrappingArchitecture。

该模块构建一个特权、平台签名的应用 com.android.gbaservice，以 android.uid.system 身份运行，且为 directBootAware。它在 BIND_GBA_SERVICE 之后把服务声明在 GBA action 上 （packages/modules/GenericBootstrappingArchitecture/Android.bp、 AndroidManifest.xml）。DefaultGbaService 继承 android.telephony.gba.GbaService，并通过单线程 executor 串行化请求，因为每次引导都要访问 SIM （packages/modules/GenericBootstrappingArchitecture/src/com/android/gbaservice/DefaultGbaService.java）。

真正的协议工作在 GbaAuthManagerImpl 中。它构建一个按 3GPP-bootstrapping（GBA_ME）或基于 UICC 的变体（GBA_U）参数化的 GbaNetworkTask，对 BSF 执行 HTTP Digest-AKA 交换，并返回携带 Ks_NAF、B-TID 与密钥有效期的 GbaResult （packages/modules/GenericBootstrappingArchitecture/src/com/android/gbaservice/GbaAuthManagerImpl.java、 GbaNetworkTask.java）。

SIM 本身通过 TelephonyManager 的 ICC 认证（TelephonyManagerGbaMe / TelephonyManagerGbaU）回答 AKA 挑战。这也是该应用持有 USE_ICC_AUTH_WITH_DEVICE_IDENTIFIER 一类特权的原因。推导出的引导密钥按 NAF id 缓存在一个小型 SQLite 数据库（GbaDbHelper）中，重复请求因而可跳过往返，直至密钥有效期结束。

在相关配置中指定的厂商 GBA 服务可取代 DefaultGbaService，厂商服务保持同一份框架契约。IMS 服务也可以同样的方式被覆盖（见 §36.5.2）。

36.14.1 ims-common——进程内 IMS 客户端库

§36.5 与 §36.12 讨论的是 IMS 框架（ImsResolver）以及框架所绑定的 IMS 服务（ImsStack 或厂商 APK）。二者之间的黏合层是一个独立库 ims-common，构建自 frameworks/opt/net/ims（在 frameworks/opt/net/ims/Android.bp 中声明的 java_library）。它携带 com.android.ims 包，是运行在任何需要与已绑定 ImsService 通信的进程内的客户端。最主要这样的进程是承载 ImsPhone / ImsPhoneCallTracker 的电话进程；设置应用与 QualifiedNetworksService 也属于此类进程。

36.14.2 QualifiedNetworksService——按 APN 的传输选择

§36.8.12 提到 AccessNetworksManager 决定某条 APN 的流量走蜂窝（WWAN）还是 IWLAN（Wi-Fi），但这一决定并非由它自己做出。AccessNetworksManager 是一个客户端，它绑定 QualifiedNetworksService，并就每种 APN 类型向其索要一份按优先级排序的接入网列表。框架基类与绑定 action 是 android.telephony.data.QualifiedNetworksService （frameworks/base/telephony/java/android/telephony/data/QualifiedNetworksService.java， 常量 QUALIFIED_NETWORKS_SERVICE_INTERFACE），绑定则通过 frameworks/opt/telephony/src/java/com/android/internal/telephony/data/AccessNetworksManager.java 中的 QualifiedNetworksServiceConnection 完成。

AOSP 以独立服务的形式提供了一个默认、可由厂商扩展的实现： packages/services/QualifiedNetworksService（包名 com.android.telephony.qns，在 packages/services/QualifiedNetworksService/AndroidManifest.xml 中声明于 android.telephony.data.QualifiedNetworksService action 上，由 BIND_TELEPHONY_DATA_SERVICE 守护）。其核心 QualifiedNetworksServiceImpl 继承框架基类，AccessNetworkEvaluator 则按 APN 产出蜂窝、IWLAN、NR-SA 的有序列表，综合了蜂窝业务状态、IwlanNetworkStatusTracker 跟踪的 IWLAN 可达性以及运营商策略 （packages/services/QualifiedNetworksService/src/com/android/telephony/qns/QualifiedNetworksServiceImpl.java、 AccessNetworkEvaluator.java、IwlanNetworkStatusTracker.java）。

36.14.3 AlternativeNetworkAccess——机会性网络服务（ONS）

packages/services/AlternativeNetworkAccess 即机会性网络服务（ONS），包名 com.android.ons。它的职责是实现 eSIM／多 SIM 的「机会性数据」特性：扫描、选择并激活一张次级（机会性）订阅，在合作伙伴网络覆盖的区域（例如一个 CBRS 配置文件）用它承载数据，同时不干扰用户用于语音的主 SIM。

OpportunisticNetworkService 是所绑定的服务。其 javadoc 称它「扫描网络并把结果与机会性订阅匹配……从而在具备相应网络的区域为用户提供机会性数据」 （packages/services/AlternativeNetworkAccess/src/com/android/ons/OpportunisticNetworkService.java）。

工作分由三个辅助类完成：ONSNetworkScanCtlr 执行网络扫描并报告可用性； ONSProfileSelector 把扫描结果与候选机会性配置文件匹配并选定一个； ONSProfileActivator 在插入机会性数据 pSIM 时确保所选 CBRS/eSIM 配置文件被下载、激活并分组 （packages/services/AlternativeNetworkAccess/src/com/android/ons/ONSNetworkScanCtlr.java、 ONSProfileSelector.java、ONSProfileActivator.java）。机会性订阅的选择又回连到 §36.8.15 所述的数据切换：一旦 ONS 激活了某个配置文件，PhoneSwitcher / AutoDataSwitchController 即可让数据经它承载。

36.14.4 CellBroadcastReceiver——紧急告警应用

§36.4.10 介绍了解析 3GPP 与 3GPP2 小区广播 PDU 的框架 CellBroadcastService。它未涵盖的是那个把已解析的告警变成用户真正看到的全屏警告、警报音与振动的应用。

该应用是 packages/apps/CellBroadcastReceiver（包名 com.android.cellbroadcastreceiver），属于可更新的 Mainline 模块，随 com.android.cellbroadcast APEX 一同发布 （packages/apps/CellBroadcastReceiver/apex/Android.bp）。同一 APEX 也承载 CellBroadcastService 模块；第 54 章的 Mainline 目录把它列为模块 6（R 版本首发，「紧急告警消息处理（CMAS/ETWS）」）。

分工很清晰：服务负责解码字节，应用负责呈现告警。

在应用侧，CellBroadcastReceiver 是接收告警 intent 的广播接收器； CellBroadcastAlertService 决定是否以及如何告警；CellBroadcastAlertDialog 是全屏警告 Activity； CellBroadcastAlertAudio 播放标准化警报音并驱动振动；CellBroadcastContentProvider 持久化已收告警以供历史查看（均位于 packages/apps/CellBroadcastReceiver/src/com/android/cellbroadcastreceiver/ 下）。

它呈现的告警类别是受监管的紧急标准：CMAS（商业移动告警系统：总统级、迫近威胁与 AMBER 告警）以及 ETWS（地震与海啸预警系统）。相关类型常量与字符串在 CellBroadcastResources.java 中解析。

36.14.5 ImsServiceEntitlement——TS.43 权益与 WFC 激活

运营商允许设备使用 Wi-Fi 通话、VoLTE 或 VoNR 之前，设备通常需要先向运营商的权益服务器报到。报到使用 GSMA 的 TS.43 协议，设备由此获得服务权益。 packages/apps/ImsServiceEntitlement（包名 com.android.imsserviceentitlement）是完成此事的 AOSP 应用。它轮询权益服务器并解析 TS.43 状态文档 （ts43/Ts43VowifiStatus、Ts43VolteStatus、Ts43VonrStatus、 Ts43SmsOverIpStatus）。若运营商要求交互式开通，它会在 WfcActivationActivity / WfcWebPortalFragment 中驱动基于 WebView 的激活流程，其 javadoc 引用了「TS.43 v5.0 第 3.4 节」 （packages/apps/ImsServiceEntitlement/src/com/android/imsserviceentitlement/）。

轮询由运营商配置驱动。ImsEntitlementReceiver 监听 android.telephony.action.CARRIER_CONFIG_CHANGED （packages/apps/ImsServiceEntitlement/AndroidManifest.xml）。当生效的运营商配置启用 TS.43 权益时，该接收器会调度 ImsEntitlementPollingService 去（重新）查询服务器。HTTP 交换与结果处理经 ImsEntitlementApi 与 EntitlementConfiguration 完成。其结果最终决定 §36.5 所述的 IMS 特性是否对用户提供。

36.14.6 gsma_services——SatelliteClient 与 TS.43 认证库

权益与卫星两条路径所依赖的两个可复用库位于 frameworks/libs/gsma_services。SatelliteClient（模块名 SatelliteClient，frameworks/libs/gsma_services/satellite_client/Android.bp） 是 SatelliteManagerWrapper 中卫星框架 API 的版本化包装，它暴露带编号的回调变体，使客户端可以针对 §36.11 所述卫星协议栈的稳定接口面、跨越不同平台版本进行编译。Ts43AuthenticationLibrary（模块名 Ts43AuthenticationLibrary， frameworks/libs/gsma_services/ts43authentication/src/com/android/libraries/ts43authentication/Ts43AuthenticationLibrary.java） 提供 TS.43 运营商权益认证（EAP-AKA 与 OIDC）；§36.14.5 的权益流程依赖它从运营商权益服务器取得已认证的令牌。

36.14.7 Stk——SIM 应用工具箱应用

SIM 应用工具箱（STK，即 3GPP 的「卡应用工具箱」／CAT）让 SIM 自身驱动界面：卡片可要求手机显示文本、呈现菜单、提示输入，也可要求手机发起呼叫、发送短信、播放提示音或打开浏览器。卡片以 主动命令（proactive command） 的形式下发，手机逐条执行并返回终端响应（terminal response）。这项工作由两部分分担：框架侧服务解析卡片的命令字节，独立应用负责渲染。

解析器是 com.android.internal.telephony.cat 包中的 CatService （frameworks/opt/telephony/src/java/com/android/internal/telephony/cat/CatService.java），由 UiccProfile 按 UICC 配置文件构造（见 frameworks/opt/telephony/src/java/com/android/internal/telephony/uicc/UiccProfile.java 中的 CatService.getInstance(...)）。它注册 RIL_UNSOL_STK_PROACTIVE_COMMAND（按 MSG_ID_PROACTIVE_COMMAND 处理），把原始 APDU 解码为带类型的 CatCmdMessage——为此使用同包内的 BER-TLV／comprehension-TLV 解析器与 CommandParamsFactory。命令种类即 AppInterface.CommandType 枚举，包括 DISPLAY_TEXT（0x21）、GET_INKEY （0x22）、GET_INPUT（0x23）、SET_UP_MENU（0x25）、SELECT_ITEM、SET_UP_CALL （0x10）、SEND_SMS、PLAY_TONE、LAUNCH_BROWSER、REFRESH 等 （frameworks/opt/telephony/src/java/com/android/internal/telephony/cat/AppInterface.java）。

CatService 不绘制任何东西。对需要界面的命令，它调用 broadcastCatCmdIntent：该方法把 CAT_CMD_ACTION （com.android.internal.stk.command）连同 CatCmdMessage 发给默认 STK 应用，广播由 RECEIVE_STK_COMMANDS 权限（AppInterface.STK_PERMISSION）守护。该应用是 Stk（包名 com.android.stk， packages/apps/Stk），运行在电话进程内 （packages/apps/Stk/AndroidManifest.xml 中的 android:process="com.android.phone"）。

StkCmdReceiver 接收广播并转发给 StkAppService（一个长期存活的 Service）。StkAppService.handleCmd 按 CommandType 分支并拉起对应界面：DISPLAY_TEXT 用 StkDialogActivity， SET_UP_MENU / SELECT_ITEM 用 StkMenuActivity， GET_INPUT / GET_INKEY 用 StkInputActivity， PLAY_TONE 用提示音播放器，如此类推 （packages/apps/Stk/src/com/android/stk/StkAppService.java）。当用户应答（或命令完成）时，结果经 StkAppService 回流至 CatService.sendTerminalResponse，该方法编码终端响应并经 RIL 返回给卡片。

小结

架构层面的经验

电话子系统体现了 Android 架构中若干反复出现的主题：

  • 分层抽象：每一层（SDK → 服务 → 框架 → RIL → HAL → 调制解调器）都有清晰的边界，且可独立替换。
  • 异步 Handler/Message 模式：Phone、RIL、DataNetwork 与 InboundSmsHandler 等类都继承 Handler，并通过消息传递驱动状态机。
  • AIDL HAL 稳定性：无线电 HAL 从 HIDL 迁移到带 @VintfStability 的 AIDL，确保厂商实现能够经受平台升级。
  • 领域分解：原先单体的 IRadio 被拆分为七个聚焦的接口：IRadioModem、IRadioSim、IRadioNetwork、 IRadioData、IRadioVoice、IRadioMessaging 与 IRadioIms，各自拥有自己的响应与指示回调。
  • 运营商定制：CarrierConfigManager 体系允许数百项按运营商的行为覆盖，而无需改动平台代码。

电话协议栈是 Android 中最古老的代码之一，它从简单的 GSM 电话层演进为支持多 SIM、IMS 与 5G 切片的系统。这表明平台的模块化架构能够支撑即便是最关键的子系统也进行渐进式现代化。

完整的电话流程——从拨号到调制解调器

要完整理解这套架构，不妨考虑一次呼出语音呼叫的全流程：

graph TD

    B --> C["3. Telecom 的 CallsManager 创建 Call 对象"]

设计原则

电话协议栈体现了若干值得注意的设计原则：

  1. Telecom 与 Telephony 分离：呼叫路由（Telecom）与无线电控制（Telephony）分离，使 VoIP 及其他呼叫来源可通过同一 ConnectionService 接口接入。

  2. 按 SIM 隔离：每个 SIM 槽位都有自己的 Phone、RIL、 ServiceStateTracker、DataNetworkController 与 ImsPhone。这通过结构性隔离而非条件分支逻辑，确保多 SIM 的正确性。

  3. 一切皆异步：每一次调制解调器操作都是异步的（RIL 使用 wake lock、序号与回调消息），从而避免任何一次缓慢的调制解调器响应阻塞整个电话协议栈。

  4. 特性开关：FeatureFlags 接口（包 com.android.internal.telephony.flags）让每个构建可以启用或停用单项电话特性。aconfig 在构建时依据 frameworks/opt/telephony/flags/*.aconfig 中的声明生成该接口。这对复杂电话改动的渐进式上线至关重要。

  5. 运营商可扩展性：CarrierConfigManager + CarrierService 体系让任何运营商都能定制数百项电话行为，而无需修改或分叉平台代码。

  6. HAL 稳定性契约：每个无线电 HAL 接口上的 @VintfStability 注解确保厂商调制解调器实现能够经受 Android 版本升级。对蜂窝生态而言这是关键要求——调制解调器固件的开发周期与 Android 版本相互独立。

第 57 章：测试框架与基础设施

第 57 章：测试框架与基础设施

在 Android 开源项目中，测试绝非后期硬贴上去的附属品。它是贯穿构建系统、持续集成流水线与兼容性认证流程每一层的一等公民。Android 出货于数百家 OEM 制造的数十亿台设备之上，这使得规模化地验证正确性成为生存必需，而非可选奢侈品。

本章系统梳理 AOSP 中所有主要测试子系统。先讲指导“测试放在哪里、如何运行”的理念，再讲编译测试的构建系统模块类型，最后讲在宿主机与设备上执行测试的测试框架。每一节都会引用代码树中的真实源文件，方便你在自己的检出中对照阅读。

57.1 测试哲学

57.1.1 Android 测试金字塔

Android 的测试策略借用了经典的测试金字塔概念，并针对一个横跨内核、原生库、托管运行时框架与用户态应用的平台做了扩展。

                           /\
                          /  \
                         / E2E\         Fewest, slowest, most realistic
                        /------\
                       / Integr.\       Medium count, device or emulator
                      /----------\
                     /   Unit     \     Most numerous, fastest, host-preferred
                    /--------------\

金字塔每一层的宽度代表测试数量，高度代表执行成本。Android 的工具链主动把测试往下层推：

层级 典型运行器 目标 速度 示例
单元（宿主机） 宿主机 JVM/二进制上的 JUnit / GoogleTest 无需设备 毫秒级 Ravenwood、Robolectric、cc_test_host
单元（设备） AndroidJUnitRunner 设备/模拟器 秒级 范围较小的 android_test
集成 TradeFederation 套件 设备/模拟器 分钟级 CTS 模块、VTS HAL 测试
端到端 UIAutomator / TAPL / Flicker 设备/模拟器 分钟级 Launcher 切换测试

57.1.2 主要测试套件

Android 定义了若干兼容性与验证套件。每个套件都是一个 TradeFederation plan（计划），用于选取一组测试模块。每个模块通过其构建规则中的 test_suites 属性声明自己归属哪个套件。

套件 全称 目的 运行器
CTS Compatibility Test Suite（兼容性测试套件） 验证应用兼容性所需的 API 契约 cts-tradefed
VTS Vendor Test Suite（厂商测试套件） 跨 Treble 边界验证 HAL/内核契约 vts-tradefed
GTS Google Test Suite 验证 Google 移动服务的要求 gts-tradefed
STS Security Test Suite（安全测试套件） 验证月度安全公告对应的补丁 sts-tradefed
MTS Mainline Test Suite（主线测试套件） 验证可升级的 Mainline 模块 mts-tradefed
CTS-root 需 root 的 CTS 需要 root 权限的 CTS 模块 cts-root-tradefed
Catbox 汽车合规测试 面向汽车构建的 CTS 子集 catbox-tradefed

57.1.3 宿主机测试与设备测试

Android 测试的一条基本维度是测试在何处执行：

  • 宿主机测试运行在构建机的 JVM 上，或作为原生二进制运行。它们从不接触设备。示例：java_test_host、cc_test_host、android_robolectric_test、android_ravenwood_test。

  • 设备测试运行在真机或模拟器上。它们经 adb 推送，由 TradeFederation 管理其生命周期。示例：android_test、面向设备的 cc_test。

  • 宿主机驱动的设备测试在宿主机上运行控制逻辑，但在设备上执行被测代码。CTS 宿主机侧测试（cts/hostsidetests/）是典型例子。

构建系统以模块类型和 test_suites 属性编码这一区分。atest 工具据此决定是否需要连接设备。

57.1.4 提交前与提交后的分工

Android 的 CI 流水线区分两个阶段：

  • 提交前（Presubmit）：测试在变更合入之前运行，必须快速且稳定。TEST_MAPPING 文件声明哪些测试在提交前运行。

  • 提交后（Postsubmit）：测试在变更合入之后运行，通常在完整构建上执行。更慢、更易抖动或更耗资源的测试放在这里。

TEST_MAPPING 体系（57.4 节）是为某个目录声明提交前与提交后覆盖范围的主要机制。

纯宿主机测试最快也最稳定。除构建机外没有外部依赖，可以在 CI 中运行而不必分配设备。Ravenwood 与 Robolectric 让 Java/Kotlin 框架测试也能只在宿主机上运行。

57.1.6 测试规模注解

Android 用规模注解来划分测试执行时间：

import androidx.test.filters.SmallTest;
import androidx.test.filters.MediumTest;
import androidx.test.filters.LargeTest;

@SmallTest     // < 200ms, no I/O or network
@MediumTest    // < 1000ms, may use filesystem
@LargeTest     // No time limit, may use network/database

这些注解有多种用途：

  1. TradeFed 可按测试规模过滤，以支持快速的提交前运行
  2. CI 流水线可据此分配恰当的超时
  3. 开发者可快速判断测试的预期开销

AOSP 中使用的其他注解：

注解 用途
@Presubmit 必须在提交前通过
@FlakyTest 已知不稳定，从提交前检查中排除
@RequiresDevice 需要真机（不能用模拟器）
@SecurityTest 与安全相关的测试
@AppModeFull 在完整（非 instant）应用模式下运行
@AppModeInstant 在 instant 应用模式下运行
@CddTest 映射到某条 CDD 要求

57.1.7 测试隔离原则

Android 测试力求隔离，以避免相互干扰：

  1. 进程隔离：每个插桩测试运行在自己的进程中

  2. 用户隔离：测试可以创建和销毁测试用户

  3. 状态清理：target preparer 在测试后恢复设备状态

  4. 类加载器隔离：Ravenwood 使用 IsolatedHostTest，为每个模块分配独立的类加载器

  5. 分片隔离：每个 TradeFed 分片拿到的是克隆的配置对象

57.2 Trade Federation（TradeFed）

57.2.1 概述

Trade Federation —— 通称 TradeFed 或简称 TF —— 是 Android 主要的测试执行框架。它管理完整生命周期：设备分配、构建产物准备、测试执行、结果收集与重试逻辑。

源码位置：

tools/tradefederation/
  core/         -- Main harness
  contrib/      -- Community-contributed modules
  prebuilts/    -- Pre-built JARs for bootstrapping

核心 Java 源码树位于：

tools/tradefederation/core/src/com/android/tradefed/
  command/        -- CommandScheduler, CommandRunner
  config/         -- XML configuration parsing
  invoker/        -- TestInvocation, InvocationExecution
  invoker/shard/  -- ShardHelper, StrictShardHelper, DynamicShardHelper
  testtype/       -- Test runners (IRemoteTest implementations)
  targetprep/     -- Device preparers (flash, install APK, root, etc.)
  result/         -- Result reporters and listeners
  retry/          -- BaseRetryDecision, RetryStatistics
  device/         -- Device abstraction (ITestDevice)
  build/          -- Build info providers
  suite/          -- Suite-level execution

57.2.2 架构

TradeFed 的架构围绕一组定义清晰的阶段构成的流水线，每个阶段对应一个可在 XML 中配置的可插拔 Java 对象。

关键类与接口：

CommandScheduler（tools/tradefederation/core/src/com/android/tradefed/command/CommandScheduler.java）： 中心调度器，接受命令行调用，把它们匹配到可用设备，并派发 TestInvocation 实例。它从 DeviceManager 处理设备分配，同时支持交互式控制台模式与无头批处理模式。

TestInvocation（tools/tradefederation/core/src/com/android/tradefed/invoker/TestInvocation.java）： 代表一次测试运行，负责编排整条流水线：

  1. 拉取构建产物（IBuildProvider）
  2. 准备目标设备（ITargetPreparer）
  3. 运行测试（IRemoteTest）
  4. 收集结果（ITestInvocationListener）
  5. 清理（由各 preparer 自己的 tearDown 完成）

InvocationExecution（tools/tradefederation/core/src/com/android/tradefed/invoker/InvocationExecution.java）： 驱动上述各阶段的具体执行逻辑。对沙箱化调用，SandboxedInvocationExecution 与 ParentSandboxInvocationExecution 提供隔离。

57.2.3 配置系统

TradeFed 用 XML 配置文件描述测试计划。一个配置会指定：

<configuration description="Example test config">
    <build_provider class="com.android.tradefed.build.BootstrapBuildProvider" />

    <target_preparer class="com.android.tradefed.targetprep.DeviceSetup" />
    <target_preparer class="com.android.tradefed.targetprep.TestAppInstallSetup">
        <option name="test-file-name" value="MyTest.apk" />
    </target_preparer>

    <test class="com.android.tradefed.testtype.AndroidJUnitTest">
        <option name="package" value="com.example.mytest" />
        <option name="runner" value="androidx.test.runner.AndroidJUnitRunner" />
    </test>

    <result_reporter class="com.android.tradefed.result.ConsoleResultReporter" />
</configuration>

该配置由 ConfigurationFactory （tools/tradefederation/core/src/com/android/tradefed/config/ConfigurationFactory.java） 与 ConfigurationXmlParser 解析。每个 <option> 标签都经 OptionSetter 注入目标对象，它依赖 Java 反射与 @Option 注解：

// From InstrumentationTest, which AndroidJUnitTest extends
public class InstrumentationTest
        implements IDeviceTest, IRemoteTest, /* ... */ {
    @Option(name = "package",
            description = "The manifest package name of the Android test "
                + "application to run.")
    private String mPackageName = null;

    @Option(name = "runner",
            description = "The instrumentation test runner class name to use. "
                + "Will try to determine automatically if it is not specified.")
    private String mRunnerName = null;
    // ...
}

注意：当 runner 选项留空时，运行器会从已安装的测试包中自动探测，而不会默认成某个固定类名。

57.2.4 分片

分片把测试套件拆分到多台设备或多个调用上并行执行。TradeFed 提供若干分片策略：

ShardHelper（tools/tradefederation/core/src/com/android/tradefed/invoker/shard/ShardHelper.java）： 创建分片调用的主要辅助类。它把配置对象克隆给每个分片，以避免共享状态。源码如下：

/** Helper class that handles creating the shards and scheduling them
 *  for an invocation. */
public class ShardHelper implements IShardHelper {
    public static final String LAST_SHARD_DETECTOR = "last_shard_detector";
    public static final String SHARED_TEST_INFORMATION = "shared_test_information";
    // ...
}

StrictShardHelper：确保每个分片拿到确定且互不重叠的测试用例划分。

57.2.5 重试逻辑

TradeFed 内置重试支持，用于处理不稳定测试与偶发失败。重试子系统位于：

tools/tradefederation/core/src/com/android/tradefed/retry/
  BaseRetryDecision.java    -- Core retry logic
  IRetryDecision.java       -- Interface
  ResultAggregator.java     -- Aggregates results across retries
  RetryStatistics.java      -- Tracks retry counts and outcomes

BaseRetryDecision 实现重试策略：

  • 失败重试：只重跑失败的测试用例
  • 重试次数：可配置的最大重试次数
  • 结果聚合：ResultAggregator 合并多次尝试的结果，对每个测试用例取最佳结果

重试决策经 IRetryDecision 接入 TestInvocation，它检查每个测试运行模块的结果并决定是否重试。

57.3.14 执行计划与 ACME 模式

上述默认路径会产生一个内部的 _TestExecutionPlan （tools/asuite/atest/atest_main.py），它抽象了“本次调用的测试将如何执行”。_TestExecutionPlan.create() 会在两种具体计划中选一种：_TestMappingExecutionPlan 用于 TEST_MAPPING 运行，_TestModuleExecutionPlan 用于显式的模块/类引用。每种计划都暴露 required_build_targets()、requires_device_update() 与 execute()。主循环据此决定要构建什么、是否需要刷写设备、以及如何运行。运行器代码不需要知道测试是如何被选出来的。

Android 17 在此基础上叠加了一层声明式选择模型，称为 ACME。开发者（或 CI 触发器）不再直接点名模块，而是点名义在 protobuf 中定义的测试触发器（test trigger）与执行计划（execution plan）（test_configs_proto，以 test_configs_pb2 导入）。随后 atest 把它们解析成要运行的模块。这些入口在 tools/asuite/atest/arg_parser.py 中注册，由 tools/asuite/atest/acme/ 下的模块处理：

标志 处理器 含义
--run-affected-triggers acme/run_affected_triggers_mode.py 运行本地修改文件所影响的全部测试触发器
--test-execution-plans acme/run_direct_mode.py 直接运行指定的 TestExecutionPlan
--test-triggers acme/run_direct_mode.py 运行指定触发器所引用的执行计划
--test-workflows acme/run_direct_mode.py 运行指定工作流（workflow）

acme_utils.py 遍历 test_configs.triggers，由 get_execution_plans_for_test_triggers() 把触发器名映射到它们引用的工作流与执行计划。“受影响触发器”模式复用 TEST_MAPPING/test_mapping 机制来算出某次 diff 触及哪些触发器。开发者可以用它在本地精确复现提交前将为该变更运行的内容，而无需手写模块列表。

在测试框架一侧，17 增加了配套的 TradeFed 套件运行器。ExecutionPlanSuiteRunner （tools/tradefederation/core/src/com/android/tradefed/testtype/suite/ExecutionPlanSuiteRunner.java） 及其面向 atest 的子类 AtestExecutionPlanSuiteRunner （tools/tradefederation/core/test_framework/com/android/tradefed/testtype/suite/AtestExecutionPlanSuiteRunner.java，由 res/config/atest-execution-plan.xml 配置）把预先算好的执行计划当作一个套件运行，而不是在 TradeFed 内部重新推导模块。该特性在稳定之前由灰度开关（下一小节）控制。

57.3.15 灰度控制特性

由于 atest 持续交付给成千上万名开发者，有风险的行为变更都以按比例灰度而非硬切换的方式引入。tools/asuite/atest/rollout_control.py 定义 RolloutControlledFeature 对象，每个对象带一个 rollout_percentage 与一个 env_control_flag，供本地强制开启或关闭该特性。每个对象还可以按运行 ID 做随机化，使单个开发者在一次运行内看到一致的行为。Android 17 交付了以下受控特性（及其他）：

特性 环境标志 说明
流式 TradeFed 子进程输出 ROLLING_TF_SUBPROCESS_OUTPUT 实时流式输出 TF 子进程输出（100%）
TradeFed preparer 增量准备 TF_PREPARER_INCREMENTAL_SETUP 跨运行复用先前的设备状态（100%）
atest 索引并行化 ATEST_INDEXING_PARALLEL 并行解析 module-info/索引文件
AtestExecutionPlanSuiteRunner USE_ATEST_EXECUTION_PLAN_SUITE_RUNNER 经新的 TF 执行计划运行器运行
自动重建 module info AUTO_REBUILD_MODULE_INFO 自动重建过期的 module-info.json
早期设备检查 EARLY_DEVICE_CHECK 设备测试无设备时快速失败

若要无视灰度比例强制开启某特性，设置其环境标志即可（例如 ATEST_INDEXING_PARALLEL=true atest ...）。这正是 17 中可见提速（并行索引与增量 preparer 准备）背后的机制 —— 不必一次性把所有人都绑上去。

57.4.6 TestMappingSuiteRunner

TradeFed 的 TestMappingSuiteRunner （tools/tradefederation/core/src/com/android/tradefed/testtype/suite/TestMappingSuiteRunner.java） 从 TEST_MAPPING 文件加载并执行测试。它会：

  1. 收集被改动路径对应的所有 TEST_MAPPING 文件
  2. 按请求的测试组（presubmit、postsubmit 等）过滤
  3. 应用 file_patterns 过滤
  4. 把模块名解析为测试配置
  5. 经标准套件流水线执行

57.4.7 TEST_MAPPING 最佳实践

  1. 保持提交前测试快速：只纳入 5 分钟内完成的测试

  2. 善用 file_patterns：对大目录，把测试限定在相关变更上

  3. 避免重复：若父目录已覆盖某模块，不要在子目录重复声明

  4. 按逻辑分组：为专用目标（汽车、wear 等）使用自定义组

  5. 尽量标明宿主机：纯宿主机测试加 "host": true，避免无谓的设备分配

  6. 用 options 做过滤：对大型模块用 include-filter 只运行相关测试类

57.4.8 查找 TEST_MAPPING 文件

CI 系统与 atest 都会遍历目录树查找 TEST_MAPPING 文件。搜索从被改动文件所在目录开始，向上逐级走到仓库根。

# From cli_translator.py
# Pattern used to identify comments in TEST_MAPPING.
_COMMENTS_RE = re.compile(r'(?m)[\s\t]*(#|//).*|(\".*?\")')

TEST_MAPPING 支持注释（以 // 或 # 开头的行），这并非标准 JSON。解析器在 JSON 解析前会先剥掉这些注释。

57.4.9 校验

TEST_MAPPING 文件在提交前阶段接受校验。校验内容包括：

  • JSON 合法（剥除注释之后）
  • 引用的所有测试模块都存在于构建中
  • 测试组名匹配已知组
  • 选项是合法的 TradeFed 选项
  • 无循环引用

57.5.4 进程隔离的 GoogleTest（gtest_extras）

57.5.3 中出现的 isolated: true 属性会把默认的 libgtest_main 换成 libgtest_isolated_main，即进程隔离 gtest 运行器的静态库入口。该运行器位于 system/testing/gtest_extras/（运行器代码约 2.3K 行，含其自身测试约 4.8K 行）。原生运行器把每个测试方法都跑在同一个地址空间里。隔离运行器（gtest_isolated/）则为每个测试 fork 一个全新的子进程（fork() 位于 system/testing/gtest_extras/gtest_isolated/Isolate.cpp），并等待其结束。它按可配置的并发数（gtest_isolated/Options.h）同时运行若干子进程。

进程隔离带来两点单进程原生运行器做不到的能力。第一，崩溃或破坏全局状态的测试不再能拖垮整个二进制——失败被限制在自己的子进程内。父进程记录导致终止的信号（Isolate.cpp 经 WIFSIGNALED 报告 terminated by signal:），其余测试照常运行。第二，每个子进程都有按测试计的墙钟截止时间（Options.h 中的 deadline_threshold_ms）。挂起的测试会被杀掉并记为超时，而不是把整次运行卡死。

底层测试套件刻意要跑故障与信号处理路径：bionic、ART 的 native-bridge 测试，以及 jemalloc/scudo 分配器测试。正因如此，它们选择 isolated: true 并链接 libgtest_isolated。除此之外运行器是即插即用的：57.5.3 中同一份 GoogleTest 写法的 cc_test 源码，对两个入口都能编译。

57.6.8 跨设备 CTS 分片

对大型 CTS 运行（1 万以上测试用例），分片必不可少。CTS 支持：

  • 静态分片：把模块切成 N 份等量分片
  • 动态分片：用基于池的方式做负载均衡
  • 模块级分片：每个模块在一台设备上运行
  • 测试级分片：模块内的单个测试用例被拆分
# Shard across 4 devices
cts-tradefed run cts --shard-count 4

# Dynamic sharding with pool
cts-tradefed run cts --dynamic-sharding

另一个选项 --enable-token-sharding 让分片遵循设备 token（例如 SIM 卡能力）。这样，需要特定 token 的测试只会在具备该能力的设备所在分片上运行。

57.8 Ravenwood —— 宿主机侧框架测试

57.8.1 概述

Ravenwood 是 Android 的方案，用于在宿主机 JVM 上运行框架测试，无需设备或模拟器。它提供一套轻量环境，让 Android 框架类直接运行在 JDK 21+ 的宿主机 JVM 上，把测试执行时间从分钟级大幅降到秒级。

57.8.12 宿主机图形桩（libhostgraphics）

Ravenwood（以及其他宿主机侧框架测试）可以编译并链接那些内部会调用 libhwui 的类。但 libhwui 原本是要和真实的 SurfaceFlinger、真实的 BufferQueue 与真实的 ANativeWindow 打交道的。在 Linux/Mac/Windows 工作站上跑的宿主机 JVM 里，这些都不存在。libhostgraphics 就是让 libhwui 能在宿主机上编译与链接的静态 C++ 兼容层，它为 hwui 依赖的图形栈部分提供最小化的进程内替代实现。

源码：frameworks/base/libs/hostgraphics/（五个 C++ 文件，外加 include/gui/ 与 include/ui/ 下的 9 个头文件 shim）。

该库在 libhwui 的 Android.bp 中作为 host: 目标下的静态依赖接入：

// Source: frameworks/base/libs/hwui/Android.bp:171
host: {
    static_libs: [
        "libandroidfw",
        "libhostgraphics",
        "libutils",
    ],
},

正是这行 static_libs 让“宿主机版 hwui”成为可能。在设备上，libhwui 会引入 libgui、libui、libnativewindow、libnativedisplay 与 libsurfaceflinger。在宿主机上，这些 shared_libs 条目不存在，libhostgraphics 提供宿主机构建所需的符号。

五个桩翻译单元

文件 桩掉的东西
ANativeWindow.cpp ANativeWindow_* C-API。每个函数直接转发到底层窗口的 vtable（window->perform、window->query、window->dequeueBuffer、incStrong/decStrong），而不经过 libnativewindow。
HostBufferQueue.cpp HostBufferQueue 类，在单个 GraphicBuffer 之上同时实现 IGraphicBufferProducer 与 IGraphicBufferConsumer。BufferQueue::createBufferQueue 把同一个对象同时返回为生产端与消费端。
ADisplay.cpp 一套硬编码的 1080x1920@60 显示配置，经 apex/display.h 的 ADisplay_* C-API 暴露。无 HWC、无 VSYNC 偏移、无多显示逻辑。
Fence.cpp 定义 Fence::NO_FENCE 单例，因为 libui 的 Fence.cpp 没有被链接进来。
PublicFormat.cpp PublicFormat、HAL 格式与 dataspace 之间的空操作映射函数（总是返回输入值的强制转换）。

有意思的是 HostBufferQueue。在设备上，生产端（应用/hwui 一侧）与消费端（SurfaceFlinger 或某个 BufferItemConsumer）位于不同进程，经 Binder 通信，并交换一圈由 fence 守着的槽位索引缓冲区。在宿主机上没有生产者/消费者分离，也没有双缓冲。createBufferQueue 把同一个对象作为两个端点返回，每个“缓冲区”都是同一个 GraphicBuffer：

// Source: frameworks/base/libs/hostgraphics/HostBufferQueue.cpp:101
void BufferQueue::createBufferQueue(sp<IGraphicBufferProducer>* outProducer,
                                    sp<IGraphicBufferConsumer>* outConsumer,
                                    bool consumerIsSurfaceFlinger) {
    sp<HostBufferQueue> obj(new HostBufferQueue());
    *outProducer = obj;
    *outConsumer = obj;
}

这种合并是刻意的。宿主机测试只需要验证 hwui 对某个缓冲区发出了正确的绘制调用，不需要验证缓冲区经过 SurfaceFlinger 往返后依然完好。跳过生产者/消费者协议也避免了引入 Binder、libgui 与 libnativedisplay 的 HWC shim —— 它们各自都需要自己的宿主机桩。

头文件 shim

include/gui/ 与 include/ui/ 下的 9 个头文件是这套戏法的另一半。它们并非设备头文件，而是签名匹配的独立声明（Surface.h、BufferQueue.h、BufferItem.h、IGraphicBufferProducer.h、IGraphicBufferConsumer.h、ConsumerBase.h、BufferItemConsumer.h、Fence.h、GraphicBuffer.h）。libhostgraphics_headers 这个 cc_library_headers 导出它们，libhwui 的宿主机目标会取而代之地拾取它们，而不使用真正的 libgui_headers / libui_headers。因此像 Surface surf(producer); 这样的 hwui 代码可原样编译，但在链接时解析到桩版 Surface 类。

设备与宿主机上的 hwui 组成

        DeviceHwui["libhwui"]
        DeviceHwui --> Libgui["libgui<br/>（真实 BufferQueue、<br/>Binder、ashmem）"]

下面这行就是整个宿主机图形栈 —— 没有 IPC、没有独立进程、没有 fence 同步，只有一个在测试生命周期内存活的缓冲区。

Windows 支持

libhostgraphics 是少数在 Windows 构建上被显式启用的框架宿主库之一：

target: {
    windows: {
        enabled: true,
    },
},

这对需要在开发者的 Windows 工作站上链接 libhwui 的 SDK 工具（layoutlib 风格的渲染器、宿主机 APK 构建辅助工具）很重要。

libhostgraphics 测不了什么

因为缓冲区只有单槽、显示是固定 mock，宿主机构建的 hwui 无法验证：

  • 真实帧节奏或由 VSYNC 驱动的失效
  • 生产者/消费者背压（宿主机队列从不阻塞）
  • HDR / 广色域路径选择（PublicFormat 总是返回原始强制转换值）
  • HWC 合成或显示旋转
  • 基于 fence 的 GPU/CPU 同步（NO_FENCE 是唯一存在的 fence）

这些仍然需要设备或模拟器。libhostgraphics 的职责只是让链接器满意，让 hwui 算法核心（绘制、canvas、字体、层级遍历）的单元测试能在开发者笔记本上以毫秒级运行。

57.8.13 进程内 System Server

早期 Ravenwood 只能承载末端的工具类。到 Android 17，它会启动一个轻量的、进程内的 system server。这让通过 Context.getSystemService() 或 ServiceManager 查找框架服务的代码也能在宿主机上运行。RavenwoodSystemServer （frameworks/base/ravenwood/junit-impl-src/android/platform/test/ravenwood/RavenwoodSystemServer.java） 在运行器启动时把假实现或代理实现注册进 ServiceManager 与 LocalServices，覆盖如下服务：

  • PLATFORM_COMPAT_SERVICE / PLATFORM_COMPAT_NATIVE_SERVICE（应用兼容性变更门控）
  • INPUT_SERVICE、INPUT_METHOD_SERVICE、AUTOFILL_SERVICE
  • USER_SERVICE、ACTIVITY_SERVICE、ACTIVITY_TASK_SERVICE
  • WINDOW_SERVICE、DISPLAY_SERVICE
  • 内容服务（ContentResolver.CONTENT_SERVICE_NAME）与 dream 服务

这些并非真服务 —— 大多数是代理，要么委派给假实现，要么对不支持的调用抛出“未实现”。只有 PLATFORM_COMPAT_* 与 INPUT_SERVICE 无条件注册；其余在 maybeRegisterExperimentalServices() 中注册，由 isExperimentalApiEnabled() 门控。

配套的 RavenwoodAppDriver （frameworks/base/ravenwood/junit-impl-src/android/app/RavenwoodAppDriver.java） 在宿主机上把 ActivityThread/Application 的状态拉起足够多。测试于是能拿到真实的 Context、settings provider 与兼容性配置。实际效果是 Ravenwood 现在不再只覆盖数据结构，还能覆盖与系统服务打交道的框架逻辑；仍然无需设备，也不再局限于无依赖的末端类。

57.8.14 何时使用 Ravenwood

Ravenwood 非常适合：

  • 测试 android.os.* 工具类（Bundle、Parcel、Handler 等）
  • 测试 android.util.* 数据结构（SparseArray、LruCache 等）
  • 测试 android.content.* 基础类
  • 测试经进程内 system server（57.8.13）访问系统服务的框架逻辑，例如应用兼容性变更门控或用户服务查询
  • 测试使用 Android 特性标志（aconfig）的代码

Ravenwood 不适用于：

  • 需要真实 UI 渲染或 GPU 合成的测试
  • 需要真实硬件的测试（相机、传感器）
  • 依赖某个尚未实现 Ravenwood 代理的服务的测试（进程内 system server 只伪造了一小撮精选服务，而非整个平台）
  • 需要完整、真实、带窗口的 Activity 生命周期的测试

57.11.10 按形态与环境门控 UI 测试

随着 Android 扩展出桌面窗口、大屏与汽车形态，UI 测试越来越需要在某些形态上运行、而在其他形态上不运行。它们还需要在无设备（Ravenwood/Robolectric）运行时干净地跳过，而不是失败。 LimitDevicesRule （platform_testing/libraries/health/rules/src/android/platform/test/rule/LimitDevicesRule.kt） 是执行这些约束的 JUnit TestRule，其注解与 Build.PRODUCT 做匹配：

注解 效果
@AllowedDevices(...) 仅在列出的 DeviceProduct 值上运行
@DeniedDevices(...) 在列出的设备上跳过
@ScreenshotTestDevices(...) 限定到默认截图设备（CF_PHONE、CF_TABLET）或一组覆盖值
@FlakyDevices(...) 仅在设置了 running-flaky-tests 插桩参数时于列出的设备上运行
@SkipOnDesktop 在桌面环境中跳过（Build.PRODUCT 属于桌面产品集合）
@SkipOnDeviceless 在设备之外运行（Ravenwood/Robolectric）时跳过
@IgnoreLimit(true) 完全绕过该规则（供在任意设备上本地运行时使用）

目标设备由 DeviceProduct 枚举命名（Cuttlefish 产品如 CF_PHONE、CF_TABLET、CF_FOLDABLE、CF_DESKTOP、CF_AUTO，以及真实产品）。一个免费的 isDesktop() 辅助方法把同样的桌面判定暴露给测试体。测试这样给自己加门控：

class MyLargeScreenTest {
    @get:Rule val limitDevices = LimitDevicesRule.readParamsFromInstrumentation()

    @Test
    @AllowedDevices(CF_TABLET, CF_FOLDABLE)
    @SkipOnDesktop
    fun splitScreenLayout_isCorrect() { /* ... */ }
}

当当前设备与注解不匹配时，该规则抛出 AssumptionViolatedException，于是测试被报告为跳过而非失败。同一个模块因此可参与手机、平板、折叠屏、桌面与无设备运行，而无需按配置派生测试分支。配套的 @SkipOnDesktop/@SkipOnDeviceless 注解正是 17 中桌面窗口与 Ravenwood 测试清扫背后的平台侧机制。尚不能在桌面窗口或设备外通过的测试被加注注解，而不是全局禁用；其手机覆盖范围保持不变。

Dexmaker 让 mock 能在 Android 的 ART 运行时上于运行期生成 —— 标准 Java 字节码操纵库在那里用不了。

源码：external/dexmaker/

Dexmaker 解决的是 Android 的一个根本挑战：Dalvik/ART 运行时无法使用 cglib 或 ByteBuddy（JVM 上的标准 mock 生成库），因为二者生成的是 JVM 字节码而非 DEX 字节码。Dexmaker 则在运行期为 mock 类生成 DEX 文件。

57.13.13 编写有效的模糊测试目标

编写有效模糊测试目标的准则：

// GOOD: Focused on a single parser
extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size) {
    // Create a FuzzedDataProvider for structured fuzzing
    FuzzedDataProvider fdp(data, size);

    // Consume structured data from fuzz input
    std::string format = fdp.ConsumeRandomLengthString(256);
    int width = fdp.ConsumeIntegralInRange<int>(1, 8192);
    int height = fdp.ConsumeIntegralInRange<int>(1, 8192);
    std::vector<uint8_t> image_data =
        fdp.ConsumeRemainingBytes<uint8_t>();

    // Exercise the code under test
    ImageDecoder decoder;
    decoder.SetFormat(format);
    decoder.Decode(image_data.data(), image_data.size(), width, height);

    return 0;
}

关键原则：

  1. 单一入口：每个模糊器只有一个 LLVMFuzzerTestOneInput
  2. 结构化模糊测试：对复杂输入使用 FuzzedDataProvider
  3. 无全局状态：每次调用都应相互独立
  4. 执行要快：让每一轮迭代保持在 1ms 以内
  5. 覆盖所有错误路径：不要在把输入交给被测对象（SUT）之前做校验
  6. 无内存泄漏：模糊器要跑数百万轮

57.14.3 插桩流水线

JaCoCo 插桩流水线分三步：

  1. 剥离（Strip）：用 zip2zip 配合 include/exclude 过滤，从输入 JAR 中提取相关类

  2. 插桩（Instrument）：对剥离后的 JAR 运行 jacoco instrument，插入覆盖率探针

  3. 合并（Merge）：把插桩后的类与原 JAR 重新合并，优先采用插桩版本

func jacocoInstrumentJar(ctx android.ModuleContext,
    instrumentedJar, strippedJar android.WritablePath,
    inputJar android.Path, stripSpec string) {

    tmpJar := android.PathForModuleOut(ctx, "jacoco", "tmp", strippedJar.Base())
    ctx.Build(pctx, android.BuildParams{
        Rule:           jacoco,
        Description:    "jacoco",
        Output:         instrumentedJar,
        ImplicitOutput: strippedJar,
        Input:          inputJar,
        Args: map[string]string{
            "strippedJar": strippedJar.String(),
            "stripSpec":   stripSpec,
            "tmpDir":      filepath.Dir(tmpJar.String()),
            "tmpJar":      tmpJar.String(),
        },
    })
}

57.14.4 过滤规范

JaCoCo 过滤器控制哪些类会被插桩。过滤语法使用带通配符的 Java 包写法：

func jacocoFilterToSpec(filter string) (string, error) {
    recursiveWildcard := strings.HasSuffix(filter, "**")
    nonRecursiveWildcard := false
    if !recursiveWildcard {
        nonRecursiveWildcard = strings.HasSuffix(filter, "*")
        filter = strings.TrimSuffix(filter, "*")
    } else {
        filter = strings.TrimSuffix(filter, "**")
    }
    spec := strings.Replace(filter, ".", "/", -1)
    if recursiveWildcard {
        spec += "**/*.class"
    } else if nonRecursiveWildcard {
        spec += "*.class"
    } else {
        spec += ".class"
    }
    return spec, nil
}

在 Android.bp 中，模块这样指定覆盖率过滤：

java_library {

    srcs: ["src/**/*.java"],

        exclude_filter: ["com.android.mypackage.test.**"],
    },
}

func (test *testDecorator) moduleInfoJSON(ctx android.ModuleContext,
    moduleInfoJSON *android.ModuleInfoJSON) {
    if android.PrefixInList(moduleInfoJSON.CompatibilitySuites, "mts-") &&
        !android.InList("mts", moduleInfoJSON.CompatibilitySuites) {
        moduleInfoJSON.CompatibilitySuites = append(
            moduleInfoJSON.CompatibilitySuites, "mts")
    }
}

57.17.10 测试检查清单

为你负责的 AOSP 模块添加测试时，对照这份清单：

  • 所有公开函数/方法都有单元测试

  • 优先宿主机：该测试能否不依赖设备运行？用 cc_test_host、android_ravenwood_test 或 android_robolectric_test

  • 已更新 TEST_MAPPING：把测试加入 presubmit 组

  • 已声明 test_suites：模块至少指定 general-tests

  • auto_gen_config：让构建系统生成 TradeFed XML

  • 安全攸关代码已模糊测试：创建 cc_fuzz 或 rust_fuzz 目标

  • 已度量覆盖率：为覆盖率报告设置 JaCoCo 过滤

  • 无不稳定：连续运行 100 次以上都能稳定通过

  • 执行要快：单元测试在 1 秒内完成

  • 最小化设备依赖：只有确实必要时才用设备

57.17.13 端到端工作流：从代码变更到测试执行

本节追踪从开发者提交代码变更，到测试在 CI 中执行完毕的完整路径。

sequenceDiagram
    participant Dev as 开发者
    participant Repo as 代码仓库
    participant CI as CI 系统
    participant TM as TEST_MAPPING 解析器
    participant Soong as Soong 构建系统
    participant TF as TradeFederation
    participant Device as 测试设备

    Dev->>Repo: 上传 CL（代码变更）
    CI->>Repo: 检测变更文件
    CI->>TM: 沿目录树查找 TEST_MAPPING
    TM-->>CI: 提交前测试清单
    CI->>Soong: 构建测试模块及其依赖
    Soong->>Soong: 编译、链接、生成 TF 配置
    Soong-->>CI: 测试 APK、二进制、配置
    CI->>TF: 用测试计划创建一次调用
    TF->>TF: CommandScheduler.addCommand()
    TF->>TF: 分配设备
    TF->>Device: 准备（刷机、安装、配置）
    loop 对每个测试模块
        TF->>Device: 执行测试
        Device-->>TF: 结果
    end
    TF->>TF: 汇总结果，应用重试
    TF-->>CI: 通过/失败报告
    CI-->>Dev: 提交前检查结果
    alt 全部测试通过
        CI->>Repo: 允许合并
    else 测试失败
        CI->>Dev: 阻止合并，展示失败
    end

步骤 1：变更检测 CI 系统识别 CL 中哪些文件发生变更，并通过目录向上查找把它们映射到 TEST_MAPPING 文件。

步骤 2：测试选择 解析 TEST_MAPPING 文件，收集 presubmit 组中的测试。file_patterns 与变更文件比对，以限定测试范围。

步骤 3：构建 Soong 编译所需的测试模块及其全部依赖，并为每个测试模块自动生成 TradeFed XML 配置。

步骤 4：执行 TradeFederation 接收测试计划并：

  • 从设备池中分配设备
  • 运行目标准备器（安装 APK、推送文件等）
  • 逐个执行测试模块
  • 通过 ITestInvocationListener 收集结果
  • 对失败应用重试逻辑

步骤 5：报告 汇总结果回报给 CI 系统，由 CI 更新 CL 状态。

57.17.14 性能优化技巧

  1. 减少构建噪音：用 atest 的 --build-output logged 把构建输出写入日志文件，而不是流式打印。该参数仅有 streamed 与 logged 两个有效值。

  2. 使用 –host：对纯宿主机测试始终加 --host，跳过设备准备

  3. 善用缓存：atest 会缓存测试发现结果，除必要外不要 --clear-cache

  4. 并行分片：对大型测试套件用 --sharding N 跨多台设备运行

  5. 增量测试：用 atest --test-mapping 只运行与本次变更相关的测试

  6. 跳过安装：迭代时（首次构建之后）用 atest -t <module> 只跑测试步骤。-b、-i、-t 分别选择构建、安装与测试步骤。

小结

Android 的测试基础设施是一套横跨整个技术栈（从内核到 UI）的综合生态，支撑着数百家厂商、数十亿台设备。本章的关键要点：

  1. TradeFederation 是统一所有测试执行的中央测试框架。其可插拔的准备器、运行器与报告器架构支持平台上的每一种测试类型。

  2. 构建系统提供专门的模块类型（cc_test、android_test、rust_test 等），它们自动生成 TradeFed 配置、管理依赖并正确安装测试。

  3. TEST_MAPPING 把代码变更与测试执行连起来，无需手工配置即可实现有针对性的提交前测试。

  4. 宿主机侧测试（Ravenwood、Robolectric、宿主 GTest）通过消除设备依赖提供快速反馈回路。新代码应尽可能优先采用宿主机侧测试。

  5. 合规套件（CTS、VTS、MTS）落实那些让 Android 生态能在多样硬件上运转的契约。

  6. 模糊测试是一等公民，构建系统对 cc_fuzz、rust_fuzz、java_fuzz 目标提供支持，并与 LLVM sanitizer 集成，以实现全面的漏洞发现。

  7. atest 弥合开发者与测试基础设施之间的鸿沟，提供一个简单 CLI 来处理代码树中任意测试的构建、安装与运行。

对任何 AOSP 模块而言，最佳测试策略都遵循金字塔：最大化快速宿主机侧单元测试；为需要真实硬件的行为添加聚焦的设备集成测试；并确保你的组件符合相应的测试套件。

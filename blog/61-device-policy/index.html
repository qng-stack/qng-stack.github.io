第 61 章：设备策略与 Android Enterprise

第 61 章：设备策略与 Android Enterprise

Android Enterprise 是一个统称，涵盖一组 API、基础设施组件与管理模式，让组织能够成规模地管理 Android 设备。其核心是设备策略框架（Device Policy Framework）。这套系统服务子系统以 DevicePolicyManagerService（DPMS）为中心。DPMS 把高层企业意图（“要求六位 PIN 码”“在工作资料中禁用摄像头”）翻译成贯穿 Android 技术栈的具体强制执行变更。

本章沿真实 AOSP 源码追踪每一条主要通路。这些通路始于声明管理组件（admin component）的 XML 元数据，穿过庞杂的 DPMS 实现，进入策略引擎的裁决层，最后落到让每条策略生效的各个子系统执行器（enforcer）。

61.1 企业架构

61.1.1 问题空间

企业移动管理（EMM）必须调和两项相互冲突的需求：

  1. 企业控制 —— 组织需要强制安全策略、部署应用、下发配置、在设备丢失时擦除数据，以及审计活动。

  2. 用户隐私 —— 员工不希望雇主看到自己的私人照片、读到私人消息，或在非工作时间追踪自己的位置。

Android Enterprise 用三种方式化解这一张力：用户空间隔离（工作资料）、权限层级（设备所有者 vs 资料所有者），以及细粒度的策略 API（现代 AOSP 中有 250 多项可独立控制的策略）。

61.1.3 设备所有者（DO）

设备所有者是一个对整台设备拥有完整管理权限的设备策略客户端（DPC）应用。它在初始设置向导期间配置（开发时也可通过 adb）。从源码角度看，设备所有者记录在：

// frameworks/base/services/devicepolicy/java/com/android/server/devicepolicy/Owners.java
class Owners {
    @GuardedBy("mData")
    private final OwnersData mData;
    // mData.mDeviceOwner holds the OwnerInfo for the Device Owner
    // mData.mDeviceOwnerUserId identifies which user the DO runs as
}

关键特征：

  • 单例：每台设备上只能存在一个设备所有者。

  • 配置时机：在开箱体验（OOBE）期间通过 NFC 触碰、二维码、零接触注册或 adb shell dpm set-device-owner 设置。

  • 作用域：可以设置全局策略（Wi-Fi、时区、系统更新策略、恢复出厂保护）以及按用户划分的策略。

  • 不可移除：一旦设置，设备所有者只能通过恢复出厂设置移除（或由 DO 自身调用 clearDeviceOwnerApp()）。

DPMS 通过统计日志常量跟踪管理模式：

61.1.4 资料所有者（PO）

资料所有者管理单个 Android 用户（通常是一个受管资料）。与设备所有者不同，一台设备上可以并存多个资料所有者（每个用户一个）。Owners 类把它们存在以 userId 为键的 ArrayMap 中：

// OwnersData.java
// mData.mProfileOwners is ArrayMap<Integer, OwnerInfo> keyed by userId

Owners 类从磁盘加载配置时，会把所有者信息推送到多个子系统：

// Owners.java, load()
void load() {
    synchronized (mData) {
        int[] usersIds =
            mUserManager.getAliveUsers().stream().mapToInt(u -> u.id).toArray();
        mData.load(usersIds);
        // ... push to DeviceStateCache, ActivityTaskManager, PackageManager
        notifyChangeLocked();
        pushDeviceOwnerUidToActivityTaskManagerLocked();
        pushProfileOwnerUidsToActivityTaskManagerLocked();
    }
}

61.1.5 COPE（企业所有、个人可用）

COPE 是 Android 11 引入的混合模式。设备归企业所有，但没有设备所有者。一个资料所有者运行在工作资料中，并被标记为“组织所有设备上的资料所有者”。这一标记赋予它对个人侧有限的一组权力。只有当不存在设备所有者，且工作资料的资料所有者满足 isProfileOwnerOfOrganizationOwnedDevice() 为真时，DPMS 才报告 COPE 管理模式。

COPE 关系编码在配置参数中：

// frameworks/base/core/java/android/app/admin/ManagedProfileProvisioningParams.java
public final class ManagedProfileProvisioningParams implements Parcelable {
    private final boolean mOrganizationOwnedProvisioning;
    // When true, the profile owner gains elevated privileges over
    // the personal profile (e.g., suspending personal apps).
}

UserManagerInternal 中的所有者类型跟踪区分三种情况：

61.1.6 BYOD（自带设备）

在 BYOD 模式下，设备归员工所有。只创建工作资料，且资料所有者仅管理该资料。IT 管理员对个人侧没有任何控制权。这是最尊重隐私的管理模式。

61.1.10 无头系统用户模式

现代 Android 支持无头系统用户模式，这在车机与多用户场景中尤其重要。DeviceAdminInfo 类定义了三种无头模式：

// frameworks/base/core/java/android/app/admin/DeviceAdminInfo.java
public static final int HEADLESS_DEVICE_OWNER_MODE_UNSUPPORTED = 0;
public static final int HEADLESS_DEVICE_OWNER_MODE_AFFILIATED = 1;
public static final int HEADLESS_DEVICE_OWNER_MODE_SINGLE_USER = 2;

在“关联”（affiliated）模式下，资料所有者会被自动加入除系统用户（设备所有者所在用户）之外的所有用户。在“单用户”模式下，设备所有者被配置进第一个次要用户，并且禁止创建更多次要用户。

61.2.8 裁决机制

每条策略定义都声明一种裁决机制，决定多个管理员给出的冲突取值如何调和：

// frameworks/base/services/devicepolicy/java/com/android/server/devicepolicy/
//   PolicyDefinition.java
public static final MostRestrictive<Boolean> FALSE_MORE_RESTRICTIVE =
    new MostRestrictive<>(
        List.of(new BooleanPolicyValue(false), new BooleanPolicyValue(true)));

static final MostRestrictive<Boolean> TRUE_MORE_RESTRICTIVE =
    new MostRestrictive<>(
        List.of(new BooleanPolicyValue(true), new BooleanPolicyValue(false)));

每个裁决机制都是抽象类 ResolutionMechanism<V> 的子类。Android 17 的树中共有八个子类（全部位于 com.android.server.devicepolicy 包内）。其中七个是具体类，第八个是抽象的 ListUnion<T>，通过其 STRING 与 PACKAGE 变体实例化。LeastRecent 与 ListUnion 是本版新增的：

机制 源文件 说明 示例策略
MostRestrictive<V> MostRestrictive.java 最严格的值胜出（依据预先声明的次序） 摄像头禁用、截屏禁用
TopPriority<V> TopPriority.java 权限优先级表中优先级最高的管理员胜出 锁定任务、持久首选活动
MostRecent<V> MostRecent.java 最近设置的值胜出 无严格次序的按管理员设置
LeastRecent<V> LeastRecent.java 最早设置的值胜出（17 新增） 先写者胜出的策略
PackageSetUnion PackageSetUnion.java 所有管理员包集合的并集 用户可控的已禁用包
ListUnion<T> ListUnion.java 所有管理员列表值的并集（抽象类，17 新增） 允许输入法之类的列表
FlagUnion FlagUnion.java 所有管理员整型标志按位或 锁屏界面特性禁用标志
StringSetIntersection StringSetIntersection.java 所有管理员字符串集合的交集 跨资料 widget 提供方

示例：安全日志以 TRUE_MORE_RESTRICTIVE 裁决，意味着只要有任一管理员启用安全日志，它就保持启用：

// PolicyDefinition.java
static PolicyDefinition<Boolean> SECURITY_LOGGING = new PolicyDefinition<>(
    new NoArgsPolicyKey(DevicePolicyIdentifiers.SECURITY_LOGGING_POLICY),
    TRUE_MORE_RESTRICTIVE,
    POLICY_FLAG_GLOBAL_ONLY_POLICY,
    PolicyEnforcerCallbacks::enforceSecurityLogging,
    new BooleanPolicySerializer());

61.2.9 策略标志

每个 PolicyDefinition 都携带控制其作用域与行为的标志：

// PolicyDefinition.java
static final int POLICY_FLAG_NONE = 0;
public static final int POLICY_FLAG_GLOBAL_ONLY_POLICY = 1;
public static final int POLICY_FLAG_LOCAL_ONLY_POLICY = 1 << 1;
static final int POLICY_FLAG_INHERITABLE = 1 << 2;
static final int POLICY_FLAG_NON_COEXISTABLE_POLICY = 1 << 3;
static final int POLICY_FLAG_USER_RESTRICTION_POLICY = 1 << 4;
static final int POLICY_FLAG_SKIP_ENFORCEMENT_IF_UNCHANGED = 1 << 5;
private static final int POLICY_FLAG_PACKAGE_POLICY = 1 << 6;
  • GLOBAL_ONLY：策略作用于整台设备（如自动时区）。
  • LOCAL_ONLY：策略按用户生效（如权限授予）。
  • INHERITABLE：子资料从父资料继承该策略。
  • NON_COEXISTABLE：各管理员的取值彼此隔离保存（如应用限制）。
  • USER_RESTRICTION：标记用户限制类策略，以便特殊处理。
  • SKIP_ENFORCEMENT_IF_UNCHANGED：裁决结果未变化时跳过执行器回调，避免无谓的下游工作。
  • PACKAGE_POLICY：标记包作用域策略，其执行回调只对已安装的包生效；当包被（重新）安装时会再次应用该回调。

61.2.10 EnforcingAdmin：策略引擎中的管理员身份

EnforcingAdmin 类在策略引擎内部刻画管理员的身份。在 Android 17 的树中，它识别四种权限类型，以常量字符串（或字符串前缀）编码：

// frameworks/base/services/devicepolicy/java/com/android/server/devicepolicy/
//   EnforcingAdmin.java
public final class EnforcingAdmin {
    public static final String ROLE_AUTHORITY_PREFIX = "role:";
    public static final String SYSTEM_AUTHORITY_PREFIX = "system:";
    public static final String DPC_AUTHORITY = "enterprise";
    public static final String DEVICE_ADMIN_AUTHORITY = "device_admin";

    private final ComponentName mComponentName;
    private final AdminKey mAdminKey;
    private Set<String> mAuthorities;
    private final boolean mIsRoleAuthority;
}

早前的 DevicePolicyEngine 以 <packageName, userId> 作为管理员的键。Android 16/17 把它重构为密封的 AdminKey 层次（AdminKey.Package、AdminKey.Legacy、AdminKey.System）。有了这一层次，企业/角色管理员、旧式设备管理员与系统管理员即便共用一个包名也绝不会撞键。若干静态工厂方法为每种权限构造合适的身份：

static EnforcingAdmin createEnterpriseEnforcingAdmin(
        ComponentName componentName, int userId) {
    return new EnforcingAdmin(
        new AdminKey.Package(userId, componentName.getPackageName()),
        componentName, /* isRoleAuthority */ false,
        new HashSet<>(Set.of(DPC_AUTHORITY)));
}

static EnforcingAdmin createDeviceAdminEnforcingAdmin(
        ComponentName componentName, int userId) {
    return new EnforcingAdmin(
        new AdminKey.Legacy(userId, componentName),
        componentName, /* isRoleAuthority */ false,
        new HashSet<>(Set.of(DEVICE_ADMIN_AUTHORITY)));
}

static EnforcingAdmin createSystemEnforcingAdmin(String systemEntity) {
    return new EnforcingAdmin(
        new AdminKey.System(systemEntity),
        /* componentName */ null, /* isRoleAuthority */ false,
        getSystemAuthority(systemEntity));
}

第四个工厂 createRoleEnforcingAdmin 只接收包名与用户（没有 ComponentName），并把该包持有的角色解析成一组 role:<roleName> 权限。SYSTEM_AUTHORITY_PREFIX（"system:"）与 createSystemEnforcingAdmin 这条通路是承重的新增项：它们让受信平台服务能通过 DPC 所用的同一个引擎设置设备策略，而无需自己成为 DPC。其中最值得注意的是高级保护模式（61.8.28 节）。

把持久化的权限字符串解析回 android.app.admin.Authority 实例的逻辑位于 getParcelableAuthority：它把 "enterprise" 映射为 DpcAuthority，把 "device_admin" 映射为 DeviceAdminAuthority，role: 前缀映射为 RoleAuthority，system: 前缀映射为 SystemAuthority。

61.3 工作资料

61.3.1 概念模型

工作资料是一个 Android 受管资料（managed profile）—— 与个人资料跑在同一台设备上的独立用户空间。它拥有自己的：

  • 应用实例（应用的独立副本）
  • 数据目录（/data/user/<profileUserId>/）
  • 联系人数据库
  • 日历存储

61.4.3 密码策略

密码策略是最常用的设备管理能力之一。Android 支持两种思路：

旧式基于质量等级的做法（已弃用但仍受支持）：

// DevicePolicyManager.java
public static final int PASSWORD_QUALITY_UNSPECIFIED = 0;
public static final int PASSWORD_QUALITY_BIOMETRIC_WEAK = 0x8000;
public static final int PASSWORD_QUALITY_SOMETHING = 0x10000;
public static final int PASSWORD_QUALITY_NUMERIC = 0x20000;
public static final int PASSWORD_QUALITY_NUMERIC_COMPLEX = 0x30000;
public static final int PASSWORD_QUALITY_ALPHABETIC = 0x40000;
public static final int PASSWORD_QUALITY_ALPHANUMERIC = 0x50000;
public static final int PASSWORD_QUALITY_COMPLEX = 0x60000;

现代基于复杂度等级的做法（推荐）：

// DevicePolicyManager.java
public static final int PASSWORD_COMPLEXITY_NONE = 0;
public static final int PASSWORD_COMPLEXITY_LOW = 0x10000;
public static final int PASSWORD_COMPLEXITY_MEDIUM = 0x30000;
public static final int PASSWORD_COMPLEXITY_HIGH = 0x50000;

复杂度等级对应具体要求：

复杂度 PIN 图案 密码
LOW 4 位以上数字 任意 4 个字符以上
MEDIUM 4 位以上数字，不得有重复/连续 不适用 4 个字符以上
HIGH 8 位以上数字，不得有重复/连续 不适用 6 个字符以上，且含至少一个非数字字符

图案凭据永远只能满足 LOW（PasswordMetrics 只在 LOW 与 NONE 两档允许图案凭据类型）。HIGH 的最小长度，在凭据含任意非数字字符时为 6，否则为 8。

ActiveAdmin 类把密码策略存在一个专用对象中：

// ActiveAdmin.java
PasswordPolicy mPasswordPolicy = new PasswordPolicy();
// Fields include: quality, length, uppercase, lowercase,
// letters, numeric, symbols, nonletter, history length

61.8.28 作为系统管理员的先进保护模式

Android 16 引入、Android 17 扩展了先进保护模式（Advanced Protection Mode，AAPM）。AAPM 是“设置”中的一个用户可见开关，一次性开启一组强化过的安全特性。架构上真正有意思的是它如何落实这些特性：AAPM 不属于 DPMS，也不是 DPC，而是一个独立的系统服务。它以系统管理员的身份驱动若干既有的设备策略，靠的正是 61.2 节描述的那个策略引擎。

该服务及其客户端 API 位于 devicepolicy 包之外：

// frameworks/base/services/core/java/com/android/server/security/advancedprotection/
//   AdvancedProtectionService.java                (the system service)
// frameworks/base/core/java/android/security/advancedprotection/
//   AdvancedProtectionManager.java                (the @SystemService client)
public static final String ADVANCED_PROTECTION_SYSTEM_ENTITY =
        "android.security.advancedprotection";

每项强化能力都是 services/core/java/com/android/server/security/advancedprotection/features/ 下的一个“特性钩子”，以 AdvancedProtectionManager 中的稳定特性 ID 为键：

// AdvancedProtectionManager.java
public static final int FEATURE_ID_DISALLOW_CELLULAR_2G = 0;
public static final int FEATURE_ID_DISALLOW_INSTALL_UNKNOWN_SOURCES = 1;
public static final int FEATURE_ID_DISALLOW_USB = 2;
public static final int FEATURE_ID_DISALLOW_WEP = 3;
public static final int FEATURE_ID_ENABLE_MTE = 4;
public static final int FEATURE_ID_DISALLOW_INSECURE_WIFI_AUTOJOIN = 5;
public static final int FEATURE_ID_RESTRICT_NON_TOOL_A11Y_SERVICES = 6;

把本章串起来的，正是通进设备策略的这座桥。以 MemoryTaggingExtensionHook 为例，它调用的是 setMtePolicy 的系统重载，而不是公开的、接收 ComponentName 的那个：

// services/core/java/com/android/server/security/advancedprotection/features/
//   MemoryTaggingExtensionHook.java
mDevicePolicyManager.setMtePolicy(ADVANCED_PROTECTION_SYSTEM_ENTITY, mtePolicy);

该重载（DevicePolicyManager.setMtePolicy(String systemEntity, int policy)）调用 IDevicePolicyManager.setMtePolicyBySystem(systemEntity, policy)，DPMS 再把取值记录到一个 createSystemEnforcingAdmin(ADVANCED_PROTECTION_SYSTEM_ENTITY) 身份之下 —— 也就是 61.2.10 节里的 system: 权限。AAPM 的 MTE 偏好作为“又一个管理员”的取值进入引擎，于是它按常规裁决规则与任何 DPC 的 MTE 策略共存，而不是与之对抗。

17 的树中随版本发布四个具体钩子（均 extends AdvancedProtectionHook）：MemoryTaggingExtensionHook、DisallowInstallUnknownSourcesAdvancedProtectionHook、DisallowCellular2GAdvancedProtectionHook 与 UsbDataAdvancedProtectionHook。其中三个经 DPMS 以 system: 管理员身份落地，但走的是两条不同的 DPM 调用。MTE 用上文所示的 setMtePolicy(ADVANCED_PROTECTION_SYSTEM_ENTITY, ...)；而安装未知来源与 2G 这两个钩子则是从系统实体挂上一条全局用户限制，例如

// DisallowInstallUnknownSourcesAdvancedProtectionHook.java
mDevicePolicyManager.addUserRestrictionGlobally(ADVANCED_PROTECTION_SYSTEM_ENTITY,
        UserManager.DISALLOW_INSTALL_UNKNOWN_SOURCES_GLOBALLY);
// DisallowCellular2GAdvancedProtectionHook.java -> ...DISALLOW_CELLULAR_2G

addUserRestrictionGlobally(systemEntity, ...) 最终同样落在 DPMS 中，并把该限制记录在同一个系统 EnforcingAdmin 之下。因此这条用户限制留在策略引擎里，与任何 DPC 的取值并列，而不是被直接写进 UserManager。

USB 钩子是其中最特殊的一个：它完全不设置用户限制。启用时它经 setUsbDataSignalIfPossible(...) 切换 USB 的数据信号。这一切换受锁屏状态门控 —— 钩子只在设备锁定时断开数据线，解锁时再通过 IUsbManagerInternal.enableUsbDataSignal 重新接通。UserManager 中并没有 DISALLOW_USB 常量；FEATURE_ID_DISALLOW_USB 只是该钩子的特性 ID。

61.8.29 多用户受管设备配置

无头系统用户模式（61.1.10 节）需要一条不假定“设备所有者由面向人的用户承载”的配置流程。Android 17 正是为此落地了多用户受管设备配置路径。DevicePolicyManager 中新增的客户端接口是：

// frameworks/base/core/java/android/app/admin/DevicePolicyManager.java
public static final String ACTION_PROVISION_MULTIUSER_MANAGED_DEVICE =
        "android.app.admin.action.PROVISION_MULTIUSER_MANAGED_DEVICE";
public static final String ACTION_PROVISION_MULTIUSER_MANAGED_USER =
        "android.app.admin.action.PROVISION_MULTIUSER_MANAGED_USER";

// Kicks off the provisioning state machine (system API)

从概念上说，这把“配置设备”与“在该设备上配置一个受管用户”拆开了：设备所有者建立在无头系统用户之上，受管用户随后带着自己的所有者状态被配置。这正是 DeviceAdminInfo 中 HEADLESS_DEVICE_OWNER_MODE_SINGLE_USER 与 HEADLESS_DEVICE_OWNER_MODE_AFFILIATED 在配置流程上的对应物。

61.8.30 策略模式版本化与迁移

策略引擎会把裁决后的状态持久化到磁盘（61.2.13 节），因此磁盘上的模式是有版本的 —— 这让 OTA 能把旧版 XML 向前迁移。DPMS 固定当前模式版本：

// frameworks/base/services/devicepolicy/java/com/android/server/devicepolicy/
//   DevicePolicyManagerService.java
static final int DPMS_VERSION = 6;
// ... during boot:
upgrader.upgradePolicy(DPMS_VERSION);

PolicyVersionUpgrader.upgradePolicy(int) 从磁盘上记录的版本开始，沿一串 if (currentVersion == N) 步骤走到 DPMS_VERSION，每一步都重写策略并递增存储的版本号。例如 5 -> 6 这一步翻转了某个布尔策略的默认值，因此版本 5 的文件加载时该字段仍是旧默认值，直到它被以版本 6 重新持久化。

另有一个 PolicyMigrator.migrateV1PoliciesToDevicePolicyEngineLocked() 处理“引擎之前时代”（Android 13 及更早）策略的一次性迁移 —— 允许输入法、禁用账户管理之类 —— 把它们转成 DevicePolicyEngine 的表示形式。两者都在启动期间于 DPMS 锁内运行。正因如此，大版本升级后的首次启动会先做一些少量的策略簿记工作，管理 API 才完全可用。

            PASSWORD_COMPLEXITY_HIGH);

        AttestedKeyPair keyPair = dpm.generateKeyPair(admin, "EC", spec,
            DevicePolicyManager.ID_TYPE_SERIAL
                | DevicePolicyManager.ID_TYPE_IMEI);

        if (keyPair != null) {
            List<Certificate> chain = keyPair.getAttestationRecord();
            Log.i(TAG, "Attestation chain length: " + chain.size());

            // Send chain to server for verification
            sendAttestationToServer(chain);
        }
    } catch (Exception e) {
        Log.e(TAG, "Attestation failed", e);
    }
}

private byte[] generateServerChallenge() {
    // In production, this comes from the EMM server
    byte[] challenge = new byte[32];
    new java.security.SecureRandom().nextBytes(challenge);
    return challenge;
}

小结

Android Enterprise 框架是 AOSP 中最复杂的子系统之一，横跨核心服务与其客户端 API。以下是几条关键的架构洞见：

  1. 管理模式（完全受管、工作资料/BYOD、COPE）构成一条从“IT 完全控制”到“最大用户隐私”的谱系。模式在配置阶段即已确定，它从根本上决定了哪些策略能够被强制执行。

  2. DevicePolicyManagerService 是中枢式的策略经纪人，也是 AOSP 体量最大的系统服务之一。它校验调用方权限、把裁决委派给策略引擎、把有版本的状态持久化为 XML（Android 17 中 DPMS_VERSION = 6），并向各子系统通知策略变化。

  3. DevicePolicyEngine（Android 14 引入）带来了正式的多管理员策略裁决。Android 17 提供八种裁决策略：MostRestrictive、TopPriority、MostRecent、LeastRecent、PackageSetUnion、ListUnion、FlagUnion 与 StringSetIntersection。它还有四种管理员权限类型（enterprise、device_admin、role:，以及较新的 system:），从而让 DPC 管理员、基于角色的管理员、旧式设备管理员与受信任的系统服务（如先进保护模式）能在同一批策略上共存。

  4. 工作资料借助 Android 的多用户基础设施，为工作数据创建一个密码学上隔离的容器。跨资料通信通过 intent 过滤器、provider 访问策略与 CrossProfileApps API 被严格管控。

  5. 安全基础设施包括安全日志（事件来自 logd）、网络日志（经 netd 的 DNS 与 TCP 事件）、硬件背书的设备证明、证书管理与合规检查。这些共同为企业提供关于设备状态的可验证保证。

  6. 权限模型已从要求特定的管理员 ComponentName 演进为细粒度的 MANAGE_DEVICE_POLICY_* 权限。非 DPC 应用现在可以通过角色与委派参与设备管理。

第 66 章：在 Android 上运行 Windows 游戏

第 66 章：在 Android 上运行 Windows 游戏

一台现代 Android 手机带着足以跑桌面 PC 游戏的 ARM64 GPU。但游戏本身是 x86-64 的 Windows 二进制：它们期待 Win32 API、Wine 底下一套 glibc 风味的 Linux 内核 ABI，以及一个桌面图形驱动。而这些在原生、未 root 的 Android 设备上一概不存在。

GameNative 这类项目，以及它所构建其上的 Winlator 运行时，完全在用户空间里补上了这道鸿沟：不 root、不打内核补丁、不刷自定义 ROM。它们把一串翻译层叠在本书其余章节所剖析的同一套 AOSP 内部机制之上，每一层解决阻抗失配中的一个切片。

本章以 GameNative 为实例，自上而下走完整套栈：从 Android 应用与它塞进 APK 里的 glibc 根文件系统开始，接着是 bionic/glibc 边界以及跨越该边界的各种重定向；然后是 x86-64 到 AArch64 的翻译器（FEX 与 Box64），以及作为 Windows API 层的 Wine；最后是抵达真实 Adreno GPU 的 Direct3D 到 Vulkan 图形链，以及收于 AAudio 的音频通路。

每一层都是自成一体的技术，因此每一层都有自己的架构、自己的理由，以及自己在前面章节所述 Android 内部机制中的插入位置。

关于源码引用有一点说明。Android 侧触点按本书其他地方的惯例，以 AOSP 树中的文件路径与行号引用；而翻译栈项目（GameNative、Winlator、Wine、FEX、Box64）是演进很快的外部仓库，因此只给仓库内相对路径、不给行号 —— 行号在墨迹干之前就会过期。

66.1 问题与分层蛋糕

66.1.1 两个正交的翻译

在 ARM 手机上跑 Windows 游戏不是一个问题，而是两个容易被混为一谈的无关问题：

  1. 指令集翻译。 游戏是一串 x86-64 机器指令，ARM64 CPU 无法执行。必须有人把 x86-64 翻成 AArch64，或提前翻、或即时翻。这是 FEX 或 Box64 的活。它是纯粹的 CPU 模拟：不懂窗口、文件或套接字，只懂操作码、寄存器与标志位。

  2. API 与 ABI 翻译。 游戏调用 Windows API：CreateFileW、NtUserCreateWindowEx、D3D11CreateDevice。这些函数在 Linux 上不存在，必须有人把 Windows API 实现在 POSIX/Linux 内核之上。这是 Wine 的活。它不是模拟器：完全不含指令翻译，只有用原生代码对 Windows 行为的重新实现。

把这两件事分开，是整个栈里最重要的一个架构思想。整个系统的性能取决于“尽量少模拟”——理想情况下只模拟游戏自己的代码；Wine、图形驱动与音频服务器则都可以作为原生 ARM64 运行。我们会反复回到这个主题，因为最新的设计（ARM64EC，见 66.5.8）恰恰是为了把“被模拟”的那个盒子缩到只剩游戏。

66.1.3 不 root，不改内核

客户带里的一切都以普通已安装应用的权限运行：没有 su、没有 insmod、不改 SELinux 策略、不动系统镜像。这一约束让这些应用能在锁着 bootloader 的设备上从商店安装，也逼出了本章大部分工程巧思。桌面版 Wine 可以 chroot 进 rootfs、挂载文件系统，并直接 dlopen 系统的 glibc GPU 驱动；Android 应用一样都做不了。每缺一项能力，就换一个用户空间的替代品：

桌面能力 在未 root 的 Android 上 用户空间替代
chroot 进 rootfs 需要 CAP_SYS_ADMIN PRoot（ptrace 路径改写）
挂载 rootfs 镜像 需要 root 解包进应用私有存储
System V 共享内存 受内核限制 ashmem/memfd 支撑的 shim
dlopen glibc GPU 驱动 驱动是 bionic 库 与原生渲染器 IPC，或用 thunk
跑系统 PulseAudio 无系统守护进程访问权 在应用内自带一个 PulseAudio 服务器

66.1.4 用 AOSP 术语说清未 root 应用的约束

三个 AOSP 机制决定了这套栈能做什么、不能做什么，三者都在前面章节中介绍过。

链接器命名空间（第 7 章）。 应用的原生库在隔离的链接器命名空间中加载，看不到任意的系统库。管辖这一点的 android_dlopen_ext 标志位于 bionic/libc/include/android/dlext.h。ANDROID_DLEXT_USE_NAMESPACE（bionic/libc/include/android/dlext.h:115）允许调用方为某个库指定目标命名空间，但该头文件把它标注为仅限内部使用 —— 因为命名空间没有 NDK API。

公开的 ANDROID_DLEXT_USE_LIBRARY_FD（bionic/libc/include/android/dlext.h:80）允许调用方直接从文件描述符加载库，例如 APK 中以未压缩形式存放的 .so。Vulkan loader 自己在打开设备驱动时就用到了这个命名空间标志，我们会在 66.7.4 看到。

W^X 强制（第 7 章）。 JIT 必须先写机器码再执行它。对于目标 API 26 及以上的应用，动态链接器拒绝加载任何同时可写且可执行的 ELF load segment。bionic/linker/linker_phdr.cpp:1057 会打出 "has load segments that are both writable and executable" 诊断，bionic/linker/linker_phdr.cpp:1061 记录 W+E load segments 警告。因此 FEX 或 Box64 这样的翻译器无法发布带 RWX 段的预置 .so。

不过那道检查只覆盖链接器映射的 ELF 文件，匿名 JIT 映射不受其约束；SELinux 甚至给应用进程授予 execmem（system/sepolicy/private/app.te:213），所以应用可以映射匿名的 PROT_WRITE | PROT_EXEC 内存。但翻译器们仍然遵守加固惯例：先以可写映射 JIT 页、填入内容，再用 mprotect 翻成可执行 —— 任一时刻每页都是写异或执行。

应用数据目录的执行限制。 在近期 Android 上，从应用可写数据目录执行二进制受到越来越强的限制。翻译栈必须通过它自己掌控的加载器（PRoot，或某个重定向库）来运行客户端的可执行文件，而不能把应用数据目录下的路径直接交给内核并调用 execve。这是 GameNative 那个闭源 libredirect.so 的职责之一，66.4.4 会讲。

66.2 GameNative：集成式应用

GameNative 是一个在本机运行 Windows PC 游戏的 Android 应用，内置 Steam、Epic Games Store、GOG 与 Amazon Games 的商店集成。它是整套栈最完整的公开范例，因此作为本章的锚点。它采用 GPL-3.0 许可，包名为 app.gamenative。

66.2.1 血统：Pluvia 与 Winlator 的嫁接

最好把 GameNative 理解为两个上游代码库的嫁接，而不是单一分支：

  1. 应用与 Steam 客户端层来自 Pluvia —— 一个轻量的非官方 Android Steam 客户端。它留在源码里的指纹很清楚：Application 子类是 PluviaApp.kt，Room 数据库是 PluviaDatabase.kt，Steam 连接使用 JavaSteam 库。Pluvia 提供账号登录、游戏库视图与 SteamPipe depot 下载器。

  2. 运行时与兼容层来自 Winlator。 整个 com.winlator.* Java 树被内置在 app/src/main/java/com/winlator/ 之下，子包包括 container、core、xserver、xenvironment、winhandler、box86_64、fexcore、inputcontrols 与 renderer；app/src/main/cpp/winlator/ 下的原生侧也来自 Winlator。

所以从代码来源讲，GameNative 是 Pluvia（商店应用）加上 Winlator（Wine 与模拟运行时），由 GameNative 的 GPL-3.0 Kotlin 层统一起来。流行的一些文章说它只是“Winlator 的一个分支”，把这种双源结构折叠掉了；准确的说法是上面这句。本章余下部分依赖的是 Winlator 那一半，因为真正运行游戏的是它。

66.2.2 应用架构

面向 Android 的那一半是 Kotlin + Jetpack Compose UI + Dagger Hilt 依赖注入。对我们而言有三块：

  • SteamService（一个前台 Service）掌管 Steam 会话，Epic、GOG、Amazon 各自的对店服务与它并列。
  • XServerScreen 是游戏渲染进去的全屏 Compose 表面，由 XServerViewModel 驱动 —— 应用内 X 服务器、音频服务器与图形渲染器都在此拉起。
  • 内置的 Winlator 运行时承担实际的容器、rootfs、Wine 与模拟器工作，由 com.winlator.xenvironment 包编排。

66.2.3 容器模型

容器是一个游戏独占的 Windows 环境：一个 Wine prefix 加上它的配置（图形驱动、模拟器、音频驱动、DLL 覆盖、环境变量）。com.winlator.container.Container 与 ContainerManager 定义并管理它们，而默认值是对“GameNative 栈到底是什么”最清楚的一句话陈述。摘自 app/src/main/java/com/winlator/container/Container.java：

// GameNative: app/src/main/java/com/winlator/container/Container.java
public static final String DEFAULT_EMULATOR        = "FEXCore";
public static final String DEFAULT_AUDIO_DRIVER    = "pulseaudio";
public static final String DEFAULT_DXWRAPPER       = "dxvk";
// graphics driver default resolves to "vortek"

被钉住的组件版本就在旁边，在 app/src/main/java/com/winlator/core/DefaultVersion.java：Box64、Box86、FEXCore 的构建号、Turnip（Mesa 的 Adreno Vulkan 驱动）、DXVK、VKD3D 等等。默认 Wine 记录在 WineInfo.java。这两个文件一眼看尽整条默认流水线 —— 这就是为什么本章末尾的一个“动手试试”练习就是读它们。

66.2.4 默认栈

把容器默认值合起来看，一个新建的 GameNative 容器会跑：

  • Wine / Proton，以 ARM64EC 配置充当 Windows API 层（66.6）；FEXCore 翻译游戏的 x86-64 代码；一个 WoW64 辅助件翻译任何 32 位代码（66.5.8）。
  • DXVK 把 Direct3D 9/10/11 翻成 Vulkan，VKD3D-Proton 负责 Direct3D 12（66.7.2）。
  • Vortek 作为抵达设备 Adreno 驱动的 Vulkan 路径（66.7.3），Turnip（Mesa）作为备选。
  • PulseAudio 作为音频服务器（66.8）。

Box64 加经典 glibc 启动路径也一并打包，作为非 ARM64EC Wine 构建的替代路线；由不同的启动器组件选择该路径（66.5.6）。

66.2.5 打包：各部件如何到达设备

GameNative 在一个应用里塞进了数量惊人的预置原生软件，通过三种不同的交付机制。

  1. Android 进程原生库随 jniLibs/arm64-v8a/ 发布，由平台的包管理器解到应用的 nativeLibraryDir。这些库加载进 Android（bionic）进程，包括 PulseAudio 服务器库（libpulse.so 及其同伴）、原生图形渲染器（libvortekrenderer.so、libvirglrenderer.so）、应用内 X 服务器（libwinlator.so），以及闭源的 libsteambootstrap.so。

  2. 客户侧组件以压缩 tar 包形式放在 assets/（Zstandard 的 .tzst 与 xz 的 .txz），运行时由 com.winlator.core.TarCompressorUtils 解进 rootfs。Wine、FEX、Box64、DXVK、VKD3D、Vulkan 驱动与 Windows DLL 组件都以这种方式到达；解包后，它们的 ELF 解释器与 RPATH 会被一个内置的 patchelf 打补丁。

  3. 体积大或可选的负载按需下载。Ubuntu rootfs 作为一个独立的 Android 动态功能模块（ubuntufs/，dist:on-demand）交付；图形驱动、额外的 DXVK 构建与 Proton 容器模板则按 assets/*_download.json 清单从 GameNative 的下载服务器取。这样基础 APK 保持可安装，而数 GB 的 Linux 用户环境只在首次运行游戏时才到位。

66.2.7 许可与 GPL 聚合问题

GameNative 是 GPL-3.0，内置的 Winlator 代码也是。打包的运行时大多带自己的上游许可，多为宽松许可或 LGPL：Wine 与 PulseAudio 是 LGPL-2.1，Mesa（Turnip、Zink）大体是 MIT，DXVK 是 zlib 许可，Box64 与 FEX 是 MIT/BSD 风格。项目的 THIRD_PARTY_NOTICES 文件对 copyleft 组件做了一份概括性的书面源码提供承诺。

有两个组件刻意闭源，而它们在法律上最有意思：

  • libredirect.so（随 assets/redirect.tzst 发布）只通过 LD_PRELOAD 加载进 Wine/Proton 子进程，从不进入 Android 应用自身的地址空间。它改写了旧的包标识符，并使进程启动适配近期 Android 对“从数据目录执行”的限制。
  • libsteambootstrap.so 是一个 JNI 垫片，驱动一个真正在进程内的 Steam 客户端，用于成就、云存档与覆盖层。

维护者陈述的立场是：这些作为独立的程序/子进程运行，只通过操作系统接口通信，因此在 GPL-3.0 第 5 条下属于单纯的“聚合”，而不是 GPL 应用的衍生作品。那是项目方的论点，不是已裁决的事实。闭源的 LD_PRELOAD 与 JNI 垫片在和 GPL-3.0 应用一起分发时能否经得起审视，确实是一个未定的 GPL 问题。应用去掉这两个库也能构建并运行，只是兼容性下降 —— 这也是维护者“可分离性”论点的一部分。

66.3 rootfs：应用内的 glibc Linux 用户环境

66.3.1 rootfs 里有什么

Wine、模拟器的客户库与游戏都期待一个按常规布局的 Linux 文件系统：/usr/lib、/bin、一个 ld-linux 动态加载器，以及最重要的一个 glibc C 库。Android 一样都不给应用 —— 它给的是 bionic 和一个应用私有数据目录。于是这套栈直接塞进一整套小型 Linux 发行版（在 Winlator 里历史上称为 imagefs），并把它解到应用的私有存储中。

rootfs 基于 Ubuntu（最初的 Winlator 用 Focal Fossa，20.04）。里面是一套 glibc 用户环境、/opt 下的 Wine 安装，以及每个容器的 Wine prefix（位于 /home/xuser/.wine）。路径常量定义在 com.winlator.xenvironment.ImageFs。

66.3.2 交付与解包

用户环境以压缩形式交付、首次使用时解包，从不用挂载（应用无法挂载）。相关代码在两个类里：ImageFsInstaller 把 Wine tar 包解到 <rootfs>/opt/<version>，TarCompressorUtils 处理 GameNative 用到的 Zstandard .tzst 与 xz .txz 两种格式。解包之后，ELF 二进制会被 patchelf 修整，使其解释器与库搜索路径指向 rootfs 内部，而不是指向一个并不存在的系统。

体量正是 rootfs 走按需动态功能模块交付的原因（66.2.5）。一套完整的 Ubuntu 加 Wine 用户环境有数百 MB 到数 GB，绝无可能放进基础 APK。

66.3.3 进入 rootfs：PRoot

桌面环境会 chroot 进 rootfs，未 root 的应用不能。经典 Winlator 的答案是 PRoot —— 一个完全建立在 Linux ptrace 系统调用之上的、用户空间版的 chroot 与 bind mount。

PRoot 把客户程序作为被跟踪的子进程启动。每当子进程发起一个带路径的系统调用，PRoot 就在内核边界截住它，改写被跟踪进程内存中的路径字符串，让比如 /usr/lib/... 变成 <app data>/imagefs/usr/lib/...，然后放内核继续。客户以为自己活在 /，但 PRoot 在飞行中重映射了每个路径。同一个把戏会在 execve 上重演，使子进程仍被限制住；--bind=/dev、--bind=/proc 这类 bind mount 也用同样的方式实现 —— 重映射相关前缀。

这个代价是走上无 root 之路的入场费：每个带路径的系统调用都要往 PRoot 进程走一趟 ptrace 的停-继续往返。这项开销正是较新的 bionic 设计（66.3.6）试图彻底去掉 PRoot 的主要原因。

66.3.4 glibc 对 bionic：核心错配

rootfs 给了 Wine 一个 glibc 世界，这正是 Wine 想要的。但它同时制造了整套栈的定义性问题：进程里现在装着 glibc，而每个 Android 原生库（包括 GPU 驱动）都是对着 bionic 构建的。 你没法简单地把一个 bionic 的 .so dlopen 进 glibc 进程 —— 两个 C 库在 TLS 布局、动态加载器内部结构、errno、pthread_t、栈金丝雀上都各说各话。把一个 libc 的共享对象加载进另一个 libc 的进程，会破坏状态并崩溃。

这就是“bionic 重定向”要解决的问题，重要到值得单独一节（66.4）。现在先记住两种答案的形状：第一种是保留 glibc 世界，通过进程间通信而非链接来触达 Android 服务 —— PulseAudio 服务器、Vortek 渲染器与 SysV-SHM 服务器都是经套接字到达的独立端点；第二种是放弃 glibc，让 Wine 直接跑在 bionic 上（较新的分支）。

66.3.5 架在 ashmem 上的 System V 共享内存

bionic 重定向最干净的具体例子是 System V 共享内存。X11、DXVK 等组件用 shmget/shmat 在进程间共享大缓冲。Android 内核对 System V SHM API 有限制，因此 Winlator 的 glibc rootfs 自带一个小 shim 库 libandroid-sysvshm.so，由启动器组件用 LD_PRELOAD 注入客户进程。它拦截 shmget/shmat/shmdt 这一族，并在 Android 的匿名共享内存之上重新实现。Android 侧一个小服务器（com.winlator.sysvshm）充当中间人。

Android 侧最自然的原语是 ASharedMemory_create（frameworks/native/include/android/sharedmem.h:78），这个 NDK 入口返回一块匿名、引用计数的共享内存区域的文件描述符；其底层由 memfd_create（bionic/libc/include/sys/mman.h:183，API 30 起可用）或更老的 ashmem 驱动支撑。重定向把客户内的一个 System V shmget 调用，变成宿主上一个 ASharedMemory 式的 fd，再经套接字传回。客户继续用它当初被写出来的 System V API，宿主则用一个内核真正允许的 Android 原语满足它。

66.3.6 bionic-Wine 替代方案

最新的 Winlator 分支、以及 GameNative 的默认路径，走的是另一条路：为 bionic 构建 Wine，并丢掉 PRoot。如果 Wine 本身就跑在 bionic 上，与 Android GPU 驱动就不存在 libc 错配，也没有每次系统调用的 ptrace 税。代价是 Wine 原先依赖 glibc 的一切都必须改由 bionic 提供 —— 这就是这条路要依赖 ARM64EC Wine 构建（66.5.8）和一组重定向库的原因：这些库替代 PRoot 来修正路径与行为差异。接下来就讲它们。

66.4 bionic 重定向与 libc 边界

“bionic 重定向”是对这一类技术的统称：它们让一套围绕 glibc 风味 Linux 软件搭起来的栈，能与一套围绕 bionic 搭起来的 Android 系统协作。这个说法底下藏着几个不同的问题，各有各的解法。

66.4.1 为什么两个 libc 不能共处一个进程

这里精确陈述核心约束，因为其余一切都由它推出来。一个 Linux 进程恰好有一个动态加载器和一个 C 库；这个库提供加载器的内部状态、TLS 块、malloc 与系统调用包装。glibc 与 bionic 是内部布局互不兼容的两个实现。

glibc 进程的线程有 glibc 的 pthread 结构与 glibc 的 TLS 模型；一个按 bionic 偏移去找自己线程控制块的 bionic .so 会读到垃圾。没有任何开关能让两者共存。二者之间的边界必须由某种不需要链接的机制来跨越 —— 这套栈里恰好有三种这样的机制：进程间通信、ABI thunk，以及整个进程统一选用一个 libc。

66.4.2 链接器命名空间与 dlext

即使栈里跑的是原生 bionic 代码，它仍受第 7 章的链接器命名空间隔离约束：应用原生库加载进一个受限命名空间，看不到大多数系统库。驱动加载路径用 android_dlopen_ext 配合 ANDROID_DLEXT_USE_NAMESPACE（bionic/libc/include/android/dlext.h:115）指向特定命名空间。adrenotools 这类自定义驱动加载器（用来侧载比设备自带更新的一份 Turnip 构建）依赖的正是这套机制：让选定的 .so 加载进一个能触达 GPU 内核接口的命名空间。ANDROID_DLEXT_USE_LIBRARY_FD 标志（bionic/libc/include/android/dlext.h:80）是它的搭档，可直接从文件描述符加载驱动。

66.4.3 W^X 与 JIT

翻译器是 JIT，66.1.4 的 JIT 纪律适用。Android 上每个翻译器都遵循同一模式：先用 PROT_READ | PROT_WRITE 映射代码缓冲、往里写 AArch64 指令，然后清该范围的指令缓存，最后在跳进去之前对缓冲调用 mprotect 改成 PROT_READ | PROT_EXEC。一页永不同时可写且可执行。

这是翻译器自身的加固模式，而不是在遵守链接器对 W+E 的拒绝（bionic/linker/linker_phdr.cpp:1057）—— 那道拒绝只针对 ELF load segment，根本看不到这些匿名代码缓冲。某些设备与 Android 版本会进一步限制从应用数据执行内存，那里翻译器必须把自己的代码页分配为它拥有的匿名内存，而不能映射数据目录中的文件。

66.4.4 路径重定向：PRoot 对 libredirect

PRoot（66.3.3）是路径重定向的一种形式：用 ptrace 在内核 ABI 上改写路径。它通用但慢。bionic 路径则用一个预加载库替代它 —— GameNative 的 libredirect.so，经 LD_PRELOAD 注入 Wine 子进程。该库不通过 ptrace 拦截每个系统调用，而是拦截那些带路径的 libc 函数并在进程内改写其参数，没有跟踪器往返。

这个库还让进程启动适配近期 Android 对“从应用数据目录执行”的限制，顶替未 root 应用不被允许使用的内核机制。取舍是通用性换速度：预加载库只能抓到经由它所拦截函数发起的调用，而 PRoot 在内核边界抓到一切；但预加载方式避开了主导 PRoot 开销的每系统调用 ptrace 成本。

66.4.5 IPC 逃生口

最稳妥的重定向，是完全不在进程内跨越 libc 边界。这套栈里有三个服务以独立端点形式住在 Android（bionic）侧，由客户经 Unix 域套接字访问：

  • PulseAudio 服务器 —— 客户内的 Wine 音频后端作为普通 PulseAudio 客户端连上去（66.8）；
  • Vortek Vulkan 渲染器 —— 客户只持有一个薄薄的 Vulkan ICD，该 ICD 把命令经套接字序列化给原生渲染器（66.7.3）；
  • System V SHM 服务器（66.3.5）。

因为边界是套接字，两侧可以用不同的 C 库、不同的指令集、不同的内存模型 —— 这些都不重要，唯一的契约是线协议。这与 Binder 能跨不同运行时通信是同一个道理（第 9 章）。它付出一次序列化与一次拷贝，却彻底绕开 libc 问题。这也是为什么性能关键但非最热的路径（音频、命令提交）这样建，而真正的热路径（CPU 翻译）没有。

66.5 FEX 与 Box64：把 x86-64 翻成 AArch64

这一层做的是 66.1.1 里那项真正的指令集模拟。两个项目主导局面，GameNative 两者都带：FEX（默认，通过其 FEXCore 引擎）与 Box64。它们用相反的哲学解决同一个问题，理解这处差异，就解释了用户遇到的“兼容性对速度”取舍的大部分。

本章与第 19 章互补。那一章讲的是 Android 自身的、插入 Native Bridge 的进程内二进制翻译器：一个是 Berberis，在 x86_64 设备上跑 riscv64 应用代码的 AOSP 翻译器（它的 CPU 模拟核在 Android 17 中被归并到 frameworks/libs/binary_translation/cpu_emulation/ 之下）；另一个是历史上的闭源 Houdini，在 Intel x86 上跑 ARM 应用代码。两者都在 ART 下运行客户 Android APK 的原生代码，方向与这里的“x86-64 跑在 AArch64 上”相反，且都不参与这套栈。

FEX 与 Box64 是同一个 dynarec 思想作用于整个 Linux/Windows x86-64 程序：它们跑在普通应用进程内，不是 Native Bridge 插件；它们把 x86-64 翻成 AArch64 —— 一个没有任何 AOSP 自带翻译器覆盖的方向。

66.5.1 动态重编译器做什么

动态重编译器（dynarec）是针对外部机器码的 JIT。它读入一块 x86-64 指令，一次性翻成 AArch64 指令，把结果缓存起来，此后每次客户执行流回到该地址就跳到缓存里的译文。译文把客户的寄存器放进宿主寄存器、把客户的内存当作普通宿主内存，只在块边界回落到分派器，以决定接下来跑什么。

dynarec 通常比解释器快五到十倍，因为逐指令的解码成本只在翻译时付一次，而不是每次执行都付。

有三件事让 x86 到 ARM 特别难，每一件都是 FEX 与 Box64 投入工程精力的地方：

  1. 标志位。 几乎每条 x86 算术指令都更新 EFLAGS。每次运算后在 ARM 上算出那些标志位代价高得离谱，于是一个好的 dynarec 会推迟并省略标志位计算 —— 只有在真有东西读它们时才具现化。
  2. 向量指令。 SSE、AVX 与 x87 浮点必须映射到 ARM 的 NEON 向量寄存器（宿主支持时还有 SVE），这需要对 NaN 处理与舍入格外小心。
  3. 内存模型。 x86 是强内存模型（全存储序 Total Store Ordering），ARM 较弱。在此保持正确性既微妙又昂贵，值得单独一小节（66.5.3）。

66.5.2 FEXCore 流水线

FEX 是面向 AArch64 宿主的用户空间 x86 与 x86-64 模拟器，其模拟引擎是一个叫 FEXCore 的库，翻译流水线是干净的四级设计：

  • 前端解码器读取原始字节流并找出指令边界，处理 x86 的 legacy 前缀、REX 前缀，以及 AVX 使用的 VEX/EVEX 编码。
  • OpcodeDispatcher（FEXCore/Source/Interface/Core/OpcodeDispatcher.cpp，向量与 x87 处理拆到 OpcodeDispatcher/Vector.cpp 与 OpcodeDispatcher/X87.cpp）把每条解码后的指令翻成 FEX 自己的 SSA 形式中间表示。IR 操作码本身定义在 FEXCore/Source/Interface/IR/IR.json。
  • PassManager（FEXCore/Source/Interface/IR/PassManager.cpp）在 IR 上跑优化 pass，对性能最重要的几个是寄存器分配、冗余标志位消除，以及一个 x87 栈优化 pass：寄存器分配把 IR 值映射到 ARM 寄存器；冗余标志位消除丢掉从不被读取的 EFLAGS 更新。
  • JIT 后端（FEXCore/Source/Interface/Core/JIT/JIT.cpp）从优化后的 IR 向代码缓存发射原生 AArch64 指令。FEX 使用自研的 ARM64 发射器而不是现成汇编器，以保持代码生成快而紧凑。

FEX 支持 MMX、SSE 到 SSE4、x87 以及 AVX/AVX2。它翻译多块区域而非单个基本块，并通过查找缓存在各缓存译文之间分派。FEX 处理自修改代码：它检测客户对含已翻译代码的页面的写入，并使受影响的缓存块失效。

66.5.3 TSO 内存模型问题

这是整个模拟层里最重要的性能微妙之处。x86 保证全存储序：一个核的存储在程序序上对其他核可见。ARM 不保证；除非你插入屏障或使用 acquire/release 指令，它允许存储被重排。一个为 x86 强序编写的小多线程游戏，若其内存操作被朴素地翻成普通 ARM load/store，就会竞态并崩溃。

FEX 默认正确的答案是模拟 TSO：它使用 ARM 的 acquire/release load/store 指令（FEAT_LRCPC 扩展）与原子指令（FEAT_LSE2，用于 x86 允许而 ARM 通常禁止的非对齐原子）。这种模拟很贵 —— 在弱模型上忠实复现 x86 序，在受影响的访存流量上可能带来约 10 倍的减速，代价在向量密集的游戏代码中感受最明显。

泄压阀是硬件 TSO。某些 ARM 核可以切到硬件全存储序模式 —— Apple Silicon 就是这么做的（这也是 Rosetta 2 快的原因）。在宿主 CPU 暴露该模式的地方，FEX 会请求它并放宽软件模拟，换来大幅收益。FEX 还提供一些可调项，可对向量访问或栈内存（线程私有、安全）关闭 TSO 模拟，这些可调项用一点稳定性换速度。

对手机而言的实务结论是：骁龙芯片具体的内存序能力会实质影响模拟跑多快，这与原始主频无关。

66.5.4 FEX thunk：调用原生 ARM64 图形

如果 FEX 要翻译游戏进程执行的每一条指令 —— 包括整个 Vulkan 驱动 —— 性能就没救了。避开这一点的杠杆是 thunk，也叫库转发：thunk 让被模拟的 x86 客户代码直接调用 原生 AArch64 宿主库，于是 GPU 驱动这类重型库以原生代码运行，而不是被翻译的代码。

设计是双向的。客户侧，FEX 提供一个小的 x86 桩库，呈现正常的客户 ABI（例如一个客户版 libvulkan.so）；它不含驱动，而是把每次调用转发过边界。宿主侧，一个原生 ARM64 thunk 库接收转发的调用并调用真正的宿主库。FEX 源码为关键图形库带了两半：Vulkan 的 ThunkLibs/libvulkan/Guest.cpp 与 ThunkLibs/libvulkan/Host.cpp，以及 OpenGL 的 ThunkLibs/libGL/。

66.5.5 FEX 的 rootfs 需求

当 FEX 作为独立 Linux 模拟器运行时，它模拟的是一个完整的 x86-64 进程，因而需要一个 x86-64 根文件系统来提供客户 glibc 与基础库。桌面 Linux 上，FEXRootFSFetcher 正是为此下载 SquashFS 或 EroFS 镜像。这是“全部模拟”模型，也是 Box64 与之差异的主轴 —— Box64 包装宿主库，不模拟完整客户用户环境。

不过，在 GameNative 的默认 ARM64EC 配置中，FEX 根本不是作为 Linux 模拟器运行，而是作为纯 CPU 模块插进 Wine（66.5.8）。由 Wine 服务 Windows 系统调用，而不是客户 glibc，所以独立的 x86 rootfs 不再需要了。FEX 的 rootfs 需求因此是“全部模拟”路径的属性，而不是 ARM64EC 默认的属性 —— ARM64EC 卸掉了这个需求，这是它的具体收益之一。

66.5.6 Box64：包装原生库

Box64 出自 ptitSeb，是核心工作相同但系统库哲学不同的 dynarec。Box64 不从一个 rootfs 模拟 x86-64 的 glibc、GL 与 Vulkan，而是在检测到客户即将调用这些知名库时，替换为宿主的原生 ARM64 实现：它包装每次调用来转换调用约定。手写包装器位于 Box64 源码的 src/wrapped/ 下，例如 Vulkan 的 src/wrapped/wrappedvulkan.c、C 库的 src/wrapped/wrappedlibc.c。

结果是对它所包装的库，Box64 不需要完整的 x86 rootfs —— 它借用宿主的。这使它比 FEX 更轻，也是经典 Winlator 的历史默认，那里的启动链字面上就是 proot 然后 box64 然后 wine。GameNative 的 GuestProgramLauncherComponent 为 glibc 路径构建的正是 box64 <guest exe> 这条命令。取舍是：包装的正确性只等于包装器的正确性；当某个被包装库的行为偏离客户预期时，它可能以全模拟方案不会出现的方式出错。

32 位故事是对称的：Box64 处理 x86-64，它的兄弟 Box86 处理 32 位 x86。对没有 32 位 ARM 环境的宿主，Box64 有一个实验性的 BOX32 模式，在 64 位环境内模拟一个 32 位环境。Box64 自己的 docs/WINE.md 列出了 Wine 各变体（x86、x86-64、x86-64 WoW64、ARM64 WoW64）与各自所需 Box 组合的矩阵 —— 关于模拟器与 Wine 如何拼在一起，它是最好的单一首要参考。

66.5.8 ARM64EC 与 WoW64：只模拟游戏

近期最重要的转变是架构性的而非渐进性的：不再让 Wine 自己也被模拟器跑一遍。在“全部模拟”模型里，JIT 翻译游戏以及整个 Wine 以及 Wine 之下所有 x86 Linux 库 —— 模拟器处在每条指令的热路径上。ARM64EC 模型反过来，为 ARM64 原生构建 Wine，只模拟游戏的 x86-64 代码。

ARM64EC（“Emulation Compatible”，模拟兼容）是微软的一套 ABI，在 Wine 中重新实现：原生 ARM64 代码的布局使其能与被模拟的 x86-64 代码互相调用。Wine 的系统 DLL 按此 ABI 编译，于是被模拟的游戏一旦调用 Windows API，执行流就转入原生 ARM64 的 Wine 代码，而不是更多模拟。模拟器被缩成一个 CPU 核，在 ABI 边界上作为可加载模块插进 Wine。

在这种配置里，模拟器作为 Windows DLL 发布、由 Wine 加载：FEX 对 64 位代码发布为 libarm64ecfex.dll；32 位 WoW64 路径用的是 libwow64fex.dll（FEX）或 wowbox64.dll（Box64）。GameNative 在 BionicProgramLauncherComponent 里根据所配置的 Wine 构建是否为 ARM64EC 在这些之间选择。

66.6 Wine：实现 Windows API

Wine 是让游戏以为自己跑在 Windows 上的那一层。模拟器管指令，Wine 管语义。它在 Linux 内核之上重新实现 Windows API，为游戏对该 API 发起的每一次调用提供服务。

66.6.1 不是模拟器

这个名字是递归缩写，“Wine Is Not an Emulator”（Wine 不是模拟器）。在 ARM Android 上，这一区分不是学究气，而是架构本身。Wine 完全不含指令翻译：它取来一个 Windows PE 二进制，加载进 Linux 进程，用与 Linux 对话的原生代码去应答该二进制的 Windows API 与 NT 系统调用。

在 x86-64 Linux 上那些原生代码直接运行；在 ARM Android 上，Wine 自身要么被模拟（全部模拟模型），要么被编译成原生 ARM64EC（混合模型）。两种情形里 x86 到 ARM 的翻译都不由 Wine 做 —— 那永远是 FEX 或 Box64。两层正交，正如 66.1.1 所述。

66.6.2 PE/Unix 分界

现代 Wine 围绕 Windows PE 代码与 Unix 后端之间的一道硬边界来组织。Wine 的内置 DLL（ntdll、kernel32、kernelbase、user32、gdi32）被编译成真正的 PE 文件，所以从游戏的角度看，它调用的就是普通 Windows DLL。那些必须触达宿主 OS 的 DLL 被拆成 PE 部分与 Unix 部分。

典型例子是 ntdll。PE 侧（dlls/ntdll/）构建 ntdll.dll；Unix 侧（dlls/ntdll/unix/）构建 ntdll.so —— 一个启动时被 dlopen 的 ELF 库，关键文件是 dlls/ntdll/unix/loader.c、dlls/ntdll/unix/virtual.c 与 dlls/ntdll/unix/signal_x86_64.c。两半之间的契约声明在 dlls/ntdll/unixlib.h。

进程启动时首先是一个完全普通的 Linux 进程：一个小加载器 dlopen 了 ntdll.so，该库构建 Windows 的进程控制结构（PEB 与 TEB）、映射 PE 的 ntdll.dll 与初始可执行文件、连接 wineserver，最后跳进 PE 侧的初始化。此后，控制流“就像在 Windows 上一样”运行。

66.6.3 wineserver

wineserver 是一个独立守护进程，大致提供 Windows 上内核所提供的那些服务。共用同一 prefix 的每个 Wine 进程，都通过 wineserver 共享 NT 在内核空间保存的东西：句柄与对象命名空间、同步对象（事件、互斥量、信号量）、进程与线程、窗口管理状态，以及注册表。

客户端经 AF_UNIX 套接字与它通信，通过 wine_server_call 编组请求；服务器的请求处理器在 server/request.c。该套接字位于按 prefix 划分的目录中、以 prefix 的设备与 inode 为键，因此每个 prefix 有自己的服务器。一个特别重要的细节是：该套接字用标准的 SCM_RIGHTS 辅助数据在进程间传文件描述符，于是一个 Windows HANDLE 可以由服务器交出的真实 Linux fd 支撑。

性能上的注意事项在手机上很重要。游戏不停地同步线程，而经典“每次都问 wineserver”的模型让每次同步都变成一趟套接字往返。Wine 逐步把同步移出服务器：esync（基于 eventfd）、fsync（基于 futex），以及最近的 ntsync —— 一个暴露 /dev/ntsync、在内核里建模 NT 同步原语的 Linux 内核驱动。

更快的路径能否用，取决于宿主内核。Android 内核可能根本不暴露 /dev/ntsync，那种情况下这套栈回落到 futex 上的 fsync，而 Android 是有 futex 的。

66.6.4 prefix、C: 盘与注册表

一个 Wine prefix（即 WINEPREFIX，这里是 rootfs 内的 /home/xuser/.wine）是一份自成一体的虚拟 Windows 安装：有自己的 C: 盘、自己的注册表、自己的 wineserver。其中 drive_c/windows/system32 放 64 位系统 DLL，drive_c/windows/syswow64 放 32 位的（Windows 那套反直觉命名被保留下来）；dosdevices/ 放把盘符映射到宿主路径的符号链接。注册表在 prefix 根目录以文本 .reg 文件保存（HKLM 的 system.reg、HKCU 的 user.reg），由 wineserver 实时服务。

这套布局正是容器可移植、可丢弃的原因：它只是一棵目录树。GameNative 的按游戏容器就是按游戏的 prefix，两个 DLL 或注册表需求冲突的游戏因此得以隔离。

66.6.5 DLL 覆盖：DXVK 如何替换 Wine 的 Direct3D

Wine 逐个 DLL 决定用自己内置的实现，还是用放进 prefix 的一个原生 DLL。选择由 WINEDLLOVERRIDES 环境变量与 HKCU\Software\Wine\DllOverrides 下的注册表项驱动。

整条图形快路径就是靠这一个机制装上的。DXVK 与 VKD3D-Proton 发布的 PE DLL 名字与 Wine 内置 Direct3D DLL 完全一样（d3d9.dll、d3d11.dll、dxgi.dll、d3d12.dll），安装器把它们拷进 prefix 的 system32/syswow64，并把这些名字设为 native。于是游戏下次调用 D3D11CreateDevice 时，Wine 的加载器把 d3d11.dll 解析到 DXVK 的文件，而不是自己那个基于 wined3d 的内置实现 —— Direct3D 这时被翻成 Vulkan（66.7），而不是 OpenGL。

66.6.6 Wine 与模拟器的交汇处

本节把 66.5 与 66.6 绑在一起。在 ARM64EC 配置中，Wine 是原生 ARM64EC，其 DLL 在系统调用边界转进原生代码；模拟器（libarm64ecfex.dll 或 WoW64 辅助件）只在运行游戏的 x86-64 指令流时被调用。在全部模拟配置中，整个 Wine 都是 x86-64，跑在 Box64 或 FEX 之上、对着 rootfs 的 glibc。

两种配置呈现给游戏的都是同一个 Windows，区别只在于游戏之下有多大一部分进程被模拟、多大一部分是原生。这是帧率最大的单一决定因素。

66.7 图形：从 Direct3D 到 Adreno GPU

图形是这套栈要么成功、要么肉眼可见地失败的地方，也是本书中最长的翻译链：一个 x86-64 游戏发出的 Direct3D 调用，最终变成由手机 Adreno 驱动执行、由 SurfaceFlinger 合成的 Vulkan 命令。这条链上每一环都是独立的技术。

66.7.2 D3D 到 Vulkan：DXVK、VKD3D 与回退方案

几个翻译器覆盖 Direct3D 的各代版本，全部作为 Wine DLL 覆盖安装（66.6.5）：

  • DXVK 把 Direct3D 9/10/11 翻成 Vulkan，发布 d3d9.dll、d3d11.dll、dxgi.dll 等相关 DLL，是 GameNative 容器中的默认 DEFAULT_DXWRAPPER。
  • VKD3D-Proton 把 Direct3D 12 翻成 Vulkan，发布 d3d12.dll 与 d3d12core.dll，是 WineHQ 自家 vkd3d 的 Valve 调优分支，为游戏性能优化。
  • D8VK 把 DXVK 延伸到 Direct3D 8。
  • wined3d 是 Wine 的内置回退，把 Direct3D 翻成 OpenGL 而非 Vulkan，更慢，只在游戏与 DXVK 不兼容时使用。
  • cnc-ddraw 处理老式 DirectDraw 作品。

关键架构点在于：在 ARM64EC 下这些翻译器是原生 ARM64 代码（66.5.8），只有游戏的 D3D 调用源自被模拟的代码；把一帧的绘制调用变成 Vulkan 命令缓冲这件重活以原生方式运行。这就是手机上 DXVK 远快于“在完全模拟的 x86 Wine 里翻译 Direct3D”这一替代方案的原因。

66.7.3 抵达真实 GPU：Turnip 与 Vortek

Vulkan 命令现在必须到达真正的 Adreno GPU。有两条策略，而这一选择是图形设计中最重要的分叉。

Turnip 是 Mesa 面向 Adreno GPU 的开源 Vulkan 驱动。这套栈打包了一份 Turnip，也可以通过 adrenotools 侧载更新的构建（66.4.2），因此客户拥有一个真实、完整的 Vulkan 实现，直接与 Adreno 内核接口对话。

Turnip 之所以存在，是因为手机上随附的 Vulkan 驱动面对 Wine 与 DXVK 产生的非常规负载常常不完整或有 bug；一份已知良好的 Mesa 驱动绕开该问题。在 FEX 世界，客户经 thunk 机制（66.5.4）抵达 Turnip：一个客户 libvulkan 桩把调用转给原生 Turnip。

Vortek 是 Winlator 自己的 Vulkan 兼容层，走 66.4.5 的 IPC 路线、不用 thunk。它是客户端/服务器设计：客户链接一个薄薄的 Vortek Vulkan ICD，该 ICD 从 assets/.../vortek-* 压缩包发布进 rootfs。

ICD 把每次 Vulkan 调用序列化成命令流，经 Unix 套接字发给一个原生 Android 服务器；该服务器就是预置的 libvortekrenderer.so，由 VortekRendererComponent 驱动。服务器对着设备的真实 Vulkan 驱动重放这些命令，途中还能修补 SPIR-V 着色器、解码宿主驱动不支持的纹理格式、模拟某些特性。

Vortek 正是 GameNative 的默认图形驱动，原因就在于套接字边界让它对 glibc/bionic 错配天然免疫 —— 客户与宿主驱动从不共享地址空间。

在多数设备上 ANGLE 并不是平台的默认 GLES 驱动 —— EGL 加载器自己就这么注明（frameworks/native/opengl/libs/EGL/Loader.cpp:555）；它是按应用或全系统选择的。Windows 游戏这套栈不走 ANGLE，因为客户在 rootfs 内部自己做 GL 到 Vulkan 的翻译（Zink，或 wined3d 的 GL 输出），再经 Vulkan loader 抵达设备 —— 这种平行是概念上的，不是共享的代码路径。

66.7.4 Android Vulkan loader

不论用哪条客户路径，链的底部都是第 13 章那个 AOSP Vulkan loader。加载器在 frameworks/native/vulkan/libvulkan/driver.cpp 中发现在并加载设备的 Vulkan 驱动。LoadDriver 例程（frameworks/native/vulkan/libvulkan/driver.cpp:153）通过两条分支之一打开 HAL 驱动（vulkan.<board>.so）：当提供了驱动命名空间（可更新、经 Play 交付的驱动路径）时，它用 android_dlopen_ext 配合 ANDROID_DLEXT_USE_NAMESPACE（frameworks/native/vulkan/libvulkan/driver.cpp:171）—— 就是 66.4.2 那个命名空间标志；普通的内置驱动则从 sphal 命名空间用 android_load_sphal_library（frameworks/native/vulkan/libvulkan/driver.cpp:178）打开。

像 Vortek 服务器或 thunk 后的 Turnip 这样的原生渲染器，最终不过是这个加载器和这个驱动的又一个客户端 —— 这就是整座大厦在完全不改平台的前提下能工作的原因：GPU 是通过任何 Android 游戏都在用的同一个公开 Vulkan 接口抵达的。

66.7.5 呈现：应用内 Surface

渲染好的帧必须变成屏幕上的像素。游戏拿不到真正的 X 显示，也拿不到真正的窗口系统，它拿到的是 GameNative 的应用内 X 服务器：一个在应用内实现的小型 X11 服务器（com.winlator.xserver，原生代码在 app/src/main/cpp/winlator/）。它接收游戏的输出与游戏绘制的窗口，其内容用 Vulkan 绘制并呈现到一个 Android Surface。

最后这一步使用第 13 章的原生窗口 API：帧经 ANativeWindow 到达合成器。CPU 访问路径用的是 ANativeWindow_lock（frameworks/native/libs/nativewindow/include/android/native_window.h:179）与 ANativeWindow_unlockAndPost（frameworks/native/libs/nativewindow/include/android/native_window.h:188）；零拷贝 GPU 路径把一个 AHardwareBuffer（frameworks/native/libs/nativewindow/include/android/hardware_buffer.h:479，经 AHardwareBuffer_allocate）绑定为 Vulkan swapchain 图像，GPU 于是直接渲染进一块 SurfaceFlinger 能扫描输出的缓冲。从 SurfaceFlinger 往前（第 24 章），游戏的帧就只是又一个被合成到显示屏的图层。

66.7.6 帧生成

作为可选的最后一道润色，GameNative 可以插入一个执行帧生成的 Vulkan 隐式层：该层拦截 vkQueuePresentKHR，在已渲染的帧之间插值出合成帧。它是 Vulkan 意义上的图层，嵌入加载器的图层链 —— 这说明图形栈的很大一部分是从标准 Vulkan 扩展点搭起来的，而不是靠定制钩子。

66.8 音频：从 WASAPI 到 AAudio

音频链比图形短，但跨越的是同一个 libc 边界。66.4.5 的 IPC 模式解决了它：真正的音频服务器跑在 Android 侧，客户作为客户端连上去。

66.8.1 Wine 的音频后端

Windows 游戏通过若干前端 API 之一发声：现代的 WASAPI（经 mmdevapi）、传统的 DirectSound，或旧的 winmm/waveOut。Wine 把它们全都叠到一个运行时选定的后端驱动上。这里重要的是 winepulse.drv，它面向 PulseAudio；替代项是 winealsa.drv（ALSA）与 wineoss.drv（OSS）。在现代 Wine 里，每个后端都是一个仅 Unix 的库，例如由 dlls/winepulse.drv/pulse.c 构建的 winepulse.so，它调用宿主的 PulseAudio 客户端库。

PE 那一半住在 mmdevapi 自己里：它用 __wine_load_unix_lib 加载后端，并经 __wine_unix_call 调进去（dlls/mmdevapi/main.c）。

在 ARM64EC 配置下，后端及其客户端库是原生 ARM64，因此混音与传输不被模拟 —— 只有游戏对前端 API 的调用跨过模拟器。

66.8.2 应用内的 PulseAudio 服务器

未 root 的应用没有系统 PulseAudio 守护进程可用，于是这套栈自带一个。GameNative 的 PulseAudioComponent 从打包的原生库启动一个 PulseAudio 服务器（jniLibs/ 中的 libpulse.so 以及 libpulsecommon/libpulsecore 这些 PulseAudio 13 库）。Wine 的 winepulse.drv 连上这个服务器，方式与连桌面 PulseAudio 完全一样 —— 走 PulseAudio 正常的套接字协议。契约是 PulseAudio 线协议，于是客户侧（glibc，可能被模拟）与服务器侧（bionic，原生）跨 libc 边界互通，而不共享地址空间。

66.8.3 ALSA 桥

Winlator 还提供一条更底层的 ALSA 路线。rootfs 带一个自定义 ALSA PCM 插件（Winlator 的 android_alsa，module_pcm_android_aserver.c），暴露一个“android aserver” PCM 设备；Android 侧由 com.winlator.alsaserver 实现服务器端点，一个原生客户端（app/src/main/cpp/winlator/ 中的音频代码）把 PCM 帧送到应用。无论音频走 PulseAudio 路线还是 ALSA 路线，结构完全相同：一个客户音频 API、一个套接字、一个原生 Android 端点。

66.8.4 经 AAudio 抵达扬声器

Android 端点最终把解码后的 PCM 写入一个 Android 音频流，最自然的 API 是第 15 章的 AAudio。流由 AAudio_createStreamBuilder（frameworks/av/media/libaaudio/include/aaudio/AAudio.h:1216）创建，然后配置、打开，用 AAudioStream_write 喂数据，此后帧经音频 HAL 流向扬声器。（更老或受 targetSdk 约束的构建可能改用 AudioTrack 或 OpenSL ES，但 AAudio 是现代的低延迟路径。）

因此音频链的终点，与任何原生 Android 游戏的音频终点，是同一个 AOSP 子系统。

66.8.5 延迟

音频穿过一个客户 API、一个套接字和一个服务器，代价是延迟。这套栈为此做了调优：PulseAudio 配置了刻意偏大的缓冲，各容器把 PULSE_LATENCY_MSEC 设在一百多毫秒的量级。这是用响应性换播放无杂音，以抵抗模拟与 IPC 引入的抖动。

这是务实的选择。经过这么多层，完美的紧音频延迟不可能达到；对多数游戏而言，稳定播放比几十毫秒的滞后更重要。

66.9 汇总：追踪三条路径

要把整章收拢，最清楚的办法是跟着三个不同的操作从游戏一路下到 Android 平台，注意每一个在层间走的是不同路线。

图：三个操作，三条穿越栈的路线

graph TD
    subgraph G["Windows 游戏（被模拟的 x86-64）"]
        D3D["D3D11 绘制调用"]
        FILE["CreateFile 调用"]
        SND["WASAPI 写入"]
    end
    D3D -->|"原生 ARM64"| DXVKn["DXVK 转 Vulkan"] --> GPUn["Vortek / Turnip 到 Adreno"]
    FILE -->|"NT 系统调用"| NTDLL["ntdll 系统调用分派器"] --> WS["wineserver + Linux fd"]
    SND -->|"原生 ARM64"| PULSEn["winepulse 到 PulseAudio"] --> AAUDIOn["AAudio"]

  1. 一次 Direct3D 11 绘制调用。 游戏的 ID3D11DeviceContext::Draw 是一次 x86-64 调用（被模拟），它进入 DXVK —— 在 ARM64EC 下是原生的，构建 Vulkan 命令缓冲；随后调用经 thunk（Turnip）或套接字（Vortek）跨过 libc 边界抵达 Adreno 驱动，由 SurfaceFlinger 合成结果。这几乎全都不被模拟，只有最初那个调用点被模拟。

  2. 一次 CreateFile 调用。 游戏请求打开一个文件，这是 Windows API 调用，会变成 NT 系统调用：调用经 Wine 的 __wine_syscall_dispatcher 汇入 ntdll.so，该库自己把 NT 路径翻成 Unix 路径（nt_to_unix_file_name，dlls/ntdll/unix/file.c），再以一个 create_file 请求把该 Unix 路径发给 wineserver。

    服务器打开文件并返回一个 Windows HANDLE；需要时，底层 Linux fd 经 SCM_RIGHTS 从服务器取回。途中 PRoot 或 libredirect 把路径重映射进 rootfs，Linux 的 openat 最终落在应用私有存储里。不涉及 GPU、不涉及音频，机制与路径 1 完全不同。

  3. 一次音频缓冲写入。 游戏的 WASAPI 写入进入 winepulse.drv（ARM64EC 下原生），驱动经 PulseAudio 套接字把 PCM 送到应用内服务器，服务器把它写进 AAudio 流，抵达扬声器。

三个操作、三条完全不同的路径，而只有画在“被模拟盒子”之内的部分才真正被逐指令翻译。整套栈的全部艺术，就在于让那个盒子保持小。

66.10 Android 17 为这套栈带来了什么变化

本章没有任何翻译项目随 AOSP 发布，所以 Android 17 并没有“加入”一个 Windows 游戏运行时。17 做的是挪动这套栈所站的平台地板。有三处变化值得钉住，因为它们各自在帮助或约束上方某一层。

66.10.1 这套栈所依托的平台接口是稳定的

整个设计能成立，是因为它只碰公开、稳定的 AOSP 表面。这些表面是：

  • Vulkan loader（frameworks/native/vulkan/libvulkan/driver.cpp）
  • 原生窗口 API（frameworks/native/libs/nativewindow/include/android/native_window.h）
  • AHardwareBuffer
  • AAudio（frameworks/av/media/libaaudio/include/aaudio/AAudio.h）
  • ASharedMemory（frameworks/native/include/android/sharedmem.h）
  • android_dlopen_ext 的扩展标志（bionic/libc/include/android/dlext.h —— 实践中稳定，尽管命名空间标志本身被标注为仅限内部使用）
  • 链接器的 W^X 规则（bionic/linker/linker_phdr.cpp）

在 Android 17 中，这些全部在场，契约与前面各节所依赖的一致。这正是 Winlator 这类应用能跨版本持续工作、无需平台补丁的原因：这套栈在底部什么也没发明，因此它继承该版本公开 Vulkan、音频与链接器表面所提供的一切。

66.10.2 Berberis 不是这套栈，而 17 重组了它

很容易以为 Android 自己的二进制翻译器必然参与其中 —— 并没有。Android 17 重组了 Berberis（第 19 章）：其 CPU 模拟核的每个模块都被归并到新的 frameworks/libs/binary_translation/cpu_emulation/ 目录下，三层引擎（cpu_emulation/interpreter/、cpu_emulation/lite_translator/、cpu_emulation/heavy_optimizer/）与层分派器（cpu_emulation/translator/）如今是它下面的同级目录。

但 Berberis 翻译的是 riscv64 客户代码到 x86_64 宿主（frameworks/libs/binary_translation/README.md），并通过 Native Bridge 插进 ART（frameworks/libs/binary_translation/native_bridge/）。对 PC 游戏而言这是错的方向（riscv64 到 x86_64，而非 x86-64 到 AArch64），也是错的集成点（ART 内的 APK 代码，而非整个 Windows 进程）。

17 的这次重组真实存在，也对第 19 章有意义，但它在本章里什么也没改变：这里的 x86-64 到 AArch64 翻译仍完全由 FEX 与 Box64 完成，没有任何 AOSP 自带翻译器与之竞争。

66.10.3 ANGLE 在哪里适用，在哪里不适用

Android 的 GLES-on-Vulkan 翻译器 ANGLE（external/angle/，第 13 章）是平台自己对“在只有 Vulkan 驱动的环境里表达 OpenGL ES”的答案，它在概念上与客户内部的 Zink 与 wined3d-to-GL 路径重叠。把 ANGLE 说成 Android 17 上的“默认”很诱人，但 EGL 加载器自己的注释明说它不是多数设备上的默认 GLES 驱动（frameworks/native/opengl/libs/EGL/Loader.cpp:555），而是按应用选择或经系统配置启用。

对这套栈而言，实务结论没有变化：客户自己做 GL 或 D3D 到 Vulkan 的翻译，并经 Vulkan loader 抵达 GPU，所以设备的 ANGLE 设置既不帮也不碍一个 Windows 游戏。两者是同一个形状的问题在 libc 边界两侧的平行解法，而不是共享路径。

66.11 动手试试

这些练习需要一份 GameNative 源码检出，以及一台装了 Winlator 类应用的设备或模拟器。读源码只需要一次 clone；设备上的步骤假定你已合法安装了此类应用，并拥有一个自己的游戏。

  1. 从默认值把整套栈读出来。 Clone GameNative，打开 app/src/main/java/com/winlator/container/Container.java 与 app/src/main/java/com/winlator/core/DefaultVersion.java。记下默认的模拟器、图形驱动、音频驱动与 DX wrapper，记下 Wine、DXVK、VKD3D、Turnip 的钉住版本。你刚刚用两个文件重建了整条默认流水线。

  2. 找到启动命令。 读 app/src/main/java/com/winlator/xenvironment/components/GuestProgramLauncherComponent.java，找到它拼接 box64 <guest exe> 命令的位置。再读 BionicProgramLauncherComponent.java，找到它按“Wine 构建是否为 ARM64EC”分支的位置，比较两条启动路径。

  3. 检查打包的组件。 列出 app/src/main/assets/，找出 FEX、Box64、DXVK 与 Vulkan 驱动的 .tzst/.txz 压缩包，找出按需取回其余组件的 *_download.json 清单，记下哪些在 APK 内、哪些要下载。

  4. 在设备上观察进程。 在应用里运行一个游戏，用 adb shell ps -A 找在应用 UID 下运行的 Wine、wineserver、PulseAudio 与 X 服务器进程；再对 Wine 进程运行 adb shell cat /proc/<pid>/maps，观察 JIT 的匿名可执行映射与 rootfs 库。

  5. 看见那些套接字。 对 Wine 进程运行 adb shell ls -l /proc/<pid>/fd，找出把它连到 wineserver、Vulkan 渲染器与 PulseAudio 的 Unix 域套接字 —— 这些就是 66.4.5 的边界跨越被具象化出来的样子。

  6. 探索 prefix。 在应用数据目录中找到该容器的 Wine prefix，查看 drive_c/windows/system32 里覆盖了 Wine 内置 Direct3D 的 DXVK DLL，查看 user.reg 中把这些 DLL 放进去的 Software\Wine\DllOverrides 条目。

  7. 确认 AOSP 触点。 在一份 AOSP 检出中打开 frameworks/native/vulkan/libvulkan/driver.cpp 的 LoadDriver 函数（第 153 行），找到它的两条分支：带 android_dlopen_ext 与 ANDROID_DLEXT_USE_NAMESPACE 的分支用于更新过的驱动，带 android_load_sphal_library 的分支用于内置驱动。整条图形栈最终汇入的，就是这个加载器。

66.12 小结

一个 Windows 游戏在未 root 的 ARM Android 手机上运行，靠的是一串单一职责的翻译层，每一层填补 Windows x86-64 游戏与本书其余章节所讲 AOSP 内部机制之间的一道鸿沟。

层 它解决的问题 关键技术
GameNative 应用 编排、商店、打包 Pluvia + Winlator 嫁接，GPL-3.0
rootfs（imagefs） 一个无 root 的 glibc Linux 用户环境 解到应用存储的 Ubuntu 树，经 PRoot 或 bionic 加载器进入
bionic 重定向 在 bionic 系统上跑 glibc 软件 路径改写、SysV-SHM 架在 ashmem 上、IPC 服务器
FEX / Box64 AArch64 上的 x86-64 指令 dynarec、TSO 模拟、thunk 对包装库
ARM64EC / WoW64 只模拟游戏 原生 ARM64 Wine，模拟器作为 DLL
Wine Linux 上的 Windows API PE/Unix 分界、wineserver、DLL 覆盖
DXVK / VKD3D Vulkan GPU 上的 Direct3D D3D 到 Vulkan，作为原生 DLL 覆盖安装
Turnip / Vortek Vulkan 到真实 Adreno GPU 经 thunk 的 Mesa 驱动，或经套接字的客户端/服务器
PulseAudio Windows 音频到扬声器 应用内音频服务器，经 AAudio 输出

反复出现的几课：

  1. 两个正交的翻译。 指令集翻译（FEX/Box64）与 Windows API 翻译（Wine）是完全分开的两个问题。把它们混为一谈，是对这些应用工作原理最常见的误解。

  2. 能少模拟就少模拟。 这套栈里每一分性能收益，都来自离开“被模拟盒子”的工作：主要情形是 GPU 驱动的 thunk 与包装器、原生 ARM64 的 DXVK，以及最重要的 ARM64EC —— 它只让游戏自己的代码保持被模拟。

  3. libc 边界是难的部分。 glibc 与 bionic 无法共处一个进程。跨边界的三条路（IPC、ABI thunk，或在 bionic 上原生执行）塑造了这套栈里的每一个设计决定。

  4. 底下全是标准 AOSP。 Vulkan loader、ANativeWindow、AHardwareBuffer、AAudio、链接器命名空间、ASharedMemory 与 W^X 规则，就是任何 Android 应用都在用的平台接口。这套翻译栈在底部什么也没发明，它的天才之处是从高悬其上的一个 Windows 游戏抵达那些公开接口。

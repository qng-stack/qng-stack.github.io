第 55 章：OTA 更新

第 55 章：OTA 更新

空中下载（Over-the-Air，OTA）更新是 Android 设备获取新系统镜像、安全补丁与功能更新的机制，既不需要物理接触设备，也不需要手动刷机。OTA 起初只是简单的“下载一个 zip、启动进 recovery、应用它”模式，如今已演化为 AOSP 最复杂的子系统之一：它包含专门的原生守护进程（update_engine）、内核级写时复制快照、引导加载程序集成协议，以及一条能把 GB 级载荷流式应用、全程无需把完整镜像写入 userdata 的流水线。

本章追踪一次 OTA 更新的全过程，从服务器宣告更新可用的那一刻起，直到设备重启进新软件并把该槽标记为成功为止。我们逐层剖析：

  • 载荷二进制格式
  • update_engine 内部的动作流水线
  • A/B 与虚拟 A/B 的槽切换机制
  • 让压缩写时复制能在用户态实现的 snapuserd 守护进程
  • 生成载荷的 Python 工具链
  • 作为遗留兜底的 recovery 模式
  • 把这一切串联起来的框架 API

55.1 OTA 架构总览

55.1.1 三种更新方案

Android 历史上用过三种不同的 OTA 方案。三者都要理解，因为现役设备横跨全部三档。

Source path: system/update_engine/         -- A/B and Virtual A/B engine
             bootable/recovery/            -- Non-A/B recovery updater
             system/fs/fs_mgr/libsnapshot/ -- Virtual A/B snapshots

在 Android 17 中，快照代码已移出 system/core：libsnapshot、snapuserd 与 COW 格式实现如今位于 system/fs/fs_mgr/libsnapshot/。更早的版本使用 system/core/fs_mgr/libsnapshot/ 路径，该路径已不复存在。本章所有关于快照的引用都使用新位置。

非 A/B（遗留方案）。这是最初的方案，自 Android 1.0 用到约 Android 9（至今仍受支持）。设备只有一套分区（system、boot、vendor 等），外加一个专门的 recovery 分区。更新时设备重启进 recovery，由 recovery 挂载 OTA 包（一个含 updater 可执行文件与镜像数据的已签名 zip），就地打块级补丁。若更新中途失败，设备可能停留在无法启动的状态 —— 即俗称的“变砖”。

A/B（无缝）。Android 7.0 引入。设备为每个可更新分区保留两份副本：槽 A 与槽 B。用户在其中一个槽上运行时，update_engine 在后台把新镜像写入另一个槽；写完后指令引导加载程序切换活动槽；若新槽启动失败，引导加载程序会回滚。

设备为 OTA 目的从不进入 recovery，用户在写入阶段感受不到任何停机。代价是分区存储大致翻倍。

虚拟 A/B（Virtual A/B）。Android 11 引入，自 Android 13 起强制。虚拟 A/B 保留 A/B 的无缝更新体验，但不再需要物理复制每一份分区，而是用 device-mapper 快照（以及自 Android 12 起的、经 snapuserd 的压缩写时复制）只记录更新期间的被改动块。重启并校验成功后，快照被合并回基础分区，收回临时存储。于是既获得 A/B 的可靠性，又接近非 A/B 的存储效率。

  • 用于供应快照的 UBLK 用户态块驱动后端（dm-user 路径之外的另一种选择）
  • REPLACE 操作使用 zstd 压缩
  • 移除 squashfs 的构建/OTA 支持

这些在 55.26 节详述。

update_engine 采用动作流水线（action pipeline）模式：更新的每一步都是一个 Action 子类，由 ActionProcessor 串联起来；动作之间通过类型安全的 ActionPipe 连接传递数据。

ActionProcessor 一次只运行一个动作。动作完成（成功或失败）时，处理器推进到下一个或终止：

// action_processor.cc
void ActionProcessor::ActionComplete(AbstractAction* actionptr,
                                     ErrorCode code) {
  // ... notify delegate, run current_action_->ActionCompleted(code) ...
  current_action_.reset();
  if (!actions_.empty() && code != ErrorCode::kSuccess) {
    // Pipeline failed: drop the remaining actions
    actions_.clear();
  }
  // ... suspend handling ...
  StartNextActionOrFinish(code);
}

void ActionProcessor::StartNextActionOrFinish(ErrorCode code) {
  if (actions_.empty()) {
    // ... notify delegate that processing is done ...
    return;
  }
  current_action_ = std::move(actions_.front());
  actions_.pop_front();
  current_action_->PerformAction();
}

55.2.3 UpdateAttempterAndroid

UpdateAttempterAndroid 类是 Android 更新的顶层编排者。它实现 ServiceDelegateAndroidInterface（由 Binder 服务调用）与 ActionProcessorDelegate（接收流水线的回调）。

Source: system/update_engine/aosp/update_attempter_android.h

关键职责：

  • ApplyPayload：一次更新的入口。解析 URL/fd 与头部，构造 InstallPlan，构建动作流水线并启动它。

  • SuspendUpdate / ResumeUpdate：暂停与恢复进行中的下载。

  • CancelUpdate：中止运行中的更新并清理。

  • ResetStatus：清除已完成或已失败更新的持久状态。

  • CleanupSuccessfulUpdate：在虚拟 A/B 上触发快照合并。

55.3.5 完整载荷与增量载荷

完整载荷包含完整的目标镜像，每项操作都是 REPLACE 变体、ZERO 或 DISCARD 之一，不需要任何源分区。其次版本为 0（kFullPayloadMinorVersion）。完整载荷更大，但无论设备当前处于何种状态都能更新。

增量（incremental）载荷只编码已知源镜像与目标之间的差异，使用 SOURCE_COPY、SOURCE_BSDIFF、PUFFDIFF、ZUCCHINI 等引用源块的操作。增量载荷体积小得多（常常只有 50-200 MB，而完整载荷为 2-4 GB），但要求设备运行的正是那个源构建。

55.5.5 回滚机制

回滚是自动的，无需用户干预：

  1. 启动失败：若设备完全无法启动新槽，引导加载程序的重试计数器归零，它便切回原槽。

  2. 校验失败：update_verifier 读取 care_map 中列出的所有块，并依靠 dm-verity 检测损坏。任一次读取失败就重启设备；失败次数足够多之后，引导加载程序把该槽标记为不可启动。

  3. 显式回滚：可以请求 update_engine 把上一个槽重新标记为活动来实现回滚，但这一般不向用户暴露。

care_map 是一个 protobuf 文件，列出每个分区上哪些块承载有意义的数据（相对于空闲/未用空间）。update_verifier 只读这些“需关照”的块来触发 dm-verity 校验，无需读取整个分区：

    string fingerprint = 4;   // Build fingerprint
  }

55.6.2 动态分区与 super

虚拟 A/B 建立在动态分区特性（Android 10 引入）之上，该特性使用一个内含逻辑卷元数据的 “super” 分区。super 分区是一个物理分区，内含类 GPT 的元数据表（LpMetadata），描述其中的逻辑分区（system、vendor、product 等）。

对虚拟 A/B 而言，逻辑分区在元数据中同时有 A、B 两项，但实际数据可以重叠 —— 因为在 COW 建立之前，非活动槽可能并不物理存在。

55.6.8 压缩与 XOR

虚拟 A/B 压缩（Virtual A/B Compression，VABC）会压缩 COW 数据以降低空间占用。支持的压缩算法：

算法 属性值 特点
LZ4 lz4 解压快，压缩率中等
Zstandard zstd 压缩率更好，速度也不错
None none 不压缩

XOR 压缩（ro.virtual_ab.compression.xor.enabled=true）通过存放 XOR 差分而非完整替换块，进一步缩小 COW 体积。一个块可能只是轻微变化（例如头部里一个时间戳），此时旧块与新块的 XOR 结果比完整新块好压得多。

55.7.4 delta_generator

真正做差分计算的原生可执行文件：

Source: system/update_engine/payload_generator/generate_delta_main.cc

// delta_diff_generator.h
bool GenerateUpdatePayloadFile(const PayloadGenerationConfig& config,
                               const std::string& output_path,
                               const std::string& private_key_path,
                               uint64_t* metadata_size);

对每个分区，delta_generator 会：

  1. 读取源镜像与目标镜像。
  2. 判定文件系统类型（ext4、EROFS 等）。
  3. 按文件对块分组，以便更好地做差分。
  4. 为每段块范围挑选最佳差分算法：
    • 完全相同的块用 SOURCE_COPY。
    • 全零块用 ZERO。
    • 依据内容类型与已启用的特性，选用 BSDIFF、PUFFDIFF、ZUCCHINI 或 LZ4DIFF。
    • 兜底用 REPLACE（带压缩）。
  5. 把操作与数据块序列化进载荷格式。

55.8.2 流式流程

由于 DeltaPerformer 是增量处理载荷的：

  1. 它从第一个数据块中解析头部（24 字节）。

  2. 它累积字节，直到完整清单可用。

  3. 它解析清单并准备分区。

  4. 对随后每一项操作，它等到所需的数据块字节全部到达，就立刻应用该操作。

  5. 写入是流水化的：一项操作的数据正在写往目标时，下一项操作的数据正在下载。

这意味着设备无需留出与完整载荷等量的空闲空间。DeltaPerformer::buffer_ 只持有当前操作的数据。

55.8.4 网络考量

更新引擎支持：

  • 挂起/恢复：设备失去连通性时，下载暂停；恢复后使用 HTTP Range 头从断点继续。

  • 多网络：NETWORK_ID 头允许指定使用哪个网络接口。

  • 计费网络感知：是否经计费连接下载，通常由 OTA 客户端（而非 update_engine 本身）决定。

55.11 Postinstall

55.11.1 什么是 postinstall？

所有分区数据写完并校验之后，update_engine 可以运行刚写入的目标分区中的 postinstall 脚本。这主要用于：

  • 为新构建对系统应用做 DEX 优化（dex2oat）。
  • 文件系统重新打标签。
  • 各 OEM 自定义的初始化步骤。

55.11.2 Postinstall 配置

postinstall 配置嵌在 OTA 包清单中：

message PartitionUpdate {
  // ...
  optional bool run_postinstall = 2;
  optional string postinstall_path = 3;   // e.g., "bin/postinstall"
  optional string filesystem_type = 4;    // e.g., "ext4"
  optional bool postinstall_optional = 9; // OK to skip if it fails
}

55.11.3 PostinstallRunnerAction

flowchart TD
    A[PostinstallRunnerAction 启动] --> B[对每个 run_postinstall 为真的分区]
    B --> C[以只读方式挂载目标分区]
    C --> D[fork 并 exec postinstall_path]
    D --> E{退出码为 0？}
    E -->|是| F[卸载，处理下一个分区]
    E -->|否| G{postinstall_optional？}
    G -->|是| H[记警告，继续]
    G -->|否| I[使更新失败]
    F --> B
    B --> J[全部完成]

postinstall 脚本在受限环境中运行：

  • 在 Android 上，目标分区被挂载到固定的 /postinstall 挂载点。
  • 脚本运行在专门的 postinstall SELinux 域中；挂载点下的文件被标记为 postinstall_file。
  • 进度经进度管道回传。

55.11.4 单独触发 Postinstall

Binder 接口允许对指定分区触发 postinstall，无需走完整 OTA：

// binder_service_android.h

    const android::String16& partition) override;

这适用于只更新某个需要 postinstall 处理的 APEX 之类的场景。

55.16 进阶主题

55.16.1 部分更新

自次版本 7 起，载荷格式支持部分更新 —— 只更新一部分分区。这由 --partial 标志控制：

ota_from_target_files.py --partial "boot vendor" \
    -i source.zip target.zip partial_ota.zip

部分更新适用于：

  • 不触碰 system 的安全关键内核更新。
  • 独立于 system 的 vendor 分区更新。
  • 针对特定组件更快的 OTA 周期。

InstallPlan 中的 untouched_dynamic_partitions 字段记录哪些分区保持不动。

55.16.2 多载荷更新

update_engine 支持经 InstallPlan 中的 payloads 向量依次应用多个载荷：

struct InstallPlan {
  std::vector<Payload> payloads;
  // First payload might update system/vendor
  // Second payload might update a secondary slot image
};

55.17 安全考量

55.17.1 载荷签名

所有生产 OTA 载荷都必须用设备的 OTA 密钥签名。签名链为：

  1. 构建系统用发布密钥给载荷签名。
  2. 设备在 otacerts.zip 中携带匹配的证书。
  3. update_engine（或 recovery）在应用前校验签名。

开发时使用 build/make/target/product/security/ 中的测试密钥。

55.17.2 元数据签名

元数据（头部 + 清单）与完整载荷分开签名。这使 update_engine 能在处理任何操作之前先校验清单，防止利用清单处理器解析漏洞的攻击。

55.17.3 传输安全

update_engine 用 HTTPS（经 libcurl）下载载荷，提供传输层加密与服务器身份认证。载荷签名提供独立于传输安全的端到端完整性。

55.17.4 SELinux 上下文

update_engine 运行在 update_engine SELinux 域中，该域具有：

  • 对源分区的读权限。
  • 对目标分区（非活动槽）的写权限。
  • 对 Boot Control HAL 的访问权。
  • 对其持久数据（位于 /data/misc/update_engine/）的访问权。
  • 不可访问用户数据、应用数据或大多数系统服务。

55.17.5 verity 与 COW 的交互

对虚拟 A/B，dm-verity 必须与快照层协同工作：

dm-user (snapuserd) --> dm-verity --> mounted filesystem

verity 哈希树与 FEC（前向纠错）数据属于目标分区镜像的一部分，也被纳入 COW。snapuserd 在提供内容块的同时也提供这些元数据块，使 dm-verity 能透明地校验合并视图。

55.20 详解 DownloadAction

55.20.1 DownloadAction 初始化

DownloadAction 是流水线中最复杂的动作。它协调 HttpFetcher、DeltaPerformer 与续传逻辑。

Source: system/update_engine/download_action.cc
void DownloadAction::PerformAction() {
  http_fetcher_->set_delegate(this);

  install_plan_ = GetInputObject();  // From InstallPlanAction
  install_plan_.Dump();              // Log the plan

  // Calculate total bytes across all payloads
  bytes_total_ = 0;
  for (const auto& payload : install_plan_.payloads)
    bytes_total_ += payload.size;

  // Handle resume: skip already-applied payloads
  if (install_plan_.is_resume) {
    int64_t payload_index = 0;
    if (prefs_->GetInt64(kPrefsUpdateStatePayloadIndex, &payload_index)) {
      resume_payload_index_ = payload_index;
      for (int i = 0; i < payload_index; i++)
        install_plan_.payloads[i].already_applied = true;
    }
  }

  // Mark target slot as unbootable during write
  LOG(INFO) << "Marking new slot as unbootable";
  boot_control_->MarkSlotUnbootable(install_plan_.target_slot);

  StartDownloading();
}

关键设计决策：

  • 在开始任何写入之前先把目标槽标记为 不可启动，确保引导加载程序不会尝试启动只写了一半的镜像。

  • MultiRangeHttpFetcher 包装原始 HttpFetcher，以支持续传所需的 Range 请求。

55.20.2 进度上报

进度更新会做节流，以免把 Binder 回调淹没：

55.20.3 MultiRangeHttpFetcher

MultiRangeHttpFetcher 是对基础 HttpFetcher 的一层简单包装。客户端给它一份字节范围列表，它通过同一个底层 fetcher 依次抓取每个范围。update_engine 用它主要是为了从某个偏移开始抓取载荷（例如续传时）。DownloadAction 负责编排各个载荷的顺序，并把接收到的字节转交给 DeltaPerformer：它构造 fetcher，并在自己的 ReceivedBytes 回调中喂给 performer。

55.21 文件系统校验

55.21.1 FilesystemVerifierAction

所有操作应用完毕后，FilesystemVerifierAction 回读目标分区并计算其哈希：

flowchart TD
    A[FilesystemVerifierAction 启动] --> B[对 InstallPlan 中的每个分区]
    B --> C[打开目标分区设备]
    C --> D[顺序读取全部块]
    D --> E[计算 SHA-256 哈希]
    E --> F{哈希与 InstallPlan 一致？}

  • 存储介质上的位衰减。
  • DeltaPerformer 的缺陷。
  • 断电导致的写入不完整（检查点之前）。

55.21.2 verity 哈希树生成

对启用 dm-verity 的分区，performer 在更新过程中还会生成 verity 哈希树与 FEC（前向纠错）数据：

    B --> C["在 /sys/block/dm-* 中找到<br/>已映射 dm-verity 的块设备"]

55.24.3 dm-verity 集成

update_verifier 自己并不计算哈希，而是依靠内核中的 dm-verity 在读取每个块时进行校验：

  • 强制模式（enforcing）：dm-verity 在发现损坏时重启设备。
  • EIO 模式：dm-verity 返回 I/O 错误，由 update_verifier 重启。
  • 其他模式：不支持；update_verifier 直接重启。

这样的设计意味着校验强度等同于设备的验证启动链，无需对校验器可执行文件本身额外信任。

55.26 Android 17 的 OTA 变更

Android 17 并未增加第四种更新方案，而是在三条轴线上精修虚拟 A/B：第一条是用于供应快照的新用户态块设备后端（UBLK）；第二条是 REPLACE 操作的 zstd 压缩；第三条是生成端与应用端的一系列移除与内存优化。本节汇总这些变更，并把它们与本章前文描述的机制挂接起来。

55.26.1 UBLK 快照后端

直到 Android 16，snapuserd 都只经内核 dm-user 设备供应快照块设备：内核对每个 I/O 请求，通过一个 dm-user 字符设备把它转发到用户态，snapuserd 则用“基础 + COW”的合并数据作答。Android 17 引入了基于 UBLK（用户态块驱动）的第二个后端。有了它，snapuserd 注册一个 /dev/ublkb* 块设备，经由 libublksrv 宿主库（external/ublksrv）通过内核内 ublk 驱动处理请求。

两个后端都位于同一个 IBlockServer 抽象之后，因此合并逻辑、COW 读取器与工作线程都不变，差异只在内核与守护进程之间的传输方式。

即使在配置了 UBLK 的设备上，某次具体 OTA 也能强制使用遗留的 dm-user 后端。载荷清单在 DynamicPartitionMetadata 中带有一个 disable_ublk 开关：

55.26.3 REPLACE 操作的 zstd 压缩

更早的版本用 bzip2（REPLACE_BZ）或 XZ（REPLACE_XZ）压缩 REPLACE 数据。Android 17 新增 REPLACE_ZSTD（操作类型 14，载荷次版本 10），它把 zstd 数据块解压到目标区段。zstd 的压缩率接近 XZ，而解压速度快得多 —— 这很重要，因为 REPLACE 数据在完整载荷、以及增量载荷的完整更新部分中占主导。

Source: system/update_engine/payload_consumer/zstd_extent_writer.cc
        system/update_engine/payload_consumer/install_operation_executor.cc
        system/update_engine/payload_generator/zstd_android.cc

在应用端，REPLACE_ZSTD 与其他 REPLACE 变体走同一条 PerformReplaceOperation 路径（55.4.2 节）。 InstallOperationExecutor 只是在目标写入器之上叠加一个 ZstdExtentWriter。在生成端，--enable_replace_zstd（55.7.1 节）指示 delta_generator 输出 REPLACE_ZSTD 而非 REPLACE。注意这与 VABC 的 --vabc_compression_param=zstd,<level> 不同：前者压缩的是载荷中的 REPLACE 数据块，后者压缩的是在设备上写出的 COW 镜像。

55.26.4 移除项与内存优化

Android 17 修剪了 OTA 栈并降低了它的峰值内存占用：

  • 移除 squashfs 的 OTA 支持。 对 squashfs 镜像的构建与 OTA 支持已从 Soong、init 与 releasetools 路径中移除（libsquashfs_utils 依赖被去掉）。使用 squashfs 系统镜像的设备不再受 OTA 生成器支持。

  • 去掉 retrofit 动态分区逻辑。 针对“通过更新获得动态分区”的设备所走的遗留 retrofit 路径被移除，简化了 DynamicPartitionMetadata 的处理。

  • 降低应用期的峰值内存。 update_engine 解析完清单后不再把原始清单字节常驻内存，并在某个分区处理完毕后释放该分区的清单内存。大型差分补丁现在会写入临时文件，经文件描述符应用，而不是整体缓冲在内存中。这对现代设备上动辄数 GB 的分区很有意义。

  • 简化合并统计接口。 独立的 ISnapshotMergeStats / snapshot_stats.h 累加器被移除，合并指标改为从持久化的 SnapshotMergeReport 回读（55.13.2 节）。该报告新增 ublk_used 字段，用于记录是哪个后端完成了合并。

Source: build/make/tools/releasetools/ota_from_target_files.py
        system/update_engine/aosp/cleanup_previous_update_action.cc
        system/fs/fs_mgr/libsnapshot/android/snapshot/snapshot.proto

这些变更对 OTA 客户端不可见：UpdateEngine Java API、载荷格式头部与动作流水线都没有变化。升级到 17 的设备，可能只是发现自己的快照改由 UBLK 供应、REPLACE 数据改成 zstd 承载而已；更新如何请求、如何监控，一切照旧。

55.27 动态系统更新（DSU）与 gsid

到目前为止描述的每种机制都会改写已安装的系统：A/B OTA 翻转槽位，虚拟 A/B OTA 在真实分区之上写入 COW 快照。动态系统更新（Dynamic System Updates，DSU） 做的则是相反的取舍：它启动一个下载来的通用系统镜像（Generic System Image，GSI），完全不触碰已安装的系统。

真实的 system/product 分区保持原样。GSI 与一份全新的空 userdata 生活在 /data 上的镜像文件中，被暴露为 device-mapper 块设备，设备在若干次启动中进入它们。

禁用或擦除 DSU 后，下一次重启就回到原来那份未被触碰的系统。这使 DSU 成为试用新平台构建、或对 GSI 跑 CTS 的首选工具，也让应用开发者能针对干净镜像做验证。这一切都无需刷机，且完全可逆。

DSU 复用本章已为虚拟 A/B 讲过的同一套动态分区与镜像映射机制（libfiemap 的 ImageManager、liblp 元数据、device-mapper）。DSU 独有的一块是一个小型系统守护进程 gsid（位于 system/gsid/）：它把镜像暂存进那些动态镜像文件，并武装一次性启动。

55.27.3 武装一次性启动

enableGsi(oneShot, dsuSlot) 才是真正让已暂存镜像可启动的一步。GsiService::EnableGsi 在 /metadata/gsi/dsu/ 下写入三份状态：

  • 活动槽名写入 kDsuActiveFile（active），
  • 经 ResetBootAttemptCounter 把启动尝试计数写入安装状态文件 （kDsuInstallStatusFile，内含一个 int 计数器，或 ok / disabled / wipe），
  • 以及当 oneShot 为真时，经 SetBootMode 写入标记文件 kDsuOneShotBootFile （one_shot_boot）。
Source: system/gsid/gsi_service.cpp (EnableGsi line 1017, SetBootMode line 558,
        ResetBootAttemptCounter line 549)
        system/gsid/libgsi.cpp (CanBootIntoGsi, MarkSystemAsGsi, DisableGsi, UninstallGsi)

一次性语义位于 libgsi.cpp::CanBootIntoGsi，在启动早期被调用。它最多允许 kMaxBootAttempts（1）次尝试。若一次性标记存在，它会预先往状态文件里写入 disabled —— 这样本次启动进入 GSI，而下一次重启自动回落到已安装的系统。

随后 gsid run-startup-tasks（gsid.rc 中的 exec_background 行，运行 RunStartupTasks）会把成功的 GSI 启动标记为 ok，并兑现待处理的 wipe 请求以收回镜像。兜底逻辑刻意做成故障安全：启动失败一次就放弃该 GSI，糟糕的镜像永远不会把设备变砖。

55.27.4 DSU 在本书其他位置的呈现

DSU 接入到其他章节讲述的两个子系统中：

  • 开发者选项（第 50 章）。 设置的开发者选项界面暴露一个 SelectDSUPreferenceController（50-settings-app.md 中关于开发者选项偏好控制器的部分），让开发者挑选并加载一个 DSU 镜像。这是同一批 IGsiService 调用（gsi_tool 所发）的 GUI 前端。
  • first-stage 挂载（第 4 章）。 早期启动期间，FirstStageMountAndroid（system/core/init/first_stage_mount_android.cpp）会咨询 libgsi（CanBootIntoGsi、GetActiveDsu、MarkSystemAsGsi），把 DSU 镜像文件映射为 system/userdata 的 device-mapper 设备，然后导出 ro.gsid.image_running / DSU 槽属性（04-boot-and-init.md）。DSU 复用普通动态分区与虚拟 A/B 所依赖的同一套 first-stage 逻辑分区挂载路径。

简言之，gsid 是一个目标明确的“暂存 + 武装”守护进程：它借用 OTA 的动态分区与镜像映射基础设施，把一个下载来的系统镜像放进 /data，在 /metadata/gsi/dsu 下写入少量标记文件，然后让 first-stage init 启动该镜像，从而对一整套新系统镜像做可控、可逆的试用。

OTA 子系统是 Android 最关键、却又最不显眼的基础设施之一。一条运转良好的 OTA 流水线，意味着设备无需用户干预就能保持安全与更新。从非 A/B 到 A/B、再到虚拟 A/B 的演进，体现出一以贯之的工程追求：可靠性（不变砖）、用户体验（不停机）、存储效率（不浪费空间）。

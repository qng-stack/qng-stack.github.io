第 56 章：虚拟化框架

第 56 章：虚拟化框架

Android 虚拟化框架（Android Virtualization Framework，AVF）把硬件支撑的虚拟机带到了 Android 设备上，使机密计算（confidential computing）负载即便面对宿主机操作系统也能保持隔离。AVF 建立在 pKVM（protected KVM，受保护的 KVM）、crosvm 与 Microdroid 之上，构成一套完整生态，用于在受保护的虚拟机（protected VM，pVM）中运行可信代码。本章逐层剖析这套栈：EL2 虚拟机监控器、虚拟机固件、Rust 编写的虚拟机监视器，以及轻量级 guest OS；最后一层是把它们全部串起来的用户态服务架构。

56.1 Android 虚拟化框架（AVF）

56.1.1 概述与动机

Android 虚拟化框架提供安全且私密的执行环境，其隔离强度超出传统的 Android 应用沙箱。应用沙箱给出的是由 Linux 内核实施的进程级隔离，而 AVF 通过 CPU 虚拟化扩展给出硬件强制的隔离：受保护虚拟机的内存，即便面对已被攻破的 Android 宿主机内核，也不可访问。

框架在 packages/modules/Virtualization/README.md 中给出了核心价值主张：

Android 虚拟化框架（AVF）为代码执行提供安全且私密的执行环境。对于安全导向的用例——需要比 Android 应用沙箱更强的隔离保证——AVF 是最理想的选择。

AVF 面向若干关键用例：

  1. 机密计算 —— 运行机器学习模型或敏感算法，而代码与数据不可被宿主机观测。

  2. 可信编译 —— composd 服务借助 AVF 在虚拟机内编译 ART 产物，以确保编译器本身未被篡改。

  3. 远程密钥发放（Remote Key Provisioning，RKP） —— RKP 虚拟机在隔离环境中处理密钥操作，并由远程服务器背书（attest）。

  4. 隔离服务 —— 需要为执行环境提供强保证的第三方负载。

56.1.3 com.android.virt APEX

AVF 以 com.android.virt APEX 模块的形式交付，因而可以独立于 Android 主平台升级。该 APEX 包含：

  • vm 命令行工具
  • VirtualizationService 与 virtmgr 守护进程
  • Microdroid 内核与系统镜像
  • crosvm 可执行文件
  • Java 与原生客户端库

有两个关系密切的组件不在这个 APEX 内：负责编译编排的 composd 守护进程随另一个独立的 com.android.compos APEX 交付；pvmfw.bin 则是独立的固件镜像（在产品输出中安装为 system/etc/pvmfw.bin），由引导加载程序加载，并非从 APEX 中解出。

从源码安装该 APEX：

banchan com.android.virt aosp_arm64
UNBUNDLED_BUILD_SDKS_FROM_SOURCE=true m apps_only dist
adb install out/dist/com.android.virt.apex
adb reboot

56.1.4 受保护虚拟机与非受保护虚拟机

AVF 支持两种虚拟机模式：

属性 非受保护虚拟机 受保护虚拟机（pVM）

56.1.6 DICE 背书链

设备标识组合引擎（Device Identifier Composition Engine，DICE）提供一条密码学信任链，从设备 ROM 贯穿每个启动阶段，直到正在运行的虚拟机载荷。每一阶段都度量下一阶段，从而形成一条能证明虚拟机身份的证书链。

如 packages/modules/Virtualization/docs/pvm_dice_chain.md 所述：

虚拟机 DICE 链是一条密码学关联的证书链，捕获虚拟机整个执行环境的度量值。

这条链应当根植于设备的 ROM，并涵盖参与虚拟机加载与启动过程的所有组件。

厂商构造从 ROM 到 ABL 的这条链，然后把它交给 pvmfw。交接格式为 CBOR 编码。下面给出三个字段的示意性 CDDL。这里的标签只是描述性的，并非源码中的标识符。Rust 一侧把它解析为 BccHandover，并通过 packages/modules/Virtualization/guest/pvmfw/src/dice/chain.rs 中的 DiceChainInfo / DiceChainEntry 逐级遍历：

DiceHandover = {
  1 : bstr .size 32,     ; CDI_Attest
  2 : bstr .size 32,     ; CDI_Seal
  3 : DiceChain,         ; Android DICE chain
}

CDI（Compound Device Identifier，组合设备标识符）值有两种用途：

  • CDI_Attest —— 用于派生身份证明所需的背书密钥对
  • CDI_Seal —— 用于派生持久数据加密所需的封存密钥

56.1.7 远程背书

虚拟机的远程背书（remote attestation）可让 pVM 向第三方证明自身可信。该机制分两个阶段，见 packages/modules/Virtualization/docs/vm_remote_attestation.md：

  1. RKP 虚拟机背书 —— 轻量的 RKP 虚拟机接受远程 RKP 服务器背书，后者确认其 DICE 链根植于真实设备。

  2. pVM 背书 —— 此时已可信的 RKP 虚拟机为客户端 pVM 校验 DICE 链，确认它们是在真实虚拟机环境中运行预期代码。

56.2 pKVM 虚拟机监控器

56.2.1 架构概述

pKVM（protected KVM，受保护的 KVM）是运行在 ARM 异常级别 2（EL2）上的轻量级虚拟机监控器（hypervisor）。它扩展了标准 Linux KVM，提供即便宿主内核被攻破也依然成立的内存隔离保证。与传统虚拟机监控器不同，pKVM 的设计目标是拥有尽可能小的可信计算基（trusted computing base，TCB）。它不管理设备，也不调度虚拟机，而只专注于内存访问控制。

56.2.2 内存隔离模型

pKVM 的根本安全属性是：受保护虚拟机的内存对宿主机不可访问。这由 EL2 虚拟机监控器独占控制的 ARM Stage-2 页表来实施：

  1. 宿主内存 —— 映射在宿主机的 Stage-2 表中，从所有 guest 的 Stage-2 表中解除映射。

  2. guest 内存 —— 映射在 guest 的 Stage-2 表中，从宿主机的 Stage-2 表中解除映射。宿主机不能读、写或执行 guest 内存。

  3. 共享内存 —— 显式共享的区域同时映射在宿主机与 guest 的 Stage-2 表中，用于 virtio 通信。

这样的设计意味着，即便宿主机上出现内核级漏洞利用，也无法读取 pVM 的私有内存。虚拟机监控器会拦截并校验所有内存映射操作。

  • MEMINFO（函数 ID 0xc6000002）—— 查询内存颗粒（granule）信息
  • MEM_SHARE（函数 ID 0xc6000003）—— 与宿主机共享一段内存
  • MEM_UNSHARE（函数 ID 0xc6000004）—— 撤销宿主机对共享区域的访问

MMIO 守卫：

  • MMIO_GUARD_INFO（函数 ID 0xc6000005）—— 查询 MMIO 守卫信息
  • MMIO_GUARD_ENROLL（函数 ID 0xc6000006）—— 启用 MMIO 守卫
  • MMIO_GUARD_MAP（函数 ID 0xc6000007）—— 映射一段 MMIO 区域
  • MMIO_GUARD_UNMAP（函数 ID 0xc6000008）—— 解除一段 MMIO 区域的映射

标准 ARM 接口：

  • ARM SMCCC v1.1 —— 调用约定
  • PSCI v1.0 —— 电源状态协调（复位、关机）
  • TRNG v1.0 —— 真随机数生成

56.2.4 Stage-2 页表管理

pKVM 启动受保护虚拟机时，会为该虚拟机创建一套专属的 Stage-2 页表。关键操作如下：

sequenceDiagram
    participant Host as 宿主内核
    participant pKVM as pKVM（EL2）
    participant S2 as Stage-2 页表

    Host->>pKVM: 创建虚拟机（KVM_CREATE_VM）
    pKVM->>S2: 分配 guest 的 Stage-2 页表
    pKVM->>S2: 从宿主 Stage-2 中移除 guest 页面

    Note over pKVM,S2: guest 内存从此对宿主机不可见

    Host->>pKVM: 映射共享内存区域
    pKVM->>S2: 在宿主与 guest 的 Stage-2 中同时映射该区域

    Note over pKVM,S2: 用于 virtio 传输的共享区域

56.2.5 pKVM 对 pvmfw 的加载

当 VMM 请求一台受保护虚拟机时，pKVM 会把 pvmfw 从受保护的内存区域加载进 guest 地址空间。该区域由 Android 引导加载程序（Android Bootloader，ABL）预先准备好，并通过一个保留内存（reserved memory）设备树节点描述：

reserved-memory {
    pkvm_guest_firmware {
        compatible = "linux,pkvm-guest-firmware-memory";
        reg = <0x0 0x80000000 0x40000>;
        no-map;
    }
}

关于 pvmfw 加载的要点：

  1. 虚拟机监控器不解释 pvmfw —— 它只负责保护并加载预先准备好的二进制。

  2. pvmfw 二进制在 guest 地址空间中必须按 4KiB 对齐。

  3. 配置数据追加在 pvmfw 之后，并包含在同一块受保护区域内。

  4. 加载完成后，pvmfw 成为虚拟机的入口点，先于任何 guest 代码执行。

56.2.6 内存共享协议

为实现 virtio 通信，guest 内存必须显式共享给宿主机。共享协议使用 hypercall：

sequenceDiagram
    participant Guest as guest（pvmfw/内核）
    participant pKVM as pKVM 虚拟机监控器
    participant Host as 宿主机（crosvm）

    Guest->>pKVM: MEM_SHARE(page_addr)
    pKVM->>pKVM: 在宿主 Stage-2 中映射该页
    pKVM-->>Guest: 成功

    Note over Guest,Host: 宿主机现在可以访问该共享页

    Guest->>pKVM: MEM_UNSHARE(page_addr)
    pKVM->>pKVM: 从宿主 Stage-2 中解除该页映射
    pKVM-->>Guest: 成功

    Note over Guest,Host: 宿主机不再能访问该页

guest 有责任确保敏感数据绝不放入共享内存区域。pvmfw 固件在为 virtio 传输完成初始内存共享后，才把控制权交给 guest 内核。

56.2.7 MMIO 守卫

MMIO 守卫机制阻止 guest 访问任意 MMIO 区域。这很重要：在虚拟机中，MMIO 访问通常由虚拟机监控器陷入（trap）并转发给 VMM，而恶意 VMM 可能给出伪造的设备响应。有了 MMIO 守卫：

  1. guest 必须显式加入 MMIO 守卫（MMIO_GUARD_ENROLL）。
  2. 只有已映射的 MMIO 区域（MMIO_GUARD_MAP）才会产生发往 VMM 的陷入。
  3. 访问未映射的 MMIO 区域会触发 abort，而不是陷入。

这缩小了可能已被攻破的 VMM 带来的攻击面。

56.3 crosvm：虚拟机监视器

56.3.1 概述

crosvm 是 Rust 编写的虚拟机监视器（Virtual Machine Monitor，VMM），源自 ChromiumOS，被 Android 引入 AVF。它管理虚拟机的生命周期，提供虚拟硬件设备，并充当宿主内核与 guest 之间的接口。

external/crosvm/ARCHITECTURE.md 描述了核心设计原则：

crosvm 的主要特征是：

  • 每个虚拟设备一个进程，在 Linux 上用 fork 创建
  • 每个进程都用 minijail 沙箱化
  • 支持多种 CPU 架构、操作系统与虚拟机监控器
  • 用 Rust 编写，以保证安全与可靠性

56.3.6 Minijail 沙箱

每个设备进程都用 minijail 配合 Linux 命名空间与 seccomp 过滤器进行沙箱化。seccomp 策略与架构相关：

external/crosvm/jail/seccomp/

    x86_64/            # x86_64 seccomp policies
    riscv64/           # RISC-V seccomp policies

每个设备都有自己的 seccomp 策略文件，其中只放行它所需的系统调用。策略文件包含一个公共基础（common_device.policy），再加上设备专属的系统调用。

这种沙箱提供纵深防御：即便恶意 guest 攻破了某个虚拟设备进程，攻击者也被限制在隔离命名空间内的一组最小系统调用中。

56.3.9 GuestMemory 架构

guest 内存管理是一个关键子系统。ARCHITECTURE.md 描述了五个相关类型：

  • GuestMemory —— 指向全部 guest 内存的引用。可以克隆，但底层内存始终是同一份。由 MemoryMapping 与 SharedMemory 实现。对非受保护虚拟机，它被映射进宿主地址空间，但并不连续。

  • SharedMemory —— 封装一个 memfd。可用 MemoryMapping 映射。不可克隆。

  • VolatileMemory —— 用于通用访问非连续内存的 trait。GuestMemory 实现了该 trait。

  • VolatileSlice —— 类似 Rust 的 slice，但其数据会被异步修改。适合描述分散-聚集（scatter-gather）表项。

  • MemoryMapping —— 对 mmap/munmap 的安全封装。提供 RAII 语义。禁止经 Rust 引用访问；应改用 VolatileSlice。

对受保护虚拟机，guest 内存不会映射进宿主地址空间 —— pKVM 虚拟机监控器会阻止这一点。唯一例外是用于 virtio 传输的共享内存区域。

56.3.10 虚拟机控制套接字

crosvm 用 Unix 域套接字在主进程与设备进程之间进行进程间通信。来自架构文档：

对于设备需要对全局虚拟机状态执行的操作 —— 例如映射进 guest 内存地址空间 —— 提供了虚拟机控制套接字。按其处理的请求与响应类型分为数种。这同时提供了基本的特权分离：一旦某设备被恶意 guest 攻破，损害也被限制。

控制套接字的类型处理：

  • 内存映射请求
  • MSI 路由分配
  • guest 内存的注册/注销
  • 虚拟机状态变更（暂停、恢复、复位）

外部控制可通过 --socket 参数获得，经 crosvm_control 库或 crosvm stop 之类的 CLI 子命令访问。

56.3.11 WaitContext 事件循环

crosvm 的大多数线程都用 WaitContext 作为事件循环。它是对 epoll（Linux）与 WaitForMultipleObjects（Windows）的跨平台抽象：

// Conceptual event loop (simplified)
#[derive(EventToken)]
enum Token {
    VirtioQueue,
    InterruptResample,
    Kill,
}

let wait_ctx = WaitContext::new()?;
wait_ctx.add(&queue_evt, Token::VirtioQueue)?;
wait_ctx.add(&interrupt_resample, Token::InterruptResample)?;
wait_ctx.add(&kill_evt, Token::Kill)?;

loop {
    let events = wait_ctx.wait()?;
    for event in events {
        match event.token {
            Token::VirtioQueue => { /* process queue */ },
            Token::InterruptResample => { /* resample interrupt */ },
            Token::Kill => return Ok(()),
        }
    }
}

/dev/block/by-name/system /system erofs noatime,ro wait,slotselect,avb=vbmeta,first_stage_mount
/dev/block/by-name/microdroid-vendor /vendor ext4 noatime,ro,errors=panic wait,first_stage_mount,avb_hashtree_digest=/proc/device-tree/avf/vendor_hashtree_descriptor_root_digest

关键文件系统特征：

  • 根 —— 只读，在 post-fs 之后重新挂载
  • /system —— 只读 erofs，经 AVB 验证启动（avb=vbmeta）
  • /vendor —— 可选，经 hashtree 摘要验证
  • /data —— tmpfs（128 MiB），短暂易失
  • /mnt/apk —— 载荷 APK 的挂载点
  • /mnt/encryptedstore —— 加密持久存储

56.4.6 厂商镜像支持

Microdroid 支持可选的 vendor 分区，用于设备专属模块。vendor 镜像的校验流程在受保护与非受保护虚拟机上有所不同：

非受保护虚拟机： virtualizationmanager 生成一个包含 vendor hashtree 摘要的 DTBO，并经 crosvm 传给虚拟机。该摘要取自宿主机 Android 设备树 /avf/reference/ 之下。

受保护虚拟机： pvmfw 配置数据中的虚拟机参考 DT 会用于额外校验。引导加载程序把 vendor hashtree 摘要追加进该虚拟机参考 DT。pvmfw 校验：若虚拟机设备树中存在匹配属性，其值必须与参考值完全一致。

引自 Microdroid README：

对 pVM，pvmfw 配置数据中所含的虚拟机参考 DT 还会被额外用于校验 vendor hashtree 摘要。引导加载程序应当依据 fstab.microdroid，把 vendor hashtree 摘要追加进虚拟机参考 DT。

56.5 pVM 固件

56.5.1 用途与威胁模型

pVM 固件（pvmfw）是在受保护虚拟机内最先执行的代码。它充当虚拟机的信任根，在允许任何 guest 代码运行之前，先校验 guest 环境。

引自 packages/modules/Virtualization/guest/pvmfw/README.md：

由于 pVM 由运行在不可信宿主机上的 VMM 管理，它所配置的虚拟机同样不可信。此外，尽管前述隔离能让 pVM 保护自身机密不被宿主机窥见，却无助于在启动期间把机密发放给它们。特别地，该威胁模型不允许宿主机在任何时刻访问这些机密，因而 VMM 也无法把它们传给 pVM。

威胁模型假定：

  • 宿主机操作系统可能已被完全攻破
  • VMM（crosvm）可能是恶意的
  • 虚拟机监控器（pKVM）与 pvmfw 自身是可信的
  • 设备硬件（包括直到 pvmfw 加载为止的固件）是可信的

56.5.2 源码架构

pvmfw 源码位于 packages/modules/Virtualization/guest/pvmfw/src/，是一个 no_std 的 Rust 二进制：

56.5.5 验证启动

pvmfw 使用 Android 验证启动（Android Verified Boot，AVB）校验 guest 内核与可选的 ramdisk。校验使用一个内嵌的公钥：

/// Trusted public key, used during verification of the signed kernel & ramdisk.
const PUBLIC_KEY: &[u8] = include_bytes!(
    concat!(env!("OUT_DIR"), "/pvmfw_embedded_key_pub.bin")
);

内嵌的 PUBLIC_KEY 只是可信密钥切片中的第一项。校验之前，main() 会把 TrustedKeys 配置项中携带的额外密钥追加进该切片。

验证启动过程如下：

fn perform_verified_boot<'a>(
    signed_kernel: &[u8],
    ramdisk: Option<&[u8]>,
    trusted_keys: &'a [&'a [u8]],
) -> Result<(VerifiedBootData<'a>, bool, usize), RebootReason> {
    let verified_boot_data = verify_payload(signed_kernel, ramdisk, trusted_keys)
        .map_err(|e| {
            error!("Failed to verify the payload: {e}");
            RebootReason::PayloadVerificationError
        })?;
    let debuggable = verified_boot_data.debug_level != DebugLevel::None;
    let guest_page_size = verified_boot_data.page_size.unwrap_or(SIZE_4KB);
    Ok((verified_boot_data, debuggable, guest_page_size))
}

56.5.6 DICE 派生

校验通过后，pvmfw 派生下一阶段的 DICE 密钥。 packages/modules/Virtualization/guest/pvmfw/src/dice/mod.rs 中的 DICE 模块负责此事：

// DICE Configuration Descriptor keys
const COMPONENT_NAME_KEY: i64 = -70002;
const SECURITY_VERSION_KEY: i64 = -70005;
const RKP_VM_MARKER_KEY: i64 = -70006;
const INSTANCE_HASH_KEY: i64 = -71003;

派生过程：

  1. 解析收到的 DICE 交接（CDI + 证书链）
  2. 从验证启动数据计算部分 DICE 输入
  3. 纳入实例哈希（用于区分不同虚拟机实例）
  4. 执行防回滚保护
  5. 派生下一阶段的 CDI 与证书
fn perform_dice_derivation(
    dice_handover_bytes: &[u8],
    dice_context: DiceContext,
    dice_inputs: PartialInputs,
    salt: &[u8; HIDDEN_SIZE],
    defer_rollback_protection: bool,
    next_dice_handover: &mut [u8],
) -> Result<(), RebootReason> {
    dice_inputs
        .write_next_handover(
            dice_handover_bytes.as_ref(),
            salt,
            defer_rollback_protection,
            next_dice_handover,
            dice_context,
        )
        .map_err(|e| {
            error!("Failed to derive next-stage DICE secrets: {e:?}");
            RebootReason::SecretDerivationError
        })?;
    Ok(())
}

实例专属的盐确保：载荷相同但实例不同的虚拟机拿到不同的密钥：

fn salt_from_instance_id(fdt: &Fdt) -> Result<Option<Hidden>, RebootReason> {
    let Some(id) = read_instance_id(fdt).map_err(|e| {
        error!("Failed to get instance-id in DT: {e}");
        RebootReason::InvalidFdt
    })?
    else {
        return Ok(None);
    };
    let mut ctx = Sha512::new();  // bssl_crypto::digest::Sha512
    ctx.update(b"InstanceId:");
    ctx.update(id);
    Ok(Some(ctx.digest()))
}

配置格式历经五个版本演进：

  • 条目 1：调试策略 DTBO（可选）

56.5.10 VBMeta 属性

AVF 定义了一些 pvmfw 能识别的特殊 AVB VBMeta 描述符属性：

  • com.android.virt.cap —— 能力列表（以竖线分隔）：

56.5.11 交接给 guest 内核

所有校验与派生完成后，pvmfw 准备 guest 环境并跳转到内核：

  1. 从宿主机收回所有非必需内存的共享
  2. 除 UART 外（若可调试），收回所有 MMIO 区域的共享
  3. 刷新保留内存（DICE 交接、保留内存）
  4. 计算内核入口点
  5. 跳转到载荷

DICE 链经设备树中的一个保留内存节点传给 guest：

56.6.12 实例 ID 与 CID 管理

56.8 防回滚保护

56.8.1 概述

防回滚保护（rollback protection）阻止攻击者运行旧版、存在漏洞的虚拟机载荷，并借此访问只发放给新版本的机密。pvmfw 实现多种防回滚策略，依据虚拟机类型与平台能力选择。

来自 packages/modules/Virtualization/guest/pvmfw/src/rollback.rs：

pub fn perform_rollback_protection<'a>(
    fdt: &Fdt,
    verified_boot_data: &VerifiedBootData,
    dice_inputs: &PartialInputs,
    cdi_seal: &[u8],
    rollback_config: Option<&RollbackConfig<'a>>,
    extra_keys: &[&'a [u8]],
) -> Result<(bool, Hidden, bool), RebootReason> {
    let instance_hash = dice_inputs.instance_hash;
    if let Some(fixed) =
        get_fixed_rollback_protection(verified_boot_data, rollback_config, extra_keys)
    {
        perform_fixed_rollback_protection(verified_boot_data, fixed)?;
        Ok((false, instance_hash.unwrap(), false))
    } else if (should_defer_rollback_protection(fdt)?
        && verified_boot_data.has_capability(Capability::SecretkeeperProtection))
        || verified_boot_data.has_capability(Capability::TrustySecurityVm)
    {
        perform_deferred_rollback_protection(verified_boot_data)?;
        Ok((false, instance_hash.unwrap(), true))
    } else if cfg!(feature = "instance-img") {
        perform_legacy_rollback_protection(fdt, dice_inputs, cdi_seal, instance_hash)
    } else {
        force_new_instance()
    }
}

match verified_boot_data.name.as_deref()? {

推迟防回滚保护 —— guest 经 Secretkeeper 自行处理防回滚保护。pvmfw 只校验回滚索引为正数：

fn perform_deferred_rollback_protection(
    verified_boot_data: &VerifiedBootData,
) -> Result<(), RebootReason> {
    info!("Deferring rollback protection");
    if verified_boot_data.rollback_index == 0 {
        error!("Expected positive rollback_index, found 0");
        Err(RebootReason::InvalidPayload)
    } else {
        Ok(())
    }
}

遗留防回滚保护 —— 使用 instance.img 块设备保存已记录的 DICE 度量值。后续启动时，pvmfw 将当前度量值与记录项比较：

fn ensure_dice_measurements_match_entry(
    dice_inputs: &PartialInputs,
    entry: &EntryBody,
) -> Result<(), InstanceError> {
    if entry.code_hash != dice_inputs.code_hash {
        Err(InstanceError::RecordedCodeHashMismatch)
    } else if entry.auth_hash != dice_inputs.auth_hash {
        Err(InstanceError::RecordedAuthHashMismatch)
    } else if entry.mode() != dice_inputs.mode {
        Err(InstanceError::RecordedDiceModeMismatch)
    } else {
        Ok(())
    }
}

    pub vm_ref_dt: Option<&'a [u8]>,           // Read-only

56.9.3 版本协商

解析器通过“把未知次版本按最新的已知版本处理”来实现前向兼容：

pub fn entry_count(&self) -> Result<usize> {
    let last_entry = match self.version {
        Self::VERSION_1_0 => Entry::DebugPolicy,
        Self::VERSION_1_1 => Entry::VmDtbo,
        Self::VERSION_1_2 => Entry::VmBaseDtbo,
        Self::VERSION_1_3 => Entry::ReservedMem,
        Self::VERSION_1_4 => Entry::ExtraRollback,
        v @ Version { major: 1, .. } => {
            const LATEST: Version = Header::VERSION_1_4;
            warn!("Parsing unknown config data version {v} as version {LATEST}");
            return Ok(Entry::COUNT);
        }
        v => return Err(Error::UnsupportedVersion(v)),
    };
    Ok(last_entry as usize + 1)
}

这意味着次版本号未知的 1.x 配置会被按最新的已知版本（当前为 1.4）解析。超出已知条目集合的新条目会被静默忽略。主版本变更（2.x）则会被拒绝。

56.10.2 为下一阶段修改设备树

净化之后，pvmfw 修改 FDT，以便向 guest 内核传递信息：

  1. DICE 链 —— 以 compatible = "google,open-dice" 的 /reserved-memory/dice 节点加入

  2. KASLR 种子 —— 用于内核地址空间布局随机化的随机种子

  3. 启动参数 —— 调试级别、实例状态

  4. 保留内存 —— 机密数据区域

  5. 设备分配信息 —— 若配置了设备直通

reserved-memory 中 DICE 节点的格式：

/ {
    reserved-memory {
        #address-cells = <0x02>;
        #size-cells = <0x02>;
        ranges;
        dice {
            compatible = "google,open-dice";
            no-map;
            reg = <0x0 0x7fe0000>, <0x0 0x1000>;
        };
    };
};

56.10.3 FDT 处的安全边界

FDT 构成一条关键的安全边界。VMM 构造 FDT 来描述虚拟平台，但在受保护虚拟机的威胁模型下，VMM 不可信。因此 pvmfw 必须：

  • 对不可信 FDT 中的设备地址或大小，未经校验一律不信

  • 对 CPU 数量或内存布局，未经边界检查一律不信

  • 对安全攸关的属性（例如 DICE 链位置），校验其形式是否正当

  • 在把自己移交给 guest 内核之前，用净化后的版本替换不可信 FDT

这正是 pvmfw 从模板 FDT 出发、而不是就地修改 VMM 所提供 FDT 的原因。这确保 guest 收到的设备树只包含已知安全的内容。

内存区域以显式的只读或读写权限映射：

fn map_data_slice_mut<'a>(addr: usize, size: usize)
    -> Result<&'a mut [u8], MemoryTrackerError>
{
    let nonzero_size = size.try_into().map_err(|_| {
        error!("Invalid size specified for the range: {size:#x}");
        MemoryTrackerError::SizeTooSmall
    })?;
    map_data(addr, nonzero_size)?;
    let mut_slice = unsafe {
        slice::from_raw_parts_mut(addr as *mut u8, size)
    };
    Ok(mut_slice)
}

fn map_data_slice<'a>(addr: usize, size: usize)
    -> Result<&'a [u8], MemoryTrackerError>
{
    let nonzero_size = size.try_into().map_err(|e| {
        error!("Invalid size specified for the range: {e}");
        MemoryTrackerError::SizeTooSmall
    })?;
    map_rodata(addr, nonzero_size)?;
    let slice = unsafe {
        slice::from_raw_parts(addr as *const u8, size)
    };
    Ok(slice)
}

这种区分确保内核镜像与 ramdisk 经 map_data_slice()（底层为 map_rodata）以只读方式映射，只有 pvmfw 必须修改的区域才经 map_data_slice_mut() 以读写方式映射 —— 这些区域是 FDT，以及 x86_64 上的 boot params 与 setup data。

// Worker thread for a virtio device (conceptual)
async fn process_queue(
    queue: Queue,
    mem: GuestMemory,
    interrupt: Interrupt,
) -> Result<()> {
    loop {
        // Wait for the guest to submit descriptors
        let desc_chain = queue.next_async(&mem).await?;

        // Process the request
        let response = handle_request(&desc_chain, &mem)?;

        // Write response and signal completion
        queue.add_used(&mem, desc_chain.index, response.len());
        interrupt.signal_used_queue(queue.vector());
    }
}

56.16.2 攻击面分析

宿主机到 guest 的攻击（由 pKVM 缓解）：

  • 直接内存访问：被 Stage-2 页表阻断
  • DMA 攻击：被 IOMMU 与 MMIO 守卫阻断
  • 侧信道：由缓存/TLB 隔离部分缓解

VMM 到 guest 的攻击（由 pvmfw 缓解）：

  • 恶意设备树：由 pvmfw 用模板 FDT 净化
  • 伪造设备：MMIO 守卫限制可访问设备
  • 回滚攻击：多种 RBP 策略防止机密被复用

guest 到宿主机的攻击（由 crosvm 沙箱缓解）：

  • 设备逃逸：每设备一进程，配合 seccomp + 命名空间
  • virtio 攻击：每个设备都有最小系统调用白名单
  • 资源耗尽：内存上限、CPU 配额

56.16.3 Rust 的安全保证

pvmfw 与 crosvm 都用 Rust 编写，因而具备：

  • 内存安全 —— 无缓冲区溢出、use-after-free 或 double-free
  • 线程安全 —— 数据竞争在编译期被阻止
  • 无未定义行为 —— 除显式标注的 unsafe 块
  • 零开销抽象 —— 安全而不带运行时开销

pvmfw 代码库使用 #![no_std] 以缩小可信计算基，unsafe 块仅限于：

  • 硬件寄存器访问
  • 汇编指令（HVC 调用、内存屏障）
  • FDT 解析中的裸指针操作
  • 阶段间的内存交接

56.16.4 DICE 链完整性

DICE 链在启动各阶段之间提供密码学绑定。密钥派生遵循 Open DICE 规范：

CDI_Attest_pub, CDI_Attest_priv = KDF_ASYM(KDF(CDI_Attest))

来自 packages/modules/Virtualization/docs/pvm_dice_chain.md 的要求：

  • KDF：必须使用 RFC 5869 规定的 HKDF-SHA-512。
  • KDF_ASYM：必须使用下列受支持算法之一：
    • Ed25519
    • ECDSA with NIST P-256 (RFC 6979)
    • ECDSA with NIST P-384 (RFC 6979)

若厂商引导加载程序与 pvmfw 之间的密钥派生出现任何不一致，证书链即断裂，导致远程背书、Secretkeeper 与 Trusted HAL 认证失败。

56.17.5 内存与存储气球：与 Android 共存

完整的 Debian 桌面（第 56.15 章）对内存与磁盘都很饥渴，而它运行在一台还必须保证 Android 流畅的手机上。让二者共享固定预算的技术就是气球（ballooning）。这是一个标准的虚拟化概念，并非 Android 新增子系统。virtio balloon 是 guest 内的一个驱动。宿主机可以充气（inflate）它：guest 分配页面并交还宿主机，于是 guest 可用的内存减少。宿主机也可以放气（deflate）：把内存还给 guest。

crosvm 在 devices/src/virtio/balloon.rs 中实现该设备；存储气球是同一思路在稀疏磁盘镜像上的应用。这两者在 Android 上都不算新事物。

Android 的贡献在于由应用生命周期驱动气球的策略。于是 Linux 虚拟机在闲置的瞬间就会把资源交还：

  • MemBalloonController（android/TerminalApp/.../MemBalloonController.kt）是 Terminal 应用上的生命周期观察者。在 onResume 时它把气球放气到 0 —— 即“把尽可能多的可用内存给虚拟机” —— 于是一个前台的 Linux 桌面能以全内存运行。在 onStop（进入后台）时，它经 vm.setMemoryBalloonByPercent() 从 INITIAL_PERCENT 按 INFLATION_STEP_PERCENT 逐步充气直到 MAX_PERCENT，把内存交还 Android。
  • StorageBalloonWorker 对磁盘做同样的工作，由 terminal_storage_balloon 开关（“Flag for storage ballooning support in terminal”）控制；虚拟机的配置里还带有 auto_memory_balloon。
  • IGuestAgent.trimAsync() 是 IGuestAgent 接口上的方法（见 56.30 节）。该接口在 17 中移入 virtualizationcommon 包，但 trimAsync 本身早于这次迁移。该方法让宿主机在 Android 内存压力下额外请求 guest 修剪（trim）自己的内存（丢弃缓存、回收）。它在粗粒度的气球之上进一步起作用。

56.20 可升级虚拟机与 Secretkeeper

56.20.1 升级难题

虚拟机的代码更新后，DICE 链会因代码度量值不同而变化。这意味着 CDI 值变化，任何用旧 CDI 加密的数据都无法被新版本解密。

56.20.2 Secretkeeper 协议

Secretkeeper 通过提供一个跨虚拟机升级持久存在的安全键值存储来解决该问题。虚拟机把机密存入 Secretkeeper，而不是直接用 DICE 派生密钥加密。

sequenceDiagram
    participant VM_v1 as 虚拟机（版本 1）
    participant SK as Secretkeeper HAL
    participant VM_v2 as 虚拟机（版本 2）

    Note over VM_v1,SK: 初始发放
    VM_v1->>SK: 存储机密（key=vm_id，value=data_key）
    SK->>SK: 经 DICE 链校验虚拟机身份
    SK->>SK: 用平台密钥加密后存储

    Note over VM_v2,SK: 升级之后
    VM_v2->>SK: 取回机密（key=vm_id）
    SK->>SK: 校验虚拟机身份（新 DICE 链）
    SK->>SK: 检查防回滚保护
    SK-->>VM_v2: 返回 data_key
    VM_v2->>VM_v2: 用 data_key 解密持久数据

pvmfw 的集成逻辑处理具备 Secretkeeper 能力的虚拟机：

if verified_boot_data.has_capability(Capability::SecretkeeperProtection) {
    perform_deferred_rollback_protection(verified_boot_data)?;
    Ok((false, instance_hash.unwrap(), true))
}

56.22 调试详解

56.22.1 调试策略

调试策略（debug policy）控制受保护虚拟机可用的调试特性。它以 DTBO 形式放在 pvmfw 配置数据中（条目 1）。

只有当 DICE 链表明处于调试模式时，调试策略才会被应用：

// The bootloader should never pass us a debug policy when the boot is secure
if debug_policy.is_some() && !dice_debug_mode {
    warn!("Ignoring debug policy, DICE handover does not indicate Debug mode");
    debug_policy = None;
}

56.22.2 调试级别

vm CLI 支持两个调试级别：

fn parse_debug_level(s: &str) -> Result<DebugLevel, String> {

  • full —— 调试模式。Microdroid 内输出控制台信息、记录日志、可经 ADB 访问。

56.27 AVF 多租户

在 Android 16 及以前，一台 Microdroid 虚拟机承载由单一应用拥有的单一载荷。Android 17（26Q2 版本）加入多租户。多个互不信任的载荷可以共享一台虚拟机，同时彼此保持隔离。当某个机密负载想组合来自多个属主的代码时（例如一个 APK 载荷加一个平台 APEX），这一点很重要。各属主无需各自拥有一台虚拟机，从而避开每虚拟机独立的启动、内存与背书开销。

56.27.1 签名的 TenancyConfig

信任模型是由虚拟机属主签署的可信共居声明。虚拟机属主编写 TenancyConfig，列出允许进入该虚拟机的所有租户。pVM 实例会拒绝任何未被其描述的载荷。来自 packages/modules/Virtualization/docs/multitenancy.md：

我们引入 TenancyConfig，这是由虚拟机属主签署的可信共居声明。它本质上描述了将被允许进入虚拟机的每个租户；任何未在其中描述的载荷都应由 pVM 实例丢弃。该配置将由用例属主签名，并反映在 pVM 的证书（DICE 链）之中。

具体而言，TenancyConfig 就是内嵌于 APK 的载荷配置 JSON 文件，通常通过 VirtualMachineConfig#setPayloadConfigPath 设置。该配置属于已签名载荷的一部分，因此被度量进 DICE 链（56.1.6 节）。于是被接纳的租户集合成为虚拟机可验证身份的一部分，不可信的宿主机无法篡改。

56.27.2 租户配置模式

该配置模式位于 packages/modules/Virtualization/libs/libmicrodroid_payload_metadata/config/src/lib.rs。顶层 VmPayloadConfig 新增了 tenants: Vec<TenantConfig> 字段（第 45 行）。每个 TenantConfig 是一个以 package 字段作标签的枚举，取值为 APK 或 APEX 租户（第 151-158 行）：

两个变体都携带 TenantConfiguration（第 203-222 行）：

56.27.3 microdroid_manager 中的租户校验

校验在 guest 内、microdroid_manager 中运行，代码位于 packages/modules/Virtualization/guest/microdroid_manager/src/tenant_config.rs。 validate_tenants_against_tenant_config() 函数（第 32-119 行）强制执行四项不变量，文件开头有相应说明：

  1. 提供的租户 APK 与 APEX 必须与配置所描述的集合完全一致，按包名比较（第 42-68 行）。数量不符会以 PayloadInvalidConfig 失败。
  2. 配置中租户的顺序无关紧要；查找在第 37-40 行构建的 HashMap 上按名进行。
  3. 租户的 rollback_index（无回滚索引时用 version_code）必须不小于 min_version（第 101-107 行），从而阻止回滚到存在漏洞的构建。
  4. 签名 authority 必须与 expected_authority 一致。对 APK，authority 为 hex::encode(&apk_data.cert_hash)（第 96 行）；对 APEX，为 hex::encode(Sha512::hash(&apex_data.public_key))（第 84 行）。期望 authority 为空字符串时视为“任意”，跳过该检查（第 110 行）。

由于 expected_authority 在模式中已是必需字段（有反序列化测试强制这一点），租户无法在不固定其签名者的情况下被接纳。第 217-218 行的注释解释了原因：Microdroid 并不在重放防护的实例规格中持久保存 authority 数据，因此 authority 必须在每次启动时随签名配置一同传递。

这一多租户 pVM 模型在 Android 17 上的具体消费者是 AiSeal —— 平台上的设备端 AI 宿主载荷封装环境。其在虚拟机内运行的原生宿主服务位于 frameworks/native/services/aisealhostservice/。该服务加载一份 VmPayloadConfig 以及一份列出租户的 AiSealPayloadConfig。宿主机经 vsock 访问这些租户的 exported_services（aisealhostservice/src/config.rs、aisealhostservice/src/main.rs）。

该虚拟机默认受保护。这由 service.aiseal.protected_vm 属性控制（config.rs 中的 AISEAL_PROTECTED_VM_FLAG，默认为 true）。在受保护虚拟机不可用的场合（例如 Cuttlefish，见 56.1.5 节），该属性可用于选择非受保护虚拟机。AiSeal 的框架与 API 面，以及其按用户处理的密钥管理，见第 51 章。

56.28 以受保护虚拟机形态运行的 Trusty

Android 17 允许 Trusty（参考可信执行环境操作系统）以 pVM 形态运行，而不再局限于 TrustZone 的安全世界。一个“Trusty pVM”就是由 AVF 管理的受保护虚拟机，运行 Trusty 内核及其内置的可信应用（TA）。pKVM 把它与宿主机隔离，方式与 Microdroid 完全相同。设计文档见 packages/modules/Virtualization/guest/trusty/docs/trusty_vm.md。

56.28.1 为什么在 pVM 中运行 TEE

把一个 TEE 负载迁入 pVM，可获得由 pKVM 强制的内存边界与基于 DICE 的身份，而无需占用稀缺的安全世界资源。为在 AVF 环境中工作，Trusty 内核被扩展了若干能力（trusty_vm.md，第 10-35 行）：

  • 基于 PCI 的 Virtio-vsock，用于宿主机到虚拟机的通信。
  • Virtio-vsock over virtio-msg over FF-A，这条通道让 Trusty pVM 能经 Arm 固件框架（Firmware Framework for Arm，FF-A）与 TrustZone 安全分区通信。FF-A 的内存共享让宿主内核不进入通信缓冲区，因此该通道能抵御宿主机的信息泄露攻击。
  • 设备树解析，包括承载 DICE 链的 pvmfw 内存区域，该链赋予 pVM 可验证身份。
  • PSCI 用于 CPU 开关管理，ARM TRNG 用于熵。

56.28.2 构建并签名 Trusty 载荷

Trusty pVM 镜像是一个已签名的单一 ELF。Trusty 内核及其全部 TA 都被打包进去，因为 Trusty pVM 目前还不支持动态加载 TA（trusty_vm.md，第 228-231 行）。该镜像由一串 Soong 规则生成（trusty_vm.md，第 37-121 行）：

  1. 一个 genrule（例如 trusty_security_vm_arm64.bin）把 Trusty 编译成裸二进制。
  2. 一条 avb_add_hash_footer 规则（trusty_security_vm_signed_bin）为它签名并加上 pvmfw 脚注。关键参数是 private_key（AOSP 中为 :avb_testkey_rsa4096，量产时重新签名）与作为 AVB 域分隔符的 partition_name: "boot"。其他参数包括用于可复现构建的固定公共 salt、由 platform_security_patch_timestamp 设定的 rollback_index，以及含 com.android.virt.cap 与 com.android.virt.name 的 props。
  3. 一条 cc_genrule/cc_object/cc_binary 链把已签名的数据块包进 crosvm 能加载的 ELF，并经 prebuilt_etc 安装为 trusty_security_vm.elf。

com.android.virt.name 属性是签名内唯一由 AVF 管理的值。正如 trusty_vm.md 所述（第 96-101 行），这能防止恶意宿主机让两台 Trusty 虚拟机在基于 DICE 的认证中互相冒充 —— 即便两台虚拟机由同一把密钥签名，也是如此。

56.28.3 启动器及其 CLI

该 pVM 由 packages/modules/Virtualization/guest/trusty/security_vm/launcher 下的 trusty_security_vm_launcher 二进制启动；它是一个 Rust 服务，通常由设备启动时运行的 .rc 文件调起。其参数解析位于 .../launcher/src/main.rs；它构建的 VmConfig 与 run_vm() 入口点位于 .../launcher/src/lib.rs（vm_launcher crate，结构体在第 35 行，run_vm 在第 74 行）。

CLI 标志（main.rs，第 35-83 行）包括 --kernel（已签名 ELF）、--protected、--name、--memory-size-mib、--rpc-services-config（可重复）、--cpu-topology（one-cpu 或 match-host）、--vm-instance-id 与 --allow-ffa。其中 FF-A 标志比较特殊：设置后，启动器会把它转换成一个单独的 TEE 服务请求，即 main.rs 第 33 行定义的 guest_ffa_tee_service 常量（第 138-141 行）：

let tee_services = match args.allow_ffa {
    true => vec![GUEST_FFA_TEE_SERVICE.to_owned()],

};

56.28.4 实例身份、RPC 服务与早期启动

Trusty pVM 使用一个静态定义的 64 字节实例 ID，由 gen_instance_id_for_vm_with_trusted_hal.py 依据诸如 .../launcher/security_vm_instance_id_config.json 的 JSON 配置生成（trusty_vm.md，第 181-220 行）。对 security VM 而言，该配置将其标记为持久（"is_vm_persistent": true）、固定到 "system" 分区，并赋予固定的 vm_primary_uuid。宿主机始终提供实例 ID，而它只是 DICE 链的一项输入，本身从不构成安全保证。

启动器充当 pVM 经 BinderRPC 实现的各种 AIDL 服务的访问器（accessor）。每个服务在 --rpc-services-config 的一条 JSON 项中描述，含 port、accessor_name 与 internal_rpc_service_name（main.rs 中的 RpcServiceConfig，第 178-183 行）。匹配的 IAccessor 实例在 .rc 文件中声明，好让宿主进程能发现它们。register_accessor_service()（main.rs，第 192-206 行）调用 createAccessorBinder 并把结果注册进 service manager。

必须在 /data 挂载之前运行的安全虚拟机使用早期启动。它们从 early-VM 范围取一个固定 CID。安装在 /system_ext/etc/avf/ 下的 early_vms.xml 把它们映射到各自的启动器，由 early_virtmgr 为其提供服务（trusty_vm.md，第 291-310 行；另见 56.6.11 节）。

56.29 pVM 的 TEE 服务访问

上面提到的 Trusty FF-A 通道，是 Android 17 中一项更通用机制的实例：受保护虚拟机需事先声明它可以访问哪些可信执行环境服务。宿主机不能悄悄给 pVM 授予安全世界访问权；访问由 SELinux 把关，对厂商服务还额外由 HAL 把关。

56.29.1 在配置上声明 TEE 服务

TEE 服务通过虚拟机的 raw 配置请求。AIDL 字段是 packages/modules/Virtualization/android/virtualizationservice/aidl/android/system/virtualizationservice/VirtualMachineRawConfig.aidl 中的 String[] teeServices（第 141 行），并在 VirtualMachineAppConfig.aidl（第 149 行）中镜像定义。

原生客户端经 Android 17 引入的 libavf LLNDK 中的 AVirtualMachineRawConfig_addTeeService 填充该字段。其声明位于 packages/modules/Virtualization/libs/libavf/include/android/virtualization.h （第 238-239 行，__INTRODUCED_IN(37)）。实现在 .../libs/libavf/src/lib.rs（第 326-339 行），它会校验 UTF-8 字符串并将其推入 config.teeServices。该头文件说明了相关约束：

TEE 服务仅受支持于受保护虚拟机。尝试在非受保护虚拟机上使用 TEE 服务会使 AVirtualMachine_createRaw 失败。……厂商自定义的 TEE 服务必须以 vendor. 为前缀。

服务名必须匹配某个 tee_service_contexts SELinux 文件中的标签（例如 /system/etc/selinux/plat_tee_service_contexts 或厂商对应的等价文件）。这使 TEE 服务名成为一种受策略控制的能力，而非可以任意填写的字符串。

56.29.2 SELinux 把关与厂商 HAL 交接

创建虚拟机时，virtmgr 强制执行策略。在 packages/modules/Virtualization/android/virtmgr/src/virtualmachine.rs （第 704-726 行）中，它先拒绝非受保护虚拟机上的 TEE 服务，然后调用 check_tee_service_permission(&caller_secontext, &config.teeServices)。该函数位于 .../virtmgr/src/selinux.rs（第 231-242 行），经 TeeServiceSelinuxBackend（封装 selinux_android_tee_service_context_handle，第 125-142 行）把每个服务名解析为其 SELinux 上下文，再用 tee_service 类与 use 权限检查调用者：

for tee_service in tee_services {
    let tee_service_ctx = backend.lookup(tee_service)?;
    check_access(caller_ctx, &tee_service_ctx, "tee_service", "use")
        .with_context(|| format!("permission denied for {tee_service:?}"))?;
}

此后内置服务与 vendor. 前缀服务走上不同路径。唯一的内置服务是 guest_ffa_tee_service，crosvm 会把它转换为 --ffa=auto 参数（.../virtmgr/src/crosvm.rs，第 1176-1189 行）。这就是 56.28 节所述的 Trusty FF-A 路径。

厂商服务需要 IVmCapabilitiesService HAL（56.7.1 节）。virtmgr 把它们单独挑出（virtualmachine.rs，第 714-719 行），若 HAL 缺失则拒绝启动（第 721-726 行）。

存在厂商服务时，虚拟机以挂起状态启动（start_suspended: !vendor_tee_services.is_empty()，第 817 行）。随后 virtmgr 在 HAL 上调用 grantAccessToVendorTeeServices(vm_pfd, vendor_tee_services)（handle_vendor_tee_services_internal，第 1504-1516 行），之后才用 resume_full() 恢复虚拟机（第 1519 行）。这就是 56.7.4 节所示能力授予序列背后的具体实现。

56.30 guest 内的 Linux 虚拟机管理

56.15 节中带图形加速的 Linux 虚拟机需要一个小型 guest 内代理，以便宿主机管理 guest 的生命周期。Android 17 新增了 linux_vm_manager —— 一个 host-tools 的 Rust 二进制，运行在 Debian guest 内部，并经 vsock 向宿主机暴露管理接口。其源码位于 packages/modules/Virtualization/guest/linux_vm_manager/。

56.30.1 经 vsock 回连宿主机

启动时（.../linux_vm_manager/src/main.rs），该管理器通过 RPC-binder 的 vsock 连接拨号到宿主机的 IVirtualMachineService。它用 vsock::get_local_cid() 读取自身 CID，并连接到 VMADDR_CID_HOST（get_vms_rpc_binder，第 31-40 行）：

let port = vsock::get_local_cid().context("Could not determine local CID")?;
let session = RpcSession::new();
session.set_max_incoming_threads(1);
session.setup_vsock_client(VMADDR_CID_HOST, port)

接着它启动一个 DebianService RPC 服务端，并经 service.registerGuestAgent(&guest_agent) 向宿主机注册 guest 内的 GuestAgent（main.rs，第 53-61 行）。该管理器刻意不做成静态可执行文件：其 Android.bp 警告 static_executable: true 会让 binder 运行时以 SIGSEGV 崩溃。该管理器引入了 AVF 其他地方已在使用的若干辅助 crate（forwarder_guest_launcher、shutdown_runner、storage_balloon_agent），它们让 guest 能转发端口、对存储做气球操作并干净关机。

56.30.2 IGuestAgent 接口

该代理实现 IGuestAgent，接口定义在 packages/modules/Virtualization/android/virtualizationservice/aidl/android/system/virtualizationcommon/IGuestAgent.aidl。Linux 虚拟机管理器的实现在 .../linux_vm_manager/src/guest_agent.rs（第 32-39 行），目前接通了优雅关闭路径：

impl IGuestAgent for GuestAgent {
    fn shutdownAsync(&self) -> BinderResult<()> {
        shutdown_runner::power_off().map_err(|e| { /* ... */ })
    }
}

registerGuestAgent 是 IVirtualMachineService 的第 1 号方法 （.../aidl/android/system/virtualmachineservice/IVirtualMachineService.aidl，第 37 行）；宿主机经 IVirtualMachine.getGuestAgent() 暴露已注册的代理，并通过 IVirtualMachineCallback.onGuestAgentRegistered(cid, guestAgent) 通知回调。此后宿主机便可驱动 guest：在同一条 vsock binder 通道上调用 IGuestAgent 的 shutdownAsync()、trimAsync() 以及用户生命周期钩子（userUnlocked、userLocked、userRemoved）。注意 linux_vm_manager 是针对 _non_microdroid 的 AIDL 变体（android.system.virtualmachineservice_non_microdroid、 android.system.virtualizationcommon_non_microdroid）构建的，反映它运行在完整 Linux guest 而非 Microdroid 中。

小结

Android 虚拟化框架代表了 Android 安全架构的一次根本性转变，把硬件支持的机密计算带到移动设备上。各关键组件协同工作，构成一个完整的虚拟化生态：

  • EL2 上的 pKVM 提供基础的内存隔离保证
  • pvmfw 在每台受保护虚拟机内建立信任根
  • crosvm 以每设备沙箱的方式管理虚拟机
  • Microdroid 为 VM 载荷提供最小 Android 运行时
  • VirtualizationService 从用户态编排整个生命周期
  • DICE 背书 提供从 ROM 到载荷的密码学信任链

该框架以纵深防御为设计原则：即便宿主内核被攻破，受保护虚拟机的机密仍然安全。crosvm 与 pvmfw 都以 Rust 实现，在最关乎安全的组件中提供内存安全保证。

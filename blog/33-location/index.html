第 33 章：定位服务

第 33 章：定位服务

定位服务是 Android 中隐私敏感度最高、同时又不可或缺的子系统之一。它把卫星接收机、蜂窝基站数据库、Wi-Fi 指纹定位引擎与传感器融合算法，统一在一个框架 API —— LocationManager —— 之后。它还施行一套多层次的权限模型，区分精确、粗略、前台与后台访问。本章逐层梳理整个栈：从公开的 SDK 接口出发，经过 LocationManagerService、GNSS HAL 的 AIDL 契约、融合与网络定位提供者、地理围栏和地理编码，最后到把位置转换为时区标识的 GeoTZ 模块。

本章描述的是 Android 17 状态下该子系统的样貌。在 Android 17 中，GNSS HAL 已演进到 AIDL 第 7 版；结构化的 GNSS 辅助接口在新硬件上取代了不透明的 PSDS 数据块；一系列特性标志的清理，使若干曾经实验性的行为（按人口密度粗化、GNSS 辅助注入）成为默认代码路径。

除特别说明外，所有源码路径均相对于 AOSP 根目录。

网络提供者的创建早于 GNSS 提供者，正如源码注释所述：

“network provider 应始终在 gps provider 之前初始化，因为 gps provider 对 network provider 存在一些不得已的硬依赖”

Android 17 改变了三处细节，值得在此指出：

  • GNSS 提供者可以是一个代理 overlay。 当 config_useGnssHardwareProvider 为 false 时，LMS 会先尝试通过 ProxyLocationProvider.create(..., ACTION_GNSS_PROVIDER, config_enableGnssLocationOverlay, ...) 绑定外部 GNSS 提供者；只有在没有安装 overlay 时才回退到进程内的 GnssLocationProvider。若确实存在 overlay，原始 HAL 仍会以 GPS_HARDWARE_PROVIDER 单独暴露（由 LOCATION_HARDWARE 保护）——原因是 GNSS HAL 只支持单一客户端。
  • 人口密度不再受标志门控。 ProxyPopulationDensityProvider 被无条件注册，原先用于门控的 population_density_provider 与 density_based_coarse_locations 标志已被清理。因此唯一的条件就是设备上是否存在该提供者服务（§33.5.8）。
  • GNSS 辅助代理移入 GNSS 子系统。 ProxyGnssAssistanceProvider 不再从 onSystemThirdPartyAppsCanStart() 绑定， 而是改为在 GnssManagerService.onSystemReady() 内注册（§33.10.5）。

33.2.3 提供者管理

添加提供者

void addLocationProviderManager(
        LocationProviderManager manager,
        @Nullable AbstractLocationProvider realProvider) {
    synchronized (mProviderManagers) {
        manager.startManager(this);

        if (realProvider != null) {
            // custom logic wrapping all non-passive providers
            if (manager != mPassiveManager) {
                int defaultStationaryThrottlingSetting =
                        mContext.getPackageManager().hasSystemFeature(
                            PackageManager.FEATURE_WATCH) ? 0 : 1;
                boolean enableStationaryThrottling = Settings.Global.getInt(
                        mContext.getContentResolver(),
                        Settings.Global.LOCATION_ENABLE_STATIONARY_THROTTLE,
                        defaultStationaryThrottlingSetting) != 0;
                // In Android 17 throttling is only ever applied to the GPS
                // provider, and only when keep_gnss_stationary_throttling is on.
                if (!(Flags.keepGnssStationaryThrottling() && enableStationaryThrottling
                        && GPS_PROVIDER.equals(manager.getName()))) {
                    enableStationaryThrottling = false;
                }
                if (enableStationaryThrottling) {
                    realProvider = new StationaryThrottlingLocationProvider(
                        manager.getName(), mInjector, realProvider);
                }
            }
            manager.setRealProvider(realProvider);
        }
        mProviderManagers.add(manager);
    }
}

StationaryThrottlingLocationProvider 这一装饰器的作用是：当设备处于 Doze 且加速度计表明设备静止时，降低定位频率。它不再向硬件索取新的定位结果，而是以较长的间隔重放最近已知位置。

这一门控逻辑在 Android 17 中得到了简化：旧的 Flags.disableStationaryThrottling() 标志被移除。该限流装饰器现在只应用于 GPS 提供者，且仅在 Flags.keepGnssStationaryThrottling() 启用并且 Settings.Global.LOCATION_ENABLE_STATIONARY_THROTTLE 设置为开时生效。

该设置在手机上默认为 1（开），在 Wear OS 设备（FEATURE_WATCH）上默认为 0（关）——原因是这类设备的小尺寸使静止检测不够可靠。换言之，网络与融合提供者不再被包装，这与早前版本相比是一处行为变化。

移除提供者

private void removeLocationProviderManager(LocationProviderManager manager) {
    synchronized (mProviderManagers) {
        mProviderManagers.remove(manager);
        manager.setMockProvider(null);
        manager.setRealProvider(null);
        manager.stopManager();
    }
}

33.2.4 请求处理

当应用调用 LocationManager.requestLocationUpdates() 时，Binder 调用会抵达 registerLocationListener()：

validateLocationRequest() 会对每个字段做清洗与校验：

  1. WorkSource —— 需要 UPDATE_DEVICE_STATS 权限。
  2. 低功耗模式 —— 需要 LOCATION_HARDWARE 权限。
  3. 对 AppOps 隐藏 —— 需要 UPDATE_APP_OPS_STATS 权限。
  4. ADAS GNSS 绕过 —— 仅车机可用，且仅限 GPS 提供者。
  5. 忽略位置设置 —— 需要绕过类权限。

33.2.5 当前位置请求

getCurrentLocation() 是一次性请求的变体。LMS 把它转交给 LocationProviderManager.getCurrentLocation()，后者返回一个 ICancellationSignal，应用可用它取消尚在等待的请求。

33.2.6 最近已知位置

getLastLocation() 返回指定提供者最近缓存的 Location。它同样经过 LocationProviderManager.getLastLocation()，因而会施加相同的权限检查与粗略位置模糊处理。

33.2.7 定位设置

每个用户的定位启停状态由 Settings.Secure.LOCATION_MODE 管理。LMS 监听其变化：

mInjector.getSettingsHelper().addOnLocationEnabledChangedListener(
    this::onLocationModeChanged);

模式变化时，LMS 会：

  1. 使 LocationManager 的本地缓存失效。
  2. 记录该事件。

33.2.11 LPM 的注册类型

LPM 支持三类注册：

33.2.13 位置模糊处理的细节

向仅有粗略权限的客户端投递时，LocationFudger 会对真实位置做混淆。算法如下：

  1. 给真实坐标叠加一个缓慢漂移的随机偏移。该偏移在构造时由 SecureRandom 播种（实际效果等同于每次开机一个种子），并且每隔 OFFSET_UPDATE_INTERVAL_MS （1 小时）按 CHANGE_PER_INTERVAL（3%）微调一次。这样模糊后的位置既不完美静止，也不会比网格分辨率更快地泄露移动。
  2. 把偏移后的坐标吸附到网格上，网格单元宽度为 mAccuracyM。 该宽度来自 Settings.Secure，通过 SettingsHelper.getCoarseLocationAccuracyM() 读取，默认为 DEFAULT_COARSE_LOCATION_ACCURACY_M = 2000.0f（2 km），下限为 MIN_ACCURACY_M = 200.0f。
  3. 上报的位置就是吸附到网格后的位置，accuracy 设为 Math.max(mAccuracyM, originalAccuracy) —— 模糊后的精度绝不小于提供者原本上报的精度。

源码： frameworks/base/services/core/java/com/android/server/location/fudger/LocationFudger.java 以及 injector/SystemSettingsHelper.java。

自 Android 16 起，LocationFudger 也可以改用 S2 单元密度路径：LocationFudgerCache 会咨询 ProxyPopulationDensityProvider，为每个 S2 单元选定粗化级别。城市密集区单元更小（精度更高），乡村地区单元更大（隐私保护更强）。在 Android 17 中该路径不再受标志门控—— density_based_coarse_locations 与 population_density_provider 标志已被清理。因此，只要缓存已由非空的人口密度提供者填充，密度算法就会运行；否则回退到传统的网格算法。

33.3.5 辅助 GNSS（A-GNSS）

A-GNSS 通过向接收机提供轨道预测、参考时间与近似位置来缩短 TTFF。没有辅助信息时，冷启动可能需要 30–60 秒；有 A-GNSS 后，TTFF 可降到 5 秒以内。

AIDL 接口定义了几种辅助机制：

PSDS（Predicted Satellite Data Service，预测卫星数据服务）

PSDS 旧称 XTRA（高通专有名称），提供可覆盖数天的轨道预测文件，使接收机无需解调广播星历即可推算卫星位置。

NORMAL 2 标准轨道预测 1–3 天
REALTIME 3 实时改正 数分钟

private static final int EMERGENCY_LOCATION_UPDATE_DURATION_MULTIPLIER = 3;

// No-fix timeout: stop trying after 60 seconds without a fix
private static final int NO_FIX_TIMEOUT = 60 * 1000;

// GPS polling threshold: below this interval, leave GPS on continuously;
// above it, duty-cycle the hardware.  10s is typical for hot TTFF (~5s).
private static final int GPS_POLLING_THRESHOLD_INTERVAL = 10 * 1000;

// PSDS retry with exponential backoff: 5 min initial, 4 hours maximum
private static final long RETRY_INTERVAL = 5 * 60 * 1000;
private static final long MAX_RETRY_INTERVAL = 4 * 60 * 60 * 1000;

// Maximum batching length: 1 day
private static final long MAX_BATCH_LENGTH_MS = DateUtils.DAY_IN_MILLIS;

GPS 占空比轮转

当请求的定位间隔超过 GPS_POLLING_THRESHOLD_INTERVAL （10 秒）时，GnssLocationProvider 进入占空比模式：

  1. 定位阶段：GPS 硬件上电，开始捕获定位。
  2. 休眠阶段：GPS 硬件断电（或进入低功耗模式）。
  3. 唤醒闹钟：AlarmManager 闹钟触发，启动下一轮定位阶段。
stateDiagram-v2
    [*] --> Idle
    Idle --> Navigating : setRequest active
    Navigating --> FixObtained : onReportLocation
    FixObtained --> Hibernate : fixInterval > POLLING_THRESHOLD
    FixObtained --> Navigating : fixInterval <= POLLING_THRESHOLD
    Hibernate --> Navigating : AlarmManager wakeup
    Navigating --> Idle : setRequest inactive
    Navigating --> TimedOut : NO_FIX_TIMEOUT 60s
    TimedOut --> Hibernate : retry

即：初始为 Idle；setRequest 生效后进入 Navigating 开始定位；收到 onReportLocation 后转为 FixObtained；若定位间隔大于轮转阈值则进入 Hibernate 休眠，等到 AlarmManager 唤醒再回到 Navigating，若间隔不大于阈值则继续 Navigating；setRequest 失效则回到 Idle；60 秒内未获得定位会转为 TimedOut，重试时进入 Hibernate。

唤醒锁管理使用 mWakeLock（一个标记为 *location*:GnssLocationProvider 的 PARTIAL_WAKE_LOCK），以防设备在定位与投递过程中挂起。

定位附加数据

每次 GNSS 定位都会在 Bundle 中附带附加数据：

33.4 融合定位提供者

33.4.1 概述

融合定位提供者（FLP, Fused Location Provider）把来自 GNSS、Wi-Fi、蜂窝基站、气压计与惯性测量单元的各类信号，融合为一个最优的位置估计。在 Google 认证设备上，这由 Google Play Services（GMS）实现；在 AOSP 上，它是一个可插拔的绑定服务。

ProxyLocationProvider 类负责处理绑定外部定位服务时的诸多复杂之处，它借助 ServiceWatcher 完成：

  2. 以恰当的标志绑定该服务。
  3. 服务崩溃或被更新时自动重新绑定。
  4. 在 Binder 接口上搬运 ProviderRequest 对象。

33.4.7 静止限流

当设备处于静止状态（由加速度计检测）时， StationaryThrottlingLocationProvider 包装器会降低实际定位频率。这是一项功耗优化，FLP 也会与之配合。

源码： frameworks/base/services/core/java/com/android/server/location/provider/StationaryThrottlingLocationProvider.java

静止检测使用 DeviceStationaryHelper，它监视加速度计以判定持续静止。静止时：

  1. 合并后的请求间隔被拉长。
  2. 向底层提供者请求的定位次数减少。
  3. 电池消耗显著下降。

该特性由以下设置控制：

Settings.Global.LOCATION_ENABLE_STATIONARY_THROTTLE

在手机上默认启用（1），而在 Wear OS 设备上默认关闭（0）——这类设备的小尺寸使静止检测不够可靠。

§33.2.3 已说明 Android 17 如何简化了这一门控：旧的 Flags.disableStationaryThrottling() 标志被移除， StationaryThrottlingLocationProvider 包装器现在仅应用于 GPS 提供者，且仅当 Flags.keepGnssStationaryThrottling() 开启且上述设置启用时才应用。因此融合提供者不再被包上这一限流装饰器；希望静止时限流的 FLP 实现现在改为在内部自行处理。

33.4.8 海拔换算

Android 提供了 AltitudeConverter（位于 android.location.altitude），它使用大地水准面模型把 GPS 椭球高（WGS84）换算为平均海平面（MSL）高度。大地水准面高度来自随包内置的 S2 单元地图（MapParamsProto，以 S2CellIdUtils 为键），并非来自 HAL。同一个换算器已集成进 LocationProviderManager 的定位投递流水线，因此读取 Location.getMslAltitudeMeters() 的应用能拿到有效值。

这一换算之所以重要，是因为 GPS 接收机原生上报的是相对 WGS84 椭球的高度，而该高度在某些地点与真实海拔可能相差上百米。向用户展示海拔的应用需要 MSL 高度才有意义。

AltitudeService 是这一能力在 system-server 侧的体现：它是一个 IAltitudeService.Stub（由 SystemServer 中的 AltitudeService.Lifecycle 发布），暴露 addMslAltitudeToLocation() 与 getGeoidHeight()，使厂商 HAL 客户端也能请求同样的框架侧大地水准面换算；两个方法都委托给 AltitudeConverter。方向是框架向厂商提供换算服务，而非框架从 HAL 读取大地水准面高度。Android 17 中定义了 geoid_heights_via_altitude_hal 标志，以便通过 Altitude HAL 提供大地水准面高度，但尚未接入该服务。

源码： frameworks/base/services/core/java/com/android/server/location/altitude/AltitudeService.java

33.5.3 蜂窝基站定位

NLP 通过 TelephonyManager 获取当前 CellInfo 列表，其中包含小区标识（MCC、MNC、LAC/TAC、CID）。这些标识会与数据库（本地或服务端）比对，得出近似位置。

33.5.4 Wi-Fi 定位

NLP 触发 Wi-Fi 扫描并收集 BSSID/RSSI 对，再与 Wi-Fi 指纹数据库匹配以三角定位。在城市环境中通常可达到 10–50 米的精度。

33.5.5 ProxyLocationProvider

ProxyLocationProvider 继承 AbstractLocationProvider，并用 ServiceWatcher 绑定外部服务。它把 ProviderRequest 对象搬运给所绑定的服务，并接收 LocationResult 回调。

源码： frameworks/base/services/core/java/com/android/server/location/provider/proxy/ProxyLocationProvider.java

33.5.6 ServiceWatcher 架构

NLP 与 FLP 共用同一套 ServiceWatcher 基础设施来完成服务发现与绑定。ServiceWatcher 提供：

  1. 基于 intent 的发现：查找匹配特定 action 的服务。
  2. Overlay 支持：配置资源 config_enableNetworkLocationOverlay 与 config_networkLocationProviderPackageName 允许 OEM 覆盖默认的提供者包。
  3. 版本选择：多个服务匹配时，选择版本最高的。
  4. 以当前用户绑定：服务在当前用户的上下文中绑定。
  5. 自动重连：服务消亡时，ServiceWatcher 会自动重新绑定。

33.5.7 MockableLocationProvider

每个真实提供者都被包在一个 MockableLocationProvider 里，从而可以在测试时无缝注入模拟位置。当调用 setMockProvider() 时，MockableLocationProvider 会把所有请求改道至 MockLocationProvider，而非真实提供者。

graph LR
    LPM[LocationProviderManager] --> MLP[MockableLocationProvider]
    MLP -->|normal| RP["RealProvider<br>ProxyLocationProvider"]
    MLP -->|mock mode| MP[MockLocationProvider]

这一架构意味着模拟位置会走与真实位置完全相同的投递流水线——同样的权限检查、同样的模糊处理、同样的间隔限制。

33.5.8 人口密度提供者

Android 16 引入了 ProxyPopulationDensityProvider，通过如下方式绑定：

setProxyPopulationDensityProvider(
        ProxyPopulationDensityProvider.createAndRegister(mContext));

该提供者提供人口密度数据，供 LocationFudgerCache 实现基于密度的粗略位置模糊。在人口密度高的地区（城市），模糊单元更小，使粗略定位应用仍保有合理的可用性；在乡村地区，单元更大，以提供更强的隐私保证。

在 Android 17 中，这一绑定是无条件的——原先用于门控的 population_density_provider 与 density_based_coarse_locations 标志已被清理，唯一的检查是设备是否随附了人口密度提供者服务。若 createAndRegister() 返回非 null，LMS 会在其上安装 LocationFudgerCache，密度算法随之运行；否则回退到传统网格算法（§33.2.13）。LMS 还会连同加载耗时一起记录 POPULATION_DENSITY_PROVIDER_LOADING_REPORTED。

源码： frameworks/base/services/core/java/com/android/server/location/provider/proxy/ProxyPopulationDensityProvider.java

33.6 地理围栏

地理围栏（geofencing）允许应用定义地理区域，并在设备进入或离开这些区域时接收通知。Android 支持两层地理围栏：软件实现（位于 GeofenceManager）与硬件加速实现（经由 GNSS HAL）。

地理围栏状态机

stateDiagram-v2
    [*] --> UNKNOWN : registered
    UNKNOWN --> INSIDE : distance <= radius
    UNKNOWN --> OUTSIDE : distance > radius

    OUTSIDE --> INSIDE : distance <= radius

即：注册后初始状态为 UNKNOWN；距离不大于半径则转为 INSIDE，大于半径则转为 OUTSIDE；此后距离跨过半径会在 INSIDE 与 OUTSIDE 之间来回转换；围栏过期或被移除时，两种状态都直接结束。

33.7 地理编码

地理编码（geocoding）在人类可读地址与地理坐标之间做转换。Android 通过 Geocoder 类同时提供正向地理编码（地址转经纬度）与反向地理编码（经纬度转地址）。

33.7.1 客户端 API

Geocoder geocoder = new Geocoder(context, Locale.getDefault());

// Reverse geocode (non-blocking; preferred form)
geocoder.getFromLocation(lat, lng, maxResults, addresses -> { /* ... */ });

// Forward geocode (non-blocking; preferred form)
geocoder.getFromLocationName("1600 Amphitheatre Pkwy", 1,
        addresses -> { /* ... */ });

阻塞式重载 getFromLocation(lat, lng, maxResults) 与 getFromLocationName(name, maxResults) 仍然存在，但已因 GeocodeListener 回调形式而废弃。回调形式在请求经 Binder 跨越到地理编码提供者期间不会阻塞调用线程；内部实现上，已废弃的重载会调用监听器变体并在一个 SynchronousGeocoder 上等待。

源码： frameworks/base/location/java/android/location/Geocoder.java。

33.7.2 服务端实现

Geocoder 类把请求委托给 ILocationManager.reverseGeocode() 与 ILocationManager.forwardGeocode()，两者再转交给一个 ProxyGeocodeProvider：

33.7.3 可用性

Geocoder.isPresent() 只有在已绑定地理编码提供者服务时才返回 true。在没有 GMS 的 AOSP 上它可能返回 false，此时地理编码调用会优雅地失败。

33.7.4 正向地理编码流程

正向地理编码（地址转坐标）走相似的路径：

33.8.2 LocationPermissions 工具类

源码： frameworks/base/services/core/java/com/android/server/location/LocationPermissions.java

LocationPermissions 类定义三个权限级别：

public static final int PERMISSION_COARSE = 1;
public static final int PERMISSION_FINE   = 2;

getPermissionLevel() 方法按由高到低的顺序检查权限：

public static int getPermissionLevel(Context context, int uid, int pid) {
    if (context.checkPermission(ACCESS_FINE_LOCATION, pid, uid) == GRANTED) {
        return PERMISSION_FINE;
    }
    if (context.checkPermission(ACCESS_COARSE_LOCATION, pid, uid) == GRANTED) {
        return PERMISSION_COARSE;
    }
    return PERMISSION_NONE;
}

33.8.3 精确位置与粗略位置

方面 精确 粗略
权限 ACCESS_FINE_LOCATION ACCESS_COARSE_LOCATION
精度 精确的 GPS 坐标 模糊到约 2 公里网格（默认）
提供者访问 所有提供者 所有提供者（结果被模糊）
GNSS 原始数据 有 无

当应用只持有 ACCESS_COARSE_LOCATION 时，LocationProviderManager 会施加 LocationFudger 来混淆精确位置。模糊处理会叠加一个缓慢漂移的随机偏移，然后把结果吸附到网格上，网格宽度默认 2 公里（ DEFAULT_COARSE_LOCATION_ACCURACY_M，下限 200 米）。因此小幅移动时模糊后的位置保持稳定（§33.2.13）。

自 Android 16 起还提供了基于人口密度的模糊模式：由 ProxyPopulationDensityProvider 提供密度数据， LocationFudgerCache 依据密度选定 S2 单元的粗化级别——乡村地区单元更大，密集城区单元更小。截至 Android 17，该模式不再受标志门控（ density_based_coarse_locations 与 population_density_provider 已被清理）；只要存在人口密度提供者，它就会运行。

33.8.4 后台位置

从 Android 10（API 29）起，ACCESS_BACKGROUND_LOCATION 成为一项独立权限。应用必须持有它，才能在前台之外接收位置更新。该权限在运行时权限对话框中作为单独一步授予。

后台限流机制通过 SettingsHelper 实现：

mInjector.getSettingsHelper().getBackgroundThrottlePackageWhitelist()

被列入白名单的系统豁免包不受后台限流约束。

33.8.5 定位绕过

系统组件（例如紧急拨号器、车机定位服务）即使用户已关闭定位设置，也可能仍需要位置。LOCATION_BYPASS 权限即授予这一能力：

public static void enforceBypassPermission(Context context, int uid, int pid) {
    if (context.checkPermission(LOCATION_BYPASS, pid, uid) == GRANTED) {
        return;
    }
    throw new SecurityException(...);
}

在 Android 17 中，这一强制检查是纯粹的权限检查，没有任何标志门控： location_bypass 标志（仍定义在 location.aconfig 中）在运行时已不再被咨询，旧的 enable_location_bypass 标志已被移除。另有一项独立的 READ_LOCATION_BYPASS_ALLOWLIST 权限用于保护绕过白名单的读取（LocationPermissions.enforceReadLocationBypassAllowlist*）。

源码： frameworks/base/services/core/java/com/android/server/location/LocationPermissions.java。

绕过也延伸到车机设备上的 ADAS（高级驾驶辅助系统）——即便定位已关闭，它们仍可访问 GPS：

if (request.isAdasGnssBypass()) {
    if (!mContext.getPackageManager().hasSystemFeature(FEATURE_AUTOMOTIVE)) {
        throw new IllegalArgumentException(
            "adas gnss bypass requests are only allowed on automotive devices");
    }
}

33.8.6 AppOps 集成

除运行时权限之外，位置访问还受 AppOps 门控。 AppOpsHelper 跟踪 OP_FINE_LOCATION 与 OP_COARSE_LOCATION 操作，使用户可以在设置中针对特定应用撤销位置访问，而不必彻底移除权限。

33.8.7 紧急定位

在紧急呼叫（例如 E911）期间，Android 会放宽位置限制。 EmergencyHelper 跟踪紧急状态，LMS 通过以下方式检查：

mInjector.getEmergencyHelper().isInEmergency(Long.MIN_VALUE)

GNSS HAL 回调在框架侧的 LocationRequestCallbacks 上体现为 onRequestLocation(independentFromGnss, isUserEmergency)，把紧急标志从硬件层逐级向上传递。

Android 17 收紧了紧急状态与 AppOps 限制之间的交互方式，通过若干标志实现： fix_app_ops_restriction_for_emergency_mode 在紧急状态切换时刷新 AppOps 限制（使忽略设置的允许名单只在紧急模式下被排除）； cache_emergency_callback_mode 缓存紧急回调模式的广播取值，避免在热路径上查询 TelephonyManager； check_bypass_permission_before_emergency_mode 先检查绕过权限，以跳过一次不必要的 IPC。

从 Android 10（API 29）起，需要持续后台定位的应用必须使用类型为 location （FOREGROUND_SERVICE_TYPE_LOCATION）的前台服务。随后 Android 12 又对从后台启动此类服务施加了限制。LMS 跟踪前台服务 API 的使用情况：

33.8.10 PendingIntent 的安全性

基于 PendingIntent 的定位请求还要受到额外限制。由于 PendingIntent 注册之后无法再对应用跟踪权限变化（其进程可能已消亡），系统 API 会被禁止：

if (isChangeEnabled(BLOCK_PENDING_INTENT_SYSTEM_API_USAGE, identity.getUid())) {
    boolean usesSystemApi = request.isLowPower()
            || request.isHiddenFromAppOps()
            || request.isLocationSettingsIgnored()
            || !request.getWorkSource().isEmpty();
    if (usesSystemApi) {
        throw new SecurityException(
            "PendingIntent location requests may not use system APIs: " + request);
    }
}

33.8.11 定位指示器

Android 12 引入了常驻指示器，用于显示应用何时在访问定位。AppOpsManager 跟踪位置操作，当任何应用持有活跃的位置 note 时，SystemUI 会在状态栏显示绿点或相应图标。

LocationManagerService.onSystemReady() 会向 AppOpsManager 注册一个监视器：

// Track OP_FINE_LOCATION and OP_COARSE_LOCATION
appOps.startWatchingNoted(
    new int[]{AppOpsManager.OP_FINE_LOCATION, AppOpsManager.OP_COARSE_LOCATION},

该监视器仅在调试构建上安装，用于发现“定位已关闭却仍有位置操作”这类框架缺陷。

33.8.12 归因标签

Android 11 引入了归因标签（attribution tag），用于在单个包内更细粒度地跟踪定位使用情况。贯穿定位服务的 CallerIdentity 包含该归因标签：

CallerIdentity identity = CallerIdentity.fromBinder(

33.9.4 OfflineLocationTimeZoneDelegate

源码： packages/modules/GeoTZ/locationtzprovider/src/main/java/com/android/timezone/location/provider/core/OfflineLocationTimeZoneDelegate.java

这是 GeoTZ 提供者的核心逻辑，围绕两个正交维度构建。粗粒度生命周期是一个四值 Mode 枚举（ MODE_STOPPED=1、MODE_STARTED=2、MODE_DESTROYED=3、MODE_FAILED=4， 定义于 .../provider/core/Mode.java）。只有在 MODE_STARTED 时，第二个字段 mListenMode 才会在 LOCATION_LISTEN_MODE_ACTIVE 与 LOCATION_LISTEN_MODE_PASSIVE 之间选择：

stateDiagram-v2
    [*] --> MODE_STOPPED
    MODE_STOPPED --> MODE_STARTED : onStartUpdates
    state MODE_STARTED {
        [*] --> ACTIVE
        ACTIVE --> PASSIVE : location received / active budget spent
        PASSIVE --> ACTIVE : passive timeout, no location
        PASSIVE --> PASSIVE : location received, stay passive
    }
    MODE_STARTED --> MODE_STOPPED : onStopUpdates
    MODE_STARTED --> MODE_FAILED : IOException
    MODE_STOPPED --> MODE_DESTROYED : onDestroy

即：初始为 MODE_STOPPED，onStartUpdates 后进入 MODE_STARTED；在 MODE_STARTED 内部先处于 ACTIVE，收到位置或主动监听预算耗尽后转为 PASSIVE，被动超时仍无位置则回到 ACTIVE，被动期间收到位置则继续保持 PASSIVE；onStopUpdates 回到 MODE_STOPPED，遇到 IOException 转为 MODE_FAILED，onDestroy 后转为 MODE_DESTROYED。

ACTIVE 监听模式（LOCATION_LISTEN_MODE_ACTIVE）：

  • 短时长、高功耗的监听。
  • 可能激活 GNSS。
  • 只返回一个位置，或返回“位置未知”结果。

PASSIVE 监听模式（LOCATION_LISTEN_MODE_PASSIVE）：

  • 长时长、低功耗的监听。
  • 只接收机会性（opportunistic）位置更新。
  • 不保证能收到位置。

LocationListeningAccountant 管理一套预算机制：

  1. 被动监听会累积主动监听预算。
  2. 主动监听消耗预算。
  3. 这样可确保该提供者不会把绝大部分时间花在被动模式上，从而滥用 GNSS 功耗。

33.9.7 S2 几何存储

s2storage 与 tzs2storage 库基于 Google 的 S2 Geometry 库实现高效空间索引。S2 单元把地球表面划分为层次化网格：某一层级上的每个单元覆盖一块固定面积，二进制文件则把单元 ID 映射到时区标识集合。

这种方式有若干优点：

  • 紧凑：tzs2.dat 文件只有几兆字节。
  • 查找快：对单元 ID 做 O(log n) 二分查找。
  • 离线：无需网络访问。
  • 可更新：可通过 APEX 模块更新机制 替换该文件。

33.9.8 GeoDataFileManager

GeoDataFileManager 负责加载并缓存设备上的 tzs2.dat 文件。该文件打包在 GeoTZ APEX 模块内：

/apex/com.android.geotz/etc/tzs2.dat

当 APEX 通过 Mainline 更新时，数据文件会自动刷新，无需完整 OTA。这一点至关重要，因为时区边界会定期变化（国家偶尔会调整本国时区或修改夏令时规则）。

33.9.9 错误处理与容错

该委托处理若干失败场景：

  1. 初始化超时：若在初始化时段内没有拿到位置，则上报“不确定”结果， time_zone_detector 转而使用其他来源。

  2. 查找过程中的 IOException：若 tzs2.dat 文件损坏或缺失，委托进入 MODE_FAILED 并上报永久失败。

  3. 被动模式下位置不可用：委托可能切换到主动监听（消耗预算）以获取定位。这种情形发生在被动监听超时且始终没有位置到达时。

  4. 用户切换：当前用户变化时会调用 onStopUpdates()，委托清空所有位置状态，防止跨用户的位置泄露。

33.9.11 与时区检测的集成

GeoTZ 提供者是 Android time_zone_detector 服务所消费的若干信号之一。该检测器会权衡来自以下来源的建议：

  1. 电话（基于 MCC）。
  2. 位置（GeoTZ）。
  3. 用户手动选择。

在蜂窝基站横跨多个时区的地区（例如边境附近），基于位置的提供者优先级高于电话。

GeoTZ 在如下地区尤其有价值：

  • 印度/尼泊尔边境：印度全国采用单一时区（IST，UTC+5:30）， 而尼泊尔使用 UTC+5:45。
  • 中国/中亚边境：中国采用单一时区，而 邻国各有不同偏移。
  • 美国州界：亚利桑那州不实行夏令时， 而相邻各州实行。

33.10.5 GNSS 辅助（结构化接口）

结构化 GNSS 辅助机制通过 IGnssAssistanceInterface HAL 暴露（经由 IGnss.getExtensionGnssAssistanceInterface() 取得）。该 HAL 最早出现在 GNSS HAL V5，属于 Android 17（V7）接口面的一部分；它以强类型的辅助模型补充了传统的不透明 PSDS 方式。

在 Android 17 中，注册是无条件的——原先用于门控 JNI 路径的 gnss_assistance_interface_jni 标志已被移除。因此 GnssManagerService.onSystemReady() 直接绑定代理提供者，若其存在则注册辅助回调：

public void onSystemReady() {
    mGnssLocationProvider.onSystemReady();
    mProxyGnssAssistanceProvider =
            ProxyGnssAssistanceProvider.createAndRegister(mContext);
    if (mProxyGnssAssistanceProvider == null) {
        Log.e(TAG, "no gnss assistance provider found");
    } else {
        mGnssNative.setGnssAssistanceCallbacks(this);
    }
}

源码： frameworks/base/services/core/java/com/android/server/location/gnss/GnssManagerService.java， onSystemReady()（第 106–115 行）。

当 HAL 触发 GnssAssistanceCallbacks.onRequestGnssAssistanceInject() 时， GnssManagerService 会向代理提供者查询一个 GnssAssistance 对象。 HAL 的 GnssAssistance parcelable 按星座嵌套辅助数据 （GpsAssistance、GalileoAssistance、GlonassAssistance、QzssAssistance、 BeidouAssistance），外加一个可选的 IonexAssistance。

每个按星座组织的记录都引用自己的星历 parcelable （GpsSatelliteEphemeris、GalileoSatelliteEphemeris、 BeidouSatelliteEphemeris、GlonassSatelliteEphemeris、 QzssSatelliteEphemeris），还引用历书 （GnssAlmanac/GlonassAlmanac）与电离层模型 （KlobucharIonosphericModel、GalileoIonosphericModel），以及 LeapSecondsModel、UtcModel、TimeModel、RealTimeIntegrityModel 与 AuxiliaryInformation。相比不透明的 PSDS 二进制数据块，这种结构化格式能实现更细粒度、更高效的辅助数据投递。Android 17 还为相应的 IonexAssistance 与历书“适用时刻”字段新增了 support_ionex_assistance 与 support_toa_in_gnss_satellite_almanac SDK 标志。

源码： hardware/interfaces/gnss/aidl/android/hardware/gnss/gnss_assistance/。

33.10.6 GNSS 批量上报

对于需要持续跟踪位置、又不希望应用处理器保持唤醒的应用（例如健身记录），GNSS HAL 通过 IGnssBatching 支持芯片内批量累积。

工作方式如下：

  1. 框架向 HAL 请求一个批量大小。
  2. 位置在 GNSS 芯片的内存中累积。
  3. 批量写满（或被要求冲刷）时，所有位置一次性投递。
  4. 两批之间应用处理器可以保持深度睡眠。

LMS 暴露了已废弃的批量 API（startGnssBatch、flushGnssBatch、 stopGnssBatch），其内部被映射为普通的 registerLocationListener 调用并带上 setMaxUpdateDelayMillis()：

registerLocationListener(
    GPS_PROVIDER,
    new LocationRequest.Builder(intervalMs)
        .setMaxUpdateDelayMillis(
            intervalMs * mGnssManagerService.getGnssBatchSize())
        .setHiddenFromAppOps(true)
        .build(),
    listener, packageName, attributionTag, listenerId);

33.10.9 Context Hub 集成

HardwareActivityRecognitionProxy（在 onSystemThirdPartyAppsCanStart 期间启动，除非设置了 Flags.disableHardwareAr()） 在定位服务与 Context Hub 之间架桥，用于硬件加速的活动识别。Android 17 新增了 §33.11.1 所述的 disable_hardware_ar 标志，可关闭这一遗留代码路径。

活动识别（步行、跑步、驾车等）所使用的传感器数据，与定位服务消费的数据相同。识别结果可以影响定位提供者的行为（例如 FLP 可能依据识别到的活动为不同来源赋予不同权重）。

Context Hub 本身也在该包中托管 （com.android.server.location.contexthub）。在 Android 17 中它获得了数据流／端点模型，并配有按连接的权限 PccAccessList。第 17 章（传感器与 Context Hub）介绍了这一模型。

33.11.2 新的 GNSS HAL 接口面（AIDL V7）

GNSS HAL 在 Android 17 中达到 V7（android.hardware.gnss-V7；兼容性矩阵接受第 2 至第 7 版）。可见的新增内容包括：

  • CAPABILITY_ENGINE_RESTART_AFTER_POWER_MODE_CHANGE（第 16 位）： 位于 IGnssCallback.aidl（§33.3.9），经 GnssCapabilities.hasGnssEngineRestartAfterPowerModeChange() 暴露，在 SDK 侧由 gnss_capability_restart_engine_after_power_mode_change 门控。
  • 位于 hardware/interfaces/gnss/aidl/android/hardware/gnss/gnss_assistance/ 下的结构化辅助 parcelable 新增了字段，并配有对应的 SDK 标志 support_ionex_assistance 与 support_toa_in_gnss_satellite_almanac（§33.10.5）。

33.11.3 新的 GNSS SDK API

Android 17 暴露了若干新的 GNSS SDK 接口面，每一处都置于 frameworks/base/location/java/android/location/flags/location.aconfig 中的某个标志之后：

标志 新 API
gnss_api_navic_l1 GnssNavigationMessage.TYPE_IRN_L1 = 0x0703（NavIC L1 导航电文），补充 TYPE_IRN_L5
support_codetype_in_gnss_status GnssStatus.hasCodeType()/getCodeType() 与 hasElapsedRealtimeNanos()/getElapsedRealtimeNanos()
gnss_qzss_svid_range_extension GnssStatus.getSvid() 的 QZSS 取值范围由 183–206 扩展到 183–212
gnss_capability_restart_engine_after_power_mode_change GnssCapabilities.hasGnssEngineRestartAfterPowerModeChange()

gnss_assistance_interface GnssAssistance、GnssAlmanac 与 IonexAssistance SDK 类

注意 QZSS SVID 的取值范围在各接口面之间并不一致：遗留的 GnssSvInfo HAL 文档与 GnssStatus 使用 183–212，而较新的 gnss_assistance parcelable 与 android.location.GnssAssistance 使用 183–206。

源码： frameworks/base/location/java/android/location/GnssStatus.java、 GnssNavigationMessage.java、GnssCapabilities.java、 GnssMeasurementRequest.java。

33.11.4 现代化的地理编码提供者接口面

new_geocoder 标志引入了结构化的提供者侧地理编码 API （android.location.provider.GeocodeProviderBase 以及 ForwardGeocodeRequest / ReverseGeocodeRequest parcelable），也就是 ProxyGeocodeProvider 所绑定的那套接口（§33.7.2）。在客户端侧，异步的 Geocoder.getFromLocation(..., GeocodeListener) / getFromLocationName(..., GeocodeListener) 重载现已成为首选形式，阻塞式重载则被标记为废弃（§33.7.1）。

33.11.5 紧急模式下 AppOps 的细化

Android 17 重做了紧急状态与 AppOps 限制、定位绕过路径之间的交互方式（§33.8.5、§33.8.7）：

  • fix_app_ops_restriction_for_emergency_mode 在紧急状态切换时刷新 AppOps 限制， 使“忽略设置”允许名单仅在紧急模式下被排除。
  • cache_emergency_callback_mode 缓存紧急回调模式的广播附加值， 而不是在热路径上查询 TelephonyManager。
  • check_bypass_permission_before_emergency_mode 在紧急模式检查之前 先检查绕过权限，以跳过一次不必要的 IPC。
  • 新增的 READ_LOCATION_BYPASS_ALLOWLIST 权限保护绕过允许名单的读取， 同时 change_get_adas_allowlist_from_hidden_to_system 标志把 getAdasAllowlist 从隐藏 API 提升为系统 API。

源码： frameworks/base/services/core/java/com/android/server/location/LocationManagerService.java 与 LocationPermissions.java。

33.12.11 练习 11：比较 GNSS 星座

写一个按星座分类卫星的应用：

lm.registerGnssStatusCallback(getMainExecutor(), new GnssStatus.Callback() {
    @Override
    public void onSatelliteStatusChanged(GnssStatus status) {
        Map<Integer, Integer> counts = new HashMap<>();
        Map<Integer, Integer> usedCounts = new HashMap<>();

        for (int i = 0; i < status.getSatelliteCount(); i++) {
            int type = status.getConstellationType(i);
            counts.merge(type, 1, Integer::sum);
            if (status.usedInFix(i)) {
                usedCounts.merge(type, 1, Integer::sum);
            }
        }

        for (var entry : counts.entrySet()) {
            String name = constellationName(entry.getKey());
            int total = entry.getValue();
            int used = usedCounts.getOrDefault(entry.getKey(), 0);
            Log.i("GNSS", name + ": " + used + "/" + total + " used in fix");
        }
    }

    String constellationName(int type) {
        switch (type) {
            case GnssStatus.CONSTELLATION_GPS: return "GPS";
            case GnssStatus.CONSTELLATION_GLONASS: return "GLONASS";
            case GnssStatus.CONSTELLATION_BEIDOU: return "BeiDou";
            case GnssStatus.CONSTELLATION_GALILEO: return "Galileo";
            case GnssStatus.CONSTELLATION_QZSS: return "QZSS";
            case GnssStatus.CONSTELLATION_IRNSS: return "IRNSS";
            case GnssStatus.CONSTELLATION_SBAS: return "SBAS";
            default: return "Unknown(" + type + ")";
        }
    }
});

小结

本章考察了 Android 的定位服务：从公开的 LocationManager API 出发，向下深入到 LocationManagerService 中的 system-server 实现、GNSS HAL 的 AIDL 契约，以及地理围栏、地理编码与时区检测等配套子系统。

关键架构要点如下：

  1. LocationProviderManager 中的请求复用把 数百个应用请求收敛为一次最优的硬件请求，直接以续航换精度。

  2. 提供者抽象（AbstractLocationProvider）把框架与多样化的定位技术清晰隔离。 卫星接收机、Wi-Fi 扫描器、蜂窝数据库与传感器 融合引擎，在同一个接口之后完全可互换。

  3. GNSS HAL（IGnss AIDL）提供了一套能力驱动的丰富接口，从基础定位 一直到适合厘米级定位的原始载波相位测量都能支持。

  4. 权限模型实现了纵深防御：运行时权限、AppOps、前台/后台区分、按用户 设置、紧急覆盖与 ADAS 绕过，在位置数据流上构成多道相互独立的闸门。

  5. 地理围栏在两层上运作：第一层是软件 GeofenceManager，它依据到围栏边界的距离动态调整轮询间隔；第二层是硬件 IGnssGeofence HAL，把边界监控卸载到 GNSS 芯片上，以实现最低功耗。

  6. GeoTZ 展示了 Android 的模块化架构。它是一个由 APEX 交付的模块，用离线 S2 几何数据库把位置转换为时区标识， 完全不依赖网络服务。其双模式监听策略（主动/被动 + 功耗预算） 正是贯穿整个定位子系统的能效范式的缩影。

  7. 地理编码完全是基于提供者的——框架只定义 API 契约，把所有实际地址解析 都委托给一个绑定服务，因此它可替换、且为可选。

  8. GnssConfiguration 中的运营商集成展示了 GNSS 行为如何随蜂窝环境自适应：SUPL 服务器地址、 LPP 配置档与紧急 PDN 设置都可由运营商配置。

  9. Android 17 主要通过“把实验变成默认”来推进该子系统：GNSS HAL 达到 AIDL V7（新增引擎重启能力与结构化辅助字段）；结构化 GNSS 辅助接口与基于人口密度的粗略位置模糊因门控标志被移除而成为无条件行为；静止限流 收窄到仅 GPS 提供者；新的 GNSS SDK 接口面（NavIC L1、GNSS 状态码型、QZSS SVID 扩展）以标志形式落地（§33.11）。

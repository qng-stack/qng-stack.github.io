第 59 章：架构支持

Android 运行的处理器架构范围，比任何其他主流操作系统都广。目标芯片从入门手机上低功耗的 ARM Cortex-A7，到旗舰设备里高性能的 Cortex-X4 核心；还包括 Chromebook 与模拟器中的 Intel x86，以及正在兴起的 RISC-V 生态。AOSP 构建系统必须为每一种目标产出正确且经过优化的代码。

本章逐层拆解架构支持究竟是怎么运作的：从 Soong 中选择编译参数的 toolchain 定义开始，经过 bionic libc 里针对具体 CPU 核心手工调优的汇编例程，最后到 ART 运行时中把托管 Java 代码与原生硬件接起来的 entrypoint。

理解这套机制对几类人都很重要。设备 bring-up 工程师需要新增一个 BoardConfig.mk，声明正确的 TARGET_ARCH 与 TARGET_CPU_VARIANT。性能工程师需要知道架构相关的热点路径在哪里，才能调优或替换它们。做构建系统的平台开发者则要理解三件事：Soong Toolchain 接口的分层设计、它的架构变体，以及 multilib 机制——后者让同一个 Android.bp 模块既能产出 32 位二进制，也能产出 64 位二进制。

59.1 支持的架构

AOSP 官方支持五种 CPU 架构，各自对应一个 Soong ArchType 和一个 Clang target triple。这五种架构通过 build/soong/cc/config/ 下各文件中的 registerToolchainFactory() 调用注册：

架构 Soong ArchType Clang Triple 设备配置文件 位宽
ARM（32 位） android.Arm armv7a-linux-androideabi arm_device.go 32
ARM64 android.Arm64 aarch64-linux-android arm64_device.go 64
x86（32 位） android.X86 i686-linux-android x86_device.go 32
x86_64 android.X86_64 x86_64-linux-android x86_64_device.go 64
RISC-V 64 android.Riscv64 riscv64-linux-android riscv64_device.go 64

每种架构在 build/soong/cc/config/ 下都有一个对应的 *_device.go 文件，用来定义该架构专属的编译参数、CPU 变体调优与链接参数。这五个文件，加上共享的 global.go、toolchain.go、clang.go 与 bionic.go，共同构成 AOSP 交叉编译基础设施的基础。

59.1.1 架构注册流程

每种架构都在 Go 包初始化阶段把自己注册到构建系统。五种架构的写法完全一致。下面是 arm64_device.go 中的注册：

// build/soong/cc/config/arm64_device.go
func init() {
    registerToolchainFactory(android.Android, android.Arm64, arm64ToolchainFactory)
}

以及 riscv64_device.go 中对应的注册：

// build/soong/cc/config/riscv64_device.go
func init() {
    registerToolchainFactory(android.Android, android.Riscv64, riscv64ToolchainFactory)
}

toolchain.go 中的 registerToolchainFactory 把这些工厂存进一个 map。该 map 以操作系统类型、架构类型和一个布尔值为索引；这个布尔值用来在普通 toolchain 与轻量故障隔离（LFI）toolchain 之间做选择（见 59.9 节）。与之并列的 registerLFIToolchainFactory 负责填充 true 那一格：

// build/soong/cc/config/toolchain.go
var toolchainFactories = make(map[android.OsType]map[android.ArchType]map[bool]toolchainFactory)

func registerToolchainFactory(os android.OsType, arch android.ArchType, factory toolchainFactory) {
    makeToolchainMap(os, arch)
    toolchainFactories[os][arch][false] = factory
}

func registerLFIToolchainFactory(os android.OsType, arch android.ArchType, factory toolchainFactory) {
    makeToolchainMap(os, arch)
    toolchainFactories[os][arch][true] = factory
}

Soong 需要为某个操作系统与架构编译模块时，会查出对应的工厂，同时传入目标是否为 LFI 变体，然后以目标的 Arch 结构调用该工厂。工厂返回一个 Toolchain 实现，由它提供所需的全部参数：

// build/soong/cc/config/toolchain.go
func findToolchain(os android.OsType, arch android.Arch, lfi bool) (Toolchain, error) {
    factory := toolchainFactories[os][arch.ArchType][lfi]
    if factory == nil {
        return nil, fmt.Errorf("Toolchain not found for os: %q, arch %q, lfi: %t", os.String(), arch.String(), lfi)
    }
    return factory(arch), nil
}

59.1.2 Toolchain 接口

所有架构专属的 toolchain 都实现 build/soong/cc/config/toolchain.go 中定义的 Toolchain 接口。这是核心抽象层：有了它，Soong 编译 C/C++ 代码时无需把任何架构细节硬编码进去。

// build/soong/cc/config/toolchain.go
type Toolchain interface {
    Name() string
    IncludeFlags() string
    ClangTriple() string
    ToolchainCflags() string
    ToolchainLdflags() FlagsWithDeps
    Asflags() string
    Cflags() string
    Cppflags() string
    Ldflags(ctx ToolchainFlagsContext) FlagsWithDeps
    InstructionSetFlags(string) (string, error)
    ndkTriple() string
    YasmFlags() string
    Is64Bit() bool
    ShlibSuffix() string
    ExecutableSuffix() string
    LibclangRuntimeLibraryArch() string
    AvailableLibraries() []string
    CrtBeginStaticBinary() []string
    CrtBeginSharedBinary() []string
    CrtBeginSharedLibrary() []string
    CrtEndStaticBinary() []string
    CrtEndSharedBinary() []string
    CrtEndSharedLibrary() []string
    CrtPadSegmentSharedLibrary() []string
    DefaultSharedLibraries() []string
    Bionic() bool
    Glibc() bool
    Musl() bool
    Lfi() bool
}

该接口可以分成几组逻辑：

身份标识：Name() 与 ClangTriple() 标识目标。Name() 返回像 "arm64"、"x86" 这样的短标识；ClangTriple() 返回配合 --target= 参数使用的完整 Clang target triple。

编译参数：Cflags()、Cppflags()、ToolchainCflags() 与 Asflags() 提供在各个层次传给编译器的参数。ToolchainCflags() 承载架构变体与 CPU 变体专属参数，这些参数叠加在基础的 Cflags() 之上。

链接：Ldflags()、ToolchainLdflags() 与各 CRT（C 运行时）方法控制二进制如何链接。后两者如今返回 FlagsWithDeps 结构，而不再是裸字符串；Ldflags() 还接收一个 ToolchainFlagsContext，借助它，toolchain 可以在计算链接参数的同时注册 Ninja phony 规则或 glob 路径。每个基于 bionic 的 toolchain 都使用 crtbegin_dynamic、crtend_android 这类 CRT 目标文件。

平台：Bionic()、Glibc()、Musl() 指明 toolchain 链接的是哪套 C 库。Lfi() 报告它是否为轻量故障隔离 toolchain（见 59.9 节），普通 bionic toolchain 默认为 false。

基类型 toolchain64Bit 与 toolchain32Bit 提供 Is64Bit() 方法，toolchainBionic 则提供 Android 专属的 CRT 目标文件与默认共享库：

// build/soong/cc/config/bionic.go
type toolchainBionic struct {
    toolchainBase
}

var (
    bionicDefaultSharedLibraries = []string{"libc", "libm", "libdl"}

    bionicCrtBeginStaticBinary, bionicCrtEndStaticBinary   = []string{"crtbegin_static"}, []string{"crtend_android"}
    bionicCrtBeginSharedBinary, bionicCrtEndSharedBinary   = []string{"crtbegin_dynamic"}, []string{"crtend_android"}
    bionicCrtBeginSharedLibrary, bionicCrtEndSharedLibrary = []string{"crtbegin_so"}, []string{"crtend_so"}
    bionicCrtPadSegmentSharedLibrary                       = []string{"crt_pad_segment"}
)

59.1.3 Arch 结构

Soong 用 build/soong/android/arch.go 中的 Arch 结构表示目标架构。该结构承载着挑选正确 toolchain、编译参数与源文件所需的全部信息：

// build/soong/android/arch.go
type Arch struct {
    ArchType    ArchType
    ArchVariant string
    CpuVariant  string
    Abi         []string
    ArchFeatures []string
}

各字段职责如下：

  • ArchType：Arm、Arm64、X86、X86_64 或 Riscv64 之一，决定使用哪个 toolchain 工厂。

  • ArchVariant：ISA 版本，例如 "armv8-2a" 或 "haswell"，映射到 -march= 参数。

  • CpuVariant：具体的 CPU 微架构，例如 "cortex-a55" 或 "kryo385"，映射到 -mcpu= 参数。

  • Abi：支持的应用程序二进制接口列表，例如 ["arm64-v8a"] 或 ["armeabi-v7a", "armeabi"]。

  • ArchFeatures：可选的硬件特性，例如 "branchprot" 或 "sse4_2"。

ArchType 本身只是个带名字与 multilib 分类的简单结构：

// build/soong/android/arch.go
type ArchType struct {
    Name     string   // "arm", "arm64", "x86", "x86_64", or "riscv64"
    Field    string   // Property field name, e.g., "Arm64"
    Multilib string   // "lib32" or "lib64"
}

五种架构类型以包级变量形式注册：

// build/soong/android/arch.go
Arm     = newArch("arm", "lib32")
Arm64   = newArch("arm64", "lib64")
Riscv64 = newArch("riscv64", "lib64")
X86     = newArch("x86", "lib32")
X86_64  = newArch("x86_64", "lib64")

当 BoardConfig.mk 声明 TARGET_ARCH := arm64 与 TARGET_ARCH_VARIANT := armv8-2a-dotprod 时，Soong 会构造一个 Arch 结构：ArchType=Arm64、ArchVariant="armv8-2a-dotprod"，并配上相应的 CpuVariant 与 ArchFeatures。该结构随后传给 arm64ToolchainFactory()，由它用各个字段挑出正确的参数。

59.2 ARM64（AArch64）

ARM64，正式名称 AArch64，是 Android 设备的主力架构。今天出货的几乎每一部手机、平板与可穿戴设备都用 ARM64 处理器。AOSP 构建系统支持范围很广的 ARM64 微架构，从最初的 ARMv8-A 一直到最新的 ARMv9.4-A 扩展。

源文件：build/soong/cc/config/arm64_device.go

ARM64 的基础参数如今包含栈冲突防护（stack-clash protection），以及与所有 LP64 架构共享的严格隐式声明检查：

// build/soong/cc/config/arm64_device.go
arm64Cflags = []string{
    // Help catch common 32/64-bit errors.
    // Common to all LP64 architectures.
    "-Werror=implicit-function-declaration",

    // For stack allocations larger than a page, touch each page immediately
    // to ensure we hit the guard page on stack overflow.
    // Common to all LP64 architectures.
    "-fstack-clash-protection",
}

-fstack-clash-protection 堵住了一类栈溢出攻击：一次超大栈分配直接跨过保护页。编译器会在栈帧增长时逐页探测，于是溢出必然触发缺页异常。同样这两个参数在 riscv64_device.go 中也逐字出现。

59.2.1 架构变体

ARM64 支持十个架构变体，每个对应一个具体的 -march= 编译参数：

// build/soong/cc/config/arm64_device.go
arm64ArchVariantCflags = map[string][]string{
    "armv8-a":            {"-march=armv8-a"},
    "armv8-a-branchprot": {"-march=armv8-a"},
    "armv8-2a":           {"-march=armv8.2-a"},
    "armv8-2a-dotprod":   {"-march=armv8.2-a+dotprod"},
    "armv8-5a":           {"-march=armv8.5-a"},
    "armv8-7a":           {"-march=armv8.7-a"},
    "armv9-a":            {"-march=armv9-a"},
    "armv9-2a":           {"-march=armv9.2-a"},
    "armv9-3a":           {"-march=armv9.3-a"},
    "armv9-4a":           {"-march=armv9.4-a"},
}

armv8-a-branchprot 变体值得留意：它用的 -march=armv8-a 与普通 armv8-a 相同，但构建系统知道要额外施加 branchprot 架构特性，从而补上硬件强制的控制流完整性所需的编译参数。

59.2.2 分支保护：PAC 与 BTI

指针认证码（Pointer Authentication Code，PAC）与分支目标识别（Branch Target Identification，BTI）都是硬件安全特性，用来防御控制流劫持类攻击，例如 ROP（返回导向编程）与 JOP（跳转导向编程）。

启用 branchprot 特性时，AOSP 会加上这些编译参数：

// build/soong/cc/config/arm64_device.go
arm64ArchFeatureCflags = map[string][]string{
    // When Pointer Authentication Codes (PAC) are available, -fstack-protector is unnecessary.
    "branchprot": {
        "-mbranch-protection=standard",
        "-fno-stack-protector",
    },
}

-mbranch-protection=standard 让 Clang 做两件事：

  1. 用 PAC 指令（PACIASP / AUTIASP）对返回地址签名
  2. 在函数入口与分支目标处插入 BTI 着陆垫（landing pad）

-fno-stack-protector 是刻意与 PAC 搭配的：经 PAC 签名的返回地址本身就能抵御破坏返回地址的栈缓冲区溢出——而这正是栈保护器主要防御的威胁。关掉栈保护器可以省掉多余的 canary 检查，每个函数进出少几条指令。

branchprot 特性还会驱动一个配套的链接参数。另一个 arm64ArchFeatureLdflags map 要求链接器在任何一个输入目标文件缺少 BTI 标记时直接让链接失败。这样，单个非 BTI 的编译单元就无法悄悄把整个二进制的防护等级拉低：

// build/soong/cc/config/arm64_device.go
arm64ArchFeatureLdflags = map[string][]string{
    "branchprot": {
        "-Wl,-z,bti-report=error",
    },
}

这使 BTI 成为二进制的一种“全有或全无”属性：若所有目标文件都 BTI 干净，产物库会被标记 GNU_PROPERTY_AARCH64_FEATURE_1_BTI，内核则用 PROT_BTI 映射其可执行页；只要有任何一个目标文件未标记，构建就会失败——绝不会产出一个悄悄丢掉了防护的二进制。

在 PAC+BTI 流程里，如果攻击者改写了栈上保存的 LR，AUTIASP 就无法通过已损坏指针的认证，从而触发异常。BTI 着陆垫则保证间接分支只能落到预期的目标位置。

59.2.3 内存标记扩展（MTE）

ARMv8.5-A 引入了内存标记扩展（Memory Tagging Extension，MTE），这是一种硬件特性，可以检出 use-after-free、缓冲区溢出之类内存安全缺陷。AOSP 在 bionic 层面与 MTE 做了深度集成。

bionic/libc/arch-arm64/bionic/note_memtag_heap_async.S 中含有一个 ELF note，请求内核对堆分配启用 MTE：

// bionic/libc/arch-arm64/bionic/note_memtag_heap_async.S
  .section ".note.android.memtag", "a", %note
  .p2align 2
  .long 1f - 0f                 // int32_t namesz
  .long 3f - 2f                 // int32_t descsz
  .long NT_ANDROID_TYPE_MEMTAG  // int32_t type
0:
  .asciz "Android"              // char name[]
1:
  .p2align 2
2:
  .long (NT_MEMTAG_LEVEL_ASYNC | NT_MEMTAG_HEAP) // value
3:
  .p2align 2

bionic 的 ifunc 分派器也把 MTE 作为选择依据：硬件支持时会挑选 MTE 感知的实现。摘自 bionic/libc/arch-arm64/ifuncs.cpp：

// bionic/libc/arch-arm64/ifuncs.cpp
DEFINE_IFUNC_FOR(memchr) {
  if (arg->_hwcap2 & HWCAP2_MTE) {
    RETURN_FUNC(memchr_func_t, __memchr_aarch64_mte);
  } else {
    RETURN_FUNC(memchr_func_t, __memchr_aarch64);
  }
}

MTE 感知的字符串例程需要特殊处理，因为标记位占据指针的高位。除非代码是按标记位来写的，否则普通的指针运算或基于 SIMD 的比较可能意外地被标记位绊倒。

59.2.4 CPU 变体调优与 big.LITTLE

ARM 的 big.LITTLE（以及后来的 DynamIQ）异构计算架构，把高性能的“大核”（如 Cortex-A76）与高效的“小核”（如 Cortex-A55）搭配在一起。这带来一个调度优化难题：为big 核流水线编译的代码，在小核上可能发生停顿。

AOSP 采取务实做法：按小核来调优代码。因为这样生成的代码在两类核心上都能正确且（可接受地）快地运行；反之，为big 核调优的代码在小核上可能慢得离谱：

// build/soong/cc/config/arm64_device.go
"cortex-a75": []string{
    // Use the cortex-a55 since it is similar to the little
    // core (cortex-a55) and is sensitive to ordering.
    "-mcpu=cortex-a55",
},
"cortex-a76": []string{
    // Use the cortex-a55 since it is similar to the little
    // core (cortex-a55) and is sensitive to ordering.
    "-mcpu=cortex-a55",
},

这不是源码里的笔误，注释已经交代了原因：Cortex-A75（大核）与 Cortex-A76（大核）变体故意使用 -mcpu=cortex-a55（小核），因为小核的指令调度“对顺序敏感”——调度不佳会带来明显的性能下降；而大核的乱序流水线能弥补次优调度。

受支持的 ARM64 CPU 变体全集：

// build/soong/cc/config/arm64_device.go (condensed)
arm64CpuVariantCflags = map[string][]string{
    "cortex-a53": {"-mcpu=cortex-a53"},
    "cortex-a55": {"-mcpu=cortex-a55"},
    "cortex-a75": {"-mcpu=cortex-a55"},  // Uses little core tuning
    "cortex-a76": {"-mcpu=cortex-a55"},  // Uses little core tuning
    "kryo":       {"-mcpu=kryo"},
    "kryo385":    {"-mcpu=cortex-a53"},  // kryo385 not in clang
    "exynos-m1":  {"-mcpu=exynos-m1"},
    "exynos-m2":  {"-mcpu=exynos-m2"},
}

从 CPU 变体到编译参数的映射要经过两级查表。第一级是变体到变量名的映射：

    "cortex-a53": "${config.Arm64CortexA53Cflags}",
    "cortex-a55": "${config.Arm64CortexA55Cflags}",
    "cortex-a72": "${config.Arm64CortexA53Cflags}",
    "cortex-a73": "${config.Arm64CortexA53Cflags}",
    "cortex-a75": "${config.Arm64CortexA55Cflags}",
    "cortex-a76": "${config.Arm64CortexA55Cflags}",

可以看到，大核（A72、A73、A75、A76）全都映射到对应的小核参数（A53 或 A55）。

59.2.5 Cortex-A53 勘误规避

Cortex-A53 是历史上装机量最大的 ARM 核心之一，它有两个著名的硬件勘误。Soong 只在链接期规避了其中一个：勘误 843419。

// build/soong/cc/config/arm64_device.go
pctx.StaticVariable("Arm64FixCortexA53Ldflags", "-Wl,--fix-cortex-a53-843419")
// build/soong/cc/config/arm64_device.go
arm64CpuVariantLdflags = map[string]string{
    "cortex-a53": "${config.Arm64FixCortexA53Ldflags}",
    "cortex-a72": "${config.Arm64FixCortexA53Ldflags}",
    "cortex-a73": "${config.Arm64FixCortexA53Ldflags}",
    "kryo":       "${config.Arm64FixCortexA53Ldflags}",
    "exynos-m1":  "${config.Arm64FixCortexA53Ldflags}",
    "exynos-m2":  "${config.Arm64FixCortexA53Ldflags}",
}

勘误 843419：当特定的 ADRP 指令序列恰好落在页边界附近时，会引发错误执行。链接参数 --fix-cortex-a53-843419 让 LLD 检测这些问题模式，并插入 veneer 代码绕开。该修复同样施加到 A72、A73、Kryo 与 Exynos 核心上，因为在这些 big.LITTLE 配置里它们可能与 A53 小核搭配。

另一个广为人知的 A53 勘误 835769（乘加的一个边角情形）在 Soong 层没有规避措施。ART 在它的指令集特性模型（art/runtime/arch/arm64/instruction_set_features_arm64.h）里单独跟踪它，好让编译器避免生成有问题的指令序列。59.8.8 节给出了 ART 为此查阅的变体列表。

59.2.6 ARM64 Toolchain 工厂

工厂把参数拼装工作交给一个辅助函数 arm64ToolchainFlags，它成对返回 toolchain Cflags 与 toolchain Ldflags。把辅助函数单拆出来，是为了让 LFI toolchain（59.9 节）复用完全同一套参数逻辑：

// build/soong/cc/config/arm64_device.go
func arm64ToolchainFactory(arch android.Arch) Toolchain {
    toolchainCflags, toolchainLdflags := arm64ToolchainFlags(arch)
    return &toolchainArm64{
        toolchainCflags:  toolchainCflags,
        toolchainLdflags: toolchainLdflags,
    }
}

func arm64ToolchainFlags(arch android.Arch) (string, string) {
    // Error now rather than having a confusing Ninja error
    if _, ok := arm64ArchVariantCflags[arch.ArchVariant]; !ok {
        panic(fmt.Sprintf("Unknown ARM64 architecture version: %q", arch.ArchVariant))
    }

    toolchainCflags := []string{"${config.Arm64" + arch.ArchVariant + "VariantCflags}"}
    toolchainCflags = append(toolchainCflags,
        variantOrDefault(arm64CpuVariantCflagsVar, arch.CpuVariant))
    for _, feature := range arch.ArchFeatures {
        toolchainCflags = append(toolchainCflags, arm64ArchFeatureCflags[feature]...)
    }

    extraLdflags := []string{"${config.Arm64Ldflags}"}
    extraLdflags = append(extraLdflags,
        variantOrDefault(arm64CpuVariantLdflags, arch.CpuVariant))
    for _, feature := range arch.ArchFeatures {
        extraLdflags = append(extraLdflags, arm64ArchFeatureLdflags[feature]...)
    }
    return strings.Join(toolchainCflags, " "), strings.Join(extraLdflags, " ")
}

toolchain 的 Ldflags 现在合并了两组链接参数：一组按 CPU 变体（Cortex-A53 勘误修复），一组按特性（branchprot 的 BTI 报告参数）。它们存放在 toolchain 的 toolchainLdflags 字段里，并通过 ToolchainLdflags() 暴露出来，后者返回 FlagsWithDeps。

59.2.7 页大小配置

ARM64 支持多种页大小（4KB、16KB、64KB）。链接参数用来强制最大的页大小，以保证段对齐正确：

// build/soong/cc/config/arm64_device.go
pctx.VariableFunc("Arm64Ldflags", func(ctx android.PackageVarContext) string {
    maxPageSizeFlag := "-Wl,-z,max-page-size=" + ctx.Config().MaxPageSizeSupported()
    flags := append(arm64Ldflags, maxPageSizeFlag)
    return strings.Join(flags, " ")
})

MaxPageSizeSupported() 是链接器用于 ELF 段边界的对齐值，在 ARM64 上它已不再是硬编码的 4096。到 Android 17，构建系统在 arm64 与 x86_64 设备上把它默认设为 16384，于是平台二进制会被对齐到能在 16KB 页内核上正确加载。59.10 节会追溯这个默认值，以及随之改动的 bionic 侧宏。

基础链接参数还包含出于安全的段隔离：

// build/soong/cc/config/arm64_device.go
arm64Ldflags = []string{
    // Separate-code is required for XOM
    "-Wl,-z,separate-code",
    "-Wl,-z,separate-loadable-segments",
}

这些参数确保代码段、数据段与只读段各自落在不同的内存页上，从而防止意外（或恶意地）执行数据、修改代码。其中 separate-code 尤其关键：它让仅可执行内存（execute-only memory，XOM）成为可能——把代码排除在任何同时存放可读数据的页面之外。于是，能读进程内存的攻击者也无法把指令流读回来拼出代码复用载荷。

59.3 x86 与 x86_64

x86 家族在 AOSP 中有两个主要角色：既是 Chromebook 与嵌入式设备的目标，也是 Android 模拟器的原生架构。模拟器历史上以翻译方式运行 ARM 镜像，但原生 x86/x86_64 镜像能在开发阶段提供远好于翻译的性能。

59.3.2 SIMD 指令集：SSE 与 AVX

x86 的 SIMD 生态比 ARM 的 NEON 更零碎：x86 没有单一必备的 SIMD 扩展，而是一串可选扩展。x86 与 x86_64 两个 toolchain 都为它们定义了特性参数：

// build/soong/cc/config/x86_64_device.go
x86_64ArchFeatureCflags = map[string][]string{
    "ssse3":  []string{"-mssse3"},
    "sse4":   []string{"-msse4"},
    "sse4_1": []string{"-msse4.1"},
    "sse4_2": []string{"-msse4.2"},

    // Not all cases there is performance gain by enabling -mavx -mavx2
    // flags so these flags are not enabled by default.
    // if there is performance gain in individual library components,
    // the compiler flags can be set in corresponding bp files.
    // "avx":    []string{"-mavx"},
    // "avx2":   []string{"-mavx2"},
    // "avx512": []string{"-mavx512"}

    "popcnt": []string{"-mpopcnt"},
    "aes_ni": []string{"-maes"},
}

注意被注释掉的 AVX/AVX2/AVX512 条目。注释解释了原因：AVX 并不总能带来性能收益。事实上在某些 Intel 处理器上，执行 AVX 指令会让 CPU 降低时钟频率（即“AVX 降频”），这对 AVX 与非 AVX 指令混用的代码反而是负收益。确实有收益时，各个库可以在自己的 Android.bp 里自行开启 AVX。

59.3.3 x86 专属编译参数

32 位 x86 toolchain 有几条独特要求：

// build/soong/cc/config/x86_device.go
x86Cflags = []string{
    "-msse3",
    // -mstackrealign is needed to realign stack in native code
    // that could be called from JNI, so that movaps instruction
    // will work on assumed stack aligned local variables.
    "-mstackrealign",
    // For stack allocations larger than a page, touch each page immediately
    // to ensure we hit the guard page on stack overflow.
    "-fstack-clash-protection",
}

-mstackrealign 处理一个微妙的 ABI 问题：i386 System V ABI 只要求 4 字节栈对齐，而 movaps 这类 SSE 指令要求 16 字节对齐。当原生代码被 JNI（经 Dalvik/ART 运行时）调用时，栈可能并非 16 字节对齐，从而引发崩溃。-mstackrealign 会在函数入口插入代码重新对齐栈。

x86 toolchain 的汇编还使用 Yasm：

// build/soong/cc/config/x86_device.go
pctx.StaticVariable("X86YasmFlags", "-f elf32 -m x86")
// build/soong/cc/config/x86_64_device.go

59.3.5 为兼容 ARM 而设的 Native Bridge

x86/x86_64 的 Android 设备面临一个兼容性难题：绝大多数 Android NDK 应用都是为 ARM 编译的。为了能跑这些应用，AOSP 内置了 Native Bridge 基础设施，提供透明的二进制翻译。

Native Bridge 机制定义在 frameworks/libs/binary_translation/native_bridge/native_bridge.h，该头文件声明了 NativeBridgeCallbacks 接口：

// frameworks/libs/binary_translation/native_bridge/native_bridge.h
struct NativeBridgeCallbacks {
  uint32_t version;

  bool (*initialize)(const NativeBridgeRuntimeCallbacks* runtime_cbs,
                     const char* private_dir,
                     const char* instruction_set);

  void* (*loadLibrary)(const char* libpath, int flag);

  // Get a native bridge trampoline for specified native method.
  // The trampoline has same signature as the native method.
  ...
};

Native Bridge 会拦截库加载：当 ART 的类加载器遇到为异种架构编译的原生库时，就把工作交给 native bridge 实现去翻译外来代码。

现有的实现有三种：

  • Berberis（开源，位于 frameworks/libs/binary_translation/）——Google 的参考实现，用于把 RISC-V 翻译到 x86_64

  • Houdini（Intel 私有实现）——把 ARM/ARM64 翻译到 x86/x86_64

  • DigitalisX64（开源，https://github.com/DigitalisX64）——社区实现，构建在 Berberis 之上以支持 ARM64 到 x86_64

模拟器用的是另一套策略：它在 QEMU 全系统模拟之上、配合硬件加速虚拟化来运行 ARM 系统镜像。因此常规的模拟器工作流并不涉及 native bridge。

59.3.7 ARM 32 位：遗留的次级架构

AOSP 中的 ARM 32 位支持，主要作为 ARM64 设备的次级架构存在，好让遗留的 32 位应用能跑起来。ARM toolchain 是五种架构里最复杂的一个：它支持的 CPU 变体范围最广（从古老的 Cortex-A7 到 32 位模式下的现代 Cortex-A76），还要支持两种指令编码（ARM 与 Thumb）。

ARM toolchain 的结构反映了它的 32 位属性：

// build/soong/cc/config/arm_device.go
type toolchainArm struct {
    toolchainBionic
    toolchain32Bit
    ldflags         string
    toolchainCflags string
}

ARM 的工厂函数拼装三层参数：

// build/soong/cc/config/arm_device.go
func armToolchainFactory(arch android.Arch) Toolchain {
    toolchainCflags := make([]string, 2, 3)

    toolchainCflags[0] = "${config.ArmToolchainCflags}"
    toolchainCflags[1] = armArchVariantCflagsVar[arch.ArchVariant]

    toolchainCflags = append(toolchainCflags,
        variantOrDefault(armCpuVariantCflagsVar, arch.CpuVariant))

    return &toolchainArm{
        ldflags:         "${config.ArmLdflags}",
        toolchainCflags: strings.Join(toolchainCflags, " "),
    }
}

59.4 RISC-V 64

RISC-V 是 AOSP 支持的最新架构，最早在 2022 年引入。它是一种开放、免版税的指令集架构，业界关注度很高。AOSP 的 RISC-V 移植仍在成熟过程中——配置文件更小、对尚不完整的 toolchain 支持存在显式规避，都是这一状态的证据。

源文件：build/soong/cc/config/riscv64_device.go

59.4.1 基础 ISA 与扩展

RISC-V 的配置指定了一组丰富的扩展。到 Android 17，基线已与 ARM64 共享同一套 LP64 加固参数（-Werror=implicit-function-declaration 与 -fstack-clash-protection）。ISA 字符串也新增了一个向量位操作扩展：

// build/soong/cc/config/riscv64_device.go
riscv64Cflags = []string{
    // Help catch common 32/64-bit errors.
    // Common to all LP64 architectures.
    "-Werror=implicit-function-declaration",

    // For stack allocations larger than a page, touch each page immediately
    // to ensure we hit the guard page on stack overflow.
    // Common to all LP64 architectures.
    "-fstack-clash-protection",

    // This is already the driver's Android default, but duplicated here (and
    // below) for ease of experimentation with additional extensions.
    "-march=rv64gcv_zba_zbb_zbs_zvbb",
    // TODO: remove when qemu V works (https://gitlab.com/qemu-project/qemu/-/issues/1976)
    // (Note that we'll probably want to wait for berberis to be good enough
    // that most people don't care about qemu's V performance either!)
    "-mno-implicit-float",
}

ISA 字符串 -march=rv64gcv_zba_zbb_zbs_zvbb 逐项拆解如下：

组成部分 含义
rv64 64 位基础整数 ISA（RV64I）
g “通用” = IMAFD（整数、乘法、原子、单精度浮点、双精度浮点）
c 压缩指令（常见操作用 16 位编码）
v 向量扩展（RISC-V V 1.0）
zba 地址生成指令（sh1add、sh2add、sh3add）
zbb 基础位操作（clz、ctz、cpop、rev8 等）
zbs 单比特指令（bset、bclr、binv、bext）
zvbb 向量基础位操作（向量版 clz/ctz/popcount/rotate）

这是一个相当现代的基线。其中向量扩展尤其关键：它启用了类似 ARM NEON 或 Intel SSE 的 SIMD 类操作，而且设计上可伸缩，不把向量宽度写死。Android 17 加入的 zvbb 扩展把同样的位操作原语（前导零计数、位计数、循环移位）带到了向量寄存器上，对密码学与哈希类内核很有用。

59.4.2 QEMU 与 Berberis 规避

RISC-V 配置里有一条颇具信息量的 TODO 注释，暴露了生态现状：

// TODO: remove when qemu V works (https://gitlab.com/qemu-project/qemu/-/issues/1976)
// (Note that we'll probably want to wait for berberis to be good enough
// that most people don't care about qemu's V performance either!)
"-mno-implicit-float",

这段注释道出了 RISC-V 开发的实际困难：QEMU 对向量扩展的支持还不完整；可用于开发的二进制翻译器 Berberis（能把 RISC-V 翻译到 x86_64）也仍在成熟。-mno-implicit-float 参数禁止编译器为非浮点操作（例如结构体拷贝）自动使用浮点或向量指令，从而绕开 QEMU 的 V 扩展缺陷。

59.4.3 最小化的变体配置

与 ARM64、x86 不同，RISC-V 没有 CPU 变体调优：

59.4.4 RISC-V 链接器配置

RISC-V 的链接参数很直白：

    // This is already the driver's Android default, but duplicated here (and
    // above) for ease of experimentation with additional extensions.
    "-march=rv64gcv_zba_zbb_zbs_zvbb",
    "-Wl,-z,max-page-size=4096",

注意这里把页大小硬编码成了 4KB。ARM64 与 x86_64 不同：它们的最大页大小取自可配置的 MaxPageSizeSupported()（Android 17 默认 16KB，见 59.10 节）。RISC-V 版 Android 目前只支持 4KB 页。

59.4.6 ART 的 RISC-V 特性检测

ART 运行时对 RISC-V 有完整支持，并自带 ISA 特性跟踪。Riscv64InstructionSetFeatures 类以位图形式记录各扩展：

// art/runtime/arch/riscv64/instruction_set_features_riscv64.h
class Riscv64InstructionSetFeatures final : public InstructionSetFeatures {
 public:
  enum {
    kExtGeneric    = (1 << 0),  // G extension covers the basic set IMAFD
    kExtCompressed = (1 << 1),  // C extension adds compressed instructions
    kExtVector     = (1 << 2),  // V extension adds vector instructions
    kExtZba        = (1 << 3),  // Zba adds address generation bit-manipulation instructions
    kExtZbb        = (1 << 4),  // Zbb adds basic bit-manipulation instructions
    kExtZbs        = (1 << 5),  // Zbs adds single-bit bit-manipulation instructions
  };

ART 的特性位图跟踪六个扩展（G、C、V、Zba、Zbb、Zbs）。注意 Soong toolchain 现在在编译期就要求 zvbb（见 59.4.1 节），但 ART 还没有 zvbb 位，因此 JIT 并不以它为键。这是“构建 toolchain 走在 ART 运行时特性模型前面”的一个小例子。

这些特性方法让 ART 的 JIT 编译器能查询具体能力：

// art/runtime/arch/riscv64/instruction_set_features_riscv64.h
bool HasCompressed() const { return (bits_ & kExtCompressed) != 0; }
bool HasVector() const { return (bits_ & kExtVector) != 0; }
bool HasZba() const { return (bits_ & kExtZba) != 0; }
bool HasZbb() const { return (bits_ & kExtZbb) != 0; }
bool HasZbs() const { return (bits_ & kExtZbs) != 0; }

FromVariant() 的实现目前只认 "generic" 变体，并直接使用完整的基础特性集：

// art/runtime/arch/riscv64/instruction_set_features_riscv64.cc
constexpr uint32_t BasicFeatures() {
  return Riscv64InstructionSetFeatures::kExtGeneric |
         Riscv64InstructionSetFeatures::kExtCompressed |
         Riscv64InstructionSetFeatures::kExtVector |
         Riscv64InstructionSetFeatures::kExtZba |
         Riscv64InstructionSetFeatures::kExtZbb |
         Riscv64InstructionSetFeatures::kExtZbs;
}

Riscv64FeaturesUniquePtr Riscv64InstructionSetFeatures::FromVariant(
    const std::string& variant, [[maybe_unused]] std::string* error_msg) {
  if (variant != "generic") {
    LOG(WARNING) << "Unexpected CPU variant for Riscv64 using defaults: " << variant;
  }
  return Riscv64FeaturesUniquePtr(new Riscv64InstructionSetFeatures(BasicFeatures()));
}

从 C 预处理器宏做特性检测也已实现，好让构建系统在编译期就探知扩展：

// art/runtime/arch/riscv64/instruction_set_features_riscv64.cc
Riscv64FeaturesUniquePtr Riscv64InstructionSetFeatures::FromCppDefines() {
  // Assume kExtGeneric is always present.
  uint32_t bits = kExtGeneric;
#ifdef __riscv_c
  bits |= kExtCompressed;
#endif
#ifdef __riscv_v
  bits |= kExtVector;
#endif
#ifdef __riscv_zba
  bits |= kExtZba;
#endif
#ifdef __riscv_zbb
  bits |= kExtZbb;
#endif
#ifdef __riscv_zbs
  bits |= kExtZbs;
#endif
  return FromBitmap(bits);
}

需要注意的是，FromCpuInfo() 与 FromHwcap() 两个方法在 RISC-V 上尚未实现：

// art/runtime/arch/riscv64/instruction_set_features_riscv64.cc
Riscv64FeaturesUniquePtr Riscv64InstructionSetFeatures::FromCpuInfo() {
  UNIMPLEMENTED(WARNING);
  return FromCppDefines();
}

Riscv64FeaturesUniquePtr Riscv64InstructionSetFeatures::FromHwcap() {
  UNIMPLEMENTED(WARNING);
  return FromCppDefines();
}

UNIMPLEMENTED(WARNING) 表明 RISC-V 的运行时硬件探测还不完整，这也是该架构在 AOSP 中处于早期采用阶段的又一个标志。

59.4.7 RISC-V 与 ARM64 特性跟踪对比

ART 中 RISC-V 与 ARM64 特性跟踪的差异，暴露了两者的成熟度差距：

59.4.8 ART 的 ARM64 特性位图

ART 把 ARM64 特性压成紧凑位图以便序列化：

enum {
    kA53Bitfield     = 1 << 0,
    kCRCBitField     = 1 << 1,
    kLSEBitField     = 1 << 2,
    kFP16BitField    = 1 << 3,
    kDotProdBitField = 1 << 4,
    kSVEBitField     = 1 << 5,
};

私有成员变量则逐个跟踪各特性：

// art/runtime/arch/arm64/instruction_set_features_arm64.h
const bool fix_cortex_a53_835769_;
const bool fix_cortex_a53_843419_;
const bool has_crc_;      // optional in ARMv8.0, mandatory in ARMv8.1
const bool has_lse_;      // ARMv8.1 Large System Extensions
const bool has_fp16_;     // ARMv8.2 FP16 extensions

const bool has_sve_;      // optional in ARMv8.2.

JIT 编译器用这些特性标志挑选指令模式。举例来说，has_lse_ 为真时，原子操作会使用单条指令的 LDADD、SWPAL 等，而不再使用多指令的 LL/SC 循环（LDAXR / STLXR）。在竞争激烈的场景下，这可能快 2 到 3 倍。

59.5 多架构构建

59.5.3 compile_multilib 属性

在 Android.bp 中，模块用 compile_multilib 属性控制要为哪些架构构建：

cc_library {
    name: "libexample",
    compile_multilib: "both",  // Build for both 32 and 64 bit
    srcs: ["example.cpp"],
}

合法取值由 build/soong/android/arch.go 中的 decodeMultilibTargets() 解析：

// build/soong/android/arch.go
func decodeMultilibTargets(multilib string, targets []Target, prefer32 bool) ([]Target, error) {
    var buildTargets []Target
    switch multilib {
    case "common":
        buildTargets = getCommonTargets(targets)
    case "both":
        if prefer32 {
            buildTargets = append(buildTargets, filterMultilibTargets(targets, "lib32")...)
            buildTargets = append(buildTargets, filterMultilibTargets(targets, "lib64")...)
        } else {
            buildTargets = append(buildTargets, filterMultilibTargets(targets, "lib64")...)
            buildTargets = append(buildTargets, filterMultilibTargets(targets, "lib32")...)
        }
    case "32":
        buildTargets = filterMultilibTargets(targets, "lib32")
    case "64":
        buildTargets = filterMultilibTargets(targets, "lib64")
    case "first":
        if prefer32 {
            buildTargets = FirstTarget(targets, "lib32", "lib64")
        } else {
            buildTargets = FirstTarget(targets, "lib64", "lib32")
        }
    case "first_prefer32":
        buildTargets = FirstTarget(targets, "lib32", "lib64")
    case "prefer32":
        buildTargets = filterMultilibTargets(targets, "lib32")
        if len(buildTargets) == 0 {
            buildTargets = filterMultilibTargets(targets, "lib64")
        }
    // ...
    }
    return buildTargets, nil
}
取值 含义
"both" 32 位与 64 位都构建
"first" 只为选定的那一个（优先）架构构建
"32" 只为 32 位构建
"64" 只为 64 位构建
"prefer32" 有 32 位就构建 32 位，否则 64 位
"first_prefer32" 效果类同 first，但优先 32 位
"common" 与架构无关（例如 Java）

59.6 编译器配置

AOSP 的编译器配置集中在 build/soong/cc/config/global.go，对所有架构生效。该文件定义了通用编译参数、告警策略、调试设置与 Clang toolchain 路径，它们构成每一次原生构建的基线。

59.6.1 通用全局 CFLAGS

commonGlobalCflags 数组定义了 AOSP 中每一次 C/C++ 编译都会施加的参数：

// build/soong/cc/config/global.go
commonGlobalCflags = []string{
    "-O2",
    "-Wall",
    "-Wextra",
    "-Wpointer-arith",
    "-Wunguarded-availability",

    // Warnings treated as errors
    "-Werror=bool-operation",
    "-Werror=date-time",          // Nondeterministic builds
    "-Werror=int-conversion",
    "-Werror=multichar",
    "-Werror=pragma-pack",
    "-Werror=sizeof-array-div",
    "-Werror=sizeof-pointer-memaccess",
    "-Werror=string-plus-int",
    "-Werror=unreachable-code-loop-increment",
    // ...

    // Preprocessor defines
    "-DANDROID",
    "-DNDEBUG",
    "-UDEBUG",
    "-D__compiler_offsetof=__builtin_offsetof",
    "-D__ANDROID_UNAVAILABLE_SYMBOLS_ARE_WEAK__",

    // Code generation options
    "-faddrsig",
    "-fdebug-default-version=5",
    "-fcolor-diagnostics",
    "-ffp-contract=off",
    "-fno-exceptions",
    "-fno-strict-aliasing",
    "-fmessage-length=0",
    "-gsimple-template-names",
    "-gz=zstd",
    "-no-canonical-prefixes",
}

其中若干项值得解释：

-O2：所有 Android 代码的默认优化级别，而不是 -O3。因为 -O3 会启用循环展开、函数内联等激进优化，可能增大代码体积——这对移动设备有实际影响，指令缓存压力会直接影响续航。

-DANDROID：定义 ANDROID 预处理宏。AOSP 与第三方代码里成千上万个 #ifdef ANDROID 块都依赖它。

-DNDEBUG：在发布构建中关闭 assert()。之所以全局定义，是因为即便是平台的 debug 构建，通常也不希望生产代码里出现断言失败。

-fno-exceptions：全局关闭 C++ 异常。Google C++ 风格指南禁止异常，且 bionic 的 C++ 支持库（libc++）在 Android 上就是不支持异常地构建的。

-fno-strict-aliasing：关闭基于类型的别名分析优化。虽然它可能带来性能收益，但注释说明了权衡：“启用它们目前带来的性能收益，抵不上难以复现的 bug 风险。”

-gz=zstd：用 Zstandard 压缩调试信息，在保留调试能力的前提下显著减小构建产物体积。

59.6.2 设备专属 CFLAGS

以下是只作用于设备侧（而非宿主侧）代码的参数：

// build/soong/cc/config/global.go
deviceGlobalCflags = []string{
    "-ffunction-sections",
    "-fdata-sections",
    "-fno-short-enums",
    "-funwind-tables",
    "-Wa,--noexecstack",
    "-D_FORTIFY_SOURCE=3",

    // Add stack canaries on every frame, checked on return.
    // -fstack-clash-protection isn't supported in clang for ILP32,
    // so that's in each of the LP64 architectures' configurations instead.
    "-fstack-protector-strong",

    "-Werror=non-virtual-dtor",
    "-Werror=address",
    "-Werror=sequence-point",
}

-ffunction-sections / -fdata-sections：让每个函数、每个数据对象各占一个 ELF 段，链接器就能通过 --gc-sections 丢弃未使用的函数与数据。这对移动端的体积控制至关重要。

-fstack-protector-strong：对含局部数组或取局部变量地址的函数插入栈 canary。“strong” 版本比 -fstack-protector 覆盖更多函数，又比 -fstack-protector-all 少，从而在安全与性能间取得平衡。与之配套的 -fstack-clash-protection 不在这份全局列表里，因为注释指出 Clang 在 ILP32 上不支持它；各 LP64 架构（ARM64、x86_64、RISC-V 64）在自己的架构基础 cflags 里加上它（见 59.2 节与 59.4.1 节）。实践中 32 位 x86 也在 x86Cflags 里带了该参数（59.3.3 节），尽管它属于 ILP32。于是 32 位 ARM 成了唯一没有该参数构建的架构。

-D_FORTIFY_SOURCE=3：编译期与运行期缓冲区溢出检测的最高级别。第 3 级在级别 2 的 memcpy / strcpy 基础检查之外，覆盖更多函数与使用模式。

59.6.3 设备链接参数

// build/soong/cc/config/global.go
deviceGlobalLdflags = slices.Concat([]string{
    "-Wl,-z,noexecstack",
    "-Wl,-z,relro",
    "-Wl,-z,now",
    "-Wl,--build-id=md5",
    "-Wl,--fatal-warnings",
    "-Wl,--no-undefined-version",
    "-Wl,--exclude-libs,libgcc.a",
    "-Wl,--exclude-libs,libgcc_stripped.a",
    "-Wl,--exclude-libs,libunwind_llvm.a",
    "-Wl,--exclude-libs,libunwind.a",
    "-Wl,--compress-debug-sections=zstd",
}, commonGlobalLdflags)

与安全相关的几项：

  • -Wl,-z,noexecstack：把栈标记为不可执行（NX 位）。

  • -Wl,-z,relro：只读重定位——重定位完成后 GOT 表项变为只读。

  • -Wl,-z,now：立即绑定——加载时就把所有符号解析完，而不是惰性解析，从而消除 GOT 表项可写的窗口。

这些参数合起来构成一套纵深防御的利用缓解策略。

设备侧与宿主侧共享的通用链接参数：

// build/soong/cc/config/global.go
commonGlobalLdflags = []string{
    "-fuse-ld=lld",
    "-Wl,--icf=safe",
    "-Wl,--no-demangle",
}

-fuse-ld=lld：使用 LLVM 的 LLD 链接器替代 GNU ld。LLD 快得多，也是 AOSP 唯一支持的链接器。

-Wl,--icf=safe：相同代码折叠（Identical Code Folding）——把机器码完全相同的函数合并以省空间。“safe” 模式只折叠地址从未被取用的函数，避免微妙 bug。

59.6.4 不可覆盖的告警参数

有些告警极为重要，模块即使在 Android.bp 里使用 -Wno-error 之类的参数也无法关掉：

// build/soong/cc/config/global.go
noOverrideGlobalCflags = []string{
    "-Werror=address-of-temporary",
    "-Werror=dangling",
    "-Werror=format-insufficient-args",
    "-Werror=fortify-source",
    "-Werror=incompatible-function-pointer-types",

    "-Werror=int-to-pointer-cast",
    "-Werror=null-dereference",

59.6.6 Clang Toolchain 版本

global.go 也管理 Clang 编译器版本：

// build/soong/cc/config/global.go
CStdVersion               = "gnu23"
CppDefaultStdVersion      = "gnu++20"
ExperimentalCStdVersion   = "gnu2y"
ExperimentalCppStdVersion = "gnu++2b"

// prebuilts/clang default settings.
ClangDefaultBase = "prebuilts/clang/host"
// The Clang version used in the trunk branch.
ClangDefaultVersion = "clang-r584948"

AOSP 对 C 代码使用 C23（gnu23），对 C++ 代码使用 C++20（gnu++20）。gnu 前缀表示启用 GNU 扩展。

到 Android 17，trunk 分支固定的 Clang 版本推进到 clang-r584948；原来的 ClangDefaultShortVersion 常量已移除，版本改为通过 getter 函数读取，好让每个 release 自行覆盖。默认值仍解析到 prebuilts/clang/host，也可以用 LLVM_PREBUILTS_BASE 等相关环境变量覆盖。C++ 标准版本本身如今也可按 release 配置：CppDefaultStdVersion 是回退值，而 ReleaseBuildCppStdVersion() 让 release 配置无需改这个文件就能抬高标准。

59.6.7 自动变量初始化

一项值得注意的安全特性是自动变量初始化：

// build/soong/cc/config/global.go
if ctx.Config().IsEnvTrue("AUTO_ZERO_INITIALIZE") {
    flags = append(flags, "-ftrivial-auto-var-init=zero")
} else if ctx.Config().IsEnvTrue("AUTO_PATTERN_INITIALIZE") {
    flags = append(flags, "-ftrivial-auto-var-init=pattern")
} else if ctx.Config().IsEnvTrue("AUTO_UNINITIALIZE") {
    flags = append(flags, "-ftrivial-auto-var-init=uninitialized")
} else {
    // Default to zero initialization.
    flags = append(flags, "-ftrivial-auto-var-init=zero")
}

默认所有栈变量都做零初始化，以很小的运行时代价消灭了一整类未初始化变量缺陷。注释引用了 b/131390872，该缺陷单跟踪了这项特性的推广。

59.6.10 非法参数

AOSP 完全禁用某些编译参数：

// build/soong/cc/config/global.go
IllegalFlags = []string{
    "-w",
    "-pedantic",
    "-pedantic-errors",
    "-Werror=pedantic",
    "-Wno-all",
    "-Wno-everything",
}

-w 会压制所有告警，等于废掉整套告警基础设施；-Wno-all 与 -Wno-everything 效果相同。至于 -pedantic 系列，则是因为 AOSP 里大量合法的 GNU 扩展用法会被它触发成千上万条告警。

59.6.11 语言标准版本

AOSP 指定了现代语言标准：

// build/soong/cc/config/global.go
CStdVersion               = "gnu23"
CppDefaultStdVersion      = "gnu++20"
ExperimentalCStdVersion   = "gnu2y"
ExperimentalCppStdVersion = "gnu++2b"

  • C23（gnu23）：最新的 C 标准（ISO/IEC 9899:2024）加上 GNU 扩展，可启用 typeof、auto、constexpr 以及改进的 _Static_assert 等特性。

  • C++20（gnu++20）：启用 concepts、ranges、协程、模块、三向比较等一大批 C++ 重要特性。

  • “实验性”版本（gnu2y、gnu++2b）面向下一版标准，供主动尝鲜的模块使用。

PRODUCT_NO_BIONIC_PAGE_SIZE_MACRO := true 阻止 bionic 暴露固定的 PAGE_SIZE 宏，于是代码必须在运行时读取页大小，而不能在编译期假定 4096。这很重要，因为 Android 17 把 ARM64 与 x86_64 的 ELF 段对齐默认到 16KB（59.10 节）。把 PAGE_SIZE == 4096 硬编码进去的二进制，在 16KB 页内核上就会行为异常。更大的页能降低 TLB 压力与缺页开销，代价是略微增加内存碎片。

59.8.2 Bionic：ifunc 分派模式（ARM64）

ARM64 的 bionic 使用 GNU 间接函数（ifunc）机制，在运行时为常用函数挑选最佳实现。ifunc 解析器在动态链接期间运行，依据硬件能力选定实现：

// bionic/libc/arch-arm64/ifuncs.cpp
static inline bool __bionic_is_oryon(unsigned long hwcap) {
  if (!(hwcap & HWCAP_CPUID)) return false;

  unsigned long midr;
  __asm__ __volatile__("mrs %0, MIDR_EL1" : "=r"(midr));

  // Check for implementor Qualcomm's parts 0..15 (Oryon).
  return implementer(midr) == 'Q' && part(midr) <= 15;
}

memcpy 的 ifunc 解析器展示了这种多级分派：

// bionic/libc/arch-arm64/ifuncs.cpp
DEFINE_IFUNC_FOR(memcpy) {
  if (arg->_hwcap2 & HWCAP2_MOPS) {
    RETURN_FUNC(memcpy_func_t, __memmove_aarch64_mops);
  } else if (__bionic_is_oryon(arg->_hwcap)) {
    RETURN_FUNC(memcpy_func_t, __memcpy_aarch64_nt);
  } else if (arg->_hwcap & HWCAP_ASIMD) {
    RETURN_FUNC(memcpy_func_t, __memcpy_aarch64_simd);
  } else {
    RETURN_FUNC(memcpy_func_t, __memcpy_aarch64);
  }
}

优先级顺序是：

  1. MOPS（Memory Copy and Memory Set 指令，ARMv8.8-A）——硬件 memcpy 指令

  2. Oryon——高通自研核心，可做非临时存储（non-temporal store）优化

  3. ASIMD（Advanced SIMD，即 NEON）——向量化拷贝

  4. 回退——标量实现

graph TD
    A["调用 memcpy()"] --> B{"HWCAP2_MOPS？"}
    B -->|是| C["__memmove_aarch64_mops<br/>（硬件 MOPS 指令）"]
    B -->|否| D{"是 Oryon CPU？"}
    D -->|是| E["__memcpy_aarch64_nt<br/>（非临时存储）"]
    D -->|否| F{"HWCAP_ASIMD？"}

同样的模式也用于 memmove、memset、strlen、strchr 等热点字符串函数。存在 HWCAP2_MTE 时会选择 MTE 感知的变体：

    RETURN_FUNC(memset_func_t, __memset_aarch64_nt);
  } else {
    RETURN_FUNC(memset_func_t, __memset_aarch64);
  }
}
// bionic/libc/arch-arm64/ifuncs.cpp

59.8.3 Bionic：ARM 32 位的 CPU 变体字符串函数

ARM 32 位 bionic 同样使用运行时 ifunc 分派，但选择机制不同。每个 CPU 变体的实现都被无条件编进 libc，全部并列在 bionic/libc/Android.bp 中同一个 arm: 的 srcs: 块下。由 bionic/libc/arch-arm/ifuncs.cpp 中的解析器在加载时挑一个——它们从 /dev/cpu_variant:arm 读取 CPU 名称，而不是像 ARM64 那样查 HWCAP 位。源码树为每个 CPU 变体准备了单独目录：

// art/runtime/arch/instruction_set_features.cc (line 55-80)
std::unique_ptr<const InstructionSetFeatures> InstructionSetFeatures::FromVariantAndHwcap(
    InstructionSet isa, const std::string& variant, std::string* error_msg) {
  auto variant_features = FromVariant(isa, variant, error_msg);
  if (variant_features == nullptr) return nullptr;

  // Pixel3a is wrongly reporting itself as cortex-a75, so validate the
  // features with hwcaps.
  if (isa == InstructionSet::kArm64) {
    auto new_features = down_cast<const Arm64InstructionSetFeatures*>(
        variant_features.get())->IntersectWithHwcap();
    if (!variant_features->Equals(new_features.get())) {
      LOG(WARNING) << "Mismatch between instruction set variant of device ("
            << *variant_features << ") and features returned by the hardware ("
            << *new_features << ")";
    }
    return new_features;
  }
  return variant_features;
}

关于 Pixel 3a 的那段注释很有教育意义：它说明即便是 Google 自己的设备，也可能配错 TARGET_CPU_VARIANT，因此运行时校验必不可少。

quick_entrypoints_arm64.S 里放着在托管代码（Java/Kotlin）与 ART 运行时之间搭桥的汇编例程，属于 Android 中性能最敏感的代码之一。文件开头就是被调用者保存帧的建立宏：

// art/runtime/arch/arm64/quick_entrypoints_arm64.S (line 45-60)

    LOAD_RUNTIME_INSTANCE xIP0

    INCREASE_FRAME FRAME_SIZE_SAVE_REFS_AND_ARGS

59.8.10 ART：多种特性检测策略

ART 实现了八种探测 CPU 特性的入口（七种构造方法加上 IntersectWithHwcap()）。没有任何单一检测方法在所有设备上都可靠：

// art/runtime/arch/arm64/instruction_set_features_arm64.h (line 35-55)
// 1. FromVariant() - Parse a CPU variant string like "cortex-a75"

// 2. FromBitmap() - Parse a bitmap (used for serialization/deserialization)
static Arm64FeaturesUniquePtr FromBitmap(uint32_t bitmap);

// 3. FromCppDefines() - Use C preprocessor defines set by the compiler
static Arm64FeaturesUniquePtr FromCppDefines();

// 4. FromCpuInfo() - Parse /proc/cpuinfo
static Arm64FeaturesUniquePtr FromCpuInfo();

// 5. FromHwcap() - Use the kernel's AT_HWCAP auxiliary vector
static Arm64FeaturesUniquePtr FromHwcap();

// 6. FromAssembly() - Run assembly tests to probe feature availability
static Arm64FeaturesUniquePtr FromAssembly();

// 7. FromCpuFeatures() - Use external cpu_features library
static Arm64FeaturesUniquePtr FromCpuFeatures();

// 8. IntersectWithHwcap() - Validate variant features against hardware

ARM64 上首选的做法是 FromVariantAndHwcap()：先按构建期的变体字符串生成特性，再用运行时硬件能力校验一遍。这个两步流程能抓住 Pixel 3a 这类“设备报错自己的 CPU 变体”的情形。

至于 RISC-V，目前只有 FromVariant() 与 FromCppDefines() 可用，硬件探测路径还是空壳。

三层优化策略：

  2. CPU 变体选择（构建期）：ARM 32 位为各主要 CPU 变体准备了独立的手工调优实现，构建系统把它们全部编进同一个二进制，再由 ifunc 机制或链接器按设备配置挑出合适的一份。

59.8.12 ARM 32 位指令集：ARM 与 Thumb

ARM 32 位在 AOSP 各架构中有一项独有特性：两套指令编码。ARM toolchain 支持在两者间切换：

// build/soong/cc/config/arm_device.go
armArmCflags = []string{}

armThumbCflags = []string{
    "-mthumb",
    "-Os",
}

toolchain 的 InstructionSetFlags() 方法负责选择：

// build/soong/cc/config/arm_device.go
func (t *toolchainArm) InstructionSetFlags(isa string) (string, error) {
    switch isa {
    case "arm":
        return "${config.ArmArmCflags}", nil
    case "thumb", "":
        return "${config.ArmThumbCflags}", nil
    default:
        return t.toolchainBase.InstructionSetFlags(isa)
    }
}

Thumb 模式（默认）使用 16 位指令编码并配 -Os（按体积优化），能显著减小代码体积——这对主要用于兼容性的 32 位次架构至关重要。

ARM 模式使用 32 位指令编码。模块可在 Android.bp 中通过 instruction_set: "arm" 属性选择加入，用于确实需要完整 32 位指令集的场合（例如用了 Thumb 里没有的指令的手工汇编）。

}

-mfpu= 参数指定 FPU 类型：

  • vfpv3-d16：基础 VFP，16 个双精度寄存器（无 NEON）
  • neon：完整 NEON SIMD 单元
  • neon-fp-armv8：NEON 加上 ARMv8 浮点扩展

现代 32 位设备上最常用的是 armv7-a-neon 变体，因为它启用了 NEON SIMD 优化。

59.8.14 Bionic 各架构的 strip 配置

连二进制的 strip（裁剪符号）方式都按架构不同。bionic 的 Android.bp 为各架构配置了不同的 strip 行为：

// bionic/libc/Android.bp
arch: {
    arm: {
        // arm32 does not produce complete exidx unwind information,
        // so keep the .debug_frame which is relatively small and does
        // include needed unwind information.
        // See b/132992102 for details.
        strip: {
            keep_symbols_and_debug_frame: true,
        },
    },
    arm64: {
        strip: {
            keep_symbols: true,
        },
    },
    riscv64: {
        strip: {
            keep_symbols: true,
        },
    },
    x86: {
        strip: {
            keep_symbols: true,
        },
    },
    x86_64: {
        strip: {
            keep_symbols: true,
        },
    },
},

ARM 32 位是唯一需要 keep_symbols_and_debug_frame 的架构。因为 ARM 32 位使用另一套栈展开机制（.ARM.exidx 段中的 EXIDX 表），而该机制在某些情形下并不完整，所以必须保留 .debug_frame 段作为回退。其余架构都用基于 DWARF 的展开，只需保留符号表。

59.8.15 页大小宏的处理

bionic 对页大小宏的处理是架构感知的：

// build/soong/cc/config/arm64_device.go
pctx.VariableFunc("Arm64Cflags", func(ctx android.PackageVarContext) string {
    flags := arm64Cflags
    if ctx.Config().NoBionicPageSizeMacro() {
        flags = append(flags, "-D__BIONIC_NO_PAGE_SIZE_MACRO")
    } else {
        flags = append(flags, "-D__BIONIC_DEPRECATED_PAGE_SIZE_MACRO")
    }
    return strings.Join(flags, " ")
})

x86_64 有同样的模式：

// build/soong/cc/config/x86_64_device.go
pctx.VariableFunc("X86_64Cflags", func(ctx android.PackageVarContext) string {
    flags := x86_64Cflags
    if ctx.Config().NoBionicPageSizeMacro() {
        flags = append(flags, "-D__BIONIC_NO_PAGE_SIZE_MACRO")
    } else {
        flags = append(flags, "-D__BIONIC_DEPRECATED_PAGE_SIZE_MACRO")
    }
    return strings.Join(flags, " ")
})

这与当前支持 ARM64 16KB 页的努力有关。<unistd.h> 里的 PAGE_SIZE 宏传统上返回 4096，但在跑 16KB 页内核的设备上这是错的。__BIONIC_NO_PAGE_SIZE_MACRO 让 bionic 干脆不定义 PAGE_SIZE，迫使代码在运行时调用 getpagesize() 或 sysconf(_SC_PAGE_SIZE)；__BIONIC_DEPRECATED_PAGE_SIZE_MACRO 则保留该宏但标记为废弃，代码用到它就会产生告警。

产品配置通过如下开关启用这一行为：

# build/make/target/product/aosp_arm64.mk
PRODUCT_NO_BIONIC_PAGE_SIZE_MACRO := true

59.8.16 ARM 32 位 LPAE 规避

若干 ARM 32 位 CPU 变体需要手工定义一个宏，来声明支持大物理地址扩展（Large Physical Address Extension，LPAE）：

// build/soong/cc/config/arm_device.go
"cortex-a7": []string{
    "-mcpu=cortex-a7",
    "-mfpu=neon-vfpv4",
    // Fake an ARM compiler flag as these processors support LPAE which clang
    // don't advertise.
    // TODO This is a hack and we need to add it for each processor that
    // supports LPAE until some better solution comes around. See Bug 27340895
    "-D__ARM_FEATURE_LPAE=1",
},

这是一个由来已久的规避（Bug 27340895）：对支持 LPAE 的处理器，Clang 不会自动定义 __ARM_FEATURE_LPAE。而使用 LPAE 专属 ldrd/strd 指令（64 位原子加载/存储）的代码，正是靠这个宏来判断硬件支持。

59.9 LFI Toolchain：ARM64 上的轻量故障隔离

Android 17 新增了第六个 toolchain，它并不对应任何新的 CPU 架构，而是一个为轻量故障隔离（Lightweight Fault Isolation，LFI）构建的 ARM64 变体。LFI 是一种进程内沙箱：把不受信任的原生代码限制在地址空间的某个受限区域内，既不需要单独进程，也不需要硬件特权级切换。该 toolchain 自成一个文件，与各架构的设备配置并列：

源文件：build/soong/cc/config/arm64_lfi_device.go

59.9.1 为什么需要独立的 Toolchain

59.1.1 节已经说明，toolchainFactories 以操作系统、架构以及一个 LFI 布尔标志为键，registerLFIToolchainFactory 负责填充 true 那一格。

原因在于 LFI 是一种代码生成属性：沙箱内的代码必须用不同的目标与受限的指令选择来编译，这样 LFI 的重写器/校验器才能证明代码始终留在沙箱内。这个决定必须在解析 toolchain 时就做出——而 toolchain 解析发生得很早，且只依赖目标的架构。于是 LFI 被建模成一套平行的 toolchain，而不是往普通 toolchain 上加一个开关。

android.Target 这一侧有三处配套：一个专门的 LFI bool 字段；一个 AndroidLFITarget，在模块选择加入时放在其 target 列表的最前面；以及 arch mutator 产出的独特 lfi_ 变体名：

// build/soong/android/arch.go
// If this is an LFI (Lightweight Fault Isolation) arch variant. There is also an LFI
// transition mutator, but we have separate LFI arch variants as well because toolchain
// resolution happens early, based on arch.
LFI bool
// build/soong/android/arch.go
func (target Target) ArchVariation() string {
    var variation string
    if target.NativeBridge {
        variation = "native_bridge_"
    } else if target.LFI {
        variation = "lfi_"
    }
    variation += target.Arch.String()
    return variation
}

59.9.2 LFI 的 ARM64 Toolchain

LFI toolchain 复用 ARM64 的参数拼装辅助函数，但把架构固定在一套确定配置上。工厂函数无视板子声明的变体，强制 armv8-a + Cortex-A53 调优 + branchprot 特性——这是 LFI 编译器目前唯一支持的配置：

// build/soong/cc/config/arm64_lfi_device.go
func arm64LFIToolchainFactory(arch android.Arch) Toolchain {
    // Force armv8-a when compiling for lfi, as that's all the lfi compiler supports for now.
    arch = android.Arch{
        ArchType:     android.Arm64,
        ArchVariant:  "armv8-a",
        CpuVariant:   "cortex-a53",
        Abi:          []string{"arm64-v8a"},
        ArchFeatures: []string{"branchprot"},
    }
    toolchainCflags, toolchainLdflags := arm64ToolchainFlags(arch)
    return &toolchainLFIArm64{
        toolchainCflags:  toolchainCflags,
        toolchainLdflags: toolchainLdflags,
    }
}

func init() {
    registerLFIToolchainFactory(android.Android, android.Arm64, arm64LFIToolchainFactory)
}

工厂调用的是 arm64ToolchainFlags——即 59.2.6 节从普通 ARM64 工厂中单拆出来的辅助函数。因此 LFI toolchain 继承了与常规构建完全相同的 PAC/BTI 参数与 Cortex-A53 勘误修复。这正是当初要拆出该辅助函数的原因。

toolchain 类型本身与普通 ARM64 toolchain 有两处不同。第一，它的 Clang triple 是 LFI 后端能识别的自定义 triple；第二，它嵌入的是 toolchainLFI（位于 build/soong/cc/config/lfi.go）而不是 toolchainBionic，因此不链接 CRT 目标文件，且 Lfi() 返回 true：

// build/soong/cc/config/arm64_lfi_device.go
func (t *toolchainLFIArm64) ClangTriple() string {
    return "aarch64_lfi-unknown-linux-android30"
}

func (t *toolchainLFIArm64) Cflags() string {
    return "${config.Arm64Cflags} -mno-outline-atomics"
}
// build/soong/cc/config/lfi.go
type toolchainLFI struct {
    toolchainBase
    toolchainNoCrt
}

func (toolchainLFI) Lfi() bool { return true }

aarch64_lfi- triple 把编译器引向对沙箱友好的代码模型；-mno-outline-atomics 则让原子操作保持内联——因为外联的原子辅助例程会调用沙箱之外的运行时支持。这也是 59.1.2 节给 Toolchain 接口加上 Lfi() 方法后的具体回报：普通 bionic toolchain 返回 false，只有这套 toolchain 返回 true，于是构建流程的其余部分就能按“是否在产出沙箱代码”来分支。

59.10 默认 16KB 页大小

Android 17 对架构支持影响最大的一项变化，在任何单条 -march= 参数里都看不见：平台现在默认按 16KB 页大小对齐 64 位二进制。ARM64 早就允许 4KB、16KB、64KB 三种页；但直到最近，AOSP 出厂的二进制仍按 4KB 页对齐，而 16KB 页内核无法加载这种二进制。Android 17 把这个默认值反了过来。

59.10.1 构建侧的默认值

TARGET_MAX_PAGE_SIZE_SUPPORTED 控制 ELF 段的对齐。它的默认值在 build/make/core/config.mk 中计算：

# build/make/core/config.mk
ifdef PRODUCT_MAX_PAGE_SIZE_SUPPORTED
  TARGET_MAX_PAGE_SIZE_SUPPORTED := $(PRODUCT_MAX_PAGE_SIZE_SUPPORTED)
else ifeq ($(strip $(call is-low-mem-device)),true)
  # Low memory device will have 4096 binary alignment.
  TARGET_MAX_PAGE_SIZE_SUPPORTED := 4096
else ifeq ($(call math_lt,$(VSR_VENDOR_API_LEVEL),34),true)
  TARGET_MAX_PAGE_SIZE_SUPPORTED := 4096
else ifeq (,$(filter arm64 x86_64,$(TARGET_ARCH)))
  # TARGET_MAX_PAGE_SIZE_SUPPORTED > 4096 is only supported in arm64 and
  # x86_64 targets.
  TARGET_MAX_PAGE_SIZE_SUPPORTED := 4096
else
  # The default binary alignment for userspace is 16384.
  TARGET_MAX_PAGE_SIZE_SUPPORTED := 16384
endif

默认是 16384（16KB），除非有例外主动退出：低内存设备、vendor API 级别仍停留在旧 VSR 的厂商、以及 32 位或 RISC-V 目标。在这里，只有 arm64 与 x86_64 支持大于 4KB 的页。

这个值会以 MaxPageSizeSupported() 的形式直接流入各架构的链接参数。59.2.7 节已展示它如何喂给 ARM64 的 -Wl,-z,max-page-size= 参数；x86_64 toolchain 同样消费它；RISC-V 则保持硬编码的 4096（59.4.4 节）。

59.10.2 Bionic 侧的宏

按 16KB 页对齐段只是故事的一半。若代码把 PAGE_SIZE 硬编码成编译期常量 4096，在 16KB 内核上算出的缓冲区大小与 mmap 对齐都会是错的。bionic 用 59.8.15 节所述的页大小宏控制来解决：-D__BIONIC_NO_PAGE_SIZE_MACRO 彻底移除 PAGE_SIZE 常量，迫使代码在运行时调用 getpagesize() 或 sysconf(_SC_PAGE_SIZE)；-D__BIONIC_DEPRECATED_PAGE_SIZE_MACRO 则保留宏但标记其使用。AOSP 通用 arm64 产品开启了严格形式：

# build/make/target/product/aosp_arm64.mk
PRODUCT_NO_BIONIC_PAGE_SIZE_MACRO := true

Soong 把 PRODUCT_NO_BIONIC_PAGE_SIZE_MACRO 读作 NoBionicPageSizeMacro()，由它决定各 LP64 架构的基础 cflags 函数追加哪一个宏——也就是 59.2 节与 59.8.15 节里的 Arm64Cflags、X86_64Cflags 这两个 VariableFunc。对 Android 17 而言，最终效果是：平台二进制按 16KB 对齐，同时 C 库不再允许新的平台代码假定固定页大小。于是同一份镜像能在 4KB 与 16KB 内核上都正确运行。

小结

Android 的架构支持是一套分层的体系，建立在少量设计原则之上：

  1. Toolchain 抽象：toolchain.go 中的 Toolchain 接口用统一 API 把架构细节藏起来。五种受支持的架构（ARM、ARM64、x86、x86_64、RISC-V 64）各提供一个工厂，工厂产出一个带正确编译参数的 Toolchain 实现。

  2. 三层参数叠加：全局参数（安全、优化、告警）作用于所有代码；架构参数（-march=、-mcpu=）针对目标 ISA 调优；不可覆盖参数强制关键安全告警。

  3. 双架构的 multilib：compile_multilib 属性与 TARGET_2ND_ARCH 机制让一台设备同时支持 32 位与 64 位代码，这对 ARM64 过渡至关重要。

  4. 架构专属热点路径：bionic 与 ART 里性能攸关的代码按架构手写汇编。优化选择最多有三层：架构、CPU 变体，以及经 ifunc 实现的运行时硬件探测。

  5. 务实的 big.LITTLE 调优：AOSP 不为最快的大核优化，而为能效小核调优，以避免异构配置下的病态变慢。

  6. 跨架构兼容的 Native Bridge：NativeBridgeCallbacks 接口支撑二进制翻译（Berberis、Houdini），用来运行异种架构的原生代码。

  7. 平行的 LFI toolchain：Android 17 把轻量故障隔离建模为一套独立的 ARM64 toolchain（Lfi() 返回 true），通过 toolchain 工厂 map 中的 lfi bool 键解析，复用普通 ARM64 的参数逻辑并固定一个对沙箱友好的 target triple。

Android 17 还把 arm64 与 x86_64 上 64 位二进制的 16KB 页对齐设为默认；新增 Intel pantherlake 的 x86/x86_64 变体（ART 的特性表也同步支持）；为 RISC-V 基线 ISA 增加 zvbb 向量位操作扩展；并把固定的 Clang 推进到 clang-r584948。

第 58 章：调试与性能剖析工具

Android 自带一整套丰富的调试与性能剖析工具，其中大多数就构建在 AOSP 源码树里。第三方方案是从外部接上去的；而这一套工具本身就是平台的一部分。

logd 是一个 init 服务。debuggerd 是被编译进每个原生进程的信号处理器。Perfetto 的 data source 就住在 SurfaceFlinger、ART 和内核里面。dumpsys 则与每一个注册到 Binder 的服务对话。

本章逐层讲解每个工具：先看源码树中实现该工具的代码，再看平台工程师日常使用的命令行调用方式与分析工作流。

58.1.2 设计原则

AOSP 的调试工具贯穿着几条反复出现的主线：

  1. 常驻的低开销插桩。 logd 在每台设备上都在运行；atrace 埋点被编译进框架代码里；debuggerd 的信号处理器在每个原生进程里都注册着。在没人开始监听之前，开销是零或者接近于零。

  2. 采集与分析分离。 Perfetto 把 traced（采集）与 trace_processor（分析）分开。simpleperf 把 record 与 report 分开。这样就能在资源受限的设备上采集，在性能强劲的工作站上分析。

  3. Protobuf 优先的传输格式。 tombstone、Perfetto trace 和 bugreport 的结构化数据都用 protobuf，文本渲染只是表现层。

  4. 最小化特权。 crash_dump 读完寄存器后就降权；logd 在提供日志数据前先校验凭据；heapprofd 用 SELinux 约束自己能剖析哪些进程。

  5. 与 service manager 集成。 dumpsys 通过 IServiceManager 枚举服务，每个服务实现自己的 dump() 方法——于是在数百个子系统之上就有了一个统一的诊断接口。

58.2.2 日志缓冲区与 Log ID

logd 维护若干个独立的环形缓冲区，每个都由一个 log_id_t 枚举值标识：

缓冲区 log_id_t 默认大小 用途
main LOG_ID_MAIN 256 KB 通用应用日志
system LOG_ID_SYSTEM 256 KB 框架/系统日志
radio LOG_ID_RADIO 256 KB 电话协议栈
events LOG_ID_EVENTS 256 KB 二进制事件日志
crash LOG_ID_CRASH 256 KB 崩溃/ANR trace
kernel LOG_ID_KERNEL 256 KB 内核消息（经 kmsg）
security LOG_ID_SECURITY 256 KB 安全审计事件

这些尺寸常量定义在 system/logging/logd/LogSize.h 中：

// system/logging/logd/LogSize.h
static constexpr size_t kDefaultLogBufferSize = 256 * 1024;
static constexpr size_t kLogBufferMinSize = 64 * 1024;
static constexpr size_t kLogBufferMaxSize = 256 * 1024 * 1024;

缓冲区大小可以在运行时用 logcat -G <size> 调整，也可以设置 persist.logd.size.main 之类的系统属性。GetBufferSizeFromProperties() 会在 LogBuffer::Init() 期间读取这些属性。

58.2.3 LogBuffer 接口

system/logging/logd/LogBuffer.h 中的 LogBuffer 类定义了所有缓冲区实现都必须满足的抽象接口：

// system/logging/logd/LogBuffer.h
class LogBuffer {
  public:
    virtual ~LogBuffer() {}
    virtual void Init() = 0;

    virtual int Log(log_id_t log_id, log_time realtime, uid_t uid, pid_t pid,
                    pid_t tid, const char* msg, uint16_t len) = 0;

    virtual std::unique_ptr<FlushToState> CreateFlushToState(
        uint64_t start, LogMask log_mask) = 0;
    virtual bool FlushTo(
        LogWriter* writer, FlushToState& state,
        const std::function<FilterResult(log_id_t, pid_t, uint64_t,
                                         log_time)>& filter) = 0;

    virtual bool Clear(log_id_t id, uid_t uid) = 0;
    virtual size_t GetSize(log_id_t id) = 0;
    virtual bool SetSize(log_id_t id, size_t size) = 0;
    virtual uint64_t sequence() const = 0;
};

几个关键设计点：

  • Log() 是写入路径。它接收的是已经校验过的消息，身份信息（uid、pid、tid）来自内核 socket 凭据。

  • FlushTo() 是读取路径。它用 FlushToState 遍历缓冲区，在多次调用之间保持位置，并施加一个过滤回调，回调返回 FilterResult::kSkip、kStop 或 kWrite。

  • LogMask 是一个位掩码（uint32_t），用来选择读端想要哪些缓冲区。常量 kLogMaskAll = 0xFFFFFFFF 表示全选。

58.2.4 LogBufferElement：存储单元

每条日志消息都存成一个 LogBufferElement，定义在 system/logging/logd/LogBufferElement.h：

// system/logging/logd/LogBufferElement.h
class __attribute__((packed)) LogBufferElement {
  public:
    LogBufferElement(log_id_t log_id, log_time realtime, uid_t uid,
                     pid_t pid, pid_t tid, uint64_t sequence,
                     const char* msg, uint16_t len);

    uint32_t GetTag() const;
    bool FlushTo(LogWriter* writer);
    LogStatisticsElement ToLogStatisticsElement() const;

    log_id_t log_id() const;
    uid_t uid() const;
    pid_t pid() const;
    pid_t tid() const;
    uint16_t msg_len() const;
    const char* msg() const;
    uint64_t sequence() const;
    log_time realtime() const;

  private:
    const uint32_t uid_;
    const uint32_t pid_;
    const uint32_t tid_;
    uint64_t sequence_;
    log_time realtime_;
    char* msg_;
    const uint16_t msg_len_;
    const uint8_t log_id_;
};

__attribute__((packed)) 保证了内存开销最小——当你存着几十万条消息时，每个字节都算数。该结构的布局就是为了与 socket 上传入的数据包格式对齐。

向读端刷出数据时，FlushTo() 会构造一个 logger_entry 头：

// system/logging/logd/LogBufferElement.cpp
bool LogBufferElement::FlushTo(LogWriter* writer) {
    struct logger_entry entry = {};
    entry.hdr_size = sizeof(struct logger_entry);
    entry.lid = log_id_;
    entry.pid = pid_;
    entry.tid = tid_;
    entry.uid = uid_;
    entry.sec = realtime_.tv_sec;
    entry.nsec = realtime_.tv_nsec;
    entry.len = msg_len_;
    return writer->Write(entry, msg_);
}

58.2.5 日志摄入：LogListener 与 LogKlog

有两条不同的通路把日志消息送进 logd：

LogListener（system/logging/logd/LogListener.h）通过 Unix 域套接字 /dev/socket/logdw 接收用户态进程的消息。它同时支持同步读取与 io_uring 两种方式，后者吞吐更高：

// system/logging/logd/LogListener.h
class LogListener {
  public:
    explicit LogListener(LogBuffer* buf);
    bool StartListener();
  private:
    void HandleDataUring();
    void HandleDataSync();
    void ProcessBuffer(struct ucred* cred, void* buffer, ssize_t n);
    bool InitializeUring();
    std::unique_ptr<IOUringSocketHandler> uring_listener_;
    int socket_;
    LogBuffer* logbuf_;
};

ProcessBuffer() 方法从 socket 的辅助数据（SCM_CREDENTIALS）中取出发送者的凭据（uid、gid、pid）。这就保证了日志消息无法被伪造。

LogKlog（system/logging/logd/LogKlog.h）从 /proc/kmsg 读取内核消息（/dev/kmsg 只以只写方式打开，供 logd 自身输出 dmesg 用），并把它们注入 LOG_ID_KERNEL 缓冲区。它还负责单调时钟到实时时钟的换算：

// system/logging/logd/LogKlog.h
class LogKlog : public SocketListener {
    static log_time correction;
  public:
    static void convertMonotonicToReal(log_time& real) {
        real += correction;
    }
  protected:
    log_time sniffTime(const char*& buf, ssize_t len, bool reverse);
    pid_t sniffPid(const char*& buf, ssize_t len);
};

58.2.6 日志读取：LogReader 与 LogReaderThread

logd 的读取侧服务于连到 /dev/socket/logdr 的客户端。LogReader（system/logging/logd/LogReader.h）继承 SocketListener，并为每个连上来的客户端创建一个 LogReaderThread：

// system/logging/logd/LogReader.h
class LogReader : public SocketListener {
  public:
    explicit LogReader(LogBuffer* logbuf, LogReaderList* reader_list);
  protected:
    virtual bool onDataAvailable(SocketClient* cli);
  private:
    LogBuffer* log_buffer_;
    LogReaderList* reader_list_;
};

每个 LogReaderThread 各自维护读取位置与过滤条件：

LogReaderThread 的关键字段（见 system/logging/logd/LogReaderThread.h）：

  • tail_：在 -t N / -T N 模式下，最近要显示的行数。

  • pid_：可选的 PID 过滤（对应 logcat --pid=<pid>）。

  • non_block_：为 true 时，dump 完就断开（对应 logcat -d）。

  • skip_ahead_[]：每个缓冲区各自的跳过计数——缓冲区溢出、旧条目被剪除时，读端可能还引用着它们，就靠这个计数跳过。

  • deadline_：日志回绕操作使用的 CLOCK_MONOTONIC 截止时间。

58.2.7 CommandListener：控制接口

CommandListener（system/logging/logd/CommandListener.h）在 /dev/socket/logd 提供一个控制套接字，用于管理类命令。它用一套基于宏的模式来注册命令处理器：

// system/logging/logd/CommandListener.h
#define LogCmd(name, command_string)                                \
    class name##Cmd : public FrameworkCommand {                     \

58.2.9 缓冲区大小配置详解

system/logging/logd/LogSize.cpp 中的缓冲区初始化逻辑揭示了若干重要的平台相关行为：

// system/logging/logd/LogSize.cpp
size_t GetBufferSizeFromProperties(log_id_t log_id) {
    static const bool isDebuggable =
        android::base::GetBoolProperty("ro.debuggable", false);
    if (isDebuggable) {
        static const bool mayOverride = isAllowedToOverrideBufferSize();
        if (mayOverride) {
            if (auto size = GetBufferSizePropertyOverride(log_id)) {
                return *size;
            }
        }
    } else {
        static const bool isLowRam =
            android::base::GetBoolProperty("ro.config.low_ram", false);
        if (isLowRam) {
            return kLogBufferMinSize;  // 64 KB for low-RAM devices
        }
    }
    return kDefaultLogBufferSize;  // 256 KB
}

58.2.10 压缩

在现代设备上默认使用 Zstd 压缩：对典型的日志流可以做到约 3–5 倍压缩率，而 CPU 开销极小。

LogStatistics 类分别跟踪压缩后与压缩前的大小。Sizes() 方法返回压缩后大小（实际占用的内存），SizeReadable() 返回压缩前大小（用户预期看到的值）：

// system/logging/logd/LogStatistics.h
size_t Sizes(log_id_t id) const {
    auto lock = std::lock_guard{lock_};
    if (overhead_[id]) {
        return *overhead_[id];  // compressed size
    }
    return mSizes[id];
}

size_t SizeReadable(log_id_t id) const {
    auto lock = std::lock_guard{lock_};
    return mSizes[id];  // uncompressed size
}

58.3.6 Trace Processor 与 SQL 查询

Perfetto 的 trace_processor 是一个强大的分析引擎：它导入 trace 文件，并将其暴露为一个 SQL 数据库。代码位于 external/perfetto/src/trace_processor/。

表/视图 内容

thread_slice 与线程关联的 slice
process 进程元数据（pid、name、uid）
thread 线程元数据（tid、name、process）
sched_slice CPU 调度器事件
counter 计数值（CPU 频率、内存等）

SQL 查询示例：

-- Find the longest main-thread slices (potential jank sources)
SELECT
    ts,
    dur / 1e6 as dur_ms,
    name
FROM slice
WHERE track_id IN (
    SELECT id FROM thread_track
    WHERE utid IN (
        SELECT utid FROM thread
        WHERE is_main_thread = 1
    )
)
ORDER BY dur DESC
LIMIT 20;

-- CPU frequency distribution during the trace
SELECT
    cpu,
    CAST(value AS INT) as freq_khz,
    COUNT(*) as sample_count,
    SUM(dur) / 1e9 as total_seconds
FROM counter
JOIN counter_track ON counter.track_id = counter_track.id
WHERE counter_track.name = 'cpufreq'
GROUP BY cpu, freq_khz
ORDER BY cpu, freq_khz;

-- Scheduling latency for a specific process
SELECT
    thread.name,
    AVG(sched_slice.dur) / 1e6 as avg_runtime_ms,
    MAX(sched_slice.dur) / 1e6 as max_runtime_ms,
    COUNT(*) as schedule_count
FROM sched_slice
JOIN thread USING (utid)
JOIN process USING (upid)
WHERE process.name LIKE '%myapp%'
GROUP BY thread.name
ORDER BY avg_runtime_ms DESC;

-- Binder transaction latency
SELECT
    client_ts,
    client_dur / 1e6 as dur_ms,
    client_process,
    server_process
FROM android_binder_txns
WHERE client_dur > 16e6  -- longer than one frame
ORDER BY client_dur DESC
LIMIT 20;

58.5.3 工作原理

  1. 拦截：heapprofd 通过 LD_PRELOAD（用于可调试应用）或基于信号的机制（在运行时修补 malloc 分发表）来拦截 malloc/free 调用。

  2. 采样：并非每次分配都记录。heapprofd 采用泊松采样：某次分配被采中的概率与其大小成正比。采样间隔可配置（默认 4096 字节）。

  3. 栈展开：当一次分配被采中时，客户端抓取调用栈（用帧指针或 DWARF），然后通过共享内存把栈发给守护进程。

  4. 簿记：守护进程对调用栈去重，并累计分配总量。由此得到一份紧凑的表示。

  5. 输出：剖析数据流入 Perfetto 的 trace 格式，在 Perfetto UI 中呈现为火焰图。

-- Find the allocation sites with the most bytes
-- (allocations reference a callsite, whose leaf frame carries the symbol)
SELECT
    SUM(hpa.size) as total_bytes,
    COUNT(*) as alloc_count,
    spf.name as leaf_frame
FROM heap_profile_allocation hpa
JOIN stack_profile_callsite spc ON hpa.callsite_id = spc.id
JOIN stack_profile_frame spf ON spc.frame_id = spf.id
GROUP BY hpa.callsite_id
ORDER BY total_bytes DESC
LIMIT 20;

-- Track allocations over time
SELECT
    ts / 1e9 as time_s,
    SUM(size) as cumulative_bytes
FROM heap_profile_allocation
WHERE size > 0
GROUP BY CAST(ts / 1e9 AS INT)
ORDER BY time_s;

// From dumpsys.cpp
static bool ConvertPriorityTypeToBitmask(const String16& type,
                                          int& bitmask) {
    if (type == PriorityDumper::PRIORITY_ARG_CRITICAL) {
        bitmask = IServiceManager::DUMP_FLAG_PRIORITY_CRITICAL;
        return true;
    }
    if (type == PriorityDumper::PRIORITY_ARG_HIGH) {
        bitmask = IServiceManager::DUMP_FLAG_PRIORITY_HIGH;
        return true;
    }
    if (type == PriorityDumper::PRIORITY_ARG_NORMAL) {
        bitmask = IServiceManager::DUMP_FLAG_PRIORITY_NORMAL;
        return true;
    }
    return false;
}

58.9.2 信号处理器：debuggerd_handler

每个原生进程都有一个由 system/core/debuggerd/handler/debuggerd_handler.cpp 注册的信号处理器。该处理器捕获致命信号，并拉起 crash_dump 进程：

// system/core/debuggerd/handler/debuggerd_handler.cpp
#define CRASH_DUMP_NAME "crash_dump64"  // or crash_dump32
#define CRASH_DUMP_PATH "/apex/com.android.runtime/bin/" CRASH_DUMP_NAME

该处理器遵守严格的安全规则：

  • 它运行在信号上下文中，因此不能使用 malloc、锁或大多数 libc 函数。

  • 它用 clone() 创建一个“伪线程”，再由后者安全地调用 execle() 拉起 crash_dump。

  • 它通过管道把崩溃信息（寄存器、siginfo、ucontext）传出去。

58.9.3 CrashInfo 协议

信号处理器通过管道把崩溃信息发给 crash_dump，用的是 system/core/debuggerd/protocol.h 中的 CrashInfo 结构：

struct CrashInfoDataCommon {
  uint32_t version;
  siginfo_t siginfo;
  ucontext_t ucontext;
  uintptr_t abort_msg_address;

struct CrashInfoDataDynamic {
  uintptr_t fdsan_table_address;

  uintptr_t gwp_asan_metadata;

动态部分是以下几处的地址：

  • fdsan 表：文件描述符 sanitizer 状态
  • GWP-ASan：基于采样的内存错误检测状态
  • Scudo：堆分配器元数据，用于检测 use-after-free 与缓冲区溢出

    CD->>PT: 发信号要求 fork VM 进程
    PT->>Kernel: clone() -> vm_pid
    CD->>Kernel: PTRACE_DETACH(所有线程)

    Note over CD: drop_capabilities()

    CD->>TS: connect_tombstone_server()
    TS-->>CD: output_fd, proto_fd

    alt 回溯模式
        CD->>CD: dump_backtrace()
    else tombstone 模式
        CD->>CD: engrave_tombstone()
    end

    CD->>AM: activity_manager_notify()
    CD->>TS: notify_completion()

crash_dump.cpp 中的几个关键点：

  1. 枚举线程：用 procinfo 的 GetProcessTids() 找出所有线程。

  2. 读寄存器：用 ptrace(PTRACE_SEIZE) 与 PTRACE_INTERRUPT 停住线程并读寄存器，对进程的干扰尽量小。

  3. VM 进程快照：fork 出目标进程地址空间的一份副本，这样即使线程恢复运行，crash_dump 依然能读内存。

  4. Guest 架构支持：对于跑在 NativeBridge 下的进程（例如在 x86 上跑 ARM），ReadGuestRegisters() 会从 TLS 中取出被翻译架构的寄存器状态。

  5. 栈展开：用 unwindstack::AndroidRemoteUnwinder 从 VM 进程快照生成回溯。

58.9.7 Protobuf Tombstone

58.9.10 ActivityManager 通知

发生致命崩溃时，crash_dump 会通过本地套接字通知 ActivityManager：

// crash_dump.cpp
static bool activity_manager_notify(pid_t pid, int signal,
    const std::string& amfd_data, bool recoverable_crash) {
    unique_fd amfd(socket_local_client(
        "/data/system/ndebugsocket",
        ANDROID_SOCKET_NAMESPACE_FILESYSTEM, SOCK_STREAM));

    // Protocol: pid (32-bit), signal (32-bit), recoverable (byte), dump text
    uint32_t datum = htonl(pid);
    WriteFully(amfd, &datum, sizeof(datum));
    datum = htonl(signal);
    WriteFully(amfd, &datum, sizeof(datum));
    uint8_t recoverable_byte = recoverable_crash ? 1 : 0;
    WriteFully(amfd, &recoverable_byte, sizeof(recoverable_byte));
    WriteFully(amfd, amfd_data.c_str(), amfd_data.size() + 1);
    // ...
}

这一通知会触发那个大家熟悉的“应用已停止运行”对话框，并让 ActivityManager 决定是否重启该进程。

58.10.3 CPU 剖析的工作原理

Java 方法采样用的是 ART 运行时内置的采样剖析器：它周期性记录 Java 调用栈，而不对每次方法进入/退出做插桩。

原生采样底层用 simpleperf：

  1. Android Studio 按相应的 PID 与采样率配置 simpleperf。

  2. simpleperf 通过 perf_event_open() 采集样本。

  3. 样本经传输 agent 流式回送到宿主机。

  4. Android Studio 在界面上渲染火焰图。

系统 trace 用 Perfetto：

  1. 依据用户的选择生成一份 TraceConfig。
  2. perfetto 录制全系统事件。
  3. trace 文件被拉回并载入 Android Studio 的 trace 查看器，后者与 Perfetto UI 共用代码。

58.13.1 ANR 的成因

58.18 Profiling 模块：面向应用的主线交付式剖析

Android 15 引入了 Profiling 主线模块（com.android.profiling），它把 Perfetto、heapprofd 与 simpleperf 包在一个安全、限速的 API 之后。任何应用都可以调用这个 API，无需 root，也无需特殊权限。本节考察该模块如何与本章前面讲过的那些调试工具对接。

由于它以主线模块的形式发布，Profiling 子系统跟随自己的发布节奏演进，而不是跟着平台版本走。Android 17（CINNAMON_BUN，SDK 37）是一次实质性跨越：它加入了系统侧的异常检测器（58.19 节）；把触发器目录从两类扩充到十二类（58.18.5 节）；还为结果交付加了确认机制，并会自动清理过期结果文件。

这些新行为全部由 packages/modules/Profiling/flags/flags.aconfig 中的 aconfig 开关把关。正因如此，模块的一次 OTA 就能把特性打开，而不必等平台发版。

58.18.1 动机

在 Profiling 模块出现之前，要在量产设备上采集系统 trace 或堆剖析数据，需要下列条件之一：

  1. root 权限（以便直接运行 perfetto 或 heapprofd），或
  2. 在设备上打开开发者选项，或
  3. 通过 USB 接入 Android Studio。

这些在量产环境下的崩溃排查里都行不通。Profiling 模块的解法是：允许应用以编程方式请求剖析，而结果经过脱敏，只包含请求方应用自己的数据。

58.18.3 ProfilingService 如何驱动 Perfetto

ProfilingService 收到 requestProfiling() 调用后，流程如下：

  1. 限速检查——RateLimiter 在系统级与进程级各用一套基于成本的滑动窗口（按小时、按天、按周）。若请求超出额度，回调会收到 ERROR_FAILED_RATE_LIMIT_SYSTEM 或 ERROR_FAILED_RATE_LIMIT_PROCESS。

  2. 生成配置——Configs 类按请求类型构建相应的 Perfetto TraceConfig protobuf。ProfilingManager 类型到 Perfetto data source 的对应关系：

    ProfilingManager 类型 Perfetto DataSourceConfig 底层工具
    PROFILING_TYPE_SYSTEM_TRACE FtraceConfig + ProcessStatsConfig traced_probes（ftrace）
    PROFILING_TYPE_HEAP_PROFILE HeapprofdConfig heapprofd
    PROFILING_TYPE_STACK_SAMPLING PerfEventConfig traced_perf（simpleperf 后端）
    PROFILING_TYPE_JAVA_HEAP_DUMP JavaHprofConfig ART hprof 生产者

  3. 调用 Perfetto——ProfilingService 以生成的配置为参数，把 perfetto CLI 作为子进程拉起。输出落在 /data/misc/perfetto-traces/profiling/。

  4. 会话监控——一个 TracingSession 对象跟踪状态机：

    REQUESTED -> APPROVED -> PROFILING_STARTED -> PROFILING_FINISHED ->
REDACTED -> COPIED_FILE -> NOTIFIED_REQUESTER -> CLEANED_UP

    失败状态为 ERROR_OCCURRED。

    服务会周期性检查 Perfetto 进程是否已结束（间隔为 PROFILING_DEFAULT_RECHECK_DELAY_MS，即 5 秒）。

  5. trace 脱敏——对系统 trace，由 trace_redactor 二进制（随 APEX 一起分发）过滤原始 trace，只保留请求方 UID 的数据。这会剥掉调度事件、内存映射以及其他进程的数据。

  6. 文件传输——脱敏后的文件经 ParcelFileDescriptor 传给应用的私有存储（/data/data/<pkg>/files/profiling/）跨 Binder 交付，应用会收到一个带文件路径的 ProfilingResult。

58.18.7 结果交付与排队结果

结果通过 Binder 回调交付。若结果就绪时应用未在运行（系统触发的剖析中很常见），服务会把结果排队并重试交付：

  • 最大重试次数：3（可通过 DEFAULT_MAX_RESULT_REDELIVERY_COUNT 配置）
  • 最长保留时间：7 天（QUEUED_RESULT_MAX_RETAINED_DURATION_MS）
  • 排队结果以 protobuf 形式落盘

应用下次通过 registerForAllProfilingResults() 注册全局监听器时，排队的回调就会被交付。

Android 17 用两项改进收紧了这一环节，两者都在开关控制之下：

  • 交付确认（notify_result_delivered）。应用的 callback 消费掉一个排队结果后，ProfilingManager 会回调服务（mProfilingService.notifyResultDelivered(...)，见 packages/modules/Profiling/framework/java/android/os/ProfilingManager.java）。因此服务能确知应用真的收到了该结果：它可以停止重试、把结果从队列里丢掉，而不必只靠重试次数/保留时长这两道上限兜底。

  • 旧文件清理（old_files_cleanup）。已交付的结果文件会在服务侧与应用侧双向回收，这样日积月累的触发器 trace 就不会在应用的私有存储里堆积磁盘占用。

58.19 异常检测器

Android 17 给 Profiling 模块加了第二根支柱：设备端的异常检测器。ProfilingManager 是拉取式的——应用主动要一份 trace。异常检测器则是推送式的：有权限的控制器安装一组描述异常行为的规则，系统持续观察连续信号是否命中这些条件；一旦命中，系统产生一份 AnomalyReport，并可经 Profiling 流水线自动抓取 Perfetto trace。

代码位于独立目录 packages/modules/Profiling/anomaly-detector/，与前者打包在同一个 com.android.profiling APEX 中。

58.19.1 为什么平台里需要一个检测器

动机问题是“那个悄悄伤害设备的应用”。这类应用是个后台进程：它猛捶某个 system_server 的 binder 接口，或者一直泄漏内存直到撞上运行时上限，或者以别的方式拖垮系统，但它永远不崩溃。事后从 bugreport 里追查这些问题很慢；而要求每个应用自己做埋点又不现实、不可扩展。

有了异常检测器，平台（或 OEM 的有权限系统应用）只需声明一次条件，系统便既负责检测、也负责反应。最典型的反应是“在发生的那一刻抓一份 trace”——这复用的正是 58.18 节那套带脱敏、带限速的 Profiling 管道。

58.19.2 规则 API

对外暴露的是 AnomalyDetectorManager（packages/modules/Profiling/anomaly-detector/framework/java/android/os/profiling/anomaly/AnomalyDetectorManager.java），一个 @SystemApi 系统服务，注册在 Context.ANOMALY_DETECTOR_SERVICE（“anomaly_detector”）之下，由 aconfig 开关 anomaly_detector_core_c 控制。它只暴露一个主要调用：

// AnomalyDetectorManager (SystemApi, PRIVILEGED_APPS, requires
// CONFIGURE_ANOMALY_DETECTOR, @RequiresApi(37))
public void setAnomalyDetectorRules(@NonNull Set<Rule> rules);

API 契约中隐含了几个重要性质：

  • 每台设备只有一个控制器。 只有单个有权限的应用可以设置规则，第二个调用方会被拒绝。这样检测器不会变成多套互相冲突的策略的混战场。

  • 整体替换，而非合并。 每次调用都替换整套规则；传空集即完全关闭检测。

  • 权限守护。 调用方需要签名级/特权级权限 CONFIGURE_ANOMALY_DETECTOR。

一个 Rule（packages/modules/Profiling/anomaly-detector/framework/java/android/os/profiling/anomaly/Rule.java）由一个名字和一个条件构成。Android 17 只带一种条件类型：CONDITION_TYPE_BINDER_SPAM。它的参数通过一个 bundle 传入，键包括 BUNDLE_KEY_CONDITION_BINDER_SPAM_INTERFACE_NAME、..._METHOD_NAME、..._CALL_LIMIT、..._BINDER_CALL_INTERVAL_MILLIS。换句话说，“在这个时间窗内对某接口/方法的调用超过 N 次，就算异常”。规则以 RuleParcel 对象形态跨 binder 边界，通过 IAnomalyDetectorService.setRules() 送到服务。

58.19.4 从报告到 trace

连回本章其余部分的枢纽是 ProfileAnomalyHandler。检测器发出 AnomalyReport 后，该处理器请求 Profiling 流水线抓取一份 trace。这份 trace 带 TRIGGER_TYPE_ANOMALY 标签（在 ProfilingTrigger 中值为 8，见 58.18.5 节）。它和其他系统触发的剖析走同一套机制：traced 负责采集，trace_redactor 负责脱敏，只保留越界进程的数据；trace 受限速约束，并交付给已注册的监听器。

ProfilingSessionHelper（.../anomaly/handler/ProfilingSessionHelper.java）把检测器的报告接到一次 Profiling 会话上。它还会经 PerfettoMetadata 工具把标注出异常的元数据一并打包进结果，这样消费结果的一方可以直接跳到异常时间窗。

实际收益很直接：有权限的监控应用只需安装一条 binder 刷接口规则，此后每个越界的后台应用都会产出一份脱敏的 Perfetto trace，且抓取发生在不当行为发生的那一刻。监控应用既不用轮询，也不用挂剖析器，更不需要预先知道哪个应用会出问题。

58.20 UprobeStats：动态插桩

Android 17 中趋于成熟的另一个与剖析相邻的主线模块是 UprobeStats（com.android.uprobestats），位于 packages/modules/UprobeStats/。它提供动态插桩——一种可由服务端配置的用户态进程探测（尤其是 system_server）。它用内核的 uprobe 加 eBPF 观察函数调用，既不修改、也不重新编译目标二进制。平台正是靠它来收集那些罕见或难以插桩的代码路径的全网统计。在 Android 17 中，它新增了 binder 事务探测和一个面向应用的事件交付 API。

58.20.1 一次 uprobe 如何变成一条统计

一个 UprobeStats task 指定一个目标进程、一个或多个探针（一个 BPF 程序加上要挂载的函数偏移），以及一个输出汇。守护进程在目标二进制中解析出函数偏移，经 uprobe 在这些地址上挂载 BPF 程序。函数每次被命中，BPF 程序就往环形缓冲区写一条记录。守护进程从环形缓冲区取出记录，把每条记录或作为 atom 转发给 statsd，或投给已注册的监听器。

58.20.2 Android 17 的新增

17 中有三处变化，都能在该模块的提交历史与当前 API 面中看出来：

  • binder 事务探针。 config.proto 增加了 BinderTransactionFilter，BPF/处理器侧也学会了捕获 binder 接口/方法调用，并把 binder 事务事件写入 statsd。这与异常检测器 binder-spam 规则所消费的原始信号在概念上是同一个，但这里变成可配置、可全网汇总的统计。

  • 面向应用的事件 API。 Android 17（CINNAMON_BUN，SDK 37）新增 dynamic_instrumentation 系统服务，以及一个 @SystemApi 的 DynamicInstrumentationEventService（packages/modules/UprobeStats/framework/java/android/service/uprobestats/DynamicInstrumentationEventService.java），由有权限的应用继承以接收 DynamicInstrumentationEvent。向服务投递事件受 SEND_DYNAMIC_INSTRUMENTATION_EVENTS 权限管控；通过 UprobeStatsBridgeService 注册与配置插桩则需要 DYNAMIC_INSTRUMENTATION 权限。事件经由改名后的桥接服务 UprobeStatsBridgeService/UprobeStatsBridgeServiceImpl（原称 “uprobestats_service”）交付，该服务对事件做批量处理，且只在 SDK 37 及以上可用（@RequiresApi(Build.VERSION_CODES.CINNAMON_BUN)）。

  • 更稳健的错误上报。 BPF 的挂载/加载路径现在会返回细粒度错误码（UprobeStatsError 类型）；挂载前会先排空环形缓冲区；环形缓冲区句柄会被持久化以避免重复事件。一旦这些数据要喂给量产统计，这类可靠性工作就变得关键。

58.21 dmesgd：从内核日志到 DropBox 的桥

dmesgd（system/dmesgd/）是一个小型原生守护进程（几百行 C++）。它把内核环形缓冲区接进与 tombstone、ANR 同一条崩溃上报流水线。启动时它执行 popen("dmesg", "r")，把每一行喂给 DmesgParser（system/dmesgd/dmesg_parser.h）。该解析器识别内核的 WARNING/ERROR 段落，剥掉 64 位地址之类的敏感数据，并组装出一份带标题和报告类型的逐故障报告。

报告就绪后，dmesgd 把它投给 DropBoxManager（system/dmesgd/dmesgd.cpp 包含 <android/os/DropBoxManager.h> 并调用 addText()），标签形如 SYSTEM_<type>_ERROR_REPORT。这正是 dumpstate 生成 bugreport 时会抓取的标签空间（58.8 节）。为避免跨启动重复上报，它把报告标题记在 /data/misc/dmesgd/sent_reports.txt 里，并对每次运行的报告数设上限。这条路径在内核侧的部分——消息如何进入 dmesg 环形缓冲区、又如何经 pstore 跨重启保留——见第 5 章。

58.22 liburingutils：io_uring socket 辅助库

liburingutils（system/liburingutils/）是对外部 liburing 库的薄封装。它只暴露一个辅助类 IOUringSocketHandler（system/liburingutils/include/IOUringSocketHandler/IOUringSocketHandler.h）。该类通过 io_uring 的 multishot recvmsg 从 socket 接收数据报。logd 的 LogListener 正是把这个类放在自己的 uring_listener_ 成员里（58.2.5 节），以实现高吞吐的日志记录摄入。该库也被打进 statsd APEX（system/liburingutils/Android.bp），服务于同一种异步、批量的 socket 接收模式。

58.23 Traceur 的新增 trace 类别

Traceur（packages/apps/Traceur/），即系统跟踪界面，在 Android 17 中新增两个可切换的 Perfetto 类别，两者都定义在 packages/apps/Traceur/src_common/com/android/traceur/PerfettoUtils.java，用户可见的标签则写在 TraceUtils.java 里。wattson 类别（“Wattson power estimation”）服务于设备端功耗模型：它启用 linux.sys_stats data source 以周期性采样 cpufreq 与 cpuidle，同时启用一组 linux.ftrace 事件，如 power/cpu_frequency、power/cpu_idle、power/suspend_resume、sched/sched_switch，以及 cpuhp/* 热插拔 tracepoint。mq 类别（“messagequeue tracing”）则开启一个限定到 mq 类别的 track_event data source，用来捕获 Looper 与 MessageQueue 的分发。

58.24 DeviceDiagnostics：设备端硬件健康

本章至此的工具都在检视软件状态。DeviceDiagnostics（packages/apps/DeviceDiagnostics/，包名 com.android.devicediagnostics）检视的是硬件本身。它就是 设置 > 重置选项 > 设备诊断 背后的应用：一个 Settings 偏好项会拉起它的 MainActivity，用户在那里运行各部件检查，并生成一份带签名的设备物理状况报告。

这个应用服务于翻新与以旧换新：它回答的是“这块屏、这块电池、这块存储还好不好，以及这台设备是不是它自称的那台”，而不是“这个应用为什么慢”。

58.24.1 两条入口

MainActivity（一个渲染 res/xml/preferences_main.xml 的 CollapsingToolbarBaseActivity）提供两条顶层路径：

  • 部件健康（DiagnosticsActivity、diagnostics_landing.xml）跑设备端检查。它含手动屏幕测试与触摸测试：evaluated/ScreenTest* 与 TouchTest* 系列 Activity 引导用户走完全屏图案与触摸网格；另有只读的电池与存储详情页（BatteryActivity、StorageActivity）。
  • 评估模式（EvaluationModeActivity）是带密钥证明的双机流程，用于给设备做以旧换新评级。它通过蓝牙配对，在被测设备与一台可信验证设备之间交换二维码（trusted/ 下的各 Activity）。仅在蓝牙开启时才提供。

58.24.2 DeviceReport 与密钥证明

应用负责收集硬件事实。DeviceDiagnosticsLib/src/main/java/com/android/devicediagnostics/evaluated/ 下的各辅助类（battery、storage、camera、hinge、sensor、screen、lock、product）把它们汇总进单个 DeviceReport protobuf，schema 定义在 DeviceDiagnosticsLib/src/main/proto/diagnostics.proto。报告里带的都是买家关心的字段：电池的 cycle_count 与 state_of_health、存储的 useful_lifetime_remaining、铰链折叠次数、进水检测传感器状态、恢复出厂保护状态，以及屏幕/触摸测试结果。

为了让报告可信，它内嵌一条来自设备 keystore 的密钥证明证书链。AttestationController 把证明记录（附调用方提供的 challenge）发给验证方，验证方将其解析成 ParsedAttestationRecord 并在线校验这条链。自检场景下网络这一步可以软失败，但参与评级的设备必须校验通过。这才能让远端一方相信：报告来自真实、未被 root 的硬件，而不是一个冒名的应用。

58.24.3 以旧换新模式与特权接口

有三个 exported content provider 把报告与以旧换新流程开放给有权限的调用方，而非普通应用。GetStatusContentProvider 以单行 cursor 返回组装好的 DeviceReport，由 DeviceReportJsonFormatter 渲染成 JSON，受 READ_PRIVILEGED_PHONE_STATE 权限保护。EvaluateContentProvider 与 TradeInModeTestingContentProvider 驱动评估流程，受 ENTER_TRADE_IN_MODE 权限保护。

以旧换新模式本身位于独立的 tradeinmode/ 组件中。该组件带一个 tradeinmode Java 命令行工具（一个 java_binary，main_class 为 com.android.devicediagnostics.commands.Commands），另有 AttestationCli。两者都以系统属性 persist.adb.tradeinmode 为开关依据。

随包发布的 tradeinmode.rc 并不直接启动该命令，而是用这个属性来闸控 adbd：在非 debuggable 版本上，当 persist.adb.tradeinmode 为 -1 时它停掉 adbd，这样设备就无法回退到普通 shell。

这套机制可把设备置入受限状态：在此状态下，自助终端或合作方可以经 adb 读取带证明的诊断报告，而无需解锁设备。UI 与采集逻辑的主体被做成可复用的 DeviceDiagnosticsLib Android 库，app/ 与 tradeinmode/ 则是实际出货的产物。

小结

Android 的调试与剖析工具链覆盖全面，且与平台深度集成。本章要点如下：

  1. logd（system/logging/logd/）提供基础日志设施。它的 LogBuffer 抽象、按 UID 的统计以及裁剪算法，确保日志数据既可得又有界。LogListener 类用 io_uring 实现高吞吐摄入，LogReaderThread 则提供按客户端的过滤与 tail 支持。

  2. Perfetto（external/perfetto/）是系统级跟踪平台。其生产者-消费者架构配合共享内存缓冲区，能从数十个 data source 以极低开销采集数据。基于 SQL 的 trace_processor 提供强大的分析能力，Web UI 则让 trace 可视易读。

  3. simpleperf（system/extras/simpleperf/）利用内核的 perf_events 子系统做 CPU 剖析，支持硬件计数器、经 DWARF 展开的调用图，以及与 JIT 感知的符号解析。

  4. heapprofd（external/perfetto/src/profiling/memory/）对 malloc/free 调用做泊松采样，经共享内存传输到 Perfetto，从而以低开销完成原生堆剖析。

  5. dumpsys（frameworks/native/cmds/dumpsys/）为每个已注册 Binder 服务的诊断状态提供统一访问入口，支持优先级过滤、超时保护与 proto 输出。

  6. Winscope（development/tools/winscope/）抓取 WindowManager 与 SurfaceFlinger 状态的时间序列快照，用于排查窗口层级与转场问题。

  7. bugreport/dumpstate（frameworks/native/cmds/dumpstate/）把上述一切聚合成单个 ZIP 供离线分析，采用并行 dump 采集与进度跟踪。

  8. debuggerd/tombstoned（system/core/debuggerd/）提供自动崩溃 dump 生成：经 ptrace 抓取寄存器、展开栈、借 VM 进程 fork 做内存快照，并与 GWP-ASan、Scudo 集成以诊断内存错误。tombstone 现在还会记录崩溃进程的父进程 id（ppid，system/core/debuggerd/proto/tombstone.proto）。

  9. Profiling 主线模块（packages/modules/Profiling/）把 Perfetto、heapprofd 与 simpleperf 包在安全、限速的应用 API 之后，并交付脱敏结果。Android 17 把它的触发器目录扩到十二种类型，加入结果交付确认与旧文件清理，还引入异常检测器（anomaly-detector/）——一个规则驱动的子系统，观察 binder 刷接口之类的信号，并沿 TRIGGER_TYPE_ANOMALY 路径自动抓取脱敏 trace。

    UprobeStats（packages/modules/UprobeStats/）与之并列。它提供由服务端配置的 uprobe + eBPF 系统进程插桩。在 17 中新增 binder 事务探针与 dynamic_instrumentation 事件 API。

这些工具在设计上互相配合：

  • 用 logcat 与 bugreport 做分诊。
  • 用 Perfetto 做时序分析。
  • 用 simpleperf 做 CPU 剖析。
  • 用 heapprofd 做内存剖析。
  • 用 dumpsys 检视服务状态。
  • 用 tombstone 调查崩溃。
  • 用 Profiling 模块（及其异常检测器）做安全、自动、量产级的采集。

掌握这套工具链，对任何 Android 平台工程师都是必修课。
